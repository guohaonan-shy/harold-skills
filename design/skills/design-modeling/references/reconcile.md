# 对账

拿法去量代码。下面每一类发现都摆给人**逐条**确认，每一条都等人定：

| 发现 | 处置 |
|---|---|
| **法和代码对不上**（`DESIGN.md` 写 X，代码是 Y） | 人判：法错了就改法；代码错了就起草一个目标仓库的 GitHub issue。法在撒谎比法过期更危险，所以由人选 |
| **不该在文件里的内容**：「明确不进 DESIGN.md 的内容」表里的各行 | 按「准入分层表」分走。缺陷进目标仓库的 GitHub issue（起草，人确认后才开）；迁移计划、实现细节以文字交给人，建议去处是 spec 或代码注释；历史叙事和划掉的条目直接删，git 留着历史 |
| **先例 / 判例 / 带日期的条目** | 被多处遵循的，先改写成无日期的全局规则并入对应章节，原条目删掉；其余移出（页面决定留在设计档案）或删除 |
| **被取代的内容** | 删掉，连「已被取代」的说明一起删 |
| **同一规则的两种写法** | 统一成一条，只保留一处（「五条写法规则」第 2 条） |

再过三样：

- **官方 `lint` 的 warning**（定义了却没被引用的 token、组件 token 的对比度不达标）：逐条判是改 token、补 `omitted` 说明，还是交人裁决。
- **「五条写法规则」逐条**：影响渲染的属性是否都在 token 里，规则与禁令是否都带理由（没有理由的禁令每次会话都会被重新争论）。
- **底线少而能检查**：全文五到八条底线，每条带可检查的 token 或实测值。「无障碍」不是底线，「正文对比度 ≥ 4.5:1，从真 DOM 读」才是。无障碍底线一定要有，它是唯一不该由品味决定的一条。

一次对账只加不减，多半是把盘点当成了法（「维护原则」的判断标准）。
