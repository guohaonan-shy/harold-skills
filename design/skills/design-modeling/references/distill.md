# 蒸馏

**输入**：设计法候选（「设计法候选的形态」），以及人在会话里口述的规则。口述的也按候选处理：先帮人补成候选的形态，再过同一张表。

**默认等那一页上线之后再蒸馏**：上线的代码是证据，冻结时的画布还不是。人要求提前的，在报告里注明「未经线上验证」。

## 对每一条候选

1. 过「准入分层表」，给出去向和一句理由。
2. 按去向处理：
   - **产品设计系统**：按「维护原则」落——先在已有章节里找被它影响的内容，矛盾的统一、过时的改写、已覆盖的不加，只有缺口才新增，新增时同步 front matter 的 token。候选里的「并进」是建议，最终落在哪由这一步定。
   - **通用设计原则**：起草成 idea-loop 插件仓库的 issue 文字（标题 + 原则 + 来源 + 建议落在 `/idea-loop:uiux-refine` 设计协议的哪一份），问人要不要开；人同意后才跑 `gh issue create -R guohaonan-shy/harold-skills`。
   - **页面或组件的决定**：留在设计档案里对象的「决定」，`DESIGN.md` 不动。
   - **现状、缺陷**：起草一个目标仓库的 GitHub issue（标题 + 现状 + 在哪 + 来源），人同意后才跑 `gh issue create`。
   - **驳回**：写一句理由。
3. 一批候选的起草结果一起摆给人，人逐条改或批，再走「一次写入怎么走」落笔。
4. **处理完的候选删掉**；去向（落进哪一章 / 开了哪个 issue / 留在原处 / 驳回理由）记在这次执行的结果里。

## 单条蒸馏

人在会话里口述一条规则（「以后这类卡片都用 X」），带着它手动跑一次 `/idea-loop:dreaming` 要当场落时，**只处理这一条**，不跑全量对账：

1. 补成「设计法候选的形态」：一句话规则、并进哪一章、为什么、证据。补不出证据就问人。
2. 照「对每一条候选」的第 1、2 步处理这一条。不是产品设计系统层的，处理完到此为止。
3. 产品设计系统层的：起草旧文与新文并排的改动（「一次写入怎么走」第 2 步），停下等人确认措辞，再落笔，跑 `lint` 与 `diff`（同一节第 5 步）。

人没有当场跑，这条规则就记成候选，等 `/idea-loop:dreaming` 下一次处理。
