# eval-run

一次改动从想法到「可以放量」，你带着走：评估样本与指标 → 登记新提示词版本 → 写实验配置 → 报规模 → 第一段 → 第二段 → 报告 → 放量前核对。脚本算数（比较、统计、状态），你读结果、做判断和诊断、写分析，人决定花钱、放行、放量。项目的事实（命令、路径、准出标准、费用）只从项目的 `EVAL.md` 读；命令的参数以命令的文件头为准，这里不抄。

## 词

- **被改的 AI 任务**：这次改动动到的 AI 任务（提示词、模型或思考预算）。
- **基线**：线上配置在样本集上的一次运行，每个样本 3 份。实验表里一次基线是每个任务一行。
- **第一段**：被改的 AI 任务在自己的 dataset 上跑候选，只跑断言，不跑它的下游。
- **第二段**：第一段达标后，受影响的每个用户任务端到端跑候选，断言加判官。
- **待诊断**：底线或读样本期望的断言挡了准出，实验停下，等你和人诊断。
- **新能力**：相关样本补了期望、加了读它的新 scorer 的改动。
- **当前基线**：实验表里该任务最新的一次基线；`EVAL.md`「跑基线」写的查当前基线 id 的命令打印它的 id。

## 步骤

### 1. 读 EVAL.md，确认走新做法

读全文；「还没迁到新做法的用户任务」那一节点名的用户任务不在这套 skill 里。

完成条件：你能说出被改的 AI 任务属于哪些用户任务（`USER_TASKS` 的成员关系，`EVAL.md`「AI 任务与用户任务的对应」），并且这些用户任务都已迁到新做法。有一个没迁，停下对人说，迁移它是另一件事。

### 2. 评估样本与指标（动手改之前）

先问清人：这次改动要让产物变成什么样、不该变什么。人只说「改提示词」，就问：要解决什么问题，改完用户读到的东西哪里不同？把答案写成一两句**预期变化**。

对每个被改的 AI 任务和每个受影响的用户任务各读一遍：

- 样本：用 `EVAL.md`「评测集存在哪」写的列条目命令（带全文）读条目的 `input`、`expected_output`、`metadata.covers`；数覆盖用样本描述命令加 `coverage.mjs`（`EVAL.md`「样本的问题类型」）。
- 指标：用 `EVAL.md`「指标与断言」写的命令读这个任务挂的 scorer 的 tags 和 description。

要测的东西是多轮对话里的一步、要模拟用户才能跑流水线的，转去 `ai-eval:eval-replay`，不走这套。

AI 任务条目的 `covers` 是空的；找「哪些条目会触发预期变化」靠它的 `expected_output`，和 `metadata.sample`（这条调用来自用户任务的哪个样本，到用户任务 dataset 里读那个样本）。

每个任务回答四问，每问带出处（条目编号、scorer 名）：

1. 哪些条目的输入会触发预期变化？数得出，且不少于覆盖下限。
2. 这些条目的 `expected_output` 写了预期变化吗？
3. 哪个 scorer 读得出预期变化——读 AI 任务自己的产物（第一段看得到），还是读用户的报告（第二段才看得到）？
4. 这次改动可能带来的坏变化（例如别的规则被挤掉），有底线或断言守着吗？

结论四种：**够** / **缺样本** / **缺期望** / **缺 scorer**。

完成条件：每个任务一行结论，四问各有出处；没有哪一行只写「应该够」。

### 3. 补齐（缺什么补什么，人同意才改）

把缺口和打算补的东西摆给人：补哪几个条目或哪条期望、新 scorer 读什么、为什么这样能看出预期变化。人答复前不改样本、期望、scorer。

- 缺样本：`ai-eval:eval-samples`。
- 缺期望或缺 scorer：两样一起补——只补期望没有东西读它，只加 scorer 没有样本喂它。断言写成断言目录里一个带可证伪测试的文件（位置见 `EVAL.md`「指标与断言」），判官走 `ai-eval:eval-metrics-review`；登记按 `EVAL.md`「指标与断言」，基线在新 scorer 上的分按 `EVAL.md`「跑基线」末尾「新能力」一段重算，不重跑模型；基线在新 scorer 上触发的，逐条交人判。

完成条件：缺口已补，或人明说不补、你把「没补」写进步骤 9 的分析里；新 scorer 在基线上有分。

### 4. 登记新提示词版本（改提示词时）

提示词的文字来自人，或来自人批准的草稿；你按 `EVAL.md`「改提示词的实验」把它登记成新版本，不改旧版本的字节。登记后跑这个 AI 任务的提示词测试。只改模型或思考预算时跳过。

完成条件：测试绿；`prompt_version` 在登记里。

### 5. 写实验配置

在 `EVAL.md`「两段式实验」写的实验配置目录下建 `<实验名>/`，写实验配置，格式照同目录下的范本。`feature` 写对应的 feature 或 issue，`problem` 写步骤 2 的预期变化，`baseline` 写查当前基线 id 的命令打印的 id；被改的 AI 任务属于几个用户任务（`EVAL.md`「AI 任务与用户任务的对应」）时，每个用户任务各有一个基线，写成 `{用户任务: 基线 id}`，之后每条命令带 `--user-task`（`EVAL.md`「两段式实验」）。人要同时比较几种做法，就是几套候选配置。实验名取人说的；没说就取能看出改了什么的短名。

完成条件：`plan` 命令（`EVAL.md`「两段式实验」）能读出它（未登记的版本、缺 `feature` 或 `baseline` 都会在这里报错，改文件，不绕过）。

### 6. 报规模，等同意

`plan` 报两段各调多少次模型、约多少钱、判官几次。把这几个数对人说，**等人同意**，把人的原话带进 `--approved`。

完成条件：人的同意在手。

### 7. 第一段

`run --stage 1`。起 `run` 之后告诉人在等什么、大约多久；用后台命令加 Monitor 等，不连续轮询。跑完先把候选和基线的平台报错重跑到零（命令在 `EVAL.md`「两段式实验」，规则见 `<插件目录>/references/reporting-rules.md`「平台报错先重跑」），再 `compare --stage 1`。`compare` 退出码 0 才有第二段；1 是停下（不达标或待诊断）。

`compare` 拒绝比、说基线是在另一版评测集上打的分：照它给的下一步走（只改了期望或加了 scorer 就 `rescore --baseline`；某几个样本的输入变了，先只重跑它们的基线，这条要花钱，对人说规模、等同意；`EVAL.md`「两段式实验」里列了各情形），做完再比，不改实验去适应旧基线。

停下时先读原因（`compare` 的输出写明 scorer、样本、第几遍、断言写成了什么），再把候选产物（`--out` 目录 `stage1/<任务>/<条目>.run<N>.json`）、基线产物（bucket 里 `eval_reports/offline_eval/<基线 id>/outputs/<任务>/<条目>.run<N>.json`）和不过的原因一起摆给人。诊断成三者之一，写回 `diagnose`：

- **候选变差**：这一行不达标。
- **断言判错**：修断言，基线 `rescore --baseline`、候选再 `compare`，两边重算。
- **偶然波动**：必须是人的原话放行（`--released`），不带就拒绝。

完成条件：第一段每个被改的 AI 任务的行都是「达标」，或停在不达标、等人决定下一步（写在步骤 10 的交回里）。

### 8. 第二段

第一段全部达标才开始。`run --stage 2`，平台报错照步骤 7 重跑到零（规则同 `<插件目录>/references/reporting-rules.md`），再 `compare --stage 2`；断言过了的行等判官：用 Skill 工具调 `ai-eval:eval-judge`，出 `paired-stats` 结果后 `finish`。待诊断的行同步骤 7 处理。

完成条件：第二段每个用户任务的行有状态（达标、不达标，或待诊断等人）。

### 9. 写报告的分析

读 `report --dry-run` 出的数据部分、断言的原因、判官理由和产物，写一个文件，`## 1`、`## 2`、`## 4`、`## 5` 各一小节，再 `report --analysis <文件>`：

- 1：预期变化出现了没有，凭哪个 scorer 或哪份产物。
- 2：一句话说改了什么。
- 4：每条待诊断和需诊断：是潜在问题还是偶然，和这次改动有没有因果，引产物原文。
- 5：预期变好的 scorer 变好了吗，预期不变的动了吗；**新能力**的实验必须写一句判断：新 scorer 上候选比基线好、其余 scorer 与底线不变差，才写「新能力生效」，否则写「新能力未生效」并说明差在哪。代码只把新 scorer 的分并排列出，这一句靠你判。

数字照报告第 5 部分抄，不临场重算。pass¹ 和 pass³ 一并写出，第一次出现时给定义（原样取自 `<插件目录>/references/reporting-rules.md`「pass¹ 和 pass³」）；项目的报告没有这两个数，就在分析里写「报告没给」，并在 `EVAL.md`「待确认」记一条，不自己算。

完成条件：`report.md` 的 1、2、4、5 四部分都不再是「待 eval skill 填写」。

### 10. 放量前核对，交回

用步骤 5 的实验名跑 `check-baseline`（`EVAL.md`「两段式实验」）。退出码 1：这次实验比的基线已经不是当前基线（别的实验先全量上线并升了基线），不建议放量，提示「基线已换，先对新基线重跑第二段比较」，并给出新基线的 id（实验配置的 `baseline` 改成它，再 `run --stage 2`、`compare --stage 2`）。

对人说（中文，平实，不贴 JSON）：每段的状态和原因；新能力生效与否；这一轮花了什么（调用次数、判官会话数）对照预计；达标且基线仍是当前基线时，下一步是一个 PR 把组放进生产配置，哪个组上线由人定，你不改生产配置、不合并。

完成条件：回复里有上面每一项，没有哪一项只留在文件里。

## 不绕过的规矩

- 样本、期望、scorer 的改动先摆给人，同意才改。
- 花钱的命令（`run`、`recall`、起判官）先报规模、等同意；已同意的规模内补跑失败的不用再问，超出再问。
- 第一段没达标不开第二段，不换个说法绕过。
- 偶然波动只由人的原话放行。
- 基线已换时不建议放量。
