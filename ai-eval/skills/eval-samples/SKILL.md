# eval-samples

评测集是固定的：样本和期望只在人同意之后才进，Claude 不替人挑，也不悄悄加。这个 skill 数出哪里缺，提议补什么，等人答复，再入库。样本住在 PostHog dataset（每个任务一个）；项目的事实（命令、case 名、下限、怎么造）只从项目的 `EVAL.md` 读。

## 词

- **样本**：用户任务 dataset 里的一个条目：一份完整输入（`input`）、这个样本的设计意图（`expected_output`，考哪些 case、考对了是什么样，不是一份完美输出）、覆盖的 case（`metadata.covers`）。AI 任务 dataset 的条目由基线运行从模型调用生成，这里不新增。
- **case**：一类要被样本覆盖到的问题。名字只取自 `EVAL.md`「样本的问题类型」的清单；加新名字是人在术语表里定词，不在这里。
- **覆盖不足**：一个 case 的样本数少于 `EVAL.md` 写的覆盖下限。
- **期望写在看得到它的任务上**：用户报告上看不到的东西（比如推理稿里的问题编码）写进那个 AI 任务的条目，不写进用户任务。

## 步骤

### 1. 读 EVAL.md

读「评测集存在哪」「样本的问题类型」「怎么造新样本」「费用与额度」。

完成条件：你能说出样本源文件和 PostHog dataset 各在哪、case 名清单、覆盖下限是几，以及这个用户任务造新样本的路径。

### 2. 数覆盖

```
<EVAL.md「样本的问题类型」写的样本描述命令> <用户任务> > describe.json
node <插件目录>/scripts/coverage.mjs --describe describe.json [--markdown]
```

样本描述命令读 PostHog 里现在的条目。脚本按 `EVAL.md` 的清单给每个有样本的用户任务出一张表：只有「适用的用户任务」列写了这个用户任务的名字才出一行，数 0 的也在，少于下限的标「覆盖不足」。`covers` 里有清单外的名字、或清单里有但不适用于该用户任务的名字，退出码为 1，`violations` 点名样本和那个名字，`reason` 是 `unknown` 或 `not_applicable`。

完成条件：每个有样本的用户任务有一张表；`violations` 为空。有违规时，先问人：写错了（改 PostHog 里那条样本的 `covers`）、缺一个词（人去术语表定），还是它其实也适用于这个用户任务（人决定后在 `EVAL.md` 的「适用的用户任务」列补上，同一个改动里改项目里同步 case 名清单的代码（位置见 `EVAL.md`「样本的问题类型」））；不自己改清单让它通过。

### 3. 提议

覆盖不足的 case，加上 eval-run 评估出的「缺期望」，逐个排出提议。一个新样本可以同时覆盖几个不足的 case，先找能一次补多个的设计，再补单个的。每条提议写：

- 补哪些 case，补到下限需要几个样本，或者给哪个样本的 `expected_output` 补哪一条期望；
- 样本是什么（输入、设计好的问题、期望怎么写）；期望用术语表里的词写，不写输出 JSON 的字段路径；
- 怎么造：按 `EVAL.md`「怎么造新样本」，以及这一条需要人做什么（比如读一份完整的输入）；
- 补期望的同时，读它的新 scorer 是什么（只加期望没有东西读它）。

造不出来的 case 写成「这类做不出来：<原因>」，交给人定，不用凑数的样本顶替。

完成条件：每个覆盖不足的 case 都出现在某条提议里，或被标成「做不出来」。

### 4. 先问人

把全部提议一次摆给人，每条要一个明确的答复：做、不做、改成什么样。

完成条件：每条提议都有人的答复。没答复的、没同意的，都不做，也不换个样子再做。

### 5. 造并入库

只做人同意的那些，照 `EVAL.md`「怎么造新样本」：新样本写进样本源文件（草稿），校验命令通过，写入命令先加 `--dry-run` 看会创建哪些条，再去掉 `--dry-run` 写进 PostHog；写进去以后样本以 PostHog 为准。已有样本的输入要改，直接在 PostHog 里改，不改源文件再 `seed`（写入命令不覆盖已有条目）。任务换 dataset 是改任务表（`EVAL.md`「评测集存在哪」）。

**已有条目的期望**（用户任务的样本，和 AI 任务条目里的中间产物期望等）人定了新写法之后，用 `EVAL.md`「怎么造新样本」写的改期望命令（`set-expected`）改，基线再写一遍也不覆盖 PostHog 里已有的期望：

1. 把人定的期望写成一个文件：条目号下面列要改的期望项，值照 `EVAL.md`「期望的写法」写；项写成空就是删掉它；没写到的项不会动。只写人这次定了的项。
2. 不带 `--write` 跑那条改期望命令（`<dataset> <文件> --user-task <用户任务>`），把输出的改前改后原样摆给人，等人确认。
3. 人确认后加 `--write` 再跑，读它最后的回读结论。回读报了不一致或有条目没写成，如实交回，不重试到「看起来对」。

完成条件：回读结论是「hold the planned expectation」且退出码 0；新条目在 `EVAL.md`「评测集存在哪」写的列条目命令里读得到；`covers` 过了步骤 2 的脚本；重新数覆盖，同意补的 case 不再覆盖不足（人只同意补一部分时，其余仍标不足）。

### 6. 基线

新样本在基线里没有输出：用 Skill 工具调 `ai-eval:eval-baseline`，按「加了样本」处理（整批重跑，要先报规模等同意）。只补期望、加 scorer 的，按「新能力补分」处理，不重跑模型。

完成条件：基线行已经覆盖新样本，或补分已写回；做不到的（比如 `write` 被拒）写进交回，不绕过。

## 线上采样的报告想进评测集

一份线上采样得到的报告想收进来，也从步骤 3 起走：提议写「收这份报告」，说明它覆盖哪些 case、期望怎么来（线上报告没有现成的），人同意才收。
