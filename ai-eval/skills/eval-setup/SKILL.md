# eval-setup

`EVAL.md` 是 ai-eval 与一个项目之间唯一的接口：eval-run、eval-judge、eval-samples、eval-baseline、eval-metrics-review 只从它读项目的事实，插件里不写任何项目的名字、路径或数字。这个 skill 读项目的代码和文档，写（或更新）这份文件；读不到的、拿不准的，列成清单问人，一个字都不编。

## 词

- **AI 任务**：产品流水线里的一种模型调用，有自己的模型、提示词版本、思考强度。
- **用户任务**：用户在产品里完成、能拿到一份结果的一件事。评测与准出的单位，每个用户任务串起若干 AI 任务。划用户任务时只取正常路径：重做、补救、失败重试这类异常路径，如果它用到的 AI 任务都已经在某个正常路径的用户任务里，就不单独列为用户任务，它特有的拼接与合并逻辑靠应用自己的确定性测试守。只有它用到正常路径里没有的 AI 任务时，才单列。
- **样本**：一个任务的一份输入连同它的预期输出，住在这个任务的 dataset 里。`covers` 列出它覆盖的 case。
- **case**：一类要被样本覆盖到的问题。名字只取自项目的术语表。
- **scorer**：一个指标（断言、判官或问题类枚举），定义住在评测平台上。
- **基线**：线上配置在样本集上的一次运行，每个样本若干份。
- **新做法**：样本、指标在评测平台，登记与实验在数据库，实验分两段。还没迁到新做法的用户任务单独成一节。

## 步骤

### 1. 判新建还是更新

仓库根有 `EVAL.md` 就整份读完，更新时每一节都对着它核；没有就新建。

完成条件：你能说出 `EVAL.md` 存不存在，存在时说得出哪几节有内容、哪几节标着「待建」「待确认」。

### 2. 逐节取事实

按下面「EVAL.md 的节」的顺序，每节到「去哪找」取事实。每条写进去的事实带得出处：文件路径、函数名或文档位置。写进去的路径、命令、名字当场核一遍（路径用 `ls`，名字用 grep，命令用 `--help` 或文件头），核不到的不写。命令的参数留给命令自己的文件头，`EVAL.md` 只写什么时候用哪条、完成条件是什么。

处理三种情况：

- **找到了，核过了**：写进去。
- **项目里该有、还没建**：写「待建」，括号里写负责它的工单或任务；不知道谁负责就只写「待建」。路径与名字不写。
- **缺信息，或两处来源互相矛盾**：不写数，放进最后一节「待确认」。每条写：缺什么、看过哪里、读到了什么、需要人给什么。

完成条件：每一节要么是核过的事实，要么是「待建」，要么在「待确认」里有对应的一条。

### 3. 写 EVAL.md

节的标题与顺序照下面写，其余 skill 按标题找。准出标准一节照项目里人定下的原文抄，注出处，不转述、不压缩。

### 4. 让项目的规则文件链到 EVAL.md

项目的 `AGENTS.md`（或同等的 agent 规则文件）里指向其他规则文件的那一节，没有指向 `EVAL.md` 的一行就加一行，形式照旁边已有的行。已有就不动。

### 5. 把待确认清单交给人

在回复里完整列出「待确认」的每一条，用 AskUserQuestion 或直接提问收答案。人答了就写进对应的节，并从清单里删掉；没答的留着。

完成条件：回复里出现了「待确认」的每一条，没有哪一条只写在文件里。

## EVAL.md 的节

### 评测集存在哪

样本、scorer、任务表与实验表、运行输出与报告各存在哪、怎么读写、需要哪些凭据；进版本库的清单（样本源文件、scorer 声明、断言代码、实验配置各在哪）；两处登记的先后和一致性约定；列一个 dataset 全部条目（带全文）的命令。

去哪找：评测目录的各命令文件头、存储客户端配置、`DEVELOPMENT.md`、任务表的迁移。

### 用户任务

一张表，一个用户任务一行：用户提交什么；产品侧的入口（函数或文件）；流水线接入代码在哪；要换掉的进程外依赖（存储、外部评估服务、转写、埋点）；跑一遍约多少次模型调用。表后列命令一览：要做什么、用哪条命令、细节在哪一节。

去哪找：产品的路由与服务层、流水线文档、测试里的假实现。调用次数写实测或可数出的数，数不出来标「待量」。

### AI 任务与用户任务的对应

指向项目的流水线文档和 AI 任务登记，说明改一个 AI 任务时靠什么找到所有用到它的用户任务。不复制文档里的内容。

### 样本的问题类型

`covers` 可用的 case 名清单，每个名字注明它在术语表的哪个词条；覆盖下限（写成「覆盖下限：每个 case 至少 N 个样本」）。名字做成表格的一列，列标题「covers 可用的名字」，每个名字写在反引号里：`coverage.mjs` 从这一列读合法名字。同一张表再加一列「适用的用户任务」，写这一行的名字适用于哪几个用户任务（用户任务名写在反引号里，名字与项目样本描述里的用户任务键一致）；一个名字可以适用于几个用户任务，`covers` 写了不适用的名字算违规。术语表里没有的名字不列，缺的放进「待确认」。统计的跑法（样本描述命令、脚本怎么调）也写在这一节；同步 case 名清单的代码在哪。

去哪找：项目的术语表、代码里的 case 名清单。

### 怎么造新样本

每个已迁到新做法的用户任务造新样本的路径：写在哪、本地怎么校验、什么时候要人同意、怎么写进评测平台、新样本之后基线怎么办；改已有条目期望的命令（先预演、再写回、回读）和期望的写法。还没迁的用户任务的造法指向旧文档，不抄。

去哪找：样本源文件和写入命令的文件头、造样本的脚本和 skill。

### 指标与断言

scorer 的类型和 tags 约定；声明在哪、怎么登记、列出一个任务挂了哪些 scorer 的命令；判官 description 写法的出处（哪份文件的文件头）；确定性断言的代码在哪、怎么写测试；哪些断言算硬性底线（一条触发就挡准出），哪些只用于诊断；校验命令。

### 判官配置

判官用的模型、思考强度；一次会话判哪些东西（一个 scorer × 一个样本）；同时跑几个；判官调用环境里要扣留的凭据；怎么停判官；各步骤的命令（生成判官任务、把结果目录存进 bucket 的上传命令）。

### 跑基线

基线运行的步骤与顺序、每步的完成条件、输出和 dataset 条目放哪、触发清单怎么交人判、新能力怎么补分；报规模的命令；查当前基线 id 的命令；线上配置在哪看（每个 AI 任务现在用哪个组）；改了某几个样本的输入后怎么只重跑它们。

### 两段式实验

实验配置放在哪个目录、哪一份是范本、有哪些字段；提示词版本怎么登记；两段各自的命令（含 plan、check-baseline）；待诊断怎么处理；报告的五部分。

### 准出标准

项目里人定下的准出标准原文，注出处。

### 放量与升基线

放量由谁定、放量前核对什么、升基线怎么做，以及目前代码还没覆盖的缺口。

### 费用与额度

评测用哪个密钥、从哪读、缺了怎么办；各项目的预算与在哪看；判官所用服务的额度在哪看；一次实验的预期花费。真实运行前要先向人说明规模的规定也写在这里。

### 还没迁到新做法的用户任务

点名还在旧做法里的用户任务，说明它们暂时没有 skill 入口、旧做法的文档在哪、迁移时怎么处理这一节。全部迁完、旧做法的代码也删掉之后，这一节不删（skill 按标题引用它）：写「没有了」，记下旧做法在哪个提交删的、删之前的版本怎么看。

### 待确认

上面各节里没能核实的问题，每条的写法见步骤 2。

## 更新时

- 人在 `EVAL.md` 里手写过的值，与代码或文档读到的不一致时，保留人写的，把差异列进「待确认」。
- 「待建」的东西现在建出来了：核对后改成事实。
- 只改读得到依据的节，其余原样保留。
