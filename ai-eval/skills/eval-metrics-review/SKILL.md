# eval-metrics-review

判官 scorer 是评测里最贵也最不可靠的一环：每多一个，就多一份判官额度，也多一处尺子可能不一致。这个 skill 把它们修剪到只剩「判用户读到的东西、代码判不了、有依据、不重复、判官照着就能打分」的那些。项目的事实（用户任务的入口、scorer 在哪、断言在哪、术语表在哪）只从项目的 `EVAL.md` 读。

判官 scorer 的全部内容在 PostHog 里：description 就是判官的全部指令，按固定小节写（开头一句角色、`### 步骤`、计数规则表、`### 档位`、`### 读什么`，写法出处见 `EVAL.md`「指标与断言」）。结论由人拍板：skill 出表，人批了才改 scorer。

## 词

- **用户读到的**：产品最终展示给用户的报告字段。流水线同时存下的推理稿、中间稿用户读不到，叫**中间稿**。判官只该判用户读到的。
- **判据**：评分标准里一句可以单独判真假的话（「引用了这一场真实出过错的词」）。审核的单位是判据，不是整条 description。
- **档**：`### 档位` 表里的 1.0、0.5、0 到 0.25 三档。

## 步骤

### 1. 读 EVAL.md 和被审的 scorer

读「用户任务」「指标与断言」「判官配置」「费用与额度」，再取被审用户任务挂的全部 scorer：用 `EVAL.md`「指标与断言」写的命令，判官和断言都要读（断言的 description 说明它保证什么）。

完成条件：你能说出这个用户任务有几个判官、几条断言（各自保证什么），以及产品侧入口和术语表在哪。

### 2. 列出用户读到什么

从产品代码里生成这份报告的那一步取：输出的 schema，和提示词里写明「给用户看」的字段。`EVAL.md`「用户任务」一节给了入口。每个字段一行：路径、含义、用户读到还是中间稿，出处写文件和行号。

完成条件：这个用户任务报告里的每个字段都归了「用户读到的」或「中间稿」，每行有出处。

### 3. 逐判官审前五项

每个判官按下面五项各写一句结论，带依据（description 的原文、断言的说明、产品代码的行号）。

1. **判的是不是用户读到的字段。** `### 读什么` 的「报告片段」表里每一项都在步骤 2 的「用户读到的」里。读中间稿的，看用户读到的字段里有没有承载同一件事的：有就改判那些字段；没有，说明这个判官判的是用户看不到的东西，结论倾向删。
2. **能不能改成确定性检查。** 把评分标准拆成判据，每条判据逐条对照这个用户任务的全部断言：已被某条断言覆盖的，从判官里删（写明哪条断言）；没被覆盖、但代码能判的（两处数字是否一致、字段是否为空、个数对不对、是否落在封闭集合里、格式），结论是挪成确定性断言，同时写明断言要查什么。留在判官里的只有读起来才能判的：自然、忠实、具体、语气。
3. **有没有依据。** 每个判官判得出对错靠的是什么：样本的 `expected_output`（`### 读什么` 的「样本期望」点名了哪几块）、外部服务的证据，还是只靠判官自己的感觉。靠感觉的，写明这条判据哪里会因人而异。
4. **和别的判官重不重叠。** 把各判官的判据摊开比：同一条判据出现在两个判官里，留在最贴切的那个，另一个删掉这条。
5. **评分档位清不清楚。** `### 档位` 和计数规则表的每一格是一个判官照着就能判的条件：有可数的东西、可对照的字段，或可举的例子。「自然」「具体」这类词要有界线（什么算生硬，哪类句子扣到 0.5 档）；三档之间要没有缝隙，一份报告总能落进其中一档。同时核对评分标准有没有和产品提示词的要求打架（评分标准禁止的事，产品提示词恰好要求）：这种自相矛盾会让判官各按一半打分。判官的角色那句也看：判可读性的站在读报告的用户，其余站在这个领域的资深从业者。

用到的分类和术语，逐个对术语表和产品提示词。三处说的是同一套就过；对不上的，**不选边**，记进「要你决定」：写两边各自的原文和出处、各自的取值，附两个选项和推荐。

完成条件：每个判官五项都有带依据的一句结论；用到的每个分类、术语都对过术语表和产品提示词。

### 4. 判官一致性（第 6 项，花判官额度）

同一份报告交给两个互相看不到对方的判官各判一次，比较分数；差得大的判官，是评分标准里有一句含糊。

**先报规模，等人同意。** 写明：几份报告、几个判官 scorer、几次 `codex exec`，按 `EVAL.md`「费用与额度」里的实测用量估 token，再等人答复。没同意之前不起任何判官。

选报告时让每个 scorer 都有机会拉开分：每个 scorer 至少有适用它的报告（description 的适用条件），好的一场和有毛病的一场都要有。全是满分的报告测不出档位含糊。

同意后用 Skill 工具调 `ai-eval:eval-judge`，照它的「两个判官判同一批报告」一节跑，区别只有一处：同一批报告交给**两个**判官各判一次（各是一次全新的 Codex 会话，打乱顺序的方式一样，都不知道对方的存在）。两份评分整理成脚本的输入：

```json
{ "format": 1, "judge": "A", "scores": { "<报告>": { "<scorer 名最后一段>": 0.5, "<另一个>": null } } }
```

分数 0 到 1；判官写了「无法判断」的写 `null`。然后：

```
node <插件目录>/scripts/judge-agreement.mjs --a <判官 A 的评分.json> --b <判官 B 的评分.json>
```

脚本逐 scorer 给 `consistent` / `inconsistent` / `no_data`，并列出每份报告上的分差。`inconsistent` 的标准：某份报告上两个判官差一整档（≥ 0.5），或平均差 > 0.2（一个判官整体更松），或一个判官打了分、另一个写「无法判断」。`--max-gap`、`--max-mean-gap` 可以调，调了要在结论里写明。退出码 0 全部一致，1 有不一致，2 输入有误。

对每个 `inconsistent` 的 scorer，打开分差最大的那几份报告上两个判官的理由，找出两边读法分叉的那一句评分标准，写成改写草稿：把含糊词换成可数的条件，或补一条界线例子。`no_data` 说明这个 scorer 在选出的报告上没有判官能判，换适用的报告再判，不当作一致。

改写草稿由人批准后落进 scorer；改完再用同一批报告判一次，确认不再 `inconsistent`（再次花额度，同样先报规模）。

完成条件：每个判官有一致性的结论（`consistent`，或 `inconsistent` 加上含糊的那一句和改写草稿）；用了多少判官会话和 token 记下来。

### 5. 出结论表，交人拍板

每个判官恰好一种结论：

| 结论 | 什么时候 |
|---|---|
| 保留 | 五项和一致性都过；判的已经是用户读到的 |
| 改写 | 判的东西对，但判据要换字段、要删被断言覆盖的部分、要补档位界线，或评分标准含糊 |
| 挪成确定性断言 | 判据能用代码判；写明断言查什么 |
| 删掉 | 判的是用户读不到的中间稿且没有可改判的字段，或判据全被确定性断言覆盖，或和别的判官重复到不剩独有的判据 |

表的列：判官 | 现在判什么 | 发现（五项加一致性，各一句） | 结论 | 建议（改写后的判据和档位；挪成断言的写断言查什么）。表后面是汇总（保留、改写、挪成断言、删掉各几个，改完剩几个判官，新增几条断言）、「要你决定」清单（术语不一致，以及任何拿不准的）。格式示例见 `references/audit-table-example.md`。

人批准之前，scorer 和断言代码保持原样。

完成条件：表里每个判官有且只有一种结论；每个结论带依据；术语不一致的全部列进「要你决定」，没有哪一条被悄悄选了一边。

### 6. 人批了之后落进去

按人批准的结论改：删的 scorer 从声明里去掉；改写的改声明里的 description，再经 PostHog MCP 更新那个 scorer，然后更新任务表（顺序和一致性约定见 `EVAL.md`「评测集存在哪」）；挪成断言的判官删掉并加断言（代码和可证伪测试走 `EVAL.md`「指标与断言」写的断言约定）。改完跑 `EVAL.md`「指标与断言」末尾的校验。

完成条件：校验通过；每个被批准的结论都在 PostHog 和声明里；被批准删掉的判据所保证的事，要么还在某条断言里，要么人明确说不再保证。
