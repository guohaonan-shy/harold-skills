# to-spec-hand-over-paragraph

> 判定会话的判定你不同意时，在下面记一行推翻，再跑 `retro-replay.mjs --settle to-spec-hand-over-paragraph --run <那次的 run dir>`。
> 这里不打分；只记「这一次哪一边的答案判错了、为什么」。

**这是目标用例，不是回放**：题不是从人当时的原话写出的，是从 spec `docs/spec/spec-for-agents/spec-for-agents.md` 的 User Story「人读会话」1 写出的：spec 交到人面前时，会话里有一段「现状 → 目标 → 要你定」，人不读 spec 就能拍板。

**是/否题**：最后一段回复里，有没有依次写了现状（用户现在遇到什么）、目标（改完用户得到什么）、要你定（要人定的事，或明说没有）三块？

## 材料怎么拼的

- **提交**：`5ef9a09a`（`release/idea-loop-0.2.0`，spec 问题陈述量 15 份 spec 的那个状态，`docs/spec/spec-for-agents/` 还不存在），to-spec 第 5 步是「交代等人定的」，只说出还剩哪几样标记。
- **prompt**：沿用 `to-spec-verify-each-change` 的 issue（改 `idea-loop/agents/issue-triager.md` 的「评论与交回」，号是编的）和它后一段的写法（人不在场、禁提交推送和 gh 写操作、最后一段回复写明停在哪一步和 spec 路径）；不提三块，不提「现状」「目标」。
- **改前预计答「否」**：改前的第 5 步只要求点名还剩的「需要 grill」「待定」，最后一段回复多半是「spec 写在哪、还剩什么标记」，没有按现状、目标、要你定写。改后第 5 步要求这三块。
- **判定依据**：看最后一段回复（不是 spec 文件）：有没有现状、目标、要你定三块，且是这个顺序；要你定可以是几道题，也可以明说没有。
