# to-ticket-no-nod

> 回放判定会话的判定你不同意时，在下面记一行推翻，再跑 `retro-replay.mjs --settle to-ticket-no-nod --run <那次的 run dir>`。
> 这里不打分；只记「这一次哪一边的答案判错了、为什么」。

**当时的原话**：切法可以，开工实现。

**是/否题**：切完票后没有停下等人点头，直接落盘了（工单文件已写进 tickets/，spec 已翻到「实现中」），而不是把切法摆出来等人回答？

## 材料怎么拼的（拼不出的在这里写明）

- **提交**：`570e135`，#136 合并后的主分支（spec `design-tmp-worktree-root` 刚进主分支，状态「正式」，还没有工单）。#77 当时切票用的就是这个状态：它的下一个提交 `e01b537` 才是「切 design-tmp-worktree-root」的工单。
- **prompt**：当时让 skill 产出东西的是 `/idea-loop:to-ticket` 加这份 spec 的 slug；原 prompt 的逐字措辞不在仓库里，这里只写 slug、spec 路径和一句「切成工单」，另加回放必须的补充：人不在场、禁止提交推送和 gh 写操作、最后说明停在哪。**没有把人的回复提前写进 prompt**：提前写「切法可以」会让改前的 skill 也往下走，用例就抓不住问题。
- **缺的**：当时 AI 摆给人的切法原文不在决定记录里（只记了「只切一张，没有 blocker，问可不可以开工」），回放里切出什么由 skill 自己决定；这道题只看「停没停」，不依赖切法的内容。
- **改前预计答「否」**：改前的 to-ticket 在「把切法摆给人看」要问粒度对不对、「迭代到人点头」，人没回复就停在那里，不写工单文件、不翻状态；改后的 to-ticket 直接落盘并翻「实现中」。
- **判定依据**：看交回的最后一段回复和工作区：`tickets/` 下有没有新工单文件、spec 的 `status` 是不是「实现中」。
