# retro-candidate-verify

> 回放判定会话的判定你不同意时，在下面记一行推翻，再跑 `retro-replay.mjs --settle retro-candidate-verify --run <那次的 run dir>`。
> 这里不打分；只记「这一次哪一边的答案判错了、为什么」。

**当时的原话**：要结合candidate分析，这个内容到底可以和现有的skill怎么结合，以及这块内容要如何验证这个改动确实对于之前的问题解决了

**是/否题**：每条候选都写了「验证」一栏，且写的是可跑的用例三样（当时的提交、让 skill 产出东西的那句 prompt、一道是/否题）、检查的名字，或「判不了」加原因吗？

## 材料怎么拼的（拼不出的在这里写明）

- **提交**：`571969a`，#203 合并后的主分支，是 #80 的 retro 当时仓库的样子；它的下一个提交 `78d2787` 才把决定记录写进仓库，所以回放的工作区里没有 `docs/raw/decisions/80.md`。
- **prompt**：人的三条发言取自 `docs/raw/decisions/80.md` 候选 2、3、4 的「原话」（逐字），「审草稿时」之类的情形是据决定记录补的一句话；落点和「三条都按纠正与追问」是为了让回放不依赖 skill 现场去猜，写进了 prompt。另加回放必须的补充：人不在场、不逐条回复，所以让它把每条候选原样写在最后一段回复里；禁止真的开 issue / PR / 推送。
- **缺的**：那场会话完整的 digest 不在仓库里；当时 AI 摆给人的候选原文也不在决定记录里，所以候选的措辞由 skill 自己写。这道题只看「每条候选有没有『验证』一栏、写法落在三种之内」，不依赖候选的措辞。
- **题的原话出处**：不是 #80 里说的，是 writing-for-agents-pruning-layers 的 scope grill 里人要求给候选加「验证」时说的（`docs/raw/idea-loop-decisions/2026-10-31-writing-for-agents-scope-grill.md`）；回放的输入是 #80 的 retro，因为那是一场真实的、有纠正的会话，改后的 retro 要在它上面多写一栏。
- **改前预计答「否」**：改前的 retro 候选格式只有信号、原话、落点、旧文、新文、归并、同类七栏，没有「验证」。
