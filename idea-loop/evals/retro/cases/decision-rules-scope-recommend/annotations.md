# decision-rules-scope-recommend

> 回放判定会话的判定你不同意时，在下面记一行推翻，再跑 `retro-replay.mjs --settle decision-rules-scope-recommend --run <那次的 run dir>`。
> 这里不打分；只记「这一次哪一边的答案判错了、为什么」。

**当时的原话**：影响这个spec实现的问题在这个pr里修复，上线会有影响的重要问题在pr里修，其余的按照我们的流程进入候选（人在 #174 的 retro 里说的，`docs/raw/decisions/174.md` 候选 1）

**是/否题**：摆出的范围题里，影响这份 spec 实现或上线后会有影响的改进（例如回放输入露题，会让用例改前改后都答「是」）有没有被推荐并进当前 PR，其余的没被推荐并进？

## 材料怎么拼的（拼不出的在这里写明）

- **提交**：`314a633`，「规则回放 runner 加 --run-large」，是 #174 讨论时仓库的样子；`docs/spec/replay-run-large-now/` 在它里面，runner 里还留着「这是一次无人值守的回放……做到 X 就停下」那句露题的话，所以会话对照 poteto 的做法时能自己读到它。
- **prompt**：取自 `docs/raw/idea-loop-decisions/2026-11-13-replay-verify-redesign.md` 里人的原话（逐字）：U1 和 U2 作前情（U2 的两句回复，加一句由它推出的 #174 当时的范围），U3 作这一轮的发言。回放跑不出来、必须由人补的：
  - 会话在哪（#174 的 issue 会话、对应 spec `replay-run-large-now`）；
  - A4 查到的 poteto 观点：回放里不保证能上网，写成人转述的笔记，把原文里「eval playbook」「judge」等词换成人会说的话（`prompt` 里不能出现会让被测的 agent 看出自己在被测的词）；
  - 人不在场，禁止 git 提交、推送、gh 写操作、起 Agent、改文件；讨论完把要人定的摆成题，写在最后一段回复里。
- **补的第三样：#157 那个用例改前改后都答「是」的原因**。A4 当时就把这一点摆给了人（「露了题（#157 的用例改前改后都答是，同一类问题）」），回放里没有那场会话，所以写成人记得的一句话补进 prompt（只说事实：#157 的结果没分出区别，原因是 runner 追加的那句话告诉了被验的会话该停在哪；不说它影不影响 #174）。第一次跑（run `20261114T063503`）没有这一句：改后那一遍照规则把「影响 #174 实现」的两条推荐并进，却把「输入露题」判成「跟 #174 无关」推荐另开，是/否题没过；那是因为材料里缺这条因果，不是规则没起作用，所以补材料重跑。
- **用 `/idea-loop:decision-rules` 开头**：当时的会话里这个 skill 是被引用着用的，回放里没有那场会话的上下文，直接用斜杠命令把它读进来，「摆成题」才有规矩可照。
- **缺的**：当时 AI 摆给人的那一版题（题 1 输入去不去掉露题那句、题 2 一起做还是分开）原文不在仓库里；回放里摆出什么由 skill 自己写。这道题只看一件事：摆出的范围题里，推荐并进的是哪几条。题里点名的「回放输入露题」那一条取自 `docs/spec/scope-recommend-by-delivery/scope-recommend-by-delivery.md` 的「问题陈述」：它是 #157 用例改前改后都答「是」的原因，不改它，#174 交付的回放照样出同样的错，所以属于「影响这份 spec 实现」。
- **改前预计答「否」**：改前的 `decision-rules` 只写「给推荐和一句理由」，不规定推荐哪边，当时的会话按「PR 小、好 review」推荐拆开；改后多一条，影响这份 spec 实现或上线后有影响的推荐在当前 PR 里修，其余的不进。
- **跟 issue 原文差一处**：issue 的问法是「被推荐并进当前 PR 的，是不是只有……」，改前一条都不推荐并进时也答「是」，抓不住问题；所以这里要求影响交付的那条确实被推荐并进。

## 跑过的结果（2026-11-14，工单 01）

| run | 材料 | 改前 | 改后 | 结果 |
|---|---|---|---|---|
| `20261114T063503` | 没有 #157 那一句 | 否（四条全推荐另开） | 否（把影响交付的两条推荐并进，把「输入露题」判成跟 #174 无关、推荐另开） | 不过：改后那一遍照规则做了，但没把露题那条判成「影响」，是材料缺因果 |
| `20261114T064045` | 补了 #157 那一句 | 是（只把露题并进，其余另开） | 否（四条里把不影响的也推荐并进） | 用例没抓住问题（case-missed） |
| `20261114T064617` | 同上，原样再跑 | 否（推荐另开，理由是混在一起 #174 自己的验收失去对照） | 是（推荐并进，理由「不修的话，上线后每个结果都受影响。照规则，这类问题在当前 PR 里修」） | 过 |

三次里一次过：同一条用例在同一份输入下，改前、改后两边的推荐都会摇摆（模型把四条改进归成「影响实现」还是「不影响」不稳定），所以单次结果只能算一次抽样。之后有人要重验这条规则，多跑几次看趋势，不要拿一次结果当结论。第三次是 `~/.idea-loop/bin/` 里装的旧版 runner 跑的：评委是 Claude 不是 Codex，runner 也没有做改动核对（`exercised`）；改动核对用同一个仓库里的 `exercisedBy` 对着第三次改后那一遍的事件流补算：命中（经 `/idea-loop:decision-rules` 开头的斜杠命令）。
