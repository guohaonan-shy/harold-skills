# 样本：对现状的说法带出处、核过代码

**一句话**：issue 和 spec 里写「靠每周 dreaming 兜底」，没人核过 dreaming 现在是不是定时跑、怎么对账；人一问才发现是推断。好的做法是讲现状的每个说法带出处，没核过的不当事实写。

## 出处

harold-skills#55，起草 spec 那一步（2026-10-23）和随后 PR #90 的 review 第 1 轮。决定记录 `docs/raw/decisions/55.md`：候选 4；PR #90 上「review 第 1 轮」的归档评论。

## 当时产出的原文

issue 正文里的一句（现状的说法，后来原样进了 spec）：

> 已知缺口：网页上点合并或在别的会话合并会绕过归档，靠每周 dreaming 兜底；合并统一在审核会话里做。

review 第 1 轮汇报 S3（节选，原文在 PR #90 的归档评论里）：设计档案对账分两波，先不开浏览器、靠档案查询核对象，再开浏览器逐个状态走；实现只把开浏览器那一波交给 UI 审查者，前一波留在 dreaming 里。汇报没有说 dreaming 现在什么时候跑、对账是增量还是全量。

## 人指出的问题

人原话（review 第 1 轮的批示）：「S3的核心问题是dreaming里面的设计对账是否要开浏览器……（我理解dreaming是定时的，可以根据距离上次dreaming到现在之间的变更页面进行对账，还是说完全全量），dreaming现在是这样做的吗？」

「每周 dreaming 兜底」是推断。在 spec 起草前的提交（`d3efaea`）上核：`dreaming/SKILL.md` 开头写 `disable-model-invocation: true`，是人手敲的斜杠命令；`setup/SKILL.md` 只建了 `idea-loop-retro-replay` 一个定时任务，没有 dreaming 的；`README.md` 称它是对整个知识库的批量对账（每次全量）。人问的是现状，spec 和汇报里没有答案。后来增量对账和定时任务并进了这个 PR（决定记录 题 12、13）。

## 好的长什么样

spec 写到 dreaming 的现状时：

- 先去读 dreaming 的说明、它调用的参考、setup 里有没有建 dreaming 的定时任务，再写；
- 每个说法带出处：「现在没有 dreaming 的定时任务：setup 里只建了 retro-replay 一个（文件、位置）」「设计对账现在是全量：dreaming 的 SKILL 里档案对账一段没有取上次基准（文件、位置）」；
- 查了没有的，写「查过：在哪找过，没有」；issue 里的话跟代码对不上，就把差别写出来，不照抄成现状；
- 兜底靠什么、要不要增量，是 spec 要定的事，不是已有的事。

不好的样子：把「靠每周 dreaming 兜底」直接写进现状，没有文件、没有位置。

## 回放这一格怎么跑

- 现场：spec 起草之前的提交 `d3efaea`，prompt 是起草 spec 的那一句加 issue 正文；
- 换过的地方：**第一次**用的是 review 第 1 轮那一步：提交 `0cb7b22`，prompt 把汇报 S3 和人的追问放进去，让编排者对着代码回答。那一版跑出来改前就是「是」（改前的插件在被直接问到现状时也会去核代码、带出处），说明它没抓住问题；改后那一遍也没读到这次改动涉及的文件，判成「没测到改动」。所以换到同一个 issue 的起草 spec 那一步：issue 里的话原样给出、不问现状，看会话会不会自己核（依据：候选 4 本来就是「issue 正文里对现状的说法也是推断，起草前先核过」）；
- 大小：small，只驱动 to-spec 一个 skill。
