## 标准没说清、互相冲突、我自己猜的

1. **「证据」节的之前/之后对不上**：标准要「跟问题节同一种证据、同一组输入」。问题节的证据是本机进程数（71 份），但服务没装进本机，合并后的进程数没人数过。处理：之前写「同问题」，之后写明没数、指向「没验成」，再用验收脚本的表顶上。标准没说「同一种证据做不出来时用什么替」，这是我猜的。
2. **验收表只有「之后」一列**：视图菜单的「表」要「输入 → 之前 → 现在」。基准分支没有 HTTP 服务、没有换版本，验收脚本在基准上跑不了，之前那一列只能写「不存在」。处理：只留「输入 / 结果」两列，第三行把脚本自带的对照组（卡在主循环上，3.5 秒）写进结果格。
3. **review 第 1 轮修的那条连接问题放不放**：标准说 review 跑几轮不放进证据。但「换版本时调用做完了却拿不到结果（21 次断 2 次；去掉修法后负载下 10 次断 3 次）」是换版本这一行最有力的改前对照。处理：守标准，没放；表里只写修好后的 10/10。值得人判断：它算「review 记录」还是「改动生效的证据」。
4. **「要你做的事」要不要写命令**：标准说概要之外的四节「不写代码层的叫法」，home 规则要「给能照着做的那一步」。处理：命令放在复选框里的代码块，复选框文字本身不用代码叫法；核对一项里保留了 `reload.log` 的路径，因为不给路径人找不到。这是两条规则冲突时我选了后者。
5. **「合并风险」里的 `门：双向`**：合并本身可撤；但人迁移后结束了旧进程、改了 32 份本机配置，要靠备份手工拷回。我判成双向（有备份、能回到原状）。标准没说「靠人手工恢复的本机状态」算不算单向。
6. **旧描述的「夜里替你定的」没有对应的节**：标准五节里没有它，又说「还没批的决定题不放」。两件都已定：「key 文件优先于环境变量」挪进合并风险当「出人意料的决定」；「谁来跑迁移」变成「要你做的事」和「没验成」里的理由。人要推翻这两件，新格式里没有入口提示。
7. **概要放两个视图**：标准说「要点在两处才加第二个」。我判成两处：结构（一份服务 + 换版本，时序图）和会话侧接法（`.mcp.json` 的 diff，key 离开客户端配置）。生图/转写移进线程只用一句话带过，没给视图；它的证据在证据节。
8. **时序图标签语言**：excalidrawer 默认英文标签，「用中文」要人明说。PR 描述是中文、读者按中文叫法认东西，我用了中文标签，没问人（子代理不能问）。返回样式选了「按语义」（请求实线、响应虚线），也没问。
9. **术语**：`GLOSSARY.md`（合并提交版）的「内容生产」只有 Extraction task、出题检查等，没有 toeflair MCP、常驻服务、主 checkout、重载任务、worker。处理：第一次出现时一句话说明（「出题工具（…即 toeflair MCP）」「主 checkout 是…」「重载任务是…」）；worker 只在图里出现，没解释。
10. **问题节「一两句」**：标准要一两句写现状和为什么改，但这个 PR 有两半问题（进程泄漏、换 key 不生效）。我写成两句，第二半没有频率证据（只有 #973 一次经历），放在图下一句带出处。

### 新版标准还没说清的

1. **问题有两半，之前/之后只给了一对**：模板里证据节只有一组之前/之后，这个 PR 的问题节有两件（一个会话一份进程、改 key 不生效）。我写了两组，每组前面一行写它对的是哪一件。标准没说一组还是每件一组。
2. **复现全缺时证据节几乎是空的**：材料里没有一次「同一个操作在基准和本分支各做一遍」的复现，四格都写成〔缺：复现，…〕。真服务验收只做在本分支上，基准分支没有服务，没法跑同一个操作。我把它挪进了测试块（写成伪代码加结果），并在「改 key」那组的之后里点了一句「现有的最近一次」。标准没说只有一边的实测能不能放进之后，也没说该放进测试还是删掉。
3. **生图、转写的单测「改前红、改后绿」算不算复现**：同一个输入在基准和本分支各跑一遍，严格说就是之前/之后。但它复现的是共用进程之后才会出现的卡顿，不是问题节里的问题，所以我只放在测试里。标准没说「方案自己引出的问题」它的复现放哪。
4. **「已经定了的事不进描述」与「刻意没做的」的边界**：Codex 不接、worktree 的代码不由服务跑，都是人在 grill 里定的（2026-11-24），但它们是合并后人会碰到的限制，我按「刻意没做的」留在了合并风险里。key 文件优先于环境变量是夜里按推荐定的，删了。标准没说已定、但合并后会被人撞上的行为算哪一类。
5. **门的「双向」**：同第一轮第 5 条。迁移后要靠备份手工拷回，标准仍没说这算不算单向。
6. **代码叫法的边界**：「要你做的事」的复选框文字里用到 `status`（命令的一部分，不在代码块里）。我判成「要人跑的命令」可以用；文件路径（日志、备份目录）都改成了「迁移输出里列出的备份目录」这类说法。测试块里也去掉了函数名、文件名。概要以外还留了一个 `#973`，是 issue 号，不在禁列之内。
7. **概要的两个视图**：同第一轮第 7 条，没变。
8. **合并风险第一条塞了两件事**：「迁移会断开会话」和「备份里有 key」合成一条，为的是不超过 3 条；后者同时也是「要你做的事」的一项。标准没说两节能不能重复。

## 第三轮

第二版改名为 `description-v2.md`，新版在 `description.md`。

### 字数

- 新版 `description.md` 去掉代码块后 **2158** 字（第二版 1715，第一版 1752；旧描述折叠区外 3577，去掉 section 标记行 2977）。多出来的主要是证据节第三组和概要新加的两处。

### 这一轮怎么照新规则改的

- **人定的事改变的东西**：review 第 1 轮修的「每次回完结果都让客户端换新连接」、按规则定的「依赖声明改了也触发换版本」画进了概要（一句话）。「迁移留给人在合并后跑」（夜里按推荐定的）带来的后果「合并后到迁移前本机照旧」写进了合并风险第一条。「key 文件优先于环境变量」（夜里定的）没写：迁移后客户端配置里不再写 key，服务的环境里也没有 key，找不到一条会撞上它的真实路径，按 home 规则不拿理论情况出来。
- **Refs**：PR 只关联 #987（正文 `Refs`，`closingIssuesReferences` 为空），所以只有一行。
- **每件一组**：问题两件各一组，另加一组「生图、转写移进后台线程」，它是不对应问题的改动（规则 4），概要里画成调用树 diff，证据证明行为没变。
- **真服务验收**：改代码换版本那次照常写成「之后」，「之前」标缺。

### 新版标准还没说清的

1. **为了方案才需要的改动算不算「没有对应问题」**：生图、转写移进线程，不是搬文件也不是重构，行为确实变了（不再卡别的调用），但它对应的「卡住所有会话」在合并前不存在（一个会话一份进程时只卡自己），问题节里也没有。我按规则 4 当「没有对应问题的改动」处理，证据写行为没变。可它的「改前红、改后绿」单测其实是一次之前/之后复现，证明的是行为变了，跟规则 4 要证明的方向相反，我只好放在测试块里。标准没区分「重构」和「方案引出的必要改动」。
2. **一件问题只有一半能复现**：「改了代码或 key」这件，改代码有之后，改 key 没有。我在同一组的之后里写了改代码的结果，再接一个〔缺〕给改 key。标准没说一件里两种触发要不要拆成两组。
3. **「之后」只在临时端口、用脚本客户端跑过，不是真的 Claude 会话**：规则 5 说「照常写成之后」，我照写了，并点明是临时端口、客户端一直连着。标准没说复现的条件（真会话还是脚本客户端）跟「同一个操作」差多少还算数。基准分支上没有服务，这个操作也就没有字面意义上的「同一个」。
4. **「之后」里现有的部分证据怎么写**：第一件「两个客户端连同一份服务都能调通」不是数进程，算不上之后。我写成〔缺〕，后面跟一句「现有的只是…」。标准只给了〔缺：复现，<操作>〕一种写法，没说能不能附上已有的一半。
5. **人定的事后果找不到真实路径时**：规则 1 说「合并后会带来的风险写进合并风险」。key 文件优先这件后果几乎碰不到，我没写。标准没说「没有风险就不写」，按 home 规则「找不到真实路径的不拿来让人决定」处理的。
6. **概要的视图数**：现在概要有三个视图（时序图、配置 diff、调用树 diff）加一句话，超过「要点在两处才加第二个」。规则 4 又要求没有对应问题的改动画进概要的 diff，两条叠在一起只能是三个。标准没说规则 4 的 diff 计不计入。

## 第四轮

第三版改名为 `description-v3.md`，新版在 `description.md`。

### 字数

- 新版去掉代码块后 **1486** 字，含代码块全文 2556 字。
- 前几版去掉代码块后：第三版 2158，第二版 1715，第一版 1752；旧描述折叠区外 3577，去掉 section 标记行是 2977。

### 这一轮怎么改的

- **证据节没有一组之前/之后**：按「只放两边都真做过的组」，三组都不够格。改代码换版本那次只有本分支，进程份数、改 key 两边都没做。证据节只剩测试块、全量结果和一行「没验成」，验收结果并进了测试块。
- **「行为没变」这一行没写**：生图、转写移进线程后返回不变，只有本分支的测试（出错照常报错等），两边没各做一遍同一个操作，够不上「同一个操作，两边结果一样」，所以并进了「没验成」。
- **概要两个视图**：时序图，加一个调用树 diff。调用树 diff 把第三版的配置 diff、线程 diff，以及 review 修的「每次换新连接」合在一起。依赖声明触发换版本只留一句话。

### 新版标准还没说清的

1. **一组之前/之后都没有时，证据节长什么样**：模板默认至少有一组。照规则全进「没验成」后，证据节开头直接是测试块，读的人看不到「问题没了」的直接证明，只能读测试。标准没说这种 PR 要不要在描述里标明「没有复现」，也没说该不该挡着不让合并。现在「没验成」那一行很长，它承担了原来之前/之后的信息。
2. **「行为没变」够不上时写什么**：例子是「两边逐字节相同」。只有本分支测试的时候，我当成没验成，并进那一行。标准没说只在本分支有的测试（比如「出错照常报错」）能不能写进「行为没变」。
3. **「没验成」写成一行还是几行**：标准写的是「一行」，可这里没验成的有三类：两件问题的复现、线程改动两边对照、本机真装和迁移。我写成一段，没拆。三类的理由和补的人不同，挤在一行里很难读。
4. **概要两个视图上限，规则 4 又要 diff**：这一次把两个 diff 合成了一个调用树 diff，才守住两个。合并后的 diff 既有接法（配置），又有调用内部（线程），层级混在一起。标准没说多个 diff 能不能这样合，也没说是不是该挑一个丢掉。
5. **测试块里放真服务验收**：它不是单元测试，是一次跑在临时端口上的实测，原来是第二件问题「之后」的那一半。现在只能放在测试块里，跟单测混在一起，读的人分不出哪些是真服务跑出来的。我在那几行后面标了「临时端口上起一份真服务」。
