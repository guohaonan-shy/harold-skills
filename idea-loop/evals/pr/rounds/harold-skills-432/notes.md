## 标准没说清、冲突、我自己猜的

1. **「其余四节不写代码层的叫法」碰上 skill 改写类 PR。** 这个 PR 的改动对象本身就是 skill 和 agent 的名字。问题、合并风险两节我改用中文角色名（UI 审查者、对账、实现执行方、SEO 接入、找外链候选站点），没写 `ui-reviewer`、`dreaming`；但合并风险里 `plugin.json`、证据里的 `020c5ba` 这类留着了，因为没有更好的叫法。标准该说清：插件 PR 里，skill 名算不算「代码层叫法」。
2. **「要你做的事」要给能照着做的一步（home 的规矩），但这一节又不能写命令。** 真机交出我只写了行为（「让调度开一次 issue 会话」），没写 `dyna runtime handoff --worktree … --issue …`。人要照做，其实需要那条命令。两条规矩在这里打架，我选了守 description.md。
3. **概要节「一句短文字 + 一个视图，要点在两处才加第二个」。** 这个 PR 有三个要点（逐份重写挪分支、五组合并、开会话统一）。前两个都落在文件布局上，我合成一张文件树 diff；开会话统一是行为变化，单独一张调用树 diff。去重规矩、手写命令换 dyna 这两件只有一句话，没有视图（材料里没有能直接搭的改前改后例子）。
4. **证据节的「之前」要「跟问题节同一种证据、同一组输入」。** 问题节有三行现象，但旧描述和 review 只给了第一行（字数）改后的数；决策历史和手写命令只有「剩下的命中都有理由」这种定性说法，没有改后的份数。所以「之后」只对上了字数这一行，另两行没写之后——这是材料缺，不是我漏了。
5. **开会话统一这一处没有对应的问题。** 它是 review 中途人定加进来的（19、20 号工单），问题节里没有它的「之前」证据，标准没说这种 review 中加的范围怎么摆。我把它放在概要的第二张图，证据里只放测试那两行，没在问题节补一行。
6. **「没验成」写成「一行」，但有两件。** 我写成一行，两件用分号隔开。
7. **「要你做的事」只有两类复选框（合并前 / 合并后）。** 真机交出旧描述里说可以先合再验。我保留一个复选框，末尾写「合并后再验也行」，没拆成两类，也没判它归哪类。
8. **合并风险「要特别注意的」三项合计最多 3 条。** 候选有四条：5 个旧名调不到、dyna 0.0.5 没发布、`plugin.json` 不升、几份很长的参考文件只查了违规没逐份剪（实现汇报的「没覆盖到」）。第四条我丢了：它不影响合并后的行为。
9. **影响面「一个词」。** 写了「全插件」。后面一句写「合进集成分支，0.2.0 发布前没人装得到」，这算可选的连带后果。
10. **review 里处理的 H4–H6（SEO agent 的 description、对账参考里的旧命令名、setup 走不到的分支）和顺手开的 #433–#437。** 标准说顺带开的 issue 不放合并风险，没说放哪；三件小改动在五节里都没有位置。我都没写。人要看 #433–#437 得去会话或 review 评论里找。
11. **视图选择。** 问题节用「表」（确定性的数值），概要节用「文件树上画 diff」和「调用树上画 diff」，证据节用伪代码写测试。没用 excalidrawer 图表，因为表格已经够讲清，标准说挑最小的一种。
12. **结尾的 `Refs` 和 Generated with 行。** 模板里没有，但 issue 关联和仓库的 PR 署名规矩需要，我留在最后、在五节之外。标准没说这两类尾巴放不放。

### 新版标准还没说清的

1. **人批过的决定，结果本身算不算「已经定了的事」。** D2（开 issue 会话两种运行环境用同一条命令）是人在 review 里批的，但它是这个 PR 里唯一碰行为的改动，也是「要你做的事」里真机交出那一项的来由。删掉它，人看不懂为什么要去真机验。我留下了这一处（概要第二张图），删了 D1、D3。标准该说清：不进描述的是「决定的过程和批示」，还是连它带来的改动一起不写。照字面读是后者，可那样概要就不完整了。
2. **一个 PR 关两个 issue 时，Refs 写几行。** 标准说「只留一行 `Refs <owner>/<repo>#<号>`」。旧描述有 #340、#356 两行（#356 随这个 PR 关）。我只留了 #340，#356 的关联就断了。
3. **「出处」要带版本，提交号又不能出现在问题节。** 不写提交号，「对着哪个版本查的」只能写成分支加日期，比如「同步完 #431 之后」。同一天这条分支上有好几个提交，读的人对不回准确的那一个。我按标准挪走了，但出处精度降了。
4. **问题节里三行出处不是同一个版本。** 问题节三行各自量在不同版本上：集成分支 11-20、集成分支 11-19、main。证据节要求「同一个操作在基准分支上」，只有第一行恰好量在基准上。另两行哪怕补跑复现，「之前」的数也会跟问题节的数不一样。标准没说问题节的数和证据节「之前」的数对不上时怎么写。
5. **〔缺：复现〕占位，在 PR 描述里给人看合不合适。** 两组之前 / 之后全是占位，读的人看到的是「这里本该有证据」。如果标准的意思是合并前必须补上，那应该进「要你做的事」或「没验成」；我两处都没放，只按指示写了占位。
6. **「没验成」和〔缺〕的边界。** 真机交出写进了「没验成」（有原因、有谁补）；搜索类复现写成了〔缺〕（材料缺，不是验不了）。这两者在 PR 描述里怎么区分，标准没说。
7. **「要你做的事」里命令带占位参数。** 标准要「照着复制就能跑」，但 worktree 目录、issue 号、仓库名只有人自己知道。我保留了尖括号，并说明要换成什么。
8. **命令的副作用写不写。** 这条命令会往这台设备的调度记录里追加一条，早上汇总会把它当成调度开出的会话。标准没说要人跑的命令要不要讲副作用，我写了一句。

### 新版标准还没说清的

1. **合并 skill 算「没有对应问题的改动」还是「问题 1 的解法」。** spec 里合并是方案的一部分，问题节没有一行说「skill 太多」。我当它是重构：概要画 diff，证据证明行为没变（用同一句话调合并前后的入口，看产出）。但它其实也替问题 1 腾了余量。标准没说一个改动同时服务问题、又是重构时怎么归。
2. **「行为没变」的之前 / 之后，有的改动之前根本没有那个入口，或者入口本来就是对的。** 比如 dyna 提示：在基准分支上，seo-setup 还在，报错让人跑 `/idea-loop:seo-setup` 是对的；本分支删了它，提示才必须跟着改。两边结果「一样」的意思其实是「都指向一个存在的入口」，不是字面相同。开场注入也是：6 节变 9 节是刻意的变化，不是「没变」。我写成了「原来的那节还在、多了并进来的」。标准的例子（搬录音包后听题照常）只覆盖纯搬家这一种。
3. **〔缺〕和「没验成」重叠。** 「合并后的 description 能不能被真实对话触发」我放在没验成里；「用同一句调 seo-writing 看 brief」放成〔缺〕。两者都是没做的复现，区别只在材料里有没有「之前」。标准没说同一类缺口该放哪一处。
4. **〔缺〕太多会盖住真证据。** 证据节 8 组里真有之前和之后两边的只有 2 组（字数、开 issue 会话）。读的人要在一堆占位里找这两组。标准没说缺口很多时要不要先列已证的、再列缺的，或者把〔缺〕收成一行。
5. **合并风险里由推理得出的风险能不能写。** 0.0.4 不认新参数，是我从工单 19 的「新参数 `--cap`、`--prompt-file`」推出来的，没有人实跑过。标准要求的证据是复现，没说合并风险里推出来的风险怎么标；我在句末写了「照工单推出来的，没实跑」。
6. **概要的「要点在两处才加第二个视图」。** 这一版概要讲了四件：挪分支、合并、去重和命令、开会话统一。人定的事带来的改动加进来以后，概要更难用一两张图讲完。我还是两张，去重和命令替换没有图。

### 新版标准还没说清的

1. **「没验成」一行装了三类东西。** 一是问题 2、3 没复现，二是合并后的入口没比过产出，三是真机交出。现在这一行将近 200 字，读起来已经不像一行。标准说「一行」，又要求没复现的都合进来；缺口一多，两条要求就互相顶。
2. **问题 2、3 在证据里一组都没有，问题节却照常列着。** 读的人看到三件问题，证据只证了一件。标准没说没证到的问题要不要在问题节标出来，还是留在问题节、只靠「没验成」交代。
3. **「行为没变」只有一行，但没对应问题的改动有好几处**：五组合并、开场注入、dyna 提示、「原话」统一、开会话统一。只有开会话真有两边的对比，其余的要么进伪代码（只写之后），要么进「没验成」。标准没说一行写不下多件时怎么办，也没说只写了之后的测试算不算行为没变的证据。
4. **合并风险删掉推出来的那条之后，留下的「还装着 0.0.4 的人开场注入第一句是旧的」本身也只有实现汇报的一句话，没人实跑过。** 我留着它，因为它是材料里写明的事实，不是我推的。标准该说清「有证据」是指有人实跑过，还是材料里有人写过就算。
5. **人定的事带来的风险也要有证据。** 第三轮的规矩要把人定的事带来的风险写进合并风险，这一轮又要「没证据不写」。dyna 提示改指之后，0.0.4 上的提示仍指向被删的 skill，这是从改动直接得出的，但没人实跑。照这一轮的规矩我没写，人就看不到这一处。
