### 新版标准还没说清的

1. **grep 算不算「一次复现」**：标准举的例子是「开 3 个会话、数进程」这种操作，又说「不拿线上的统计数跟合并后的数比」。脚本全路径的 154 处是对代码跑 grep 得出的，同一条 grep 两个分支各跑一遍，我当成复现用了。但之前那次是对着 11-18 集成分支上的一个提交跑的，不是这个 PR 的合并基准（合并基准是 19 号的一个提交，中间又合进了一个 PR）。处理：照用，写成「基准分支上 154 处」。严格说两次跑的条件对不上。
2. **问题节的数和证据节的数重合**：同一个 154，问题节拿它证明问题真实存在，证据节拿它当「之前」。标准没说这算不算「拿问题节的数比」。处理：留着，因为这一对确实是同一个操作。
3. **决定带出的后果放不放**：「已经定了的事不进描述」，可是 review 里你批的「换现成 YAML 库」带来一个兼容约束：不加引号的值读不出来，TOFEL-demo 要合 Tofelair#1031。处理：决定本身不写；它的后果写进「兼容」一条和「要你做的事」，只写行为，不写谁定的。静态服务器 30 分钟自动退出、第一版叫 0.0.1、`--hook` 留着，都是定了的事，全删了。
4. **「要你做的事」的命令写到多细**：合 PR 的命令没法照抄就跑通。`gh pr merge` 不带 `--merge`、`--squash` 时会交互地问，那个仓库用哪种合并方式材料里没有。处理：给了不带方式参数的命令。
5. **影响面「一个词」又不能写路径**：分支名 release/idea-loop-0.2.0 算不算代码层的叫法，标准没说。处理：写「0.2.0 的集成分支」。「集成分支」术语表里也没有。
6. **〔缺：…〕写多细**：标准只给了格式。处理：每条写清在哪个分支、做什么、看什么。四对之前 / 之后里有三对的「之前」是缺的，读者会看到三个缺口。描述该不该因此标成「证据不全」，标准没说。
