# 夜间模式

任务里写了「夜间模式」：人不在，没有人会回话。会话从认领做到 `idea-loop:pr-review` 跑完，停在等人说合并，中途不停下问人。下面每一节对应一个原本会停下问人的地方，凡 SKILL.md 和别的 skill 写了「停下等人」「翻回 triage」，夜里以这里为准。

## 要人定的，按推荐定

用户规则（`~/.claude/CLAUDE.md`）「停下问我」里的每一题、实现卡住时的「要你决定」、review 汇报里的「要你决定」，都选这一题自己的推荐，接着做。

- 起草 spec 冒出的「待定」「需要 grill」：照 [draft-spec.md](draft-spec.md) 里「AI 照推荐定」的写法自己定完，不翻回 triage。
- 实现和 review 里：把「夜间模式，人不在，按推荐：<推荐原文>」当作这一条的批示记进 review loop 文件，之后照原来人批示后的处理走（`idea-loop:implement` 的「人回复后」、`idea-loop:pr-review` 的「处理条目」），不等人。
- 只有人能做的设计（画布没冻结、要先 `/idea-loop:uiux-imagine`）推荐替代不了：照 draft-spec.md 的做法 `dyna issues set <docs> triage` 翻回去并留评论，去「收尾」（夜里的收尾不起 retro，见下）。这是交回，不算停下等人。
- `idea-loop:seo-writing` 的写作评委报出 `premise`（论点、章节或事实断言要变）：角度是人定的，推荐替代不了。已写的提交并 push，`dyna issues set <docs> triage <号> --comment=<写作评委原话和分支名>`，不按推荐改论点，去「收尾」。这是交回，不算停下等人。

**按推荐定的，只记进 review loop 文件**：每一条就是上面那条批示，写清选了什么、为什么、另一种是什么，用人话写；PR 描述只有五节，没有放它的地方。PR 还没开出来时定的，开出来后立刻记。早上汇总（`idea-loop:issue-dispatch`）从这份文件数条数。

## 只在这五类事上停

1. 合并 PR
2. 删分支或数据
3. 强推
4. 对外发信，或在别人的仓库评论
5. 碰这个 issue 以外的项目

用户规则「只由我做」里别的几样（动生产数据、真实支付、对外发布、术语起名）夜里同样不替人定：不碰它；它挡着往下走，就停下。

碰到了（合并除外）：

1. 在 issue 上留一条评论（`dyna issues note`）：停在哪件事、为什么要人来、人说了怎么做之后会话怎么接。
2. 停下。会话留在当前分组，状态不翻；调度每轮照样派新的 todo，不等它。

合并是正常的终点：报告交出去后「要你做的事」里已有「说合并」，不再另留评论。

## 做到哪停

1. 实现全部落地，PR 转 ready，issue 翻 in-review，用『会话管理』的「分组」把自己移进 in-review 分组。
2. 用 Skill 工具调 `idea-loop:pr-review` 跑到它自己的停点：交出审核报告；或跑满自动轮数上限、最后一个自动轮的修复刚落地。停在那里，等人说合并或再跑一轮。
3. 不做 retro，不归档 review loop 文件，不走「收尾」里的会话收尾：这三样等白天人在场时做。
