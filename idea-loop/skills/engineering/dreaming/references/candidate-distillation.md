# 候选蒸馏：dreaming 特有的部分

把设计档案里的「设计法候选」收进项目的 `DESIGN.md`。**判据、写入流程、单条蒸馏的步骤都不在这里**：全在写入 reference（`../../../../references/design-md.md`，下称「写入 reference」）。这份文件只写 dreaming 自己多出来的几件事：候选从哪找、每周这次怎么出提议、批了之后怎么收尾。

> 读之前先读写入 reference 的 §3（五条写法规则）、§4（先整改后追加）、§7（准入分层表）、§8（不进 `DESIGN.md` 的内容）、§11（蒸馏）、§13（一条候选的形态）。判断一条候选该不该进、进哪，只按那几节，不在这里另立。

## 1 三种来源

| 来源 | 怎么找 | 提议表里写什么 |
|---|---|---|
| **对象正文里的候选** | 设计档案里 page / component / motion / journey 文件的固定一节「## 设计法候选」；档案还没落地的项目，找冻结记录 `docs/design/tmp/<slug>/canvas/<slug>-design.md` 的同名一节。整节只有一行「无」就跳过 | 候选原文（一句规则 + 并进 / 为什么 / 证据，写入 reference §13 的形态） |
| **多个档案组件重复的做法** | 对账的源码波顺带数：同一种配方（内边距、圆角、状态处理）出现在多个组件对象里 | **次数和重复它的组件名**，把它先补成 §13 形态的一条候选 |
| **被多处引用的动效** | 查询入口反查每个动效对象被多少节点、边引用；档案没落地时数 wikilink | **引用次数和引用方**，补成一条候选（该并进 Motion 章的哪条全局原则） |

**后两种不设阈值。** 重复几次、被引用几次才值得抽，不定成数字：档案刚建时次数都很小，定死的阈值要么永远不触发，要么一建好就全触发。次数和引用方摆给人，由人判。

## 2 提议段：每条候选一行

每条候选在 `候选` 一节占一行（行的形状见 `proposal-table.md`），一条一条做三件事：

1. **过分层表**：写入 reference §7，说出去向和一句理由。拿不准落在哪两层，就把两个候选层和各自的理由写进「选项」，不替人选。
2. **先整改后追加**（§4）：在 `DESIGN.md` 里先找受它影响的已有内容——矛盾、过时、已覆盖。能改写或删除的就提议改写或删除；已覆盖的什么都不加；**只有缺这一处才提议追加**，追加时同步 front matter 的 token。所以建议处置的次序是：`改写已有规则` 优先，其次 `已覆盖不加`，最后才是 `追加新规则`。「发现」格写清楚找过哪些已有内容。
3. **证据格放图、去处和旧文新文并排**：这条规则说的那块界面的截图（先从设计档案取，没有再从实现截，见 `review-page.md` §1）；进 `DESIGN.md` 的写「并进：<章 · 条>」和 `旧：「…」→ 新：「…」`（追加写 `旧：无 → 新：「…」`）。定时那次没人在场，所以并排的文字必须在表里，不能只写「见某文件」。
4. **交给人时出候选卡**：每条一张卡——图、设计是什么样、拟写进 `DESIGN.md` 的规则原文和进哪一节、为什么在这一层、带后果和推荐的选择（采纳 / 改措辞 / 留在档案边上 / 不进 `DESIGN.md`）。格式见 `review-page.md` §2。人逐张看完就能定，不用回头翻冻结记录。

不进 `DESIGN.md` 的候选，处置按写入 reference §11 的去向分走，落到表里是这几个：

| 去向 | 建议处置 |
|---|---|
| 页面或组件自己的「决定」 | `留在原处` |
| 通用设计原则（换个产品也成立） | `起草通用原则 issue`（标题 + 原则 + 来源 + 建议落点，写在「证据」格） |
| 现状、缺陷（说的是「现在什么样」） | `起草缺陷 issue`——起草成**目标仓库的 GitHub issue**，同时在 `缺陷` 一节有对应的一行；写入 reference 里这一类若仍指向别处，以这里为准 |
| 驳回 | `驳回`，一句理由 |

### 2.1 默认等那一页上线

写入 reference §11：默认等那一页上线之后再蒸馏。每周这次碰到「页面对象还在 `tmp/`、没进 `prod/`」的候选，不进表（它们还没合并，归各自的需求）。人要求提前的在「发现」里注明「未经线上验证」。

## 3 执行段

人批了的行，逐条照写入 reference §9 的流程落笔（备份 → 旧新并排 → 人确认措辞 → 只改批过的 → lint + diff）。**dreaming 从不自己落笔**：定时那次只出提议；人批了、在会话里确认措辞之后才写。

- 一批候选里有几条要进 `DESIGN.md`，合成一次写入，不要一条一次 lint。
- **处理完的候选从档案对象里删掉**，去向（落进哪一章 / 开了哪个 issue / 留在原处 / 驳回理由）记在这次 PR 的正文里，不留在候选上。
- **整节删空时写一行「无」**（写入 reference §13）：空着分不清是没有还是漏了。
- 通用原则 issue 人批了才开（命令照写入 reference §11）；缺陷 issue 人批了才 `gh issue create` 到目标仓库，开之前先查有没有开着的同一个问题，有就改写「已有 #N」。
- 不批的候选原样留着，下一周再出现；这是正常的，不是漏处理。

## 4 单条蒸馏

人在会话里口述一条视觉规则、想当场落时，手动调一次 `dreaming` 并带上这条规则：**只处理这一条**——不开浏览器、不起 dev server、不跑知识库对账与其它任何一部分、不产出提议表。步骤逐字照写入 reference §11 的「单条蒸馏」一节（补成 §13 形态 → 过分层表 → 先整改后追加 → 旧新并排 → 等人确认 → lint 与 diff）。

- 补不出「证据」就问人，不编。
- 人确认之后在一个从 `origin/main` 新切的 worktree 里落笔，开只改 `DESIGN.md` 的 PR（跟每周那次的执行段一个去处，不直接提交到 main）。
- 人不调，这条规则就记成候选，等每周那次。
