# 审核页：把 `DESIGN.md` 的改动摆成人一眼能判的样子

提议表是给校验脚本和执行段看的底稿；**人拍板看的是审核页**。`候选` 和 `DESIGN.md 条目` 两节有行时，在提议表之外再做一页审核页（Artifact），每行一张卡片。人逐张看完就能定，不用回头翻冻结记录、不用自己起服务、也不用再问「这是什么意思」。其它几节照 `proposal-table.md` §1 摆给人，不归这份文件管。

> 这份文件来自一次真实对账。第一次交出去的是 37 行纯文字表，人先要逐条解释，再要截图。截图是事后补的，截完发现原先有 3 处描述是错的。有两条因为图点不开，人没法判。术语多绕了一轮问答，候选也被要求重做成「每条配图 + 进 `DESIGN.md` 的哪句话」。下面每一条规矩都对着当时的一个卡点。

## 1 全页共用

1. **先截图，再写描述。** 描述里的数值（圆角、尺寸、颜色、阴影）用截图时从真 DOM 读出的实测值，不用代码里猜的值，也不用 `DESIGN.md` 里写的值。先写文字后补图，补图时常会发现文字错了。
2. **截图从哪来**，按先后：
   - **设计档案**：用设计档案的查询工具（`design-archive` MCP）——`design_refs` / `design_keyword` 找出用到这块界面的状态，`design_state` 拿它的 `screenshots`（`prod/` 下的精简矩阵）。档案图和代码对不上时，以实现为准，并在卡里注明。
   - **实现**：档案里没有、或这条说的是代码现状（`法和代码对不上`），就在从 `origin/main` 起的开发环境里截。规矩照 `../../evidence/SKILL.md` §3「截图取自实现」：只截那个组件（连同它弹出的浮层），2 倍像素密度，手机宽 390，节奏靠网络拦截；为了说明而叠上去的测量标签、光圈属于叠加层，在页首用一句话说明。浏览器怎么用见 `../../../design/uiux-refine/references/design/browser-usage.md`。
   - **冻结画布**：只有候选的那一页还没上线、人要求提前蒸馏时才用，卡上标「未经线上验证」（写入 reference §11）。
   - 截不到（状态进不去、没有单独的界面）就在卡上写明缺什么、试过什么，不重画。
   - 截图放这次运行的 `.tmp/dreaming/<日期>/shots/`，跟提议表放在一起，不进仓库。
3. **图都能点开看原图。** 卡里的图是缩略图，点开是全屏大图，可以在「适应屏幕」和「原始尺寸」之间切换，Esc 或点空白处关闭。焦点环、圆角、1px 的边框这类差别，缩略图上看不出来，点不开就等于没给图。整页长截图先压成 JPEG，局部特写保留 PNG。
4. **卡里出现的术语，每个配一句白话。** 例：键盘聚焦——按 Tab 在页面上跳到按钮时停在哪个元素上，不是鼠标悬停；内边距——卡片或按钮边缘到里面文字的空白；`orphaned-tokens`——front matter 里定义了、却没有任何组件条目引用的值。写给拍板的人，不写给 agent。
5. **每个选项写后果，推荐只有一个。** 选项写清：`DESIGN.md` 改哪句、线上会不会变、哪些页面会变、代价是什么（比如「列表里 36 的小按钮会变大」）。推荐的那个排第一、标出来，一句话说为什么。不写「A / B」这种不带后果的字母。
6. **已定的条目下一版就移出页面。** 页首写一句「已处理 N 条：去向见 PR / 已开 issue #…」，页面上只留还要人定的。
7. **一览在前，逐条在后。** 页首一张一览表：编号、一句话、推荐处置、落在 `DESIGN.md` 的哪一节（不进的写「不进」）。人可以只回「按推荐，第 3 条改成…」。

## 2 候选卡

一条候选一张卡，次序固定：

| 块 | 写什么 |
|---|---|
| 标题 | 一句话规则（候选原文，写入 reference §13 的形态），右侧标推荐处置 |
| 图 | 这条规则说的那块界面，每个相关状态一张（进行中 / 完成 / 失败、桌面 / 手机）；图说一句话说明这张图里该看哪里 |
| 设计是什么样 | 用看得见的话描述图里的做法；有人当时的原话就引一句 |
| 规则原文 | 拟写进 `DESIGN.md` 的原文，**用 `DESIGN.md` 的语言**；写明进哪一章哪一条、是改写还是追加。改写时旧文划掉、新文跟在后面；下面附一句中文意思 |
| 为什么在这一层 | 过写入 reference §7 分层表的那一句理由：为什么是产品设计系统（跨页、只属于本产品、能写成无日期无页面名的规则），或为什么不是 |
| 你的选择 | 从下面的闭集里挑适用的两到四个，推荐的排第一 |

候选卡的选择（对应提议表 `候选` 一节的处置）：

- **采纳**：按卡上的原文写进去（`改写已有规则` / `追加新规则`）。
- **改措辞**：人直接回改后的句子，以人的为准。
- **留在档案边上**：只当这个页面或组件自己的决定，留在档案对象的「决定」里（`留在原处`）。
- **不进 `DESIGN.md`**：驳回（附一句理由），或分去别处——起草通用原则 issue、起草缺陷 issue，卡上放 issue 草稿全文。
- 已被已有规则覆盖的（`已覆盖不加`）也出卡，规则原文那一块换成「已有：」加那条已有规则的原文，人确认确实覆盖了。

## 3 维护卡

`DESIGN.md 条目` 一节的每一处修改一张卡（对账、清理、改写都算），次序固定：

| 块 | 写什么 |
|---|---|
| 标题 | 在哪（章 · 条）+ 一句话说改什么，右侧标推荐处置 |
| 改了什么 | 改前 → 改后，原文并排：`旧：「…」` → `新：「…」`；删除写 `→ 删`，移出写 `→ 删（移到 <去处>）`。合并为一条时，每一处旧文都列出来 |
| 依据 | **点名**这处要改是因为哪条标准，一条以上就逐条列。能引的只有三种：写入 reference（`design-md.md`）的具体一节或一条（「§3 规则 2 一条规则只写一处」「§8 带日期的先例」「§12 法和代码对不上」「§4 整改优先于追加」）；官方 `@google/design.md` 规范的某一条；官方 lint 输出里的规则名（`orphaned-tokens`、`contrast-ratio` 等，取自这次 lint 的实际输出，不凭记忆写）。说不出依据的修改不出卡——那是品味，不是维护 |
| 图 | 这处规则管的界面：法和代码对不上时放代码现状的实测截图；只是写法问题（去日期、合并重复、hex 改引用）而界面不变时可以不放，写一句「界面不变」 |
| 你的选择 | 每个选项写后果；`交人裁决` 的每个选项各带一份新文 |

维护卡的选择一般是：**按新文改**（推荐时排第一）、**改措辞**、**不改**；`法和代码对不上` 换成 **改法**（只改 `DESIGN.md`，线上不变）和 **代码错**（规则不动，起草目标仓库的 issue，线上会变），后果分别写清。

纯减法的行可以按依据分组成一张卡（比如「§8 带日期的先例：以下 6 处 → 删」），组内每一处仍列出旧文，人可以整组批，也可以点出其中一处不批。

## 4 样例

一条候选：

> **离开确认用鼓励语气，「放弃」按钮不用红色**　推荐：改写已有规则
>
> 图：结算中途点关闭弹出的离开确认弹窗（档案状态 `pages/checkout--leave-confirm`），点开看原图。
>
> 设计是什么样：「放弃这笔订单」是中性描边、深色字的次按钮，重心在「继续结算」。
>
> 规则原文（Colors · 反馈色 · Destructive，改写）：
> 旧：`Destructive / Success: error and pass states, carried on a status dot or icon beside a label.`
> 新：旧文后加 `Destructive marks something that went wrong, never a choice the user makes: a leave or discard button stays a neutral outline button, and its consequence lives in its label.`
> 意思：红色只表示出错，不用在用户自己选的操作上。
>
> 为什么在这一层：结算和编辑地址两处的离开弹窗都这样做，跨页、只属于本产品。文案语气属于写作，不进。
>
> 你的选择：**采纳**（推荐）· 改措辞 · 留在档案边上（只当离开弹窗自己的决定）· 不进 `DESIGN.md`

一处维护修改：

> **Components · 选中状态配方：去掉例外里的日期，范围补上优惠券卡**　推荐：改写为全局规则
>
> 改了什么：
> 旧：`Open/expanded accordion item (named exception, decided 2026-07-16) adds a soft glow…`
> 新：`The one glow: the item the user is looking at right now (the open order row, or the selected coupon card) adds a soft glow outside the selected ring; only one item has it at a time.`
>
> 依据：写入 reference §3 规则 5「只写当前状态，不写演进」、§8「带日期的先例」——旧文带着日期；§12「法和代码对不上」——代码里被选中的优惠券卡也用了这层光，规则只写了手风琴。
>
> 图：展开的订单行、被选中的优惠券卡，两张实测截图。
>
> 你的选择：**按新文改**（推荐；只改 `DESIGN.md`，线上不变）· 只去日期、范围不扩（优惠券卡的光算代码错，起草 issue，线上会变）· 改措辞

## 5 和提议表的关系

审核页的每张卡对应提议表里的一行，卡上的编号就是人回话时用的编号。人在会话里按卡回「采纳 / 改措辞：… / 不进」，回完后把提议表对应行改成人定的处置，再走执行段。提议表那一行的「证据」格要能撑起这张卡：校验脚本查 `候选` 行有图（或「无图：原因」）、写进 `DESIGN.md` 的候选有「并进：」和旧新并排，`DESIGN.md 条目` 行有旧新并排和「依据：」（见 `proposal-table.md` §2.6）。
