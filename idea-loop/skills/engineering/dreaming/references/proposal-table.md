# 提议表：形状，和批了之后怎么执行

`dreaming` 一次运行分两段，中间停在人身上。**提议表是提议段唯一的输出**，也是执行段唯一的输入：人没批的行，执行段不碰。这份文件写表长什么样（校验脚本守的就是这些），和批过之后每类行怎么执行。

> 下文 `proposal-table-check` 指 `node "${CLAUDE_PLUGIN_ROOT}/scripts/proposal-table-check.mjs"`。写完表、给人看之前必须先过它：退出码 0 才交出去，2 就按它逐条点名的问题改。

## 1 放哪、谁看

- 表写在 dreaming 自己 worktree 根的 `.tmp/dreaming/<YYYY-MM-DD>/proposal.md`（不进仓库）。`dreaming` 的 worktree 是从 `origin/main` 新切的，不是任何一个进行中需求的工作区。
- **有行**：量大（一屏摆不下）就发 Artifact，会话里按节摆给人；`候选` 和 `DESIGN.md 条目` 有行时，另做一页审核页，每行一张卡片（图、改前 → 改后、依据、带后果的选项），格式见 `review-page.md`；定时那次没人在场，发一条推送通知（一句话：几类、共几行）加一页可看的 Artifact。
- **空表**：只发一句推送「本周无事」，不发 Artifact——定时跑最怕变成没人看的噪音。
- 人在会话里逐行回「批 / 不批 / 改成…」。不批的行不执行；「改成…」按人的话改那一行再执行。

## 2 一张表的形状

一个 `#` 标题（写日期），下面按行类型分 `##` 节，**节名就是行类型**，闭集。每节一个表，列固定为：

| 对象 | 发现 | 证据 | 建议处置 | 选项 |
|---|---|---|---|---|

- 一行一个对象（一份文档、一个档案状态、一条候选、`DESIGN.md` 的一处）。五列都不许空。
- 「建议处置」从该行类型自己的闭集里取，后面可以跟一个括号写补充（`订正（路径改名）`）。闭集外的处置一律不许写；真遇到闭集没有的，是这份文件缺一条，先补闭集和单测，不在表里自造。
- 「选项」写人的几种回法（至少「批 / 不批 / 改成…」；两种解释分不清时把两种都写上）。
- 一节没有行就写一行 `无`，不删节、不留空表头：节在，才说明这一部分跑过了。没跑的部分整节不写。
- 节内可以有表格以外的说明行，最常见的是全站初扫末尾的 `未扫：…`；说明行不算「行」，不让表变成非空。

| 节（行类型） | 一行是什么 | 建议处置的闭集 |
|---|---|---|
| `文档` | 知识库对账里一份有话要说的文档 | 写 ADR 删 spec · 写 ADR 未采纳删 spec · 报警 · 订正 · 标注被取代 · 删漏网工单 · 标 parked · 去审核 · 去设计 · 问人 · 迁移布局 · 删除 |
| `档案对象` | 设计档案里源码一侧查出问题的一个对象 | 改代码路径 · 删对象 · 补扫页面 · 标进入方式过期 |
| `档案状态` | 实时重新驱动后，一个有话要说的状态 | 替换档案 · 改进入方式 · 补进不去说明 |
| `初扫页面` | 全站初扫建出来的一整页（人按页面批） | 新增页面 |
| `候选` | 一条待蒸馏的设计法候选 | 改写已有规则 · 追加新规则 · 已覆盖不加 · 留在原处 · 起草通用原则 issue · 起草缺陷 issue · 驳回 |
| `DESIGN.md 条目` | `DESIGN.md` 里对账出问题的一处 | 改法 · 移出 · 删除 · 改写为全局规则 · 合并为一条 · 新建 DESIGN.md · 处理 lint 警告 · 交人裁决 |
| `缺陷` | 一条要开到目标仓库的 issue 草稿 | 开 issue · 已有 #N（N 是已开着的那条的编号） |

「一致」的状态不进表：没有话要说，就没有行。

### 2.1 「发现」的开头是判定

- `档案状态`：以 `档案过期：` / `进入方式过期：` / `进不去：` 开头，判定和处置要对得上（档案过期→替换档案，进入方式过期→改进入方式，进不去→补进不去说明）。
- `缺陷`：以 `产品坏了：` 或 `法对代码错：` 开头。分不清是档案过期还是产品坏了，按产品坏了报，并在冒号后写出两种解释。

### 2.2 档案行的两张图

`档案状态` 里除了「进不去」，和 `缺陷` 里的「产品坏了」，**证据格放两张图并排**，次序固定：先是 `prod/` 里档案原本的样子，再是 `tmp/` 里这次新拍的。校验脚本查：至少两张，第一张路径在 `prod/` 下、第二张在 `tmp/` 下。「进不去」没有可拍的，证据写缺什么、试过什么。

### 2.3 产品坏了不改档案

**「产品坏了」的行不许带「替换档案」**（校验脚本点名拒绝，在哪一节都一样）：把坏掉的样子写进档案，就是把一次回归冻成真值。它单列在 `缺陷` 一节，处置只有「开 issue」或「已有 #N」。

### 2.4 初扫行指向 tmp/

`初扫页面` 的证据指向 `tmp/` 下这次建出来的页面草稿。dreaming 从不直接写 `prod/`。

### 2.5 两种行的证据要有指定的答案

- `档案对象` 的 `删对象`：证据里写「引用：」，列出还引用它的节点与边；没有就写「引用：无」。删一个图里还在用的组件会让图断掉，沉默不算答案。
- `档案状态` 的「进不去：」：证据里写「缺…」「试过…」——缺什么前置条件、试过哪些路线。这是档案对「进不去」的规则要的两样东西。

### 2.6 `DESIGN.md` 两节的证据要撑得起审核卡

人是对着审核页（`review-page.md`）的卡片拍板的，卡片的内容来自这一格，所以：

- `候选`：证据里有图（这条规则说的那块界面，取自设计档案或实现）；实在没有界面写「无图：原因」。处置是 `改写已有规则` 或 `追加新规则` 的，还要写「并进：」（进哪一章哪一条）和旧文新文并排（`旧：「…」→ 新：「…」`，追加写 `旧：无`）。
- `DESIGN.md 条目`：证据里写「依据：」并点名那条标准——写入 reference 的 `§N`（具体到哪条规则或哪一行）、官方 design.md 规范，或 lint 规则名；还要有旧文（`旧：「…」`）和改后的样子（`→ 新：「…」`，删掉写 `→ 删`）。`新建 DESIGN.md` 没有旧文；`交人裁决` 的新文写在「选项」里，每个选项一份。

档案那几类行怎么产生、怎么批，见 `archive-reconcile.md` 与 `initial-scan.md`。

## 3 样例

## 4 批了之后：执行段

**只执行批了的行**，在提议段同一个 worktree 里做（它从 `origin/main` 切出，PR 也从它开）。顺序：

1. 先处理会删掉东西的行，再处理会改写的行，最后 link sweep、刷各层 `index.md`（`docs/spec/index.md` 用 `spec-status.mjs index`）。
2. 每类行怎么执行：

| 行类型 | 怎么执行 |
|---|---|
| `文档` | 照 SKILL.md 的「四条边」：写 ADR 先、`git rm` 整个 spec 目录后；写 ADR、删 spec 时顺带把设计档案里「决定」的来源链接 `[[<spec-slug>]]` 改指新 ADR（编号不复用、原地改写）；删完跑 link sweep |
| `候选` / `DESIGN.md 条目` | 写 `DESIGN.md` 照写入 reference（`../../../../references/design-md.md`）§9 的流程，只改批过的几处，写完 lint 与 diff；处理完的候选从档案对象里删掉（见 `candidate-distillation.md`） |
| `缺陷` | `gh issue create` 到目标仓库，标题和正文用表里起草的；不打任何 `status:*` label（那归 `issue-dispatch`）；写「已有 #N」的行不开 |
| `候选` 的「起草通用原则 issue」 | 同样人批了才开，开到 harold-skills 仓库，命令照写入 reference §11 |
| `档案对象` / `档案状态` / `初扫页面` | 产物都在 `docs/design/tmp/dreaming-<日期>/delta/`：**先删掉没批的对象，再跑档案的归档脚本整目录并进 `prod/`**（它负责覆盖、删除、重算 `usedBy` 与索引、检查 LFS、清目录；dreaming 不直接写 `prod/`、不另写搬运）。步骤见 `archive-reconcile.md` §5 与 `initial-scan.md` §4 |
| `缺陷`（产品坏了） | 照上一行 `缺陷`：只开 issue，档案不动；它的 `evidence/` 图随 tmp 目录一起丢 |

**档案对象文件的任何改动都走 `delta/` 加归档脚本**，包括上面「处理完的候选从档案对象里删掉」：把改过的对象全文放进 `delta/`，随同一次归档并进 `prod/`，不直接改 `prod/`。

3. **只提交只改知识库的文件**：`docs/`、`DESIGN.md`、`GLOSSARY.md`（`docs/design/prod/` 里归档脚本写的页面、状态、组件与素材在 `docs/` 之内）。归档后 `docs/design/tmp/dreaming-<日期>/` 若还在（这次没有要归档的档案行），整个删掉，免得合并前钩子拦下这个 PR。开一个 PR（`gh pr create`，标题写「dreaming：<日期> 知识库对账」，正文按节列执行了哪些行、哪些没批留着）。开出去的 issue 编号也写进去。
4. 执行段的结果摆给人：动了什么、留了什么、为什么留（SKILL.md 流程第 7 步）。
