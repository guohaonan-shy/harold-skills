# `DESIGN.md` 对账：dreaming 特有的部分

候选蒸馏是把候选往 `DESIGN.md` 里收；对账方向相反：**拿 `DESIGN.md` 现有的内容去量代码，再按写入标准体检**。判据、对账表、写入流程全在写入 reference（`design-md.md`，下称「写入 reference」）的 §12（对账）和 §9（一次写入）；新建在 §10。这份文件只写 dreaming 特有的：每周跑、只出提议、怎么落进提议表。

> 读之前先读写入 reference 的 §3、§6、§7、§8、§12。对账表的每一行怎么判，只按 §12，不在这里复述。

## 1 先找文件

照写入 reference §9 第 0 步：`git ls-files | grep -i 'DESIGN.md$'`。一份就地对；多份（多个 app）就问人这次对哪一份——定时那次没人可问，就每一份各出一组行，对象列写清路径。

**一份都没有**：只有在**定期对账时发现项目没有 `DESIGN.md`** 才新建（第一份通常由 `uiux-imagine` 开工时写，这里只兜底）。先判来源（写入 reference §10）：

- 项目有线上 UI → 提议段照 §10.1 从代码量，量出的三桶（一致 / 不一致 / 偶然）分开写进「证据」，`DESIGN.md 条目` 一行，处置 `新建 DESIGN.md`，起草的整份文件放进 Artifact 或证据格里指向的文件。
- 没有 UI 或 UI 还是占位 → **不写**（§10.2），也不进表；在会话汇报里提一句「项目没有 `DESIGN.md`，也没有可量的 UI」。

## 2 提议段：量，不写

对账只读：读 `DESIGN.md`、读代码、在 `DESIGN.md` 上跑官方 lint（`npx -y @google/design.md@latest lint <路径>`，只报告，不改文件）。把 §12 的发现落进 `DESIGN.md 条目` 一节，每处一行，行与处置的对应是：

| §12 的发现 | 提议表里 | 处置 |
|---|---|---|
| 法和代码对不上 | 一行写法与代码各是什么；法错了还是代码错了由人判，所以不替人选 | `交人裁决`；「选项」写 A 改法 / B 代码错。选 B 时在 `缺陷` 一节起草一行（`法对代码错：…`，处置 `开 issue`），**人批了才开** |
| 不该在文件里的内容（§8 表里的各行） | 点名是哪一行、属于 §8 的哪一类 | 页面决定 `移出`（留在档案）；历史叙事、划掉的条目 `删除`；缺陷 → `缺陷` 一节起草 issue |
| 先例 / 判例 / 带日期的条目 | 点名那一条的日期或判例结构 | 被多处遵循的 `改写为全局规则`（证据格写出无日期的新文，并入哪一章）；其余 `移出` 或 `删除` |
| 被取代的内容 | 点名取代它的是哪一条 | `删除` |
| 同一规则的两种写法 | 点名两处位置 | `合并为一条` |
| 官方 lint 的 warning | 原文 warning | `处理 lint 警告`（改 token / 补 `omitted` 说明 / 交人裁决三选一写在「选项」里） |

- **证据格放旧文与新文并排**（`旧：「…」→ 新：「…」`，删除写 `→ 删`）。定时那次没人在场，人是对着表批的，并排的文字必须在表里。
- **证据格写「依据：」，点名这处要改是因为哪条标准**：写入 reference 的具体一节或一条（「§3 规则 2」「§8 带日期的先例」「§12 法和代码对不上」），官方 design.md 规范的某一条，或 lint 输出里的规则名（如 `orphaned-tokens`、`contrast-ratio`，取自这次 lint 的实际输出）。说不出依据的修改不提——那是品味，不是维护。
- **交给人时出维护卡**：每处修改一张卡——改了什么（改前 → 改后）、依据、这处规则管的界面截图（法和代码对不上时必须有，取自实现的实测截图）、带后果的选项。格式见 `review-page.md` §3。
- 「法对代码错」「产品坏了」两类缺陷的去处只有一个：**目标仓库的 GitHub issue**。dreaming 起草标题和正文（哪条规则、现在是什么样、本该是什么样、一段引文），表里一行，人批了才 `gh issue create`；不打 `status:*` label。同一个问题已经有开着的 issue 就写「已有 #N」，不重复起草。
- **健康信号**（§12 末段）：这份文件变短的次数应该和变长一样多。一次对账提议全是加、没有减，多半是把盘点当成了法；回头再过一遍。

## 3 执行段

人批了的行，照写入 reference §9 落笔：备份 → 起草 → **人确认措辞** → 只改批过的 → lint 与 diff。`dreaming` 在这里没有额外权力：定时那次永远不写 `DESIGN.md`；人在会话里批过、又确认了措辞，才写。人拒绝写文件，就把内容以文字交回。落笔后的 `DESIGN.md` 随执行段那个只改知识库的 PR 提交。

## 4 手动只跑这一部分

`/dreaming` 手动调用可以只跑对账：不跑知识库对账，也不跑候选蒸馏，只出 `DESIGN.md 条目` 和（起草缺陷时）`缺陷` 两节。
