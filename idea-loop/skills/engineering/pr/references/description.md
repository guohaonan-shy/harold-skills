# PR 描述的格式

读者是要决定这次合不合并的人：清楚方向，不清楚实现细节。只写下面五节（SEO 的 PR 多一节），不超出这个模板。不写开场白，文字短，像一个人对另一个人说话；叫法用 `GLOSSARY.md` 里的，没收的第一次出现时说清它是什么。

写之前先用 Skill 工具调 `idea-loop:evidence`：问题、概要、证据三节里用什么视图，照它挑能讲清要点的最小一种，图贴着它支撑的那句短文字。

```markdown
## 问题

<一两句：现在是什么样、为什么要改>

<一个视图：问题真的发生过、有多常见，带出处和数字>

## 概要

<一句短文字> 
<一个视图：这次改了什么。按最容易看懂的顺序讲，要点在两处才加第二个>

## 证据

- **之前**：<做什么操作（同一组输入），在基准分支上得到什么：问题出现了>
  **之后**：<同一个操作，在本分支上得到什么：问题没了>

<测试写成伪代码、用术语表的叫法；全量测试只写结果>

没验成：<哪个行为>，<为什么>，<谁补、什么时候补>

## 合并风险

**门**：<双向 / 单向>。<单向的写清退不回的是哪部分>
**影响面**：<一个词>。<可选：合并后可能的连带后果>
- <要特别注意的：迁移、兼容约束、刻意没做的>

## 要你做的事

- [ ] <合并前只有你能验的>
- [ ] <合并后要你做的>

说「合并」即可。

## 上线自查的网址

<站点上线网址> 目标词：<这个页面要排的词>
```

- **问题**：证明问题是真的，不讲方案。视图取自真实发生过的事（哪个页面、哪些样本、哪段时间、多少次），不取理论上可能的情况。
- **概要**：画解决方案。这一节可以写路径、命令名、函数名；其余四节不写代码层的叫法，写页面、流程、行为和后果。
- **证据**：只证明改动生效了。之前和之后是一次复现：同一个操作在基准分支和本分支各做一遍，之前看到问题、之后问题没了（例：开 3 个会话，之前有 3 份出题工具进程，之后只有 1 份）。不拿线上的统计数（那是问题节的）跟合并后的数比。之前和之后并排；review 跑了几轮、每条检查逐列都不放（review 的记录合并时整份贴进 PR 评论）。「没验成」一行，没有就不写。
- **合并风险**：门和影响面必写；「要特别注意的」没有就不写，最多 3 条。顺带开的 issue 不放这里。
- **已经定了的事不进描述**：你在 review 里批的事，合并时随 review loop 的归档评论贴在 PR 上（每轮一条，带你的批示原话）；Claude 照规则或夜里按推荐定的事不写。
- **要你做的事**：只放只有人能做的两类复选框；都没有，这一节就只有「说『合并』即可」。还没批的决定题、术语表缺的词不放（前者在会话里定完，后者在 review 汇报的折叠区）。
- **上线自查的网址**：只有 `type:seo/*` 的 issue 写；合并上线后按它逐个核对，没有这一节的 SEO PR 不自动合并。
