# PR 描述的四节

```markdown
## 一句话

<谁现在能做什么 / 修好了什么>。

## 改了什么

### <页面或流程：一句话说它现在怎么走>

<之前 → 之后：前端放截图对照、动图，或截图拼成的流程（带标注和注释）；后端放时序图，之前和之后并排>

**后端流程**：<这个页面背后的流程变了什么，一两句；没变就写「没变」>

**怎么验证的**
- <验证了什么行为>：<方式>，<结论>
- <没验成的行为>：没验成，<为什么>；<谁补、什么时候补>

### <下一个页面或流程>
……

## 要你做的事

**要你审的**
- [ ] <看什么>（在会话里看过、回一句就行）

**要你决定的**
- [ ] <要定什么，一句>（在会话里回答）

**上线前要注意的**
- [ ] <事>——<为什么要人来做>

## 参考

<details><summary>改动地图、spec 与工单、执行记录、合并后的清理</summary>

**改动地图**（按模块，一行一个）
- <模块>：<改了什么，一句>

**spec 与工单**：[<spec 标题>](<链接>)；工单 <NN · 标题>、……

**过程记录**：停下 <K> 次、review <N> 轮，合并时整份贴在这个 PR 的评论里

| 工单 | 提交 | 验收 | 延后 → 接手方 | 存量回归 |
|---|---|---|---|---|
| 01 · <标题> | <短 SHA 链接> | 6/6 | — | 绿 |

**顺手发现的存量问题**（不是这次引入的）：<一句话>（<在哪>）

**合并后 Claude 做的清理**：删工单、删素材分支、清 worktree 里这个 PR 的临时目录<、这个 PR 特有的几项>

</details>
```

- **一句话**写结果，不写过程。
- **改了什么按点分块，每块自成一体。** 碰了页面的，一个页面一块，写这个页面从进入到离开端到端变了什么，再写它背后的后端流程变了什么；没碰页面的，一个后端流程一块。读完一块，人就知道这一点改成了什么样、凭什么说它是对的。
  - **之前 → 之后**在转 open 前**专门拍**，不复用人验素材（那些是为验收拍的，角度不一定是对照）。同一组操作在基准分支和本分支上各走一遍，取同样的组件、同样的宽度。**碰了页面的块，「之前」从设计档案 `prod/` 取**：用档案的「单个状态」查询拿进入方式（入口地址、前置条件、沿途每一步，`design-archive-query.mjs … state <状态名>`），在基准分支上照它走进去拍，不凭记忆摸路；`prod/` 里存着的主视口截图用来核对拍对了页面，对照图本身仍在同样的宽度下重拍。档案里还没有这个页面（首次初扫之前），照旧在基准分支上手动走。前端用截图、动图或带标注的截图流程，后端用时序图；具体哪种按「最快能让人看懂」选（原则同 `review-round.md` 的「证据：选最快能让人看懂的那种」）。文件名以 `pr-` 开头，用 `evidence.mjs publish` 上传。用户感觉不到的改动，写一句「用户看不到变化」再加一句换来了什么。
  - **怎么验证的**一个验证点一条：验了用户能感到的哪个行为、用什么方式（单元、组件、浏览器端到端、测量比对、真实前后端、手动）、结论。没验成的照样列，写原因和谁补，不藏、不当成通过。不写风险，不写执行方实现时自己定的细节：给足验证，细节交给执行方。
- **要你做的事**只有三类：要你审的（还没看过的人验素材）、要你决定的（会话里还没批示的事）、上线前要你注意的（生产配置、手动迁移、真实服务的冒烟）。Claude 自己能做的不列。做完的勾上，不删。
- **参考**整节折叠，只给想追溯的人看；提交号这类查证用的东西只放这里。
