# PR 描述的节：审核报告

PR 描述就是**审核报告**，读者设定为**没跟过这件事的人**：不记得 spec，没读过会话，也没看过各轮 review 汇报。他从上往下读，读完应该能自己决定合不合并：问题是什么、怎么修的、凭什么说修对了、顺带开了什么、要他做什么。每段都用页面、流程、行为和后果说话；代码指称只放折叠的「参考」。

```markdown
## 一句话

<谁现在能做什么 / 修好了什么>。

## 问题

<没跟过的人要看得懂：用户或开发者实际碰到的现象，复现出来的样子，规模数字（几次、几个、占多少）。不写根因的代码位置>

## 怎么修

<这次做成什么样。照规则定下的做法各写一条：做了什么、依据是什么（规则原文 / 人在哪次定的原话 / 产品里已有的哪处做法）。人可以对其中任何一条说「推翻」>

**切法**（切成几张工单、先后关系）
- <NN · 标题>：<被谁挡着，或「可立即开工」>。<端到端行为：做完用户看到什么>
- <NN · 标题>：……

### <页面或流程：一句话说它现在怎么走>

<之前 → 之后：前端放截图对照、动图，或截图拼成的流程（带标注和注释）；后端放时序图，之前和之后并排。用户看不到变化的改动，写一句「用户看不到变化」再加一句换来了什么>

**后端流程**：<这个页面背后的流程变了什么，一两句；没变就写「没变」>

### <下一个页面或流程>
……

## 怎么验证

- <验证了什么行为>：<方式>，<结论>
- <没验成的行为>：没验成，<为什么>；<谁补、什么时候补>
- 要你看：<看什么>（<工单号>）

  ![..](<素材 URL>)
- review：<跑了几轮、结论一句；中途修了什么，已按规则处理的几条>

## 顺带开的 issue

- [<标题>](<链接>)：<是什么、在哪、为什么这次不修>

（这次没有就写「无」）

## 要你做的事

**要你审的**
- [ ] <看什么>（在会话里看过、回一句就行）

**要你决定的**
- [ ] <要定什么，一句>（在会话里回答）

**上线前要注意的**
- [ ] <事>——<为什么要人来做>

**合并**：说「合并」即可，合并前的收尾都已经做完。

## 参考

<details><summary>改动地图、spec 与工单、执行记录、合并后的清理</summary>

**改动地图**（按模块，一行一个）
- <模块>：<改了什么，一句>

**spec 与工单**：[<spec 标题>](<链接>)；工单 <NN · 标题>、……

**过程记录**：停下 <K> 次、review <N> 轮，合并时整份贴在这个 PR 的评论里

| 工单 | 提交 | 验收 | 延后 → 接手方 | 存量回归 |
|---|---|---|---|---|
| 01 · <标题> | <短 SHA 链接> | 6/6 | — | 绿 |

**合并后 Claude 做的清理**：照例的几项（素材分支和这个 PR 的临时目录；工单在合并前已经删了）<，加上这个 PR 特有的：……>

</details>
```

- **一句话**写结果，不写过程。
- **问题**给没跟过的人看：复现出来的现象 + 规模数字，spec 的「问题陈述」是素材，不是照抄。读完他应该明白为什么要做这件事。
- **怎么修**按点分块，每块自成一体：
  - **照规则定的做法**每条带依据，写成人能核对、能推翻的样子（依据的写法见 `idea-loop:decision-rules`）。
  - **切法**列每张工单的标题、被谁挡着、做完的端到端行为；只有一张工单也写。
  - 碰了页面的，一个页面一块，写这个页面从进入到离开端到端变了什么，再写它背后的后端流程变了什么；没碰页面的，一个后端流程一块。读完一块，人就知道这一点改成了什么样。
  - **之前 → 之后**在转 open 前**专门拍**，不复用人验素材（那些是为验收拍的，角度不一定是对照）。同一组操作在基准分支和本分支上各走一遍，取同样的组件、同样的宽度。**碰了页面的块，「之前」从设计档案 `prod/` 取**：用档案的「单个状态」查询拿进入方式（入口地址、前置条件、沿途每一步，`node "${CLAUDE_PLUGIN_ROOT}/scripts/design-archive-query.mjs" <worktree> state <状态名>`），在基准分支上照它走进去拍，不凭记忆摸路；`prod/` 里存着的主视口截图用来核对拍对了页面，对照图本身仍在同样的宽度下重拍。档案里还没有这个页面（首次初扫之前），照旧在基准分支上手动走。形态照 `idea-loop:evidence` 的交付证据「选哪种形态」选。文件名以 `pr-` 开头，用 `node "${CLAUDE_PLUGIN_ROOT}/scripts/evidence.mjs" publish` 上传。
- **怎么验证**一个验证点一条：验了用户能感到的哪个行为、用什么方式（单元、组件、浏览器端到端、测量比对、真实前后端、手动）、结论。没验成的照样列，写原因和谁补，不藏、不当成通过。review 的结论也收在这里（几轮、中途修了什么）。不写风险，不写执行方实现时自己定的细节：给足验证，细节交给执行方。
- **顺带开的 issue**是实现或 review 中发现、不是这次引入、这次不修而开的 issue，一条一行，带链接；没有写「无」。
- **要你做的事**只有三类：要你审的（还没看过的人验素材）、要你决定的（会话里还没批示的事）、上线前要你注意的（生产配置、手动迁移、真实服务的冒烟），末尾一行告诉人说「合并」即可。Claude 自己能做的不列。做完的勾上，不删。
- **参考**整节折叠，只给想追溯的人看；提交号这类查证用的东西只放这里。
