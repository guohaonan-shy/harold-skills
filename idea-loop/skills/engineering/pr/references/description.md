# PR 描述的格式

读者是没跟过这件事的人，从上往下读，读完能自己决定合不合并。每节给读者什么、谁写，见 `../SKILL.md` 的节表；这里是每节的格式。

```markdown
## 一句话

<谁现在能做什么 / 修好了什么>。

## 问题

<用户或开发者实际碰到的现象，复现出来的样子，多常见。不写根因的代码位置>

## 怎么修

<照规则定下的做法各写一条：做了什么、依据是什么（规则原文 / 人在哪次定的原话 / 产品里已有的哪处做法）。人可以对任何一条说「推翻」>

### <页面或流程：一句话说它现在怎么走>

<之前 → 之后：前端放截图对照、动图，或截图拼成的流程；后端放时序图，之前和之后并排。用户看不到变化的，写一句「用户看不到变化」加一句换来了什么>

**后端流程**：<这个页面背后的流程变了什么，一两句；没变就写「没变」>

## 怎么验证

- <验证了什么行为>：<方式>，<结论>
- <没验成的行为>：没验成，<为什么>；<谁补、什么时候补>
- review：<跑了几轮、结论一句；中途修了什么，已按规则处理的几条>

## 能否回滚

**能不能撤回**：<能 / 不能 / 部分能>。<怎么撤：撤销合并就够，还是还要回退迁移、关开关、通知谁>

**影响面**：<出错时谁会受到影响、范围多大>

**上线前要注意的**（没有就不写）
- [ ] <事>——<为什么要人来做>

**顺带开的 issue**（没有就不写）
- [<标题>](<链接>)：<是什么、在哪、为什么这次不修>

## 要你做的事

**要你审的**
- [ ] <看什么>（在会话里看过、回一句就行）

  ![..](<素材 URL>)

**要你决定的**
- [ ] <要定什么，一句>（在会话里回答）

**合并**：说「合并」即可，合并前的收尾都已经做完。

## 参考

<details><summary>改动地图、spec 与工单、执行记录、合并后的清理</summary>

**改动地图**（按模块，一行一个）
- <模块>：<改了什么，一句>

**spec 与工单**：[<spec 标题>](<链接>)
- <NN · 标题>：<被谁挡着，或「可立即开工」>。<端到端行为>

**过程记录**：Review 汇报 <K> 份、review <N> 轮，合并时整份贴在这个 PR 的评论里

| 工单 | 提交 | 验收 | 延后 → 接手方 | 存量回归 |
|---|---|---|---|---|
| 01 · <标题> | <短 SHA 链接> | 6/6 | — | 绿 |

**合并后 Claude 做的清理**：照例的几项（素材分支和这个 PR 的临时目录；工单在合并前已经删了）<，加上这个 PR 特有的：……>

</details>
```

- **问题**：spec 的「问题陈述」是素材，不是照抄。
- **怎么修**按点分块，每块自成一体。碰了页面的，一个页面一块，写它从进入到离开端到端变了什么，再写背后的后端流程；没碰页面的，一个后端流程一块。
- **之前 → 之后**在转 open 前**专门拍**，不复用人验素材。同一组操作在基准分支和本分支上各走一遍，同样的组件、同样的宽度。碰了页面的块，「之前」从设计档案取：用「单个状态」查询拿进入方式（`node "${CLAUDE_PLUGIN_ROOT}/scripts/design-archive-query.mjs" <worktree> state <状态名>`），在基准分支上照它走进去拍；档案里还没有这个页面，在基准分支上手动走。形态照 `idea-loop:evidence` 的交付证据「选哪种形态」选，文件名以 `pr-` 开头，用 `node "${CLAUDE_PLUGIN_ROOT}/scripts/evidence.mjs" publish` 上传。
- **怎么验证**一个验证点一条，没验成的照样列、不当成通过。不写风险，也不写执行方自己定的细节。
- **能否回滚**覆盖整个 PR，对着这次合并的改动判：有没有数据迁移、线上发布、不可逆的写操作。没有就直说「撤销合并即可，没有迁移、没有对外发布」。
- **要你做的事**只有人验素材的复选框（素材只放这里，不在「怎么验证」里重复）和会话里还没批示的事；Claude 自己能做的不列。做完的勾上，不删。
- **参考**整节折叠；提交号这类查证用的东西只放这里。
