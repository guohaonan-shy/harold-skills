# review 汇报

`pr-review` 每跑一轮，写一份汇报放这一轮的全部结论，**PR 描述不动**。照规则能处理的条目编排者在贴汇报之前就处理掉，汇报里单列出来让人看一眼；剩下的人在会话里批示，编排者按批示修，修完回一条汇总。下一轮在满足条件时由编排者自己起，否则由人触发（`skills/engineering/pr-review/SKILL.md` §5）。

**这份汇报写给拍板的人看。** 他要的是：问题是什么、跟 main 有什么不同、用户会感受到什么区别、要他定什么。范围说明、审法、spec 原文、提交号、代码路径堆在前面，他看完描述和图还是不知道问题是什么。所以开头只有一句结论，每条固定几段，其余的收进最后的折叠区。

## 汇报正文

```markdown
## Review 第 N 轮

**结论**：<有没有把已有功能改坏>。Spec <K> 条、Standards <M> 条，其中 <X> 条已按规则处理，<Y> 条要你拍板<，都是要你拍板的事，不是 bug>。机械检查<全绿 / 有 X 处没过>。

---

### 已按规则处理（不同意的，说「推翻某条」）

- **C1** · <标题>：<做了什么，一句>。依据：<依据是什么，一句：哪条规则 / 你在哪次定过的原话 / 产品里已有的哪处做法>。<提交或 issue 链接>
- **S2** · <标题>：……

---

### Spec：代码有没有按 spec 做

#### S1 · <后果：用户能感到的那句话>

<问题：一两句，是什么、跟 main 哪里不一样>

**对用户的影响**：<谁、在什么情况下、多常见会碰到；碰不到就写「用户感受不到」>

<证据：界面上看得到的问题，用取自实现的截图——之前 / 之后、带标注的截图流程或动图，表格只作补充；界面上看不到的，用时序图、一张小表或一行例子；非行为问题没有这一块>

**要你决定**：<一句前提：和 spec 或工单的哪条规定对不上，那条规定是干什么用的>。<选项 A>，还是 <选项 B>？建议 <A>：<一句理由>。

---

### Standards：代码有没有守仓库写下来的规则

#### C1 · <违反了什么>

- **规则**：<规则原文>（<哪份文档，用文档的名字说>）
- **现状**：<代码现在怎么做，用话说>
- **影响**：<现在会怎样；现在没事就说以后在什么情况下出事>
- **建议**：<一个改法>

---

### 术语表缺的词（不阻塞）

| 概念 | 推荐叫法 | 代码里现在的名字 |
|---|---|---|

<details><summary>本轮审了什么、没审什么、丢弃的候选，以及给修复方的位置</summary>

**审的版本**：<短 SHA>，基准 <基准分支>
**核对过、没有问题的**：<一两行>
**没覆盖到的**：<哪些没看，由谁补>
**机械检查**：<每条命令一行：命令 | 结果（只算这次改动过的行）>
**丢弃 K 条**：<每条一行：是什么，为什么丢（没复现 / 规则原文找不到 / 不在 diff 里 / 人上一轮说过不修）>
**规则有歧义、没当违反**：<每处一句>
**给修复方的位置**：<S1 → 文件:行号、提交号；C1 → 文件:行号，以及违反规则的那几行代码>

</details>

---
逐条回复就行，比如「S1 接受，C1 修，C2 开 issue」；「已按规则处理」里不同意的，说「推翻某条」；有疑问直接问。<第 2 轮及以后加一句：已跑满两轮，要再跑或合并请直接说。>
```

## 每条怎么写

- **「已按规则处理」放在最前，在 Spec 与 Standards 之前，每条一句。** 说三样：做了什么（用话说）、依据是什么、提交或 issue 链接。依据只会是三种：仓库写下来的规则（说文档的名字，不贴路径）、你在这份 spec 或这个 PR 里做过的决定（引原话）、产品里已有的统一做法（说在哪一处）。做了什么的类别：修了、同步改了说明文字、接受并补记进了 spec 或工单、恢复了被删的东西、开了 issue。**第 1 轮还带上 `implement` 期间为执行方顺手发现的存量问题开的 issue**（那几条不是审查者的条目，没有 S / C 编号，标题写存量问题是什么，依据写它跟这次改动无关）。这一节只写做完的事；没有就不写这一节。要你拍板的条目不进这里，也不在下面重复。
- **标题就是后果。** 用用户能感到的话说（「连续失败几次的学生会提前用完当天的练习次数」），不用代码视角的说法（「重试路径扣了配额」）。不是 bug、只是和 spec 对不上的，标题就说是什么（「修了一个 spec 说这次不修的 bug」）。
- **对用户的影响要具体**：谁、在什么情况下、多常见。用户感受不到就直说，这种通常是要你拍板的事，不是 bug。
- **说行为和后果，不说代码。** 正文（开头结论、问题、影响、证据、要你决定）不写变量名、函数名、「文件:行号」、提交号、spec 或工单的章节编号。要指 spec 的某条规定，就把那条规定用话说出来。代码位置只放折叠区最后的「给修复方的位置」，审查者交回编排者的报告里也有。`review-check.mjs` 会机械地查这一条（`review-standards.md` §4）。
- **「要你决定」的前提要说清那条规定是干什么用的。** 例：「工单把报告取音频的总时长上限定为 5 秒，用来让报告最多等 5 秒就出现。」规则覆盖了一部分的，直接写覆盖了谁、漏了谁，选项就是要不要补。
- **至少两个选项，并给出建议。** 不是 bug 的，选项通常是「接受，把它补进 spec 或工单」与「拆出去」。
- **Standards 的「规则」引原文**，来源说文档的名字（「后端的 AGENTS.md」）。违反规则的那几行代码放进折叠区，不放正文。

## 证据：选最快能让人看懂的那种

先分**界面上看不看得到**：

- **看得到**（页面、按钮、提示、播放、录音状态的变化）：**必须有取自实现的截图**。单点差别用之前 / 之后截图，多步流程用截图拼的流程（`../../evidence/SKILL.md`），动起来的用动图。拍板的人要看见学生看见的东西，一张表格或一段文字时间线只会让他猜，所以表格、时序图、例子只能放在截图后面作补充。确实拍不到的（比如只有真机能复现），写一句为什么。
- **看不到**（纯后端、埋点、数据）：按下表选最快能看懂的那种。一句话就说清了的，不配图。

| 人需要看见的 | 最快的形式 |
|---|---|
| 界面上哪里不一样 | 之前 / 之后两张截图并排，差别处画红圈 |
| 走到第几步分叉、出错 | 截图拼的流程（`../../evidence/SKILL.md`），带标注，出错那一步画红圈 |
| 动起来哪里不对 | 动图（`../../evidence/SKILL.md`） |
| 谁先谁后、等了多久（多为后端） | 时序图（excalidrawer `sequence`），main 和本分支的结局并排；两种实现规则不一致的，同一张图里用虚线框标出不一致的那一段 |
| 规则覆盖了谁、漏了谁 | 一张小表：场景 × 有没有覆盖 |
| 数值或计算不对 | 一行具体例子：输入 → main 的结果 → 本分支的结果 |

非行为问题（多了 / 少了一个文件、路径和 spec 写的不一致）没有证据块，diff 本身就是证据。图在汇报里写本地路径，在会话里紧跟着它那一条的文字、单独用发送文件的工具发给人；合并归档时才上传到素材分支、换成点开能看原图的链接（`review-loop.md` 的「合并：归档进 PR，删掉本地文件」）。

## 规则

- **行为问题必须复现，并带上复现证据**：界面上看得到的用截图，看不到的用图、表或例子。复现不了的，放进「丢弃的候选」，只记一行。
- **Standards 的问题必须引用规则原文，而且违反的代码必须在这次的 diff 里。** 对不上的同样丢弃。机械检查（lint、typecheck、仓库声明的检查命令）的结果并入 Standards，只计这次改动过的行；挂在改动行上的诊断才成为 `C` 条目。
- 编号 `S1` / `C1` 只在这一轮内有效，方便人批示时引用。
- **缺词**：这次 PR 引入或改名、但目标仓库 `GLOSSARY.md` 没收的领域概念，用表格写概念、推荐叫法、代码里现在的名字（这一列本来就是代码里的名字，不受上面「不说代码」的限制）。不是问题，不阻塞，loop 不写术语表（新词只在 `grill` 里加，见 `../../glossary/SKILL.md`）。没有就不写这一节。
- 两轴分开写，**不合并、不跨轴排序**：一处代码可以守规矩却做错了事，也可以做对了事却破了规矩，分开报才不会互相掩盖。
