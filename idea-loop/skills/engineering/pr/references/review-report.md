# Review 汇报的格式

在对话里给人看的汇报只有这一种：实现卡住要人定时发一份（`idea-loop:implement`），review 每跑完一轮发一份（`idea-loop:pr-reviewer`）。每节给读者什么、谁写，见 `../SKILL.md` 的节表；这里是每节的格式。照规则的条目在贴汇报之前已经处理掉，单列出来让人能推翻；剩下的等人批示。

```markdown
## 来自实现中 · 第 N 次 | 来自 review · 第 K 轮

**结论**：<有没有把已有功能改坏>。<来自实现中：落地 K 张；来自 review：Spec K 条、Standards M 条>，其中 <X> 条已按规则处理，<Y> 件要你决定。机械检查<全绿 / 有 X 处没过>。

### 已按规则处理（不同意的，说「推翻某条」）

- **<编号> · <标题>**：<做了什么，一句>。依据：<一句：哪条规则 / 你在哪次定过的原话 / 产品里已有的哪处做法>。<提交或 issue 链接，或〔链接〕待补>

### 要你决定

#### <编号> · <标题：用户能感到的后果，或卡在哪>

- **现状**：<是什么、跟 main 或 spec 哪里不一样，带出处。Standards 的把规则原文写在这里（哪份文档）>
- **对用户的影响**：<谁、在什么情况下、多常见；碰不到就写「用户感受不到」>
- **证据**：<图；没有图的写表或一行例子>
- **选项**：
  - **A**：<做法>——代价：<…>；能否回滚：<…>
  - **B**：<做法>——代价：<…>；能否回滚：<…>
- **推荐**：<A 或 B>：<一句理由>

### 能否回滚

**能不能撤回**：<这次落地的东西错了能不能撤；怎么撤>　**影响面**：<谁会受到影响、范围多大>

### 要你看的

- [ ] <看什么>

  ![..](<素材>)

<details><summary>审的版本、核对过的、没覆盖到的、术语表缺的词、给修复方的位置</summary>

**审的版本**：<短 SHA>，基准 <基准分支>
**核对过、没有问题的**：<一两行>
**没覆盖到的**：<哪些没看，由谁补>
**机械检查**：<每条命令一行：命令 | 结果（只算这次改动过的行）>
**丢弃 K 条**：<每条一行：是什么，为什么丢（没复现 / 规则原文找不到 / 不在 diff 里 / 人上一轮说过不修）>
**规则有歧义、没当违反**：<每处一句>
**术语表缺的词**（不阻塞；这次引入或改名、目标仓库 `GLOSSARY.md` 没收的概念）：<概念 | 推荐叫法 | 代码里现在的名字>
**给修复方的位置**：<S1 → 文件:行号、提交号；C1 → 文件:行号，以及违反规则的那几行代码>

</details>

---
逐条回复就行，比如「S1 接受，C1 修，C2 开 issue」；「已按规则处理」里不同意的，说「推翻某条」；有疑问直接问。<第 2 轮及以后加一句：已跑满两轮，要再跑或合并请直接说。>
```

- **没有的节不写**：没有按规则处理的事、没有要人定的事、没有人验素材，就不写那一节。
- **已按规则处理**放在要你决定之前，每条一句。依据只会是三种：仓库写下来的规则（说文档的名字，不贴路径）、你在这份 spec 或这个 PR 里做过的决定（引原话）、产品里已有的统一做法（说在哪一处）。判断规则在 `idea-loop:decision-rules`。动作：修了、同步改了说明文字、接受并补记进 spec 或工单、恢复了被删的东西、开了 issue。来自实现中的还放三类：按产品已有做法定的界面细节（依据写它沿用的那一处）、本次修的存量问题（依据写它怎么污染了这张工单）、顺手发现的无关存量问题（已开 issue，依据写它跟这张工单无关）。第 1 轮 review 把实现期间开的存量 issue 也列进来。边缘情形（只在兜底路径里出现、不丢东西）不放这里，是决定题。
- **要你决定**每条同一格式，Spec、Standards、实现卡住的题都一样；选项至少两个，每个带代价和能否回滚，推荐按 `idea-loop:decision-rules` 给。两轴的条目分开排，S 在前、C 在后，不跨轴排序。标题就是后果，用用户能感到的话说，不用代码视角的说法。证据形态照 `idea-loop:evidence` 的交付证据「选哪种形态」选：界面上看得到的必须有取自实现的截图；非行为问题没有证据块。
- **只写会改变用户看到什么的事。** 工单没说、只影响怎么写代码的细节，执行方自己定。会改变用户看到什么的事，要么工单已定，要么按产品已有做法定并列进「已按规则处理」，要么是决定题。
- **说行为和后果，不说代码。** 正文不写变量名、函数名、「文件:行号」、提交号、章节编号；代码位置只放折叠区的「给修复方的位置」。`review-check.mjs` 会机械地查这一条。
- **能否回滚**每份都写；没有数据迁移、没有对外发布的，一句话讲清「撤销合并即可」。
- **来自实现中**：只写本次停下之前新落地的工单。「要你看的」只放要人判断的人验素材（逐格比对已经全绿的不放）；没有要人定的事时，素材照列、不勾、写「留到 PR 描述的「要你做的事」看」，也省掉结尾那句「逐条回复」。
- 编号 `S1` / `C1` / 工单号只在这一次汇报内有效，方便批示时引用。图在汇报里写本地路径，合并归档时才上传（[`review-loop.md`](review-loop.md)）。
