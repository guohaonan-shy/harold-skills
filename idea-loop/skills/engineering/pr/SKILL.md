一份 spec 的所有工单共享**一条集成分支、一个 PR**。PR 描述和过程中的汇报只写给一个读者：要判断这次交付能不能合并的那个人。他每次看都要能马上知道两件事：**要我决定什么，要我看什么。** 这份文件规定 PR 描述怎么写、汇报怎么写、汇报放在哪。


## PR 描述是总览，汇报在会话里

| 阶段 | PR 状态 | 要人决定、要人看的东西 | 谁写 |
|---|---|---|---|
| **实现中**：工单没全部落地，或还有等决定的事 | draft | 每次停下一份**停下汇报**（见「停下汇报」） | `implement` 的编排者 |
| **review**：全部落地、没有等决定的事 | open | 每一轮一份 **review 汇报**（见「review 汇报」） | `pr-review` 的审查者 |

汇报在会话里给人看、人在会话里回复，同样的内容记进本地的 review loop 文件，PR 合并时按停下和轮次归档成 PR 上的评论（见下面「review loop」）。

PR 描述本身是常驻的总览。读它的人**打开时没有上下文**：活是委托出去的，spec 他可能只记得个大概。所以描述从「这是什么」往下读到「要我做什么」，越往下越可以不读；只为查证的东西折叠在最后。**描述里不放 review**：review 在会话里进行，合并时整份记录贴在 PR 的评论里，描述里再放一份摘要只会重复。

| 节 | 标题 | 写什么 | 写入方 |
|---|---|---|---|
| `summary` | 一句话 | 这个 PR 让谁能做什么，或者修好了什么。只读这一句也知道它是干嘛的 | `implement`：开 draft 时写，转 open 前按落地结果重写 |
| `changes` | 改了什么 | 按点分块：碰页面的，每个页面端到端变了什么，加上后端流程变了什么；没碰页面的，只写后端流程的变化。**每一块里**放之前 → 之后的对照、怎么验证的（一个验证点一条：验了什么行为、用什么方式、结论） | `implement` 转 open 前写，对照图专门拍 |
| `your-todo` | 要你做的事 | 要你审的、要你决定的、上线前要你注意的 | `implement` 转 open 前写；`pr-review` 的编排者在人的批示带出新事项时更新 |
| `reference` | 参考 | 折叠：按模块的改动地图、spec 和工单链接、执行记录、合并后 Claude 做的清理 | `implement`：开 draft 时写，每次停下更新 |

**整个描述是给人读的。** 折叠的「参考」以外，不写代码行、变量名、函数名、文件路径、提交号、spec 或工单的章节编号，说页面、流程、行为和后果。`pr-body.mjs` 写入前会机械地查这一条，查到就拒写；图片和链接的地址不算。

每节的格式见「PR 描述的四节」。每节夹在隐藏标记之间，由 `scripts/pr-body.mjs` 按固定顺序写入，**标题由脚本加**，内容文件里不用写：

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-body.mjs" set <owner/repo> <PR 号> <节名> <内容文件>
```

每个写入方只重写自己负责的节。标记以外的文字（人手写的说明、署名行）会被保留，放在所有节的下方。**不要直接 `gh pr edit --body` 整体覆盖**，那会把别人的节一起冲掉。PR 描述本身由 gh 当前登录的账号写：它是 PR 的一部分，不是一条发言。

## review loop

汇报在会话里给人看、人在会话里回复，每次处理完只回一条汇总；同样的内容逐字记进 `.tmp/review-loop/<PR 号>.md`，合并时归档成 PR 评论。PR 上不开 thread，不在 PR 上和人往来。文件长什么样、怎么在会话里给人看、人回复之后怎么办、合并时怎么归档：[`references/review-loop.md`](references/review-loop.md)。

## 不写什么

- **不复述 spec 和工单。** 「为什么」在 spec 的「问题」，每刀做了什么在工单里，`reference` 里给链接就够。
- **不写给 agent 看的东西。** 验收契约就是分支上的工单文件，review 的 agent 直接去读，不在 PR 里另抄一份。复现命令、检查日志、修复前后对比这些过程材料，不出现在 PR 上。
- **描述里不放 review。** 结论、条目、图都在各轮的汇报里。
- **汇报的正文不出现代码层面的指称**（见「review 汇报」里的「每条怎么写」）：变量名、函数名、「文件:行号」、提交号、spec 或工单的章节编号（「§4.7」）都不写。读汇报的是拍板的人，这些他看了也不知道是什么意思。代码位置只给修复方，放进汇报最后的折叠区。

## 停下汇报

`implement` 每次停下（没有能做的工单了）写一份：[`references/stop-report.md`](references/stop-report.md)。

## review 汇报

`pr-review` 每跑一轮写一份：[`references/review-round.md`](references/review-round.md)。

## PR 描述的四节

一句话、改了什么、要你做的事、参考，每节的格式：[`references/description.md`](references/description.md)。
