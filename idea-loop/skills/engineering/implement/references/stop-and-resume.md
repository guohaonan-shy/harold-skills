# 没活了就停下

没有在跑的、可派的也空了才停（只剩等决定的及其下游，或全部落地）。

1. 把分支推上去（PR 在接分支后就开了，号取 `prs.md`）。
   - **有 `大用例待跑`**（落地的交回里 `verified` 写了）：在会话里先告诉人几个用例、每个最长约 3×45 分钟、每个约 1.05–3.50 美元（起 agent 的更高）乘以个数，不等人点头，用 Bash 的 `run_in_background: true` 起 `node ~/.idea-loop/bin/retro-replay.mjs --cases <用例,用例> --run-large --pr <PR 号> --worktree <集成 worktree 绝对路径>`（不设 timeout），等它退出，不轮询；照 [references/replay-result.md](replay-result.md) 处理结果。
2. 写汇报（来自实现），写法照用户规则（home 固定文案的「其余你自己定」「替我定掉、交给我的」和「要我定的事写成一道题」），不读别的 skill 的汇报格式：handled 的每一条按「其余你自己定」的四类分，属于四类的进「已按规则处理」、每条写成「替我定掉、交给我的」那样一道过去时的题，其余只关于代码怎么写的写进「合并风险」之后的一节「只关于代码怎么写的」（开头一行注明「只记在这里，不贴进会话」，一条一行：什么事、做了什么、依据；这些事只在这一节出现，汇报的别的节和折叠区都不再提），新落地工单的人验素材进「要你看的」，pending 的每一条写成「要你决定」，落地的改动写「合并风险」。轮次取 `dyna pr loop next .tmp/review-loop/<PR 号>.md review impl`，条目标记写 `{"kind":"review","round":<轮次>,"from":"impl"}`，素材写本地路径；然后清空 handled。工单表和执行记录只留在这个文件里，不写进 PR 描述。
3. 推送。
4. **先看有没有要人拍板的事**：pending 不空（有等决定的事）。人验素材不算：它们照第 2 步列进「要你看的」（不勾），实现中途不停，最后收进 PR 描述的「要你做的事」，人在 PR 上一起看。
   - **有**：在会话里按条目贴汇报（不含「只关于代码怎么写的」一节，会话里至多说一句有几条、记在文件里，不点名），「已按规则处理」在最前，每项文字后紧跟它的素材；再发一条推送通知。停下等人，见下面「人回复后」。
   - **都没有**：不停，不等回复。第 2 步写进文件的条目就是留痕：已按规则处理照样列（人想推翻哪条，之后随时说，照「人回复后」的推翻处理），「要你看的」照常列（有人验素材的不勾，写明「留到 PR 描述的「要你做的事」看」；没有的不写这一节），条目末尾直接记一节「做了什么」（逐点：这次落地了什么、按规则处理了什么，带提交链接），不写「你的批示」。会话里只说一句落地了几张、已按规则处理几件，不发推送通知，然后往下走下面「全部落地」那一步。人验素材仍由人判，只是挪到 PR 描述里判；`dyna pr loop check` 对没有「要你决定」这一节的条目，记了「做了什么」就算处理完。

**人回复后**：人的回复逐字记进那个条目的「你的批示」，逐点处理，会话里只回**一条**汇总（带提交链接），同样记进「做了什么」：

- **决定**：决定里有设计变更（人接受了实现者做不下去时给的改法，或人自己改了主意）的，先走 SKILL.md 的「设计变更」（`references/design-change.md`），过了再写工单，`> 人的决定` 里指向新画布的版本。工单 `要建什么` 末尾加 `> 人的决定（<日期>）：<原文>`，验收格随之增删，提交 `docs(tickets): <NN> — 人的决定`，从 pending 删掉（先取下它的 agent id 和 worktree）。工单回到可派，按下面的「重派」；它落地后旧 worktree 和分支一并回收。
- **推翻**「已按规则处理」里按现有做法定的、或本次修的存量那条：当作一条人的决定。那条所属的工单，`要建什么` 末尾加 `> 人的决定（<日期>）：推翻「<那条做了什么>」：<原文>`，验收末尾追加 `- [ ] 人推翻（<日期>）：<人要的样子>`，提交 `docs(tickets): <NN> — 人的决定`；工单回到可派重派（同一 trailer，带上「人的决定已写进工单」）。
- **推翻**开了 issue 的那条：不回工单、不派执行方。在那个 issue 上留一条说明，按 `idea-loop:issues` 翻成 canceled；人要别的处理（比如这次就修），要修的按上一条写回所属工单。
- **人验对**（人中途主动看了，或在审核报告里看了）：在文件里勾上。**不对**：验收末尾追加 `- [ ] 人验反馈（<日期>）：<人的话>`，提交，工单回到可派重派（同一 trailer，素材同名覆盖）。
- **疑问**：直接答；要改方案的，说明要回 `idea-loop:grill`。
- **要求改写汇报**（「写成我看得懂的样子」）：改文件里那个条目的汇报部分，在会话里重贴，改了什么写进汇总。

**重派**（决定、设计变更、推翻写进工单并提交之后，工单要重新做时）：

- **先叫回原执行方。** 这张工单卡住时 pending 记了 agent id、它的 worktree 还在，就用 SendMessage 叫它回来，占一个执行方的位置。消息只给指针：「人的决定已写进工单 `<路径>`，提交 `<SHA>`」，加上要它先合进来的集成分支最新提交。它照常交回，核对、落地、回收照上面做。
- **叫不回就新起。** SendMessage 报错（id 找不到、会话重启过）或没记 id：照「派工」新起一个，带上半成品分支。
- **已经落地的工单照旧新起。** 人验反馈、review 里的修、推翻已落地的工单，那时执行方的 worktree 已经回收（「回收」的时机不改），不叫回，新起。

回到「派工」。下次停下追加新条目，不改旧的。

**全部落地、pending 清空、`dyna pr loop check` 没有未处理的条目、没有在跑或未处理的回放**（有就 PR 留在 draft，不进 review）：照 `idea-loop:pr` 的「PR 描述」给这个 PR 写齐描述（带 `type:seo/*` 的 issue 另写「上线自查的网址」一节；证据节取执行方交回的两边结果，缺的才补拍：另起一份基准分支的检出 `.tmp/implement/<spec-slug>/base`（`dyna worktree add base --detach --base <基准分支> --path .tmp/implement/<spec-slug>/base`），拍完用 `dyna worktree remove` 删），`dyna pr ready <owner/repo> <PR 号>`，然后 `dyna issues set <docs> in-review <号>`（Linear 上集成推），再**等 CI**，再用 Skill 工具调 `idea-loop:pr-review` 跑第一轮。提一句交付验收还有几项没勾。

**等 CI**：全量测试在这里跑一遍，同一个 head 之后不再跑。`dyna pr checks <owner/repo> <PR 号>` 等这个 head 的检查跑完，第一行是结论：

- **green**（退出 0）：起 pr-review。
- **red**（退出 1，列出失败的检查名字和链接）：读失败的测试日志，找到引入失败那行的提交，`dyna spec ticket-of <提交>` 读出工单；在那张工单的验收末尾追加 `- [ ] CI（<日期>）：<失败的测试验的行为>`，提交 `docs(tickets): <NN> — CI 失败`，照「重派」新起执行方（已落地的工单 worktree 已回收），落地、推送后回到「等 CI」。
- **失败跟这次无关**（基准分支最近一次 CI 上同一个检查也红）：开 issue（照「不影响本次改动的存量问题自动开 issue」），写进 Review 汇报，不回工单，起 pr-review（red 在第一个失败时就返回，没等其余检查）。
- **timeout**（退出 124，默认等 30 分钟，输出列着没跑完的检查）：不起 pr-review；把卡住的检查告诉人，人说再等就重跑 `dyna pr checks`。
- **PR 上没有检查**（结论 `none`，退出 0：命令开始 60 秒内一个检查都没有）：编排者在集成 worktree 本机跑一次 `<项目目录>/REVIEW.md`「验证命令」的全量命令，跑完用 `dyna pr full-suite record <head> <退出码> <日志文件>` 记下（`<head>` 是当前提交的完整提交号，红的也记），结果当 CI 结果用；红了同上。
