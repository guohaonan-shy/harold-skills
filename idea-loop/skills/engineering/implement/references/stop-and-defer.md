# 接着做、停下与延后

implementer 在两种时候读这份：开工时带着上次的半成品分支、或这张工单不是第一次做（读「接着做」）；做的过程中碰到行为没定、或某一格这张证明不了（读「停，还是延后」）。

## 接着做

- **上次卡住留下的半成品分支**：先对齐起点，再把它的改动拿回来：不提交、不带它的提交历史（坑：用 `git merge --squash <分支>`），接着做。
- **这张工单不是第一次做**：工单里有 `> 人的决定`，或验收标准末尾有新追加的未勾格。被 SendMessage 叫回来时不用再对齐起点，先把集成分支的最新提交合进来；只做没勾的那几格，已勾的格重跑当初的测试。

## 停，还是延后

依据照用户规则（`~/.claude/CLAUDE.md` 的「思考与决策」）：

| 情况 | 怎么办 |
|---|---|
| **行为没定**，产品里也没有现存做法（边界算不算 in scope；现状跟代码对不上；测量瓶颈是设计决策） | **停**，交回 `blocked` |
| 产品里**已有统一做法** | **沿用**，写进 `by_existing_practice`；实例找不到或不一致，按停 |
| **行为定了，这张证明不了**（要等后面那张的接口；要人看） | **延后**，写明接手方 |
| **存量问题** | 先照 review 标准（`${CLAUDE_PLUGIN_ROOT}/skills/engineering/pr-review/references/review-standards.md` 「依据：只认四种」一节）的范围题判，两个引导词：**本分支才撞上 / 挡不挡目标**。两类这次都修，标「存量本次修」，理由写清是哪一类、怎么撞上或怎么挡：① 本分支才撞上的（这次改动引入的，哪怕根源早就在代码里）：例如它写着的事实（数量、名字、路径、结构）正是这次改掉的，这次一改它就过期；只是说明文字、在工单没点名的文件里也算（例：这次给配置加了一节，别处说明文字里写死的节数跟着错）；② 挡住这张工单验收或 spec 目标的（工单验收也算目标）：例如污染了这张的输入或结论、让 CI 变红。其余不修，记进 `found`，由编排者单独开 issue |

### 延后怎么写

写进 `acceptance`，框不勾：

```markdown
- [ ] <判据> ⏭ 延后 → 07：<为什么这张证明不了>
- [ ] <判据> ⏭ 延后 → PR 交付验收：<要人判断的是什么>
```

接手方只有两种：后面某张还没落地、能证明这一格的工单（`acceptance` 里写清判据，编排者落地后在那张工单末尾追加继承格）；或 PR 交付验收（要人判断）。写不出接手方就按停。标「人看」的格和延后给 PR 交付验收的格，素材照 `ui-tickets.md` 的「要人判断的部分，录成素材」做。

### 停下时的半成品

半成品提交在你自己的分支上，不带 `Ticket:` trailer，message 写 `wip(<NN>): <停在哪>`，工作区干净；SHA 填进交回的 `blocked.wip`。
