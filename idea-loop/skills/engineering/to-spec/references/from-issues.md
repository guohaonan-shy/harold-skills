# 从 GitHub issue 起草 spec

输入不是一场 grill 对话，是一组 GitHub issue 号，通常由 `idea-loop:issue-explorer` 调。没有人在场，所以 grill 本来会做的两件事，复现和拆分，这里自己做；本来要跟人确认的，自己定好写进 spec，等人审 spec 时确认。

这份文件只写跟 `SKILL.md` 不同的地方，没写到的照它。issue 怎么读、label 是什么意思，见目标仓库根目录的 `ISSUE_TRACKER.md`。

## 输入

每个 issue 先读全文和评论（`gh issue view <号> --comments`）。已经有 `status:*` label 的已经在流程里了，跳过。哪几个放进同一份 spec，按下面「先拆分，再起草」判断，互不相关的各成一份。

## 先复现

每个 issue 先复现，再写进 spec：

| issue 的性质 | 复现手段 | spec 里写什么 |
|---|---|---|
| 逻辑、数据、API 行为 | 一个会红的测试，不提交：测试代码和输出放 `.tmp/to-spec/<spec-slug>/repro/`，`implement` 时由执行方正式写 | 白话写测了什么、看到什么、本该是什么，带一个具体例子 |
| 看得见的界面问题 | 一张截图，标注照 evidence 的「问题的复现证据」 | 截图本身 |
| 线上数据、日志、性能 | 一条查询或一段日志，写明查的是什么、什么时候查的 | 查的范围和时间，加结果；数字能列成小表就列 |

spec 里只放人读得懂的结论，不放机器的原始输出：测试的失败输出、堆栈、查询语句、整段日志都留在 repro 目录。换成一句话说清复现到的现象（「打开一次页面记了两条浏览事件：一条是 SDK 自动记的，一条是页面组件手动补的」），再接本该是什么（「应该只记一条」）。要指回原始材料的，小节末尾写一行「复现材料：`.tmp/to-spec/<spec-slug>/repro/<文件>`」。

方案、选项、范围依赖的现状也在起草时核清：代码现在怎么做、影响多大、同类入口有哪些、相邻在飞的 spec 与 issue。没人在场可问，漏核的会在审核时被人一条条追问（`idea-loop:decision-rules` 的「现状先查清」）。issue 是不是已经被做掉了，也靠这一步查出来。

复现推翻了 issue 原来的说法，在「根因」里写「修正：issue 原先认为 X，实测是 Y」。

复现不出、或已经被做掉的 issue 不进正文，列进 spec 末尾的「建议关闭」，每条带三样，缺一样人审核时就得自己去查：

- **现象**：issue 说的是什么，一句话，带 `#<号>`。
- **现状证据**：为什么现在不成立。复现不出的，写试了什么、卡在哪；已经做掉的，指出现在的规则或代码在哪。
- **怎么验证的**：什么时候、对着哪个基准分支、用什么手段核的。

证据图放这份 spec 自己目录下的 `assets/`（`docs/spec/<spec-slug>/assets/problem-<n>-<slug>.png`）：没有对话，就没有 raw 桶。

## 先拆分，再起草

一组 issue 不一定只成一份 spec：

- **要调整设计的单独成一份。** 它会走 `待设计`、`设计中`，不能拖着同组别的 issue 一起等设计。
- **功能级的单独成一份**，标题下第一行写「> 需要 grill：<为什么>」。功能级是修完多了一个原来没有的能力，或者 issue 里写着还没定的设计问题。审核会话看到这一行就先 grill 再审。
- **剩下的一份超过 5 个问题，按相关性拆**：同一个页面、同一条链路、同一个根因的放一起。

## 各节怎么写

| 节 | 从 issue 起草时 |
|---|---|
| raw transcript | 不写，没有对话 |
| 问题、根因 | 每个 issue 一个小节：issue 里原有的证据加本次复现的结果，写成人读得懂的结论 |
| 方案 | 逐条写 |
| User Stories | 不画场景树。每个问题一行「期望行为」，保留编号：pr-review 的 Spec 轴靠它逐条比对 |
| 实现决策 | 每条先自己定；依据不成立的才写成选项，带推荐，留给人审核时定。一条都没有要人定的，写「无选项」 |
| 测试决策 | seam 自己定，写进来，人审 spec 时确认 |
| 技术方案总览、Out of scope | 照 `SKILL.md` |
| 关联 | 逐个写 `#<号>` 加标题，相邻在飞的 spec 与 issue 也列上，没有写「无」 |
| 建议关闭 | 有才写，放在「关联」之后 |

## 落盘

- frontmatter `status: 草稿`。`related` 不挂 transcript，挂关联的 spec / ADR，没有就留空列表。
- 每个覆盖到的 issue 跑一次 `issues.mjs handoff`，进了「建议关闭」的也跑，它同样等着人在审核里处置。`handoff` 只写 spec frontmatter 的 `issues`；GitHub 上的 label 由调度方推送之后再同步，这一步不跑 `sync`。
- 不提交、不推送、不开会话：那是 `issue-dispatch` 的事。

收工时列出：起草了哪几份 spec（slug、各含哪几个 issue、有没有标「需要 grill」、碰不碰 UI），以及进了「建议关闭」的 issue。
