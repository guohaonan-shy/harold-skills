# 两轴 review：问什么、什么算问题、怎么验

`pr-review` 的审查者（`agents/pr-reviewer.md`）读这份文件。一轮 review 只回答两个问题：

- **Spec**：代码是否真的解决了 spec 要解决的问题、实现了工单的验收标准？
- **Standards**：代码是否遵守这个仓库**写下来的**规则？

两个问题各交给一个 Codex 进程，彼此看不到对方的上下文，最后**分开汇报**。一处代码可以守规矩却做错了事，也可以做对了事却破了规矩，合在一起排序就会让一边掩盖另一边。

> 曾经还有第三轴「Correctness」：在整个 diff 上开放式地找 bug。开放式的问题总能问出点什么，一轮 5 条里常有 3 条是测试自己不稳、或者走不到的分支里一句硬编码，人要花力气判断它们值不值得看。会让用户碰到的错误行为，本来就违背 spec 或工单写下的行为，归 Spec 轴；测试与代码的写法问题，项目写了规则的归 Standards 轴，没写规则的不报。

## 1 输入

| | Spec 进程 | Standards 进程 |
|---|---|---|
| diff | `git diff <merge-base>...HEAD`，加上提交列表 | 同左 |
| 契约 | spec 全文；这份 spec 的全部工单（验收标准、`人的决定`、`人验反馈`、`继承自` 都在里面） | 规则来源（§3） |
| 前几轮 | 人在之前几轮（review loop 文件里）批了「不修」的条目，不再重报，除非有新证据；人**推翻**过的条目，不再按同一依据标成「照规则」（§5） | 同左 |
| 额外 | — | 机械检查只留改动行后的结果（§3） |

**不推断需求。** 不从实现、分支名或过时的标题里猜 spec 想要什么。spec 和工单没写的行为，不是 Spec 问题；它可能是一个该问人的空白，那就作为一条「没写清」的 Spec 条目报出来，在建议里写明要人定什么。

### 每条候选标处置

两轴的每个候选都多一个「处置」，判断依据全在 `decision-rules.md`，这里不重写：

- **照规则**：能从那份文件推出怎么办的。带**依据**（`basis`：种类、出处、原文、给人读的一句话）和**动作**（`action`：修 / 同步改 / 接受并补记 / 恢复 / 开 issue），**不写「要你决定」**：没有选项、没有建议。编排者在贴汇报之前就按动作处理掉，汇报里单列「已按规则处理」。
- **要你决定**（没写处置就是它）：依据不成立、或本来就只能人定的，照旧写前提、选项和建议。

怎么落：

| 情形 | 处置 |
|---|---|
| Standards：有明文规则、没有歧义 | **一律「照规则 · 修」** |
| Standards：规则有歧义、两条规则冲突 | 不当违反，进汇报折叠区的「规则有歧义」 |
| spec、工单、说明文字跟已定的做法对不上 | 照规则 · 同步改（依据：人的决定原话，或写下来的规则） |
| spec 没说的界面细节，产品已有统一做法 | 照规则 · 修（依据：现存实例；指不出实例就是要你决定） |
| 执行方超范围删了东西：没有调用方、也没人读 | 照规则 · 接受并补记 |
| 执行方超范围删了东西：有人读的信息，或改了行为 | 照规则 · 恢复 |
| 只在兜底路径或罕见异常里出现、不丢东西的边缘情形 | **要你决定**，推荐接受（「代价相称」在 PR 流程里只定推荐，`decision-rules.md` §3） |
| 起名定稿、人验素材、分类体系、方案形状、对外发布、动生产数据 | 要你决定，不自动（`decision-rules.md` §4） |

**依据只认三种**：仓库写下来的规则原文、人在这份 spec 或这个 PR 里已经做过的决定（原话）、产品里已有的统一做法（指得出现存实例）。依据是规则原文的，原文要在规则文件里找得到，找不到会被丢弃（§4）。依据不成立就不要硬写成照规则，老老实实标「要你决定」。

## 2 Spec 轴

报三类，每条都**引用 spec 或工单的原文**：

1. **要求了，但没做或只做了一部分**
2. **做了，但做错了**：看起来实现了，行为却和原文对不上
3. **没要求，却做了**：超出这张工单范围的改动（scope creep）

### 每条都要核实，行为问题要复现并留下证据

Codex 给的是候选。审查者对每个候选**真的核实一遍**，并标明它是不是**行为问题**（`behavior`）：

- **行为问题**（用户能碰到的前后差别、多方调用、时序、数值）：**真的走一遍**，把复现结果做成**最快能让人看懂的证据**，并标明它在界面上看不看得到（`on_screen`）。**看得到的必须有取自实现的截图**，表格和时序图只作补充；确实拍不到的，在 `no_screenshot` 里写一句为什么。其余按人需要看见什么选（`pr-description.md` §5「证据」）：界面差别用之前 / 之后截图，走到哪一步出错用带标注的截图流程，动效用动图，后端的先后与等待多半用时序图（main 和本分支并排；两种实现规则不一致的，同一张图里用虚线框标出那一段），规则覆盖了谁漏了谁用一张小表，数值不对用一行例子。截图一律取自实现（`../../evidence/SKILL.md` §3）。图存进证据目录、文件名以 `r<轮次>-` 开头，写进 `figure`；表和例子直接写进 `example`。
- **非行为问题**（多了 / 少了一个文件、路径和 spec 写的不一致、做了没要求的清理）：用 diff 核实，**没有证据块**。

**行为问题复现不了的，丢弃**，只在「丢弃的候选」里记一行。证据目录是 `.tmp/pr-review/<PR 号>/evidence/`。

### 每条写成拍板的人读得懂的样子

汇报的格式见 `pr-description.md` §5。候选里就按那几块写，不留到发帖时再改：

| 字段 | 写什么 |
|---|---|
| `title` | 后果：用户能感到的那句话；不是 bug 的就说是什么 |
| `problem` | 问题：一两句，是什么、跟 main 哪里不一样 |
| `user_impact` | 对用户的影响：谁、在什么情况下、多常见；碰不到就写「用户感受不到」 |
| `on_screen` | 行为问题在界面上看不看得到；看得到的，`figure` 必须是取自实现的截图（之前 / 之后、截图流程、动图） |
| `figure` / `example` | 证据：图的文件名，或直接写进正文的表格 / 例子；非行为问题都不填 |
| `no_screenshot` | 界面上看得到却拍不到时，一句为什么（比如只有真机能复现）；其余不填 |
| `decide` | **要你决定**的才写：`context`（一句前提：和哪条规定对不上，那条规定是干什么用的）+ `options`（至少两个）+ `recommend`（建议和一句理由）。照规则的不写 |
| `disposition` / `basis` / `action` | 处置：`照规则` 或 `要你决定`（不写就是后者）。照规则的写 `basis`（`kind`：规则原文 / 人的决定 / 现有做法；`file` 与 `text`：出处与原文，脚本会核；`summary`：给人读的一句依据）和 `action`（修 / 同步改 / 接受并补记 / 恢复 / 开 issue） |
| `locations` | 给修复方的位置：文件:行号、提交号。**只有这个字段可以写代码** |

除 `locations` 外都**不写代码层面的指称**：变量名、函数名、文件路径、「文件:行号」、提交号、spec 或工单的章节编号。spec 定义了、实现只覆盖了一部分的，直接写覆盖了谁、漏了谁。

## 3 Standards 轴

### 规则来源：只认写下来的

读目标仓库的 `REVIEW.md`、根目录与适用子目录的 `AGENTS.md` / `CLAUDE.md`、它们链接到的约定文档（比如 `docs/reference/` 下的分层、文件划分、命名约定），以及 lint / typecheck / 格式化的配置。`@` 导入不会自动展开，被引用的文件要显式去读。**只用这个仓库自己的规则**，不带入别的项目的，也不带入通用的「坏味道」清单或命名偏好。

规则没写到的，就是没有规则可执行。规则有歧义的，作为问题报出，不当成违反。

### 机械检查

在 Standards 进程开跑之前，审查者自己把仓库声明的检查命令跑一遍（`REVIEW.md` 的 Verification paths 与 CI 里的那几条；没装的编译器不为此去装），每条输出都过一遍改动行过滤：

```
<命令> 2>&1 | node "${CLAUDE_PLUGIN_ROOT}/scripts/changed-lines.mjs" <merge-base>
```

工具要按「一行一条、带 `路径:行号`」的格式输出（比如 eslint 加 `-f unix`）。脚本只留挂在这次新增或改动行上的诊断，其余的只计数。**退出码和诊断原文由审查者交给 Codex**，Codex 只负责判断每条对应哪条规则、该不该成为 `C` 条目，不重新转述工具的结果。跑不了的检查（缺依赖、缺环境）照实写「未运行：<原因>」，不算通过。

### 每条的形状

- 违反了哪条规则：**规则原文 + 规则文件**（`rule`）
- 违反的代码：**diff 新增行里的那几行**，原样（`code`），只用于校验和折叠区，不进正文
- 现状（`now`）、影响（`impact`）、建议（`suggestion`）：各一两句，用话说，同样不写代码层面的指称；位置放 `locations`

规则只用在 diff 里的代码上。**改动行以外的存量问题不报，审查者也不去找它们**（跟这次无关的存量，由 `implement` 的编排者对执行方交回的顺手发现开 issue，不归审查者，`decision-rules.md` §1 第 2 条）。两种例外要报，处置一律是「照规则 · 修」：

- 它**污染了这个 PR 的输入或结论**：这次改动读到的数据因它而错，或这次的结论因它而站不住；
- 它**让 CI 变红**。

这两种写成 `existing: true`，再加一句 `pollutes`（它怎么影响这次，用话说，不写代码）；`code.snippet` 取现在的文件里的原样几行，不要求在 diff 里。**说不出它怎么影响这次，就是与这个 PR 无关的存量问题，照旧不报，也不为它开 issue。**

## 4 准入：机械校验

两个进程的候选合成一个 JSON，交给脚本校验：

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/review-check.mjs" candidates.json <merge-base> .tmp/pr-review/<PR 号>/evidence <轮次>
```

```json
{
  "spec": [{
    "id": "S1", "title": "…", "behavior": true, "on_screen": true,
    "quote": { "file": "docs/spec/<spec-slug>/tickets/03-….md", "text": "原文" },
    "figure": "r1-….png", "example": "（界面上看不到时可以只有它：一张小表或一行例子）",
    "problem": "…", "user_impact": "…",
    "decide": { "context": "…", "options": ["…", "…"], "recommend": "…" },
    "locations": ["src/…:42", "提交 2daa0bae"]
  },
  {
    "id": "S2", "title": "…", "behavior": false, "disposition": "照规则",
    "quote": { "file": "docs/spec/<spec-slug>/tickets/03-….md", "text": "原文" },
    "problem": "…", "user_impact": "用户感受不到",
    "basis": { "kind": "人的决定", "file": "docs/spec/<spec-slug>/<spec-slug>.md", "text": "人的原话", "summary": "人在 spec 里已经定过……" },
    "action": "同步改",
    "locations": ["docs/spec/….md:88"]
  }],
  "standards": [{
    "id": "C1", "title": "…", "disposition": "照规则", "action": "修",
    "rule": { "file": "docs/reference/….md", "text": "规则原文" },
    "code": { "path": "src/….ts", "snippet": "原样的几行" },
    "now": "…", "impact": "…", "suggestion": "…",
    "locations": ["src/….ts:17"]
  }]
}
```

第一条 Spec 是「要你决定」的老形状（没写 `disposition`），第二条是「照规则」，Standards 那条也是：Standards 的依据就是它自己的 `rule`，不用再写 `basis`。存量问题的例外（§3）在 Standards 条目上加 `"existing": true` 与 `"pollutes": "…"`。

先查**站不站得住**，没过的直接丢弃，带上脚本给的原因，进「丢弃的候选」：

- Spec：引用的原文在 spec 或工单里找得到；行为问题（`behavior: true`）有复现证据——配图（存在、以 `r<轮次>-` 开头）或写进正文的表 / 例子。非行为问题不要求证据。
- Standards：规则原文在规则文件里找得到；代码片段的每一行都是这次 diff 的新增行（`existing: true` 的则是现在文件里的行）。
- 照规则的：`basis` 的原文在它的出处里找得到（不论种类是规则原文、人的决定还是现有做法），找不到就丢弃。

除了空白字符会被归一，其他都不做模糊匹配。

再查**写得对不对**，没过的不丢弃，进 `rewrite`，审查者改写后重跑，直到它为空（脚本退出码 2 表示还有要改写的）：

- Spec 的标题、问题、对用户的影响都在，「要你决定」有前提、至少两个选项、有建议；`behavior` 标了；非行为问题没带配图；行为问题标了 `on_screen`，界面上看得到的有截图，或在 `no_screenshot` 里写了为什么没有。
- **照规则**的有依据（种类是三种之一、出处和原文都给了、有一句给人读的依据）和动作（修 / 同步改 / 接受并补记 / 恢复 / 开 issue 之一），**不带**「要你决定」；存量例外的动作是修、带 `pollutes`。处置只能是「照规则」或「要你决定」。
- Standards 的现状、影响、建议都在。
- 这些给人读的字段里没有代码层面的指称：反引号、「文件:行号」、路径、代码文件名、章节编号（§）、提交号、下划线命名、函数调用。

只有站得住、写得对的才进这一轮的汇报。

去重：同一个失败行为、同一种修法，两轴都报了，留在更贴切的那一轴，另一轴不重复写。

## 5 后面几轮

下一轮由编排者在条件成立时自己起，或由人触发（`skills/engineering/pr-review/SKILL.md` §5）。它的输入里有上一轮之后的修复提交，以及人在之前几轮的批示（review loop 文件）：

- 人批了「修」的、以及上一轮照规则修的：确认修复还在、行为对了，不再单独成条；没修好的照常报。
- 人批了「不修」或「开 issue」（旧说法「进 backlog」）的：不再报，除非这一轮有新证据，比如修复改到了它。
- 人**推翻**过的（review loop 里「你的批示」写着「推翻 C1」之类）：这条在上一轮是按某个依据标成「照规则」的，人不同意。**不再按同一依据把它标成照规则**；这一轮若仍有这个情形，处置写「要你决定」，在前提里说明「上一轮按××依据处理，被你推翻了」，推荐跟着人的意思走。人推翻的是依据本身的，同一依据下的同类条目也一样不再标照规则。
- 新的改动（修复提交）照常过两轴。不为凑数去翻已经看过、没改动的代码。

## 6 缺词

读目标仓库的 `GLOSSARY.md`（或 `GLOSSARY-MAP.md` 列出的每一份），标题和正文里的领域概念用它的标准叫法。这次 PR 引入或改名、术语表却没收的概念，列进这一轮汇报的「缺词」节：写概念和推荐叫法，不当问题、不阻塞、不写进术语表。新词只在 `grill` 里加（`../../glossary/SKILL.md`）。
