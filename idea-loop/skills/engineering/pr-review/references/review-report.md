# Review 汇报的格式

对话里给人看的汇报只有这一种：实现卡住要人定时发一份（`idea-loop:implement`），review 每跑完一轮发一份（`idea-loop:pr-review`）。PR 描述不动，这些汇报的结论等 review 全部过完才收进描述（[`deliver.md`](deliver.md)）。同样的内容逐字记进 review loop 文件（[`review-loop.md`](review-loop.md)），另有一节「只关于代码怎么写的」只记进文件、不在会话里贴。完成条件：模板里有的节，该写的都写了，没有的节不留空壳。

| 节 | 这一节给读者什么 | 谁写 |
|---|---|---|
| 开头一句 | 第几次、来自实现还是第 K 轮 review、有没有把已有功能改坏、几件已替他定、几件要他定 | 来自实现：实现编排者；来自 review：review 编排者 |
| 已按规则处理 | 已经替他定好、该他过问的四类事（分类见 home 固定文案「其余你自己定」），每条一道过去时的题：问题、选项、选了哪个、为什么，加链接；不同意可以说「推翻某条」 | 同上；实现取自 handled，review 取自标了照规则的条目 |
| 要你决定 | 真要他定的事，每条一道题，Spec、Standards、实现卡住的题都一样 | 同上；实现取自 pending |
| 合并风险 | 这次落地的东西错了，能不能撤、怎么撤、影响面 | 同上，对着落地的改动判 |
| 要你看的 | 要他判断的人验素材（流程、动效、样式）；review 来源的汇报通常没有这一节 | 来自实现的作者 |
| 折叠区 | 想核对的人查证：审的版本、核对过的、没覆盖到的、术语表缺的词、给修复方的位置 | 同上 |

```markdown
## 来自实现 · 第 N 次 | 来自 review · 第 K 轮

**结论**：<有没有把已有功能改坏>。<来自实现：落地 K 张；来自 review：Spec K 条、Standards M 条>，其中 <X> 条已按规则处理，<Y> 件要你决定。机械检查<全绿 / 有 X 处没过>。

### 已按规则处理（不同意的，说「推翻某条」）

- **<编号> · <标题>**
  - 问题：<当时卡在哪，带一个真实例子：哪个字段、怎么变了、哪个测试会怎么红>
  - 选项：A <…>；B <…>（至少两个，差在你能感到的地方）
  - 选了 <A / B>。为什么：<照规则的写规则原文（哪份文档），另一个选项就是不照它做；人的决定、产品里已有的哪处做法同理>。<提交或 issue 链接，或〔链接〕待补>

### 要你决定

#### <编号> · <标题：用户能感到的后果，或卡在哪>

<一道题，写法照 home 固定文案「要我定的事写成一道题」>

### 合并风险

**门**：<双向 / 单向>。<单向的写清退不回的是哪部分>　**影响面**：<谁会受到影响、范围多大>

### 要你看的

- [ ] <看什么>

  ![..](<素材>)

### 只关于代码怎么写的

> 只记在这里，不贴进会话。

- <什么事>：<做了什么>。依据：<一句>。<提交链接>

<details><summary>审的版本、核对过的、没覆盖到的、术语表缺的词、给修复方的位置</summary>

**审的版本**：<短 SHA>，基准 <基准分支>
**核对过、没有问题的**：<一两行>
**没覆盖到的**：<哪些没看，由谁补>
**机械检查**：<每条命令一行：命令 | 结果（只算这次改动过的行）>
**丢弃 K 条**：<每条一行：是什么，为什么丢（没复现 / 规则原文找不到 / 不在 diff 里 / 人上一轮说过不修）>
**规则有歧义、没当违反**：<每处一句>
**术语表缺的词**（不阻塞；这次引入或改名、`<项目目录>/GLOSSARY.md` 没收的概念）：<概念 | 推荐叫法 | 代码里现在的名字>
**给修复方的位置**：<S1 → 文件:行号、提交号；C1 → 文件:行号，以及违反规则的那几行代码>

</details>

---
逐条回复就行，比如「S1 接受，C1 修，C2 开 issue」；「已按规则处理」里不同意的，说「推翻某条」；有疑问直接问。
```

- **没有的节不写**：没有按规则处理的事、没有要人定的事、没有人验素材，就不写那一节。
- **已按规则处理**放在要你决定之前，只放该人过问的四类（改了范围、改了用户看得到的行为、改了 spec 的目标或方案的形状、本该问人而替人定的），分类和每条的写法照 home 固定文案「其余你自己定」和「替我定掉、交给我的」，分不清的放进来。「为什么」取 review 标准（`${CLAUDE_PLUGIN_ROOT}/skills/engineering/pr-review/references/review-standards.md`）「依据：只认四种」一节，写法：规则说文档的名字（不贴路径），人的决定引人说的话，产品做法说在哪一处，目标引 spec 里的那句原话并说达成了没有。来自实现的，按产品已有做法定的界面细节属于「改了用户看得到的行为」（写它沿用的那一处），本次修的存量问题和不影响本次改动、已开 issue 的存量问题属于「改了范围」（写它怎么影响、为什么不影响本次改动）。第 1 轮 review 把实现期间开的存量 issue 也原样列进来（取自 review loop 里各次停下的「已按规则处理」带 issue 链接的行）。
- **只关于代码怎么写的**（改测试写法、内部命名、同步改说明文字、工单没说的代码细节之类，执行方自己定的也在这里）不进「已按规则处理」，一条一行写进这一节；这些事只在这一节出现，汇报的别的节和折叠区都不再提；这一节只进 review loop 文件，不在会话里贴（会话里至多说一句有几条、记在文件里，不点名），没有就不写。会改变用户看到什么的事，要么工单已定，要么按产品已有做法定并列进「已按规则处理」，要么是要你决定的题。
- **要你决定**每条一道题，Spec、Standards、实现卡住的题同一种写法，照 home 固定文案「要我定的事写成一道题」：问题带最小的视图（视图照 `idea-loop:evidence` 的「视图菜单」选；界面上看得到的必须有取自实现的截图）、选项各带代价和能否撤回、推荐加一句理由。Standards 的题把规则原文写在问题里（哪份文档）。两轴的条目分开排，S 在前、C 在后，不跨轴排序。标题就是后果，用用户能感到的话说，不用代码视角的说法。
- **合并风险**每份都写；没有数据迁移、没有对外发布的，写「双向，撤销合并即可」。
- **来自实现**：只写本次停下之前新落地的工单。「要你看的」只放要人判断的人验素材（逐格比对已经全绿的不放）；没有要人定的事时，素材照列、不勾、写「留到 PR 描述的「要你做的事」看」，也省掉结尾那句「逐条回复」。
- 编号 `S1` / `C1` / 工单号只在这一次汇报内有效，方便批示时引用。图在汇报里写本地路径，合并归档时才上传（[`review-loop.md`](review-loop.md)）。

## 在会话里给人看

汇报在会话里给人看、人在会话里回复，PR 上不开 thread。完成条件：汇报已记进 review loop 文件，人读到了每一条和它的图。

1. 把汇报写进 review loop 文件（新条目）。
2. 在会话里贴**同样的内容（不含「只关于代码怎么写的」一节），按条目一段一段给**：先贴开头一句，然后每一条先贴这一条的文字，紧接着单独发这一条的图（一次发送只放这一条的图，caption 写条目编号和一句看什么），再贴下一条。文字和图交替发，人才不用在两堆之间来回对照。图用『发文件给人』能力发（`dyna runtime show 发文件给人`）：聊天界面加载不了私有仓库的图片链接。
3. 人可能不在电脑前：用『推送』能力（`dyna runtime show 推送`）发一条通知，一句话说停在哪、等他决定几件。

人在会话里的回复就是指示；怎么处理归调用方：来自实现的归 `idea-loop:implement`，来自 review 的归 `idea-loop:pr-review`。
