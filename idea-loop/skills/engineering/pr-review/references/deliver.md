# 交审核报告

`../SKILL.md` 的「一轮之后往哪走」判出「交审核报告」时走这份。目的：人说「合并」时，PR 上已经没有别的要做，CI 也已经绿了。`<loop>`（review loop 文件 `.tmp/review-loop/<PR 号>.md`）、设计产物的意思同 `../SKILL.md`。

## 1. 记下这一轮做了什么

最新一轮条目末尾记一节「做了什么」（没有修复就写「没有要修的，进审核报告」），`dyna pr loop check <loop>` 才不再列它。

## 2. 等 CI 绿

工单留在 home 里，代码 PR 合并成功后才删（`merge.md`），所以这里没有工单的提交要推。`dyna pr checks <owner/repo> <PR 号>` 等这个 PR 最新一次推送触发的检查：`green` 往下；`none`（这个 PR 上没有检查）不等，往下。`red` 或 `timeout`（卡住）不交报告：查原因，是这次改动引入的，按 `../SKILL.md` 的「回工单」处理；与这次无关的，开 issue，在报告里写明。spec 没有状态可翻：它覆盖的 issue 在全部 PR 合并后翻 done，见 `merge.md`。

## 3. 写审核报告

用 `dyna pr body set` 写进 PR 描述（用 Skill 工具调 `idea-loop:pr`，看它的「PR 描述」，节名、顺序、每节怎么写都照它；每节的视图照 `idea-loop:evidence` 的「视图菜单」挑）：`problem`（补上视图）、`outline`、`evidence`、`risk`、`your-todo` 各节，`live-check` 核一遍。读者是没跟过这件事的人，按节从上往下一份讲完：

- **问题、概要**取自 spec 的「问题陈述」和「方案」，工单（标题、端到端行为），review loop 文件里每份汇报的「已按规则处理」「做了什么」。人在 review 里定的事本身不写，它让方案多做的一块画进概要。
- **证据**取自执行方交回里的复现：问题的每一件，在基准分支和本分支各做一遍同一个操作，之前看到问题、之后问题没了。没复现的件写进「没验成」那一行，不拿线上的统计数跟合并后比；没有对应问题的改动写「行为没变」一行。review 跑了几轮、每条检查的结果不放（合并时随 review loop 的归档评论整份贴进 PR）。
- **合并风险**对着整个 PR 判：门（双向 / 单向，单向写清退不回的部分）、影响面、要特别注意的（迁移、兼容约束、刻意没做的，最多 3 条）；人在 review 里定的事带来的风险也写在这里。`idea-loop:implement` 和 review 期间开的 issue 不写（它们在 review loop 的归档评论里）。
- **要你做的事**收两类复选框：合并前只有人能验的（review loop 文件里「要你看的」中还没勾的项，一项一个：「看什么」+ 素材，素材照 `idea-loop:pr` 的交付证据做，用 `dyna pr evidence publish` 上传后贴进描述），合并后要人做的（例：上线前推迁移，写明为什么要人来做）；末尾一句「说『合并』即可」。人看了说对，勾上；人直接说合并，视为人验素材都看过、都对。

## 4. 在会话里给人看，停下

把同样的内容在会话里给人看（带 PR 链接，做法照 [`review-report.md`](review-report.md) 的「在会话里给人看」），用『推送』能力（`dyna runtime show 推送`）发一条通知，然后停下。人在这里读、追问、说合并；说合并之后走 `merge.md`。

## 5. 报告之后人提了要改的

人这时批示要修、说某项人验素材不对、要设计变更或说「再跑一轮」（人说合并之后，设计归档校验不过、人选了改实现或设计变更，也走这里，见 `merge.md` 的「合并前归档」）：照 `../SKILL.md` 的「处理条目」处理（人验素材不对的，在所属工单验收末尾追加 `- [ ] 人验反馈（<日期>）：<人说的话>`，照「回工单」处理）；全部处理完，从第 1 步重来（等 CI、更新报告）。
