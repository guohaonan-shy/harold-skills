**一次调用跑一轮。** 调用这个 skill 的会话是**编排者**：起审查者、处理照规则的条目、在会话里给人看汇报、处理人的批示、派修复、人说合并时合并。审查归 `idea-loop:pr-reviewer`（只读，结论不被它自己的修法影响），修复归 `idea-loop:implementer`，编排者自己不审代码、不改代码。一轮问什么、什么算问题写在 [`references/review-standards.md`](references/review-standards.md)，这里不复述。

开工先用 Skill 工具调 `idea-loop:pr`（review loop 文件、汇报与 PR 描述的写法）和 `idea-loop:decision-rules`（哪些条目不等人）。往来都在会话里：PR 上不开 thread，不以人的身份发言。

下文 `review-loop` 指 `node "${CLAUDE_PLUGIN_ROOT}/scripts/review-loop.mjs"`，review loop 文件是 `.tmp/review-loop/<PR 号>.md`。**设计产物**指集成 worktree 的 `docs/design/tmp/<spec-slug>/` 下除 `research/` 以外的东西（`research/` 是 `idea-loop:uiux-research` 落的调研页，看完就丢，合并前钩子也不算它）。

## 什么时候跑

- `idea-loop:implement` 全部落地、PR 刚转成 open：跑第 1 轮。
- 编排者自己起下一轮：只在「下一轮：什么时候自己起」的三个条件同时成立时。
- 人调 `/idea-loop:pr-review` 或在会话里说「再跑一轮」：随时可以，不受两轮上限约束，同样计入轮次编号。
- 人在会话里明确说合并：照 [`references/merge.md`](references/merge.md) 做（「合并」「合并前归档」「合并后的清理」）。合并只由人决定，编排者不批准 PR。

只有这几种。推送、`gh pr create`、某个 skill 跑完都不触发，也不装自动触发的 hook。

## 前提

- PR 是 **open**。还是 draft，说明工单没落地完或还有等决定的事，回 `idea-loop:implement`。
- **没有排队中的回放**：`~/.idea-loop/replay-queue/` 里没有这个 PR 的文件（`<owner>__<repo>-<PR 号>.json`）。有，就是改规则的回放还在等夜里跑，告诉人等结果，不起这一轮。结果出来后 `review-loop check` 若列出未处理的 `replay` 条目（有用例没过），先把它交给人，等批示处理完再起这一轮。
- 当前 worktree 是这个 PR 的集成分支，工作区干净（`git status --short --untracked-files=no` 为空），本地 HEAD 已推送、等于 PR 的 head。
- **找到 Codex companion**：`node "${CLAUDE_PLUGIN_ROOT}/scripts/codex-companion.mjs"` 打印它的路径。退出码 1 就在开跑前把它说的缺什么告诉人。

## 跑一轮

1. 轮次取 `review-loop next .tmp/review-loop/<PR 号>.md review`。这一轮的工作目录是 `.tmp/pr-review/<PR 号>/round-<N>/`。
2. **有设计产物才先 UI 审查**：用 Agent 工具起 `idea-loop:ui-reviewer`（每轮审查模式），只给指针：spec 名、集成 worktree 的绝对路径、分到的端口（挑一个没人在听的）、模式、图的前缀 `r<轮次>-ui-`、这一轮的工作目录。等它交回发现文件 `ui-findings.json` 的路径。它标了未完成（服务起不来、页面打不开）的，照实告诉人并记进汇报的「没覆盖到的」：**未完成不等于没问题**，但不阻塞代码审查。没有设计产物就跳过这一步。
3. 用 Agent 工具起 `idea-loop:pr-reviewer`，**只给指针**：worktree 路径、`<owner/repo>`、PR 号、基准分支、轮次、spec 路径 `docs/spec/<spec-slug>/<spec-slug>.md` 与同目录的 `tickets/`、review loop 文件路径、companion 路径，以及第 2 步的发现文件路径（有的话）。
4. 等它交回汇报，**不提前汇报**。
5. **先记文件**：把汇报作为新条目原样追加进 review loop 文件。
6. **处理照规则的条目**（见下一节），不等人。
7. **在会话里给人看**：汇报里「已按规则处理」每一行的 `〔链接〕` 占位补成提交或 issue 链接，一个都不剩，文件里的条目同步改成一字不差的同一份。第 1 轮还要把 `idea-loop:implement` 期间为顺手发现的存量问题开的 issue 补进这一节：从 review loop 文件里各次停下的「已按规则处理」找出带 issue 链接的几行，原样列进来。然后照 `idea-loop:pr` 的「review loop」按条目贴，「已按规则处理」在最前，每条文字后紧跟它的证据图；再发一条推送通知：第几轮、几条已按规则处理、几条要你决定。有未完成的轴或检查要明说。汇报里有缺词，念出来（概念 + 推荐叫法），问人要不要开一轮 `idea-loop:grill` 定下来。

## 照规则的条目：贴汇报之前就处理

审查者标了「照规则」的条目带依据和动作，依据已由脚本校验；编排者按动作处理，不等人。这之外的修复都等人批示。

| 动作 | 怎么处理 | 链接 |
|---|---|---|
| **修**、**恢复** | 走「人批示之后」里「修」那条路：找到归属工单、追加一格、提交、派执行方；不等它做完就继续下面的条目和贴汇报 | 追加那一格的提交；修复落地后，把它的提交补进「做了什么」和汇总 |
| **同步改** | spec、工单或说明文字跟已定的做法对不上，直接改（spec 里交代由来的历史段落保留，标明后来改了），`docs(spec): …` / `docs(tickets): …` 提交、推送 | 那个提交 |
| **接受并补记** | 代码不动，把偏差补记进 spec 或工单（例外清单、验收标准、改过的路径），同上提交、推送 | 那个提交 |
| **开 issue** | 照 `idea-loop:spec-status` 的「开一个待验证的 issue」开（为什么不做：这次不修） | issue 链接 |

「已按规则处理」每条一句：做了什么、依据、链接。没来得及落地的修复写「已派修，提交随后补上」，落地后补进「做了什么」。

边缘情形（只在兜底路径或罕见异常里出现、不丢东西）在 PR 流程里是「要你决定」，「代价相称」只定推荐（`idea-loop:decision-rules` 的「PR 流程里『代价相称』只定推荐」）。依据成立不了（规则有歧义、找不到现存实例）的条目留给人。

## 人批示之后

人在会话里批示（「S1 接受，C1 修，C2 开 issue」；「进 backlog」就是开 issue）。先把原话逐字记进这一轮条目的「你的批示」，再逐条处理：

- **修**：先找到它归哪张工单。
  - Spec 条目：它引用的那张工单。
  - Standards 条目：对代码片段所在的行跑 `git blame` 找到引入它的 commit，`node "${CLAUDE_PLUGIN_ROOT}/scripts/ticket-ledger.mjs" of <commit>` 读出工单。
  - UI 审查并进来的条目（引的是档案里冻结的原文）：归改了那个状态或组件的工单（读各工单的「要建什么」，或对实现那处 `git blame` 看 `Ticket:`）。
  - 都找不到（比如代码来自一次不带 trailer 的修复），问人归哪张。

  在那张工单的验收标准末尾追加 `- [ ] review 第 <N> 轮 <编号>（<日期>）：<应有的行为，或要遵守的规则原文>`，用 `docs(tickets): <NN> — review 第 <N> 轮 <编号>` 提交，然后派一个 `idea-loop:implementer` 做这张工单，派工、核对、落地与回收用 Skill 工具调 `idea-loop:implement`，看它的「派工」「核对与落地」「回收」（自己的 worktree、起点 SHA、分到的端口，fast-forward 落地）。它只做没勾的格，commit 带同一个 `Ticket:` trailer。同一张工单上的几条一次写完再派；多张工单可以并行派。全部落地后推送。写进工单的是行为，不抄审查者给的文件、行号。
- **接受**（选了「接受，补进 spec 或工单」一类）：代码不动，偏差写进 spec 或工单，`docs(spec): …` / `docs(tickets): …` 提交、推送。UI 审查的条目选了「改档案，接受实现」的，改 `docs/design/tmp/<spec-slug>/delta/` 里对应的文件（本地、不进 git），不提交，记进「做了什么」。
- **不修**：记下。下一轮不再报，除非有新证据。
- **开 issue**：同「照规则的条目」里的开 issue，链接记进「做了什么」。
- **推翻**（对「已按规则处理」里的某条：「推翻 C1」「S2 那个不用改」）：原话逐字记进同一个条目的「你的批示」，按人的意思改回或改做：
  - 原来是修 / 恢复：在同一张工单上再追加一格 `- [ ] review 第 <N> 轮 <编号>（推翻，<日期>）：<人要的样子>`，照上面的「修」派执行方（修复还没落地的，把没落地的那格一并说清）；
  - 原来是同步改 / 接受并补记：把那个提交改回去，或按人的意思重写，提交、推送；
  - 原来是开 issue：在那个 issue 上留一条说明并关掉（`--reason "not planned"`），人要别的处理就按那个做。
- **疑问**：直接回答。
- **批示带出上线前后的事**（「S2 接受，上线时手动处理迁移」）：要人在上线前做的，追加进 PR 描述 `your-todo` 节的「上线前要注意的」，写明为什么要人来做；Claude 合并后自己做的，追加进 `reference` 节的清理清单。都用 `pr-body.mjs set`（`idea-loop:pr` 的「PR 描述是总览，汇报在会话里」）。
- **要求改写汇报**（「写成我看得懂的样子」）：照 `idea-loop:pr` 的「review 汇报」改写 review loop 文件里那个条目的汇报部分，在会话里重贴，改了什么写进汇总。

全部处理完，在会话里回**一条**汇总，逐点说做了什么、带提交链接；同样的内容记进这一轮条目的「做了什么」，PR 描述 `your-todo` 里已决定的几项勾上。然后判下一轮。

一轮里没有任何「要你决定」（全是照规则处理），就没有批示可等：派出去的修复都落地、推送之后，在条目末尾记一节「做了什么」写修复的提交，`review-loop check` 才不再把这一轮算未处理。修复没落地之前不记。

## 下一轮：什么时候自己起

**三个条件同时成立**，编排者自己起下一轮：

1. **这一轮有修复**：「照规则 · 修」或人批了「修」的条目至少一条。只数「修」。
2. **这一轮的条目都处理完了**：要修的都已落地并推送，`review-loop check .tmp/review-loop/<PR 号>.md` 没有未处理的条目，**并且**逐题核过：对着这一轮的汇报数「要你决定」，每一道都在「你的批示」里找得到人的批示（接受 / 修 / 不修 / 开 issue / 疑问已答清）。`check` 只判整轮（有一条批示、后面有一条「做了什么」就算处理完），代替不了逐题核对；核不全就回头问人缺的那几道。
3. **还没跑满两轮**：`review-loop next` 给出的下一轮编号不超过 2（人触发的轮次也计入）。

成立时，在会话里说一句「第 N 轮的修复已落地，自动起第 N+1 轮」，发一条推送通知，回到「跑一轮」。

不成立时等：这一轮没有修复，等人说合并或「再跑一轮」；跑满两轮，停下（第 2 轮起审查者在汇报末尾写了「已跑满两轮，要再跑或合并请直接说」）；还有没批示的题或没落地的修复，等它们齐了再判一次。上限只约束自动起，不约束人。
