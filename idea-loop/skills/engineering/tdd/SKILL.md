哪些改动走 TDD、哪些换别的仪器（eval、UI 实现环、端到端检查），spec 的「测试决策」已经逐行定了。这份只管落在 TDD 那几行上的改动：怎么把循环跑对。

## 好测试是什么

测试通过公共接口验证行为。实现可以整个换掉，测试不用动。

好测试读起来像一份规格：`user can checkout with valid cart` 一眼看出存在什么能力。它不关心内部结构，所以能活过重构。

## seam：测试落在哪

**seam** 是你能观察行为、又不必伸手进内部的那个公共边界。测试住在 seam 上。

**只在 spec「测试决策」里谈拢的 seam 上测**，那里没有的 seam 不写测试。事先谈拢 seam，就是让力气落在关键路径和复杂逻辑上，而不是每一个边界情况；先写测试的动作本身就是在设计接口，所以 seam 要在写代码前定。

## 三种反模式

- **耦合实现**：mock 了内部协作者、测了私有方法，或者绕过接口从侧门验证（去查数据库，而不是用接口读回来）。判别标志：重构了、行为没变，测试却红了。
- **同义反复**：期望值是按代码同样的方式算出来的（`expect(add(a,b)).toBe(a+b)`、照着实现推出来的快照、常量等于自己），于是它天生就过，永远不会跟代码唱反调。期望值来自独立的真相源：一个已知的字面量、一个手算的例子、spec 的原文。
- **横向切片**：先写完所有测试再写所有实现。批量写出来的测试验的是想象中的行为，测的是形状而不是用户可见的行为，在理解实现之前就把测试结构锁死了。要纵向走：一个测试 → 一段实现 → 重复，每个测试是一颗曳光弹，回应上一轮教给你的东西。

## 循环的规矩

- **先红后绿。** 先写会失败的测试，再写刚好让它过的代码。只写眼前这个测试要的，后面的测试和投机性功能等它们自己的轮次。
- **一次一刀。** 一个 seam、一个测试、一段最小实现。
- **重构留给 review 阶段**，不在 red → green 里做。

## mock 只在系统边界

可以 mock：外部 API（支付、邮件）、数据库（有时候，优先用测试库）、时间与随机数、文件系统（有时候）。

你自己的类和模块、内部协作者、任何你控制得了的东西，用真的。

为可 mock 性设计：依赖注入（把外部依赖传进去，而不是在里面 new）；SDK 式接口优于万能 fetcher（每个外部操作一个具体函数，mock 时不用在里面写条件分支）。

这条只约束新写的测试。存量测试常有把自己的类替换在另一个自己模块的 import 点上的 mock（`patch("app.services.X.SomeRepository.get_by_id")` 这种），不倒查、不照抄。某类 mock 其实是被环境问题逼出来的（比如某个模块一 import 就有副作用），那是环境缺陷，单独登记单独修。
