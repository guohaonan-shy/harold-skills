# 各章写什么、不写什么

每章一个条目：定义、写什么、不写什么、例子。例子取自公开的 `DESIGN.md` 样本（VoltAgent/awesome-design-md），只用来说明写法。

## Overview

- **定义**：一屏以内的设计立场，在没有具体规则覆盖时指导取舍。
- **写什么**：品牌气质（克制或活泼、紧凑或舒展）；最多 5–8 条关键特征，每条能转成可检查的判断。
- **不写什么**：后面各章已有的规则；「signature / engineering-grade / elegant」这类没有可执行含义的修辞。
- **例**：好——tesla 一句话点明立场（radical subtraction），特征全可检查：整页一个强调色、没有阴影、没有渐变、没有边框。坏——Overview、Key Characteristics 与 Do's 三处重复同一条规则。

## Colors

- **定义**：色板，以及**每个颜色什么时候用、什么时候不能用**。
- **写什么**：按角色分组（品牌、表面、文字、语义）；每色一行：名字、token 引用、用途、限制。
- **不写什么**：采集来源页面；逐条重抄的 hex。
- **例**：好——stripe 的 Ruby 一行写明「渐变强调与图表高亮；永远不是按钮」；tesla「没有第二强调色」。「限制」比颜色本身更有价值：agent 最容易犯的错是把强调色用到不该用的地方。

## Typography

- **定义**：字阶表加排版原则。
- **写什么**：按语义命名的字阶（`display-xl`、`body-md`、`label-caps`），建议 9–15 级，每级的用途；原则——字重范围、行高与字号的关系、字体缺失时的替代。
- **不写什么**：某个页面里某个标题具体多大。
- **例**：好——hashicorp「紧的展示行高配松的正文行高，这个对比就是品牌的声音」；vodafone 说明 -1px 字距是为 144px 字号校准的。坏——figma 的 Do's 规定字重只许 320/330/340/480/540/700，Overview 里却用了 450。

## Layout

- **定义**：间距刻度、栅格、容器宽度，以及留白的理由。
- **写什么**：间距 token、最大内容宽度、栅格列数与间隙、留白原则、图片比例。
- **不写什么**：断点与折叠，它们在 Responsive Behavior。
- **例**：好——tesla 把留白写成原则：每个主要内容块占满一屏高，一屏只传达一条信息。

## Elevation & Depth

- **定义**：层级关系怎么表达。有阴影写阴影参数，没有阴影写替代手段。
- **写什么**：层级表（层级 / 处理方式 / 用在哪），明确禁用的手段。
- **不写什么**：生成的示例块。
- **例**：好——linear.app 用底色阶梯加 1px 边框，第 0 到第 4 层逐级写明处理方式和用在哪，并写明「在深色上基本不用投影」。坏——自动生成的示例块（`ex-modal-card`、`ex-toast`）写了阴影，与本章「无阴影」直接矛盾。

## Shapes

- **定义**：圆角刻度和形状规则。
- **写什么**：圆角 token、每档用在哪、图片几何、**为什么没有某一档**。
- **不写什么**：某个组件在某个页面的圆角。
- **例**：好——mastercard「要么 ≤6、要么 20–40、要么全圆，8–12 这个中间档刻意缺席」。

## Components

- **定义**：**可复用的基础组件**的配方：外观属性加全部状态，agent 可以直接抄。
- **写什么**：系统级通用组件（按钮、输入框、卡片、徽章、导航、列表项、对话框等）；每个组件用 token 引用写颜色、字阶、圆角、内边距、尺寸，一句用途，以及状态（default / hover / pressed / focused / disabled）。
- **判别**：**这个组件的配方换到任何一个页面都成立，才进这一章。** 特定组件在某个页面或场景里的样子、页面级结构（「首页 hero 的布局」）、某个页面特有的组件、生成的示例块，都不进。
- **例**：好——framer、mongodb 把 pressed、focused 单列成条目，便于机械校验。坏——只给默认态；焦点态的取值与默认态完全相同；示例引用了文件里不存在的 token。

## Do's and Don'ts

- **定义**：可判定的约束。读完这一章，agent 能判断「这样做算不算违规」。
- **写什么**：每条做 / 不做加一句理由；引用 token，不写裸值。
- **不写什么**：「应该美观」「保持一致」这类无法判定的话。
- **例**：好——tesla「不要加 scale / translate 的 hover 动画，交互只有颜色过渡」「每屏至多两个行动按钮」。坏——Do's 规定按钮内边距不得低于 14px 28px，secondary pill 却写 10px 30px。

## Responsive Behavior（扩展）

- **定义**：断点、折叠策略、触控尺寸。
- **写什么**：断点表（名称 / 宽度 / 变化）、折叠规则、触控目标最小尺寸、图片处理。
- **断点数值只出现一次**，就在这张表里；别处要用就引用。
- **例**：好——airtable 用表格写断点，触控尺寸直接引用组件 token 并对照 WCAG 的 44px。坏——断点表写 736/834，末尾却列了 734、833、480。

## Motion（扩展）

- **定义**：动效的**全局原则与禁令**。
- **写什么**：统一时长和缓动（一个或一小组，作为 token）；可以动什么、不可以动什么；reduced-motion 要求；产品有多种调性时，安静场景和活泼场景之间怎么取舍。
- **抽规律，不枚举**：多个具体动效背后有共同规律的，把规律写成一条原则；具体动效（「滑动指示器」「处理中的光扫」）和它们的参数留在设计档案的动效对象里。
- **例**：好——tesla 的原则「0.33s cubic-bezier 是所有交互状态变化的统一时长」、禁令「不加 scale / translate 的 hover 动画，交互只有颜色过渡」，全文没有一条带日期的先例。

## Known Gaps（扩展）

- **定义**：这份文件**没有覆盖什么**，以及已知的数据局限。是对读者的诚实声明。
- **写什么**：未覆盖的范围（暗色模式、错误态样式）；数值是估测还是权威；缺口的临时处理。
- **不写什么**：变更记录、决策历史。
- **例**：好——hashicorp「暗色是唯一的营销模式，亮色适配未记录」；airtable 说明颜色取自截图采样，可能随季节换色。
