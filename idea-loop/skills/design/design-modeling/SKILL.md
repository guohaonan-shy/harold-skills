项目的 `DESIGN.md` 写的是这个产品的设计系统本身。判断一条内容该不该进 `DESIGN.md`，只按这一份。

格式以官方规范为准，每次运行现读：`npx -y @google/design.md@latest spec`（写入时的 hook 和收尾校验用的都是最新版）。这里只写规范管不到的：什么该进、怎么写、怎么维护、候选长什么样。

## 是什么

`DESIGN.md` 由 YAML front matter（全部数值，即 token，是规范性的）和 Markdown 正文（给人和 agent 读的用法与理由）组成。

- 它描述设计系统**现在是什么、必须怎么做**，是这套设计系统唯一的权威版本。
- 它只收系统，不收设计过程：某天的改动、做过的决策、某个页面或组件在某个场景里的具体样子，都有别的去处（「准入分层表」）。
- 它靠整理保持可维护，不靠追加（「维护原则」）。

## 结构

front matter 之后，正文用 `##` 二级标题，只用下面这些章，按这个顺序，每章只出现一次：

| 章 | 内容 |
|---|---|
| Overview | 品牌气质与设计立场 |
| Colors | 色板与每色的用途、限制 |
| Typography | 字阶与排版原则 |
| Layout | 间距、栅格、留白 |
| Elevation & Depth | 层级怎么表达 |
| Shapes | 圆角与形状规则 |
| Components | 组件配方（含状态） |
| Do's and Don'ts | 可判定的约束 |
| Responsive Behavior（扩展） | 断点、折叠、触控尺寸 |
| Motion（扩展） | 动效的全局原则与禁令 |
| Known Gaps（扩展） | 没覆盖什么 |

- 不需要的章用 front matter 的 `omitted:` 声明并写原因，正文里不留空标题。
- 前八章来自 Google 规范；三个扩展章是我们加的。重复的章和扩展章的形态（不带日期、不枚举、不写判例），官方 lint 都不报，靠写的人守。

## 五条写法规则

对每一章都生效。

1. **准入判据。** 只收设计系统本身：全局的、当前生效的、下一个 agent 能直接照做的规则与数值。「某天做了什么改动」「做了什么决策」「某个特定组件或页面的具体描述」去「准入分层表」里各自的层。
2. **一条规则只写一处。** 最常见的缺陷是自相矛盾：同一条规则在 Overview、Do's、各组件条目里各写一遍，改一处漏一处。坏例：颜色章列了三个强调色，Don'ts 却写只许金色一个。
3. **数值只在 front matter，正文用名字引用。** 正文写 `{colors.primary}`，不重抄 hex。
4. **每条规则带「为什么」或「边界」。** 只给数值不给理由，agent 遇到没覆盖的情况无法推断。好例：解释为什么跳过 8–12px 圆角（要么小、要么大、要么全圆，中间档不存在），比单给一张圆角表有用得多。
5. **只写当前状态，不写演进。** 不写「从 X 改成了 Y」「某月某页确认」。

## 维护原则：整改优先于追加

每次有新内容要改动，按顺序：

1. **先找已有内容里受影响的部分。** 在所有章节和 front matter 里找：这条新内容是否与已有规则矛盾、是否让已有规则过时、是否已经被某条已有规则覆盖。
2. **能整改就整改。** 过时的改写或删除，矛盾的统一成一条，已覆盖的什么都不加。
3. **只有已有内容没有覆盖某个缺口时才新增。** 新增时仍写成全局规则，放进最合适的一章，并同时更新 front matter 里对应的 token。
4. **改完读一遍相关章节**，确认同一规则只剩一种写法。

判断标准：文件的大小由「设计系统有多少缺口」决定，不由改了多少次决定；它变短的次数应该和变长一样多。

## Front matter

- **定义**：文件开头 `---` 包起来的 YAML，是设计系统的全部**数值**，也是唯一的数值来源。
- **写什么**：`colors`、`typography`、`rounded`、`spacing`、`components` 五组，加 `name`、`description`、`version`，必要时 `omitted`。颜色用 CSS 颜色串（默认 hex）；字阶含 `fontFamily / fontSize / fontWeight / lineHeight / letterSpacing`；组件的值用 `{colors.primary}` 这类引用；**状态拆成独立条目**（`button-primary`、`button-primary-hover`、`button-primary-pressed`），改一个色值全局生效。
- 理由、用途说明写在正文。
- **凡是影响渲染的属性，必须在 front matter 的 token 里有。** 正文只解释怎么用、为什么，不能成为某个渲染属性的唯一出处（坏例：按钮边框只写在正文括号里，只读 token 的 agent 会漏掉）。新增内容同样同步 token。

## 各章写什么

每一章的定义、写什么、不写什么和好坏例子在 [references/chapters.md](references/chapters.md)。新建、往某一章写入或改动、对账检查某一章之前，读那一章的条目。

## 准入分层表

每条内容都先过它。从上往下问，**第一个命中的就是去处**：

| 层 | 去处 | 判据 |
|---|---|---|
| 工作流 | idea-loop 插件本身（skill 与 agent） | 说的是环怎么跑 |
| 通用设计原则 | `/idea-loop:uiux-refine` 的设计协议 | **换一个产品照样成立** |
| 产品设计系统 | 项目 `DESIGN.md` | 只对这个产品成立，**而且跨页都要服从**，并且已经能写成全局规则（无日期、无页面名、可照做） |
| 页面或组件的决定 | 设计档案里对应对象的「决定」（`idea-loop:design-archive`） | 只对这一页、这个组件成立 |
| 现状、缺陷、迁移 | 目标仓库的 GitHub issue / spec | 说的是「现在什么样」，不是「应该什么样」 |

两个用来校准的判例：

- **「营销页的图像语言是无人静物摄影」被判错。** 同一页就用了静物照、线稿、生成插图、代码动效四种，图像风格按每页内容选。这是页面决定。
- **所有介绍页共用的收尾渐变从没进过 `DESIGN.md`，是漏了。** 它跨页、只属于本产品，正好在产品设计系统这一层。

产品设计系统这一层还收一类常被漏掉的内容：**页面家族的复用机制**，比如一组同类页面共用的构图顺序。它跨页、只属于本产品、能被检查。

拿不准落在哪一层时，把两个候选层和各自的理由摆给人，由人定。`DESIGN.md` 只收真正命中这一层的内容，不为了看起来完整而补。

## 明确不进 DESIGN.md 的内容

| 内容 | 为什么不进 |
|---|---|
| 判例（情境 → 决定 → 理由，带日期） | 是决策与过程；随时间只增不减，把文件变成决策堆叠 |
| 带日期的先例（「某月某日，某页」） | 同上 |
| 具体动效的枚举（逐条列各种动画） | 只增不减，无法维护；Motion 章只收全局原则 |
| 单个页面的设计决定、特定组件在特定场景的具体描述 | 属于页面，不属于设计系统 |
| 某天的快照、变更记录 | `DESIGN.md` 描述当前状态 |
| 采集来源页面清单、脚本生成说明 | 是取证说明，对自己维护的项目没有意义 |
| 自动生成的示例块（`ex-*`、`TO_FILL`） | 几乎不增加信息，还引入错误引用 |
| 代码行号引用、已知缺陷、迁移计划、历史叙事、划掉的条目 | 各有去处（「准入分层表」） |
| 被多处遵循的先例 | 先改写成无日期的全局规则，再并入对应章节；原始判例留在别处 |

## 一次写入怎么走

新建、蒸馏、对账都走这一条。**模型起草，人批了才落笔。**

0. **找文件**：`git ls-files | grep -i 'DESIGN.md$'`。只有一份就地维护；有好几份（monorepo 的多个 app）问人这次动哪一份；没有就在仓库根新建，除非人指定了某个 app 目录。
1. **备份**当前版本到 `/tmp/design-md/before.md`。新建时没有这一步。
2. **起草**：在会话里摆出要加、要改、要删的每一处，旧文与新文并排，每处一句它为什么落在这一层。按「维护原则」先找受影响的已有内容，能整改的整改，缺口才追加。
3. **停下等人确认。** 人改过措辞以人的为准。人拒绝写文件，就把内容以文字交回。
4. **落笔**：只改人批过的几处。插件的 hook 会在每次写 `DESIGN.md` 时自动跑官方 lint。
5. **收尾校验**：

   ```
   npx -y @google/design.md@latest lint <DESIGN.md 路径>
   npx -y @google/design.md@latest diff /tmp/design-md/before.md <DESIGN.md 路径>
   ```

   `lint` 修到没有 error。`diff` 判为退化（新增了 error 或 warning）就修，或把这条 warning 摆给人并说明为什么可以接受。新版本 CLI 对老内容多报出来的 warning 不算这一次的退化，列进报告留给下一次对账。
6. **报告**：模式与依据；写进 `DESIGN.md` 的每一处（新增 / 修改 / 删除）；分到别处的各几条；校验结果；前后行数。

## 新建

项目还没有 `DESIGN.md` 时：照 [references/new.md](references/new.md) 判来源（有线上 UI 从代码量，没有 UI 接选定的语言）再写。

## 蒸馏

把设计法候选、或人口述的规则收进 `DESIGN.md` 时：照 [references/distill.md](references/distill.md)。人口述一条规则要当场落的，走里面的「单条蒸馏」。

## 对账

拿 `DESIGN.md` 现有内容去量代码、按这份标准体检时：照 [references/reconcile.md](references/reconcile.md)。

## 设计法候选的形态

不在「谁写、谁读」那两处之内、又想改 `DESIGN.md` 的，写一条候选：

```markdown
- **<一句话规则，已经是 DESIGN.md 能收的形态：无日期、无页面名、可照做>**
  - 并进：<章名>（新增 / 整改哪一条）
  - 为什么：……
  - 证据：<哪些对象这样做，wikilink>
```

- 没有候选时这一节写一行「无」：空着分不清是没有还是漏了。
- 只有这四行：处理候选的人处理完就删，去向记在那次的执行结果里，所以候选上不写情境 / 决定 / 理由三段，也不写去向。
- 写背后的**规律**，不写具体一次的参数。一个新动效模式，写成可并进 Motion 章的全局原则；具体参数留在动效对象里。
- 候选的住处：它出自的设计档案对象（页面、组件、动效、用户路径）正文的 `## 设计法候选` 一节；需求进行中先写在冻结记录（`docs/design/tmp/<slug>/canvas/<slug>-design.md`）的「设计法候选」一节，每条一行，写明规则和它将挂在哪个对象上；合并前归档时 ui-reviewer 把它们写进 `docs/design/tmp/<slug>/delta/` 的对象文件，随对象进 `prod/`。
- 写不成这个形态的（带着日期、页面名，或只对这一页成立），不是候选，留在对象的「决定」里。

## 谁写、谁读

写 `DESIGN.md` 的只有两处，都按这份写、都把措辞交人确认：

- `/idea-loop:uiux-imagine`：**只新建**。开工时项目没有 `DESIGN.md`，选定语言后在同一会话里写第一份（照「新建」）。项目已有 `DESIGN.md` 时，重探语言只产出候选。
- `/idea-loop:dreaming`：新建（发现项目没有时）、蒸馏（含单条蒸馏）、对账。

其余想改 `DESIGN.md` 的都写成候选，等 dreaming 处理：动效段签字后的新模式、静态设计签字时提炼出的规律、imagine 的修订提案、实现时冒出来的新 token。设计侧 skill、agent 和实现标准都把 `DESIGN.md` 当项目的设计法来读。
