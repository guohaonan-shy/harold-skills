# backlog 模式：从 backlog 条目起草 spec 草稿

`to-spec` 的第二种模式。输入不是一场 grill 对话，是项目 backlog 里**同一模块**的一组条目，或者一组 GitHub issue，通常由起草 routine 或 `idea-loop:issue-explorer` 调用。没有人在场，所以 grill 本来会做的两件事——复现和拆分——这里要自己做。

这份文件只写跟 grill 模式不同的地方。没写到的（spec 模板的格式、禁写文件路径、GLOSSARY、图怎么画、seam 写法）照 `SKILL.md` 和它引用的 references。

## 0 输入

两种来源，按调用方给的选：

- **backlog 文件**：一组条目，都属于同一个模块。模块划分表在 backlog 文件的「模块」一节，是项目配置（`../../../references/spec-status.md` §2）；读不到这一节就停下，说缺什么，不自己编模块。条目里带「已移交 → [[…]]」标记的，已经有 spec 了，跳过。
- **GitHub issue**：一组 issue 号。没有模块表——哪几个该放进同一份 spec，按 §2 的拆分规则自己判断，互不相关的各成一份。每个 issue 先读全文和评论（`gh issue view <号> --comments`）。已经有 `status:*` label 的，已经在流程里了，跳过（`../../../references/spec-status.md` §3）。

下文的「条目」两种来源都指。

## 1 先复现

每条条目先复现，再写进 spec。复现的手段是下面三种之一：

| 条目性质 | 复现手段 | spec 里写什么 |
|---|---|---|
| 逻辑、数据、API 行为 | 一个会红的测试。**不提交**：测试代码和它的输出放 `.tmp/to-spec/<spec-slug>/repro/`，`implement` 时由执行方正式写。 | 白话写测了什么、看到什么、本该是什么，带一个具体的例子 |
| 看得见的界面问题 | 一张截图，标注按 spec-figures §1 | 截图本身 |
| 线上数据、日志、性能 | 一条查询或一段日志，写明查的是什么、什么时候查的 | 查的范围和时间，加结果——数字能列成小表就列成表 |

**spec 里只放人读得懂的结论，不放机器的原始输出。** 测试的失败输出（`AssertionError: expected …`、堆栈、`[repro]` 打印）、查询语句本身、整段日志，都留在 repro 目录，spec 里一行都不贴：审核的人读不懂，它证明不了什么给人看。换成一句话说清楚复现到的现象，比如「打开一次页面记了两条浏览事件：一条是 SDK 自动记的，一条是页面组件手动补的」，后面接本该是什么（「应该只记一条」）。要指回原始材料的，在小节末尾写一行「复现材料：`.tmp/to-spec/<spec-slug>/repro/<文件>`」，不展开。

**复现不出的不进正文**，列进 spec 末尾的「建议关闭」一节：条目原文的指针、试了什么、卡在哪（环境缺依赖、拿不到线上权限、按条目描述的步骤走行为是对的……）。人审核时决定关掉还是补信息。

复现推翻了条目原来的说法（比如条目写的根因不对），在 §1 根因里写明「修正：条目原先认为 X，实测是 Y」。

证据图放这份 spec 自己目录下的 `assets/`（`docs/spec/<spec-slug>/assets/problem-<n>-<slug>.png`）。backlog 模式没有 raw 桶，图跟 spec 放在一起，spec 了结时跟目录一起删、或由 `dreaming` 挪进 ADR。

## 2 先拆分，再起草

一组条目不一定只成一份 spec。按这几条拆：

1. **要调整设计的条目单独成一份 spec。** 它会走 `设计中`，不能让它拖着同组别的条目一起等设计。
2. **功能级的条目单独成一份 spec**，正文标题下第一行写「> 需要 grill：<为什么>」。功能级 = 修完是「多了一个原来没有的能力」，或者条目里写着还没定的设计问题。审核会话看到这一行就先 grill 再审。
3. **剩下的一份 spec 超过 5 条问题，按相关性拆成几份**（同一个页面、同一条链路、同一个根因的放一起）。

每份 spec 都要有自己全局唯一的 slug。

## 3 章节取舍

| 章节 | backlog 模式怎么写 |
|---|---|
| raw transcript | **不写**。没有对话。 |
| §1 问题 + 根因 | 必写。每条一个小节：backlog 条目里原有的证据，加本次复现的结果，按 §1 写成人读得懂的结论。 |
| §2 方案 | 必写，逐条。 |
| §3 User Stories | **不画场景树**。每条问题一行「期望行为」，编号保留——`pr-review` 的 Spec 轴靠它逐条比对。 |
| §4 实现决策 | 只写修法有分歧的条目：给选项和推荐，留给人在审核时定。没有分歧的写「无分歧」。 |
| §5 技术方案总览 | **保留**，按 grill 模式写。不涉及的子节写「不涉及」。 |
| §6 测试决策 | 必写。 |
| §7 Out of scope | 必写。 |
| §8 关联 | 必写，逐条指回 backlog 条目（backlog 文件 + 条目编号或标题；issue 写 `#<号>` 加标题）。 |
| 建议关闭 | 有复现不出的条目才写，放在 §8 之后（§1）。 |

## 4 落盘

- frontmatter `status: 草稿`。`related` 不挂 transcript，挂这份 spec 关联的其他 spec / ADR，没有就留空列表。
- `spec-status.mjs index <docs>` 刷新 `docs/spec/index.md`。
- 每条被这份 spec 覆盖的条目写一次移交：backlog 条目跑 `spec-status.mjs handoff`（`../../../references/spec-status.md` §2）；issue 跑 `issues.mjs handoff`（同上 §3，只写进 spec frontmatter 的 `issues`，GitHub 上的 label 由调度方推送之后再同步）。进了「建议关闭」的也写——它同样等着人在这份 spec 的审核里处置。
- **不提交、不推送、不开会话。** 这些是调用方的事（`issue-dispatch`，或项目自己的起草 routine）。

收工时列出：起草了哪几份 spec（slug、各含哪几条、是否标了「需要 grill」、是否碰 UI），以及进了「建议关闭」的条目。
