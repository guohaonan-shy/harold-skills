# To Ticket

把一份 spec 切成若干 **ticket**——tracer bullet 式的**垂直切片**，每张声明挡着它的那些 ticket。

> 先读一次 `../../references/wiki-conventions.md`。

**ticket 是临时凭据。** 开工时才建，那一刀合并后就删掉。它不是归档物，不留痕——留痕的是 spec（在飞时）和 ADR（了结后）。

## 1 读 spec

`docs/spec/<slug>.md` 全文，含它的 §5 测试决策（seam 已经谈拢了，别重开）。

## 2 探代码库

看清现状。ticket 的标题和描述用项目已有的领域词汇。

顺手找**预重构**的机会：*让改动变容易，然后做那个容易的改动。*

## 3 切垂直切片

- 每一刀切穿**所有层**（schema → API → UI → 测试）的一条**窄而完整**的路径。是竖切，**不是**某一层的横切。
- 切完的一刀**自己就能演示或验证**。
- 每一刀塞得进**一个全新的上下文窗口**。
- 预重构排最前。

给每张 ticket 它的 **blocking edges**——必须先完成的那些 ticket。没有 blocker 的可以立刻开工。

**一份 spec 塞得进一个 PR 就别建 ticket**，直接开工。

### 大范围重构是垂直切片的例外

**大范围重构** = 一个机械改动（改列名、给共享符号换类型），但**爆炸半径**扇出到整个代码库——一次编辑打断上千个调用点，没有哪一刀能独自变绿。别硬塞成 tracer bullet，按 **expand–contract** 排：

1. **expand**：新形态加在旧形态旁边，什么都不坏。
2. **migrate**：按爆炸半径分批（按 package、按目录）迁调用点，每批一张 ticket、都被 expand 挡着；旧形态还在，所以每批之间 CI 都是绿的。
3. **contract**：没有调用者了，删掉旧形态，被全部 migrate 批次挡着。

批次自己都绿不了的时候，序列不变，但让它们共享一个集成分支，全部挡住最后一张"集成并验证"的 ticket——绿只在那一张上承诺。

## 4 把切法摆给人看

编号列出，每张显示：**标题** / **被谁挡着** / **它让什么端到端行为跑起来**。然后问：

- 粒度对吗（太粗 / 太细）？
- blocking edge 对吗——每张是不是只依赖真正卡它的那些？
- 有没有该合并或该再拆的？

迭代到人点头。

## 5 落盘

`docs/spec/tickets/<NN>-<slug>.md`，从 `01` 开始按依赖顺序编号（blocker 在前）。

```markdown
# NN — <标题>

**Blocked by**：<编号/标题>，或「无——可立即开工」
**设计冻结**：不涉及 UI ｜ 已冻结（<预览 HTML 路径> · <一行 fidelity/decision ledger 摘要>）｜ ⛔ 未冻结 —— 不可开工

## 要建什么
这张 ticket 让什么端到端行为跑起来，用户视角——不是逐层的实现清单。

## 验收标准
- [ ] 可独立验证的判据 1
- [ ] 可独立验证的判据 2

## 选中的存量回归
从 `docs/testing/test-cases.md` 里，按这一刀碰到的**页面**挑（不是全量套件），每条一句话说明为什么它有风险。
```

> **这个文件是本 plugin 起源项目的布局假设。** 目标仓库没有它是常态。没有就**如实写「无 test-cases 库」，并指名那个仓库真实存在的套件**（按名字/角色，不按路径）—— 不要编一个不存在的路径让模板看起来填满了。

### 设计冻结闸门挂在这里

**动 UI 的 ticket 要求设计已冻结才能开工**；spec 不要求（spec 可以停在 `status: 等设计冻结`）。

设计冻结是**开工前置条件**，不是规格的完成度指标。挂在 spec 上就会积一批"想清楚了但画不出来"的文档长期驻留。

**这份产物从哪来、怎么誊写**：涉及 UI 的分叉在 `grill` 里挂了设计子树时，`design`（设计总入口）收工带回的答案——预览 HTML 路径 + 一行 fidelity/decision ledger 摘要——已经被 `to-spec` 综合进 §1 读的那份 spec（通常在 §4 实现决策，跟这张 ticket 对应的那条决策挂在一起）。切这张 ticket 时：

- spec 里能找到这张 ticket 对应范围的产物记录 → 原样誊写路径和摘要到「设计冻结」字段，**不改写、不新编数字或措辞**——那是 `design` 产出时自己填的，切票这一步只誊写。
- 涉及 UI 但 spec 里没有对应记录（子树没跑完就被打断、或这张 ticket 划的范围比 spec 记录的更大）→ 字段落 `⛔ 未冻结 —— 不可开工`；`implement` 会照这行拦下开工。

## 6 谁来做这些 ticket

**一张 ticket = 一个全新的主线程会话。** 节奏是 `/clear` → `implement` 做这一张 → commit → `/clear`。

不派 subagent 扇出。两个理由：

1. **ticket 是写给失忆者的信。** 拿起它的会话**从没见过那份 spec** —— 这正是"每张塞得进一个全新上下文窗口"这条尺寸约束的由来。你在写 ticket 时觉得"显而易见所以不用写"的东西，对那个会话并不显而易见。所以才有那几条禁令：禁文件路径、禁代码片段、描述行为不描述过程。
2. **subagent 不能中途转向。** 实现过程中跑 red→green 时仍会撞到需要人拍板的东西（"这个边界情况算不算 in scope"）—— 主线程会话可以当场问，subagent 只能猜完往下走。

下一环是 `implement`：它只读那一张 ticket，不重开方案。

> **这一环的交接是给人的，不是模型自己往下调。** `/clear` 是人的动作 —— 模型清不了自己的上下文，所以它无法满足 `implement` 的第一条前置（一个全新会话）。`implement` 因此对模型不可见（`disable-model-invocation`，与上游一致）。落盘完 ticket 之后，**告诉人**去 `/clear` 再 `/implement`。

依赖图**是给人用的调度信息，不是自动编排**：blocker 都完成的 ticket 就在 frontier 上，可以开工，仅此而已。

> 反面数据：某团队按**层**横切了 26 张 ticket，结果是每关闭一张要跑约 20 次 agent，其中约四分之三是返工。垂直切片不是审美偏好。

## 7 收工

合并后**删掉那张 ticket 文件**。全部 ticket 都删完了，说明这份 spec 做完了。

**ADR 与 spec 的删除归 `dreaming`，但它不是这一步的立即下一环。** dreaming 是**周期性的维护扫描**（见它的 `## 触发`），不是单份 spec 的收尾。所以「**做完但还没对账**」是 spec 的一个正常状态，不是漏洞 —— 等下一次 maintain 扫过，或者 spec 堆积到你想手动跑一次。

**别在这里提前手写 ADR。** dreaming 的纪律 5 要求每个判定都靠当次跑出来的证据，手写就是凭记忆。
