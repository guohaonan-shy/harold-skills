# 交付证据：人验素材与 review 配图

`idea-loop:implement` 的执行方做人验素材、`idea-loop:pr-review` 的审查者给问题配图、PR 描述拍「之前 → 之后」时用这份。交付证据只服务于「这次交付对不对」，人的结论以文字写回工单和 spec，图用完即弃：不进代码分支、不进 `docs/`，也不写进工单（工单在 git 里，引用一张不在 git 里的图，链接一定会坏）。真遇到值得长期保留的一张，显式复制进 `docs/` 对应的位置。

## 放哪、怎么上传、什么时候删

- **做的时候**：`<worktree 根>/.tmp/implement/<spec-slug>/evidence/`（工单素材）或 `.tmp/pr-review/<PR 号>/evidence/`（review 配图），约定见 `idea-loop:wiki-conventions` 的「中间产物」。截图原图、帧序列、拼图用的 JSON 都在这里。
- **上传**：每个 PR 一条**素材分支** `idea-loop-evidence-pr-<N>`：孤儿分支，跟代码没有共同历史，从不合并。脚本用 gh 当前登录的账号、经 GitHub 的 git 数据接口直接写，本地工作区不动；分支里没有 `.github/workflows`，推上去不会触发 CI。私有仓库里只有协作者看得见。

  ```
  node "${CLAUDE_PLUGIN_ROOT}/scripts/evidence.mjs" publish <owner/repo> <PR 号> <文件>...
  ```

  输出每个文件名对应的地址，形如 `https://github.com/<owner>/<repo>/blob/idea-loop-evidence-pr-<N>/<文件名>?raw=true`，PR 描述里的之前 → 之后对照、合并时归档进 PR 的汇报，都用它做图片地址：`![图说](<地址>)`。过程中的汇报不用上传：图写本地路径，在会话里用发送文件的工具发给人（聊天界面加载不了私有仓库的图），归档时由 `review-loop.mjs archive` 统一上传、换成地址。文件名以归属开头：工单素材用 `tNN-`（`t03-flow-sentence-failed.png`），review 第 N 轮的图用 `rN-`（`r2-spec-1-quota.png`），PR 描述的对照图用 `pr-`。分支里的文件是平铺的，不带归属就会互相覆盖，脚本会拒收。同名再传会替换原文件，地址不变，所以重录一张动图不用改已经贴出去的地址。单个文件不超过 10MB。
- **点开能看大图**：图片地址用上面那种 `blob/…?raw=true`：GitHub 给评论里的图包的链接会跳到 `raw.githubusercontent.com`，浏览器直接显示原图、能放大。宽的流程图、时序图在评论里会被缩小，全靠这一点看清。
- **删除**：PR 合并或关闭后跑 `node "${CLAUDE_PLUGIN_ROOT}/scripts/evidence.mjs" cleanup <owner/repo> <PR 号>`，时机与 `idea-loop:to-ticket` 删工单相同。它删掉素材分支，顺带删掉旧版留下的同名 draft release。漏网的由 `/idea-loop:dreaming` 扫：PR 已经 MERGED 或 CLOSED，`idea-loop-evidence-pr-<N>` 分支（或旧版的 release）却还在。

## 选哪种形态：最快能让人看懂的那种

先分**界面上看不看得到**：

- **看得到**（页面、按钮、提示、播放、录音状态的变化）：必须有取自实现的截图。拍板的人要看见用户看见的东西，表格、时序图、例子只能放在截图后面作补充。确实拍不到的（比如只有真机能复现），写一句为什么。
- **看不到**（纯后端、埋点、数据）：按下表选最快能看懂的那种。一句话就说清了的，不配图。

| 人需要看见的 | 形态 | 怎么做 |
|---|---|---|
| 用户这样走，界面这样变；走到第几步分叉、出错 | 流程图：真实截图 + 光圈（点击处、出错那一步）+ 箭头上的触发条件 + 每帧下一句状态 | `flow-compose.mjs`，构图规则见 [`spec-figures.md`](spec-figures.md) 的「交互图（screen flow）」 |
| 界面上哪里不一样；悬停、按下、窄屏 | 并排截图（之前 / 之后，静止 / 悬停，宽 / 窄），差别处画红圈 | 也用 `flow-compose.mjs`：一行，`connected: false`，`label` 写「之前 / 之后」或「同一元素 · 静止 / 悬停」 |
| 动起来哪里不对 | 动图 | 见「动图」 |
| 谁先谁后、等了多久（多为后端） | 时序图，基准分支和本分支的结局并排；两种实现规则不一致的，同一张图里用虚线框标出那一段 | 用 Skill 工具调 `excalidrawer:sequence` |
| 规则覆盖了谁、漏了谁 | 一张小表：场景 × 有没有覆盖 | 直接写进正文 |
| 数值或计算不对 | 一行例子：输入 → 基准分支的结果 → 本分支的结果 | 直接写进正文 |

### 和 spec 的图有一处不同：截图取自实现

[`spec-figures.md`](spec-figures.md)「交互图（screen flow）」里的设计图取自冻结画布，因为当时还没有实现。交付证据要判断的是**实现**，所以截图一律取自实现本身：本地起的真实页面，或开发状态页（dev harness，开发环境里单独挂组件的页面）上挂着的真实组件。 节奏靠网络拦截控制：慢下载用 `page.route` 先等再 `continue`，失败用 `route.fulfill({ status: 500 })` 或 `route.abort()`。

其余照 `SKILL.md` 的「两类共用的」。

## 动图

1. **录**：Playwright 打开页面，注入一个叠加层（鼠标位置点，需要计时就加一个秒表），然后按步骤操作。录法二选一：
   - **帧序列**：对组件循环截图，每张记下时间戳。截得到的就是看到的，最稳。**动效太快截不住时**（一张截图要几十毫秒，一个 200ms 的过渡只能截到几帧）：用 CDP 的 `Animation.setPlaybackRate`（如 0.1）把页面的动画放慢再截帧，帧率按放慢后的时长算，**在状态文件和图说里写明放慢的倍率**（「10 倍慢放」），不要让人以为这是真实速度；正常与减少动效各录一个并排放时，两个用同一个倍率。
   - **录屏**：context 开 `recordVideo`，录完用 ffmpeg 裁出组件所在区域。帧序列截不住的快速过渡用这种。
2. **转**：ffmpeg 两遍调色板，控制体积：

   ```
   ffmpeg -y -framerate <帧率> -i frames/%04d.png -vf "fps=12,scale=<宽>:-1:flags=lanczos,split[a][b];[a]palettegen[p];[b][p]paletteuse" t03-<slug>.gif
   ```

   帧率按时间戳算（帧数 ÷ 时长），这样「停留 5 秒」在动图里才是 5 秒。超过 10MB 就裁短、降到 8–10fps，或者缩小宽度。
3. **一个动图只讲一件事**：「气泡进场、停留 5 秒、退场」是一个，「悬停时暂停计时」是另一个。动效里有 `prefers-reduced-motion` 分支的，正常和减弱各录一个，并排放。

## 每一项长这样

```markdown
- [ ] 气泡进场、停留 5 秒、退场；点完鼠标还停在按钮上也照常 5 秒消失

  ![气泡停留 5 秒](https://github.com/<owner>/<repo>/blob/idea-loop-evidence-pr-<N>/t03-sentence-fail-dwell.gif?raw=true)
```

- **复选框 + 一句「看什么」+ 素材。** 「看什么」写的是判断标准，不写操作步骤。人看完觉得对就勾上，不对就在下面回一句。
- 按形态分组：流程、动效、样式。
- 只放**脚本判不了、要人判断**的东西。逐格比对已经全绿的静态格不放：放了只会稀释人的注意力。

## 做素材本身就是一道验证

录素材要真的把路径走一遍，常常会走出单测和逐格比对都没抓到的问题。比如：点完按钮鼠标还停在上面，失败提示的计时被当成「悬停」一直暂停，提示永远不消失。

所以**录的过程中看到的行为和验收标准对不上，那是 bug，不是人验项**：执行方当场修、补回归测试，然后重录。只有「行为符合验收标准，但好不好看、顺不顺要人判断」的，才进人验清单。
