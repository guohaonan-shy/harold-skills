目标项目根目录的 `GLOSSARY.md` 是一份术语表，别的什么都不是。每条只回答两件事：这个东西在本项目里叫什么，它是什么。它最常见的坏法是膨胀：把「写进术语表」当成「把每个答案都存下来」，几个月后变成一份 spec。下面的规则都为挡住这一点。

## 收什么：三问全过才收

1. **换实现测试**：把实现整个换掉（改表名、换语言、重写这段代码），这句话还对吗？不对就是实现细节，不收。
2. **项目特有**：这是本项目（或它所在业务领域）的概念，还是通用编程概念？超时、错误类型、工具模式这类，项目用得再多也不收。
3. **真被当名字用，且会叫歧**：它在对话、代码或 spec 里被当成名字使用，**并且**存在不止一种叫法，或者容易跟另一个概念混。只有一种叫法、也不会跟别的概念混的词，收了也没用。

不收的东西去这里：

| 内容 | 去处 |
|---|---|
| 字段取值、枚举编码（`1=active`、`category=2`）、表结构、存储位置 | 目标项目的 `AGENTS.md`（表结构那节）或代码本身 |
| 代码约定（命名风格、下划线还是连字符） | 最近的 `AGENTS.md`，能写成 lint 规则就写成 lint 规则 |
| 指向代码常量或文件的「以 X 为准」 | 对应的 `docs/domain/` 文档或模块 `AGENTS.md` |
| 机制、调研、分类体系、「它怎么运作」 | `docs/domain/` |
| 决策和它的理由 | spec，了结后进 ADR（`idea-loop:wiki-conventions` 的「文件在不在，就是状态」） |

方向是单向的：其他文档用术语表里的叫法，术语表不链回它们。

## 文件与格式

### 位置

- 单一上下文（多数项目）：仓库根目录一份 `GLOSSARY.md`。
- 多上下文：根目录一份 `GLOSSARY-MAP.md`，指向各上下文自己的 `GLOSSARY.md`。先拿子标题分组撑着，只有当文件已经精简、仍然覆盖两块读者不会同时需要的领域时才拆：一份膨胀的文件拆开，只会得到几份膨胀的文件。
- 第一个术语定下来时才建文件。
- 它在 `docs/` 之外，不是 vault 的一部分：不带 frontmatter，不参与 slug 唯一性。

### 格式

```md
# {上下文名}

{一到两句：这个上下文是什么，为什么存在。}

## 术语

### {分组，可选}

**Practice**：
学生可以做的一条练习，属于四种题型之一。
_Avoid_: exercise, drill

**Cause layer**：
一个错词被归到的错误发生位置，三层之一：发音、听力、表达。
_Avoid_: error type, category（Issue 上另有一个也叫 category 的分类，指的是别的东西）

## 歧义词

- **status**：代码里有至少六套互不相关的 status。单独说 status 不成立，必须带上实体名（Practice status、Session status……）。
```

### 词条规则

- **词条名**用项目里实际流通的写法：代码和对话里都这么叫的那个，英文就写英文。
- **定义一到两句，写它是什么，不写它做什么。**
- **要有主见**：一个概念只留一个标准叫法，其余叫法进 `_Avoid_`。`_Avoid_` 里的词可以带一个括号，说清它其实指什么。
- **正文是纯文字**：反引号、文件路径、链接、「数字=含义」这类取值映射一出现，几乎一定是「收什么」里该挪走的东西。
- 自然成簇就用 `###` 分组，否则平铺。二级标题只有 `## 术语` 和 `## 歧义词` 两个。
- 定义用目标项目文档的语言写。

### 歧义词规则

`_Avoid_` 表达的是一个概念对多个词。**一个词对多个概念**挂在哪个词条下都不对，所以单独一节：

- 只有一个词能指两个以上概念时才进这一节；只指一个概念的，写成那个概念的 `_Avoid_`。
- 每条一到两句：这个词可能指哪几样，单独出现时该怎么说。

格式由 `glossary-check.mjs` 机械校验：plugin 的 PostToolUse hook 在每次 Write / Edit 落到名为 `GLOSSARY.md` 的文件时自动跑它，违规写到 stderr、退出码 2，当场改到通过。内容该不该收，它不判断：那是「收什么」和人的事。

## 写：人拍板之后当场写

只有两个入口能写，每次写入都以人当场的拍板为准：

| 入口 | 写什么 | 什么时候 |
|---|---|---|
| `idea-loop:grill` | 新增、改名 | 人答了术语题之后、算下一轮之前，当场写（出题时机在 grill 里） |
| `/idea-loop:dreaming` | 订正、删除 | 对账发现词条过时或跟代码对不上，逐条问人，人同意了才改 |

人没拍板的推荐叫法不写：一份没人审过、由 agent 写的术语表比没有更糟，后面的会话会把臆测当真。

每次写都是改，不是追加：

- 新增一个词，同时处理被它取代的那个：挪进 `_Avoid_`，或者删掉。不留「旧版」小节。
- 一个词条的概念在项目里已经没了，删掉它。
- 健康的术语表变短的次数和变长的一样多。

## 读：所有产出命名的地方

产出里要给领域概念起名时（spec 标题、ticket 标题、测试名、PR 描述、review 发现），读术语表（`GLOSSARY-MAP.md` 列出的每一份都读）：

- 用标准叫法，不用 `_Avoid_` 里的词。
- 碰到歧义词，按那一条说的带上限定。
- 需要的概念术语表里没有：先想一下是不是在造项目里不存在的说法（是就换个说法）；是真缺口，按下面收。

**缺词**：在 grill 里，它就是一道术语题。在别的 skill 里，用一个描述性的说法先把活干完，术语表不动；`idea-loop:pr-review` 的汇报会把这次 PR 里的缺词列出来，由人决定要不要开一轮 grill 定下来。

术语表不存在就照常干活，也不提醒人去建。

目标项目第一次有术语表、或人要求接入（`AGENTS.md` 的读取规则、CI 兜底）时，照 [references/target-repo-setup.md](references/target-repo-setup.md)。
