# 重写 skill、agent 定义时的规则

重写或新写一份 skill、agent 定义时读这份：先过「重写核对表」，命令照「外部工具命令的归类」改，主体字数守「4500 线」，共享规矩按「规矩的归属」只留指针。完成条件：核对表八项每项都过了，怎么验那一栏写的判法跑过。

## 重写核对表

| 核对项 | 改成什么 | 怎么验 |
|---|---|---|
| 只有部分运行才走到的分支移出主文件 | 进这个 skill 自己的 `references/`，主文件留一行指针，写明什么条件下去读 | 判断：Standards 轴对着「信息层级」看分支挪得对不对；字数是机械的那一半，见「4500 线」 |
| 开头写目标和交付物，每步结尾一句完成条件 | 照「步骤与完成条件」 | 判断：Standards 轴 |
| 没有决策历史 | 日期、人说过的话、「当时为什么移到 X」删掉；理由要改变 agent 行为的，只留理由本身。当时的决定在知识库的决定记录和 ADR 里，没在的靠 git 历史 | 搜索，见下面「判法」 |
| 否定句只用在硬护栏上，后面跟着该做什么 | 照「引导词」末段 | 判断：Standards 轴 |
| 反复出现的长句定义收成一个词 | 先找现成的词；新词只在这一份 skill 内定义，不进术语表；要进术语表的，停下问人 | 判断：Standards 轴 |
| 共享的规矩只写一处 | 别处只留指针，不转述；规矩归谁照「规矩的归属」 | 判断：Standards 轴 |
| 调命令行用 `dyna <模块> <命令>` | 命令名以插件最低版本那份命令登记表为准（`idea-loop/dyna-version` 的下限，对应 `dyna/registry/` 里的那份） | 机械：`scripts/dyna-scan.test.mjs` 绿 |
| 不写外部工具的具体命令和次序 | 照「外部工具命令的归类」 | 搜索，见下面「判法」 |

判法（机械的两条；其余交给 review 的 Standards 轴）：

```
# 决策历史：没有输出；例子里的日期、`captured:` 这类格式说明留下，逐处写明为什么留
grep -nE '20[0-9]{2}-[0-9]{2}-[0-9]{2}|人定|原话|依据：' <文件>

# 行内外部命令：命中的只剩适配层文件和标了「坑」的行
grep -nE '`(gh|git) [a-z]' <文件>
```

字数的量法见「4500 线」。

## 外部工具命令的归类

skill 和 agent 定义里每一处外部命令（`gh`、`git` 这类）按四类改写：

- **目标型**：拿信息或做一件常规事，换个命令同样做得到。只写要拿到的东西和完成条件。例：把用 `gh` 读一个 issue 的那条命令，改成「读 issue 全文和评论」。
- **约束型**：做法不对会出事（合并方式、只快进、一个提交、不碰共用的检出目录）。写成结果约束和理由，不写命令。例：把只快进的合并命令，改成「落地只快进，不产生合并提交；快进不了，说明集成分支动过，停下」。
- **坑**：不写那个 flag 就会做错，看帮助也想不到。留 flag，旁边一句为什么。例：被本地排除的目录要加 `-f` 才进得了提交。
- **适配层**：平台或环境的适配参考（issue 的 GitHub 参考、setup 写进目标仓库的模板与前置检查表、运行环境的能力数据）。不动。

工具不可用时，agent 换路（读 prompt 里给的内容、问人），不照一条命令失败。

## 4500 线

`SKILL.md` 与 agent 定义的主体都不超过 4500 字，给以后加分支留至少 500 字余量。主体是去掉文件开头 frontmatter 之后的部分，量法：

```
awk 'f>=2; /^---$/{f++}' <文件> | LC_ALL=en_US.UTF-8 wc -m
```

参考文件不受这条约束；重写一份 skill 时，它指向的参考一起量、一起剪。

## 规矩的归属

共享规矩留在下表那一处，别处只指过去。表外新碰到的，在交回里写一行：规矩、出现在哪几处、建议归谁。

| 规矩 | 归谁 |
|---|---|
| 依据只认三种、交给人的事写成一道题、证据怎么写 | `decision-rules` |
| 知识库落地、项目目录、frontmatter、术语表 | `wiki-conventions` |
| issue 的状态、正文格式、blocked by | `issues` |
| 评论里的 idea-loop 标记（读最近一条带标记的、写时自带） | `issues` 的「评论」 |
| Linear 项目上怎么读写 issue | `issues` 的 Linear 做法 |
| 暂缓的设计（问人要不要接着做、复制回中间物目录、接上中断恢复） | `wiki-conventions`「目录」里 `design/pending/` 那一行 |
| 第 1 轮 review 把实现期间开的存量 issue 列进「已按规则处理」 | `pr` 的 Review 汇报 |
| 执行方交回前要跑的那一组测试 | `implementer` 定义「做」里「交回前跑」 |
| SEO 方向 agent 的提示各行 | `seo-scan` 的 `findings.md`「提示模板」 |
| dreaming 的收尾（推送三种情况、回滚、中间物清理、幂等） | `dreaming` 的 `proposal-table.md`「收尾」 |
| ui-reviewer 的发现文件形状 | `design-archive` 的 `review-walkthrough.md` |
| PR 描述、汇报、review loop 文件、PR 从 spec 提交就挂着 | `pr` |
| red → green、什么测试值得留、只在系统边界 mock | `tdd` |
| 运行环境的能力做法 | `dyna runtime show <能力>` |
| 写法本身（杠杆、量法、命令归类） | `writing-for-agents` |
