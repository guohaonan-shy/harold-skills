# 决定记录的格式

目标仓库的 `docs/raw/decisions/<issue 号>.md`，一个 issue 一份（没有 issue 号时 `<YYYY-MM-DD>-<主题>.md`）。下一次 `idea-loop:retro` 靠它做两件事：数「对题的选择」同一类出现了几次、有没有反例；认出人已经驳回过的候选，不拿同样的证据再提。所以字段名和 `类别` 的写法要稳定，读的人（和脚本）按行首字段找。

```markdown
---
type: raw
source_type: conversation
captured: <YYYY-MM-DD>
title: 决定记录 —— <issue 号 + 标题，或主题>
tags: [decisions]
---

## 题 1：<一句话，摆了什么>

- 类别：<短标签，同一类的题在不同 issue 里用同一个写法，例：边缘情形-不丢数据>
- 摆给人的：<题和选项，推荐的是哪个>
- 人的原话：「<逐字>」
- 做法：<最后怎么做的>
- 情形：<什么情况下>
- 处置：<怎么办>
- 理由：<为什么>
- 不自动的：否 / 是（<`decision-rules`「不自动的」里的哪一项>）

## 候选 1：<一句话，要改什么>

- 信号：纠正与追问 / 对题的选择 / 人自己说的方向
- 原话：「<逐字>」
- 落点：<插件 skill / 目标仓库文件 / 检查>
- 结果：批（<开出的 issue 链接>）/ 不批（<人给的理由，没有就写「无」>）/ 改成（<改成什么，issue 链接>）
```

## 读它的规矩

- **数次数**：按 `类别` 找候选同类，再用 `情形` 和 `处置` 核对是不是真的同一类；类别写法不一样但情形相同的，也算。次数不含「不自动的：是」的题。
- **反例**：同一类里 `处置` 不同的，读它的 `理由` 和 `人的原话` 看差在哪；差别说得出来，提成「规则 + 例外」，说不出来就不提。
- **驳回过的候选**：`结果：不批` 的，同一条 `落点` 加同一类原话，不再提；有了新的证据（新的原话，不是同一句）才再提，并写明上次不批的理由。
- 原话逐字，不改写、不翻译；改了就不能核对。
