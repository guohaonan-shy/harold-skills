摆给人的决定，大部分是重复的：有明文规则的违规、说明文字跟已定做法对不上、跟这次无关的存量问题，人每次都定成同一个答案。所以先写下什么算判得出来：判得出来的立即办、单列出来让人能推翻，其余才问人。

## 自己定的四条

一条处置能从下面推出来，就照办，不问人：

1. **有依据就照办。** 依据只认三种，都要具体：
   - **仓库写下来的规则原文**：`CODING_STANDARDS.md`、`REVIEW.md`、`AGENTS.md` / `CLAUDE.md`、它们链接到的文档、lint 与 typecheck 的配置。能引原文、指出出处。
   - **人在这份 spec 或这个 PR 里已经做过的决定**：原话，来自 spec、工单（「人的决定」）或这个 PR 的 review loop 文件里人的批示。
   - **产品里已有的统一做法**：能指出至少一处现存实例。「大概是这样」不算。

   由此推出的处置：
   - 有明文规则、没有歧义的规范违规：**修**。
   - spec、工单、说明文字跟已定的做法对不上：**本次同步改**。spec 里交代由来的历史段落保留，标明后来改了。
   - spec 没说的界面细节（文案写法、颜色规则等），产品已有统一做法：**沿用**。
   - 执行方超出范围的删除：删掉的东西没有调用方、也没人读，**接受并补记**进工单；删掉的是有人读的信息，或改变了行为，**恢复**。
2. **归不归这次，看依赖。** 这次引入的，这次修。存量问题**开 issue**；例外是它让这次改动拿到错的数据、让这次的结论站不住、或让 CI 变红，这次修。谁去找、谁来开分开看：
   - **审查者不去找存量问题**。它只在存量污染了这次改动、或让 CI 变红时才报，处置是修；跟这次无关的存量，它不找、不报。
   - **跟这次无关的存量，由编排者开 issue**，对象是执行方交回的「顺手发现」：逐条在目标仓库开 issue，不加 `status:*` label（没 label 就是待办，`issue-dispatch` 会接手），写进汇报的「已按规则处理」，人一句话可推翻。
3. **代价跟用户会失去的东西相称。** 会丢用户已交的内容、数据、钱：修。只在兜底路径或罕见异常里出现、又不丢东西：接受，写成已知限制。等待时间、体验上的小代价：接受，上线后看数据。在 PR 流程里这一条只用来定推荐，见下面「PR 流程里『代价相称』只定推荐」。
4. **默认改动最小。** 结构性的重排（目录重构、换框架）不顺手并进来，要做就单独起。

## 依据不成立：交给人

下面这些都不算判得出来，处置写成「要你决定」：

- 规则有歧义，两种读法都说得通。
- 两条规则冲突。
- 要引的「产品已有做法」找不到现存实例。
- 人的决定只覆盖了相邻的情形，要靠推断才能套到这一条上。

**宁可多问，不要靠推断凑出一个依据。** 依据是用来让人一眼核对的，核对不了的依据比没有更糟。

## PR 流程里「代价相称」只定推荐

起草 spec 时，起草方直接按「代价相称」定，人审 spec 时会看到。到了 PR 流程（停下汇报和 review 轮次），边缘情形（只在兜底路径或罕见异常里出现、不丢东西）照旧是「要你决定」，这条只用来定推荐，不进「已按规则处理」。

理由：用户会不会丢东西，这个判断本身可能判错，判错的代价是丢用户的数据；而且被人推翻的记录还不多。等 `dreaming` 回看已合并的 PR 积累够了，再考虑升级成自动处置。

## 不自动的

下面这些只由人定，没有「照规则」这个处置：

- 起名定稿（新词只在 `grill` 里加）
- 人验素材
- 分类体系怎么切
- 方案形状被人提出第三条路的
- 对外发布
- 动生产业务数据
- 合并改了代码的 PR。只改 `docs/` 的 PR（spec PR、设计 PR）检查全过就合并：它们只是把这一段定下的东西放进主分支，让下一段从主分支接着做

## 照规则的处置，人能推翻

- 汇报里在别的内容之前单列一节「已按规则处理」，每条一句：做了什么、依据是什么、提交或 issue 链接。
- 人说一句「推翻某条」，编排者当作一条新批示：原话逐字记下，按人的意思改回或改做；之后不再按同一依据把它标成照规则。
- 所以每条照规则的处置都要留得下依据：原文、出处、实例，不能只留一句「按规则」。

## 交给人时

依据不成立、真要人拍板的题（spec「实现决策」里的选项、实现时停下汇报的决定题、review 汇报里的「要你决定」），摆给人之前先做完下面三件事。目的只有一个：人读一遍就懂、答一次就完，不用回头追问「现在到底是怎么做的」「有多少」「这个记号是什么意思」。这一半没有脚本校验，靠写题的人逐条自核。

### 现状先查清

- 题里每句关于现状的话，都核过代码、数据或文档，能说出出处（在哪、什么时候查的）。「应该是」「大概」不进题。
- 讲影响带规模数字：不写「不少用户会遇到」，写「最近 30 天 12 次」。查不到数字，写明没查到和原因，不估。
- 同一行为的其他入口查过：同一个能力还有哪些页面、接口、调用方走同一条路。写明每个是纳入还是排除，排除的给一句理由。
- 相邻还没完成的 spec、issue 查过，写明有没有重叠；有的，写明谁先谁后、互相依不依赖。
- 出题前对着最新的基准分支再核一次。别人刚合进去的改动，可能让题的前提过期；前提变了，题重写或撤掉。

### 先写交付物，再列做法

- 先写用户最终得到什么、由哪些输入决定，再列实现方式。方案的形状在这一步定，写反了，选项就会落在错的层次上。
- 选项之间要有用户能感到的差别。只差在内部结构、用户感觉不到的，不是选项，是实现细节，按「默认改动最小」自己定。
- 每个选项牵出的后续写全：选了它，哪些中间状态要处理（做到一半被打断、取消后回到哪一步、已经产生的数据怎么办）。
- 改了 spec 的文字，图和测试表同步改。图停在旧版本，等于让人在对不上的两份东西之间选。

### 每个问题、每个选项配具体例子

- 每个问题、每个选项各配一个具体例子：一个真实的输入，走一遍，看到什么、本该看到什么。
- 陌生记号先解释：缩写、内部术语、符号，第一次出现时说清它是什么。
- 不用裸编号指代选项，也不用别处定义的编号指代内容：写出它是什么。选项自己的 A / B 标签可以用，引用时带上半句内容。
- 比对类证据在同条件下做：同语言、同数据、同版本、同设备。条件对不上，证据不能拿来比。
- 要人评判文案或素材时，先给评判标准：评判什么、好和不好各长什么样。没有标准的评判题，人只能凭感觉答，下一次又得再答一遍。
