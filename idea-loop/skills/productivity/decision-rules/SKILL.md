摆给人的决定，大部分人每次都定成同一个答案。所以先判这条能不能从下面的规则推出来：推得出来的立即办、单列出来让人能推翻，推不出来的才问人。

## 自己定的四条

一条处置能从下面推出来，就照办，不问人：

1. **有依据就照办。** 依据只认三种，都要具体：
   - **仓库写下来的规则原文**：`CODING_STANDARDS.md`、`REVIEW.md`、`AGENTS.md` / `CLAUDE.md`、它们链接到的文档、lint 与 typecheck 的配置。能引原文、指出出处。
   - **人在这份 spec 或这个 PR 里已经做过的决定**：原话，来自 spec、工单（「人的决定」）或这个 PR 的 review loop 文件里人的批示。
   - **产品里已有的统一做法**：能指出至少一处现存实例。「大概是这样」不算。

   由此推出的处置：
   - 有明文规则、没有歧义的规范违规：**修**。
   - spec、工单、说明文字跟已定的做法对不上：**本次同步改**。spec 里交代由来的历史段落保留，标明后来改了。
   - spec 没说的界面细节（文案写法、颜色规则等），产品已有统一做法：**沿用**。
   - 执行方超出范围的删除：删掉的东西没有调用方、也没人读，**接受并补记**进工单；删掉的是有人读的信息，或改变了行为，**恢复**。
2. **归不归这次，看依赖。** 这次引入的，这次修。存量问题**开 issue**；例外是它让这次改动拿到错的数据、让这次的结论站不住、或让 CI 变红，这次修。
3. **代价跟用户会失去的东西相称。** 会丢用户已交的内容、数据、钱：修。只在兜底路径或罕见异常里出现、又不丢东西：接受，写成已知限制。等待时间、体验上的小代价：接受，上线后看数据。PR 流程里这一条只定推荐，见下面那一节。
4. **默认改动最小。** 结构性的重排（目录重构、换框架）单独起，不顺手并进来。

## 依据不成立：交给人

下面这些都不算判得出来，处置写成「要你决定」：

- 规则有歧义，两种读法都说得通。
- 两条规则冲突。
- 要引的「产品已有做法」找不到现存实例。
- 人的决定只覆盖了相邻的情形，要靠推断才能套到这一条上。

**宁可多问，也不靠推断凑出一个依据。** 依据是让人一眼核对的，核对不了的依据比没有更糟。

## PR 流程里「代价相称」只定推荐

起草 spec 时，起草方直接按「代价相称」定，人审 spec 时会看到。到了 PR 流程（停下汇报和 review 轮次），边缘情形（只在兜底路径或罕见异常里出现、不丢东西）照旧是「要你决定」，「代价相称」只用来定推荐，不进「已按规则处理」：用户会不会丢东西这个判断本身可能判错，判错的代价是丢用户的数据。

## 不自动的

下面这些只由人定，没有「照规则」这个处置：

- 起名定稿（新词只在 `idea-loop:grill` 里加）
- 人验素材
- 分类体系怎么切
- 方案形状被人提出第三条路的
- 对外发布
- 动生产业务数据
- 合并改了代码的 PR。只改 `docs/` 的 PR（spec PR、设计 PR）检查全过就合并：它们只是把这一段定下的东西放进主分支，让下一段从主分支接着做

## 照规则的处置，人能推翻

- 汇报里在别的内容之前单列一节「已按规则处理」，每条一句：做了什么、依据是什么、提交或 issue 链接。
- 人说一句「推翻某条」，就是一条新批示：按人的意思改回或改做，之后不再按同一依据把它标成照规则。
- 所以每条照规则的处置都留下依据本身：原文、出处、实例，而不只是一句「按规则」。

## 交给人时

题要摆给人（spec「实现决策」里的选项、停下汇报的决定题、review 汇报里的「要你决定」）时，先照 [references/handing-to-human.md](references/handing-to-human.md) 做完三组功课：现状先查清、先写交付物再列做法、每个问题和选项配具体例子。
