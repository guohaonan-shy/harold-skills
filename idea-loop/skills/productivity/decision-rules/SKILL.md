这份管两件事：一条处置自己定还是交给人，以及写给人看的东西里的证据怎么写。前六节讲处置，后三节讲证据。每个处置做到有依据可指、或已摆成一道题；每份给人看的东西做到逐条过完「证据是什么」「整体风格」。

## 核心

按 spec 的方案解决 spec 提出的问题。每个处置先问：它是不是在解决这份 spec 的问题、是不是照 spec 的方案。spec 之外的事不在这次做，交回调用方自己的流程。

## 依据只认三种

都要具体，能让人一眼核对：

- **仓库写下来的规则原文**：`CODING_STANDARDS.md`、`REVIEW.md`、`AGENTS.md` / `CLAUDE.md`、它们链接到的文档、lint 与 typecheck 的配置。引得出原文、指得出出处。
- **人已经做过的决定**：逐字引出人说的话，来自 spec、工单或这个 PR 的 review loop 文件里人的批示。
- **产品里已有的做法**：指得出至少一处现存实例。「大概是这样」不算。

## 依据明确、没冲突：照标准做

照依据做，不问人。汇报里在别的内容之前单列一节「已按规则处理」，每条一句：做了什么、依据本身（原文、出处、实例，不只是一句「按规则」）、提交或 issue 链接。

人说一句「推翻某条」，就是一条新的人的决定：按人的意思改回或改做，之后同一依据不再标成照规则。

## 依据冲突或没有：停下问人

下面这些都算依据不明确，停下，摆成一道题给人：

- 两条依据冲突，或一条规则两种读法都说得通。
- 指不出现存实例。
- 人的决定只覆盖了相邻的情形，要靠推断才能套到这一条上。
- 三种依据都没有。

宁可多问，也不靠推断凑出一个依据；核对不了的依据比没有更糟。人当场的判断会纠正项目的上下文。

## 护栏

下面这些只由人定，没有「照规则」这个处置：

- 术语：起名、改名、定稿（新词只在 `idea-loop:grill` 里加）
- 动生产数据
- 真实支付
- 对外发布
- 合并改了代码的 PR。知识库的改动不开 PR，直接提交到 home（`idea-loop:wiki-conventions` 的「知识库落地」）

**SEO 例外**：`type:seo/*` 的 issue 的 PR，下面三条都满足，由 Claude 合并；缺一条回到「只由人定」：

1. `REVIEW.md` 的检查与 `dyna seo check` 全过。
2. 两轴没有阻塞项：这一轮没有要修的、没有要交给人决定的事。
3. `dyna seo scope` 判定改动只落在内容范围内：`SEO.md`「构建与检查」的「内容路径」。`docs/` 和 `SEO.md` 在项目目录里，不在代码 PR 里。

上线自查失败时开的 revert PR，检查过了也由 Claude 合并。例外只放开合并，其余护栏照旧。

## 要人定的写成一道题

- 选项之间差在读者能感到的地方；只差内部结构的是实现细节，自己定。
- 每个选项配一个真实例子：一个真实的输入，走一遍，看到什么、本该看到什么；能从项目已有材料取就取。
- 给推荐和一句理由。
- 范围题（冒出的改动并进当前 PR，还是另开）：冒出的问题影响这份 spec 的实现，或者上线后会有影响，推荐在当前 PR 里修；其余的推荐不进当前 PR，交回调用方自己的流程。
- 要人评判文案或素材时，先给评判标准：评判什么、好和不好各长什么样。
- 题里的现状和证据照下面的「证据是什么」写。

## 证据是什么

证据支撑一个观点、想法或决策。读的人清楚方向和高层设计，不清楚实现细节，要靠证据快速看懂这件事、快速做出判断，不用回头追问「现在到底是怎么做的」「有多少」「这个词是什么意思」。

- **关于现状的话带出处和规模数字。** 每句现状说得出在哪、什么时候、对着哪个基准或版本查的；讲影响带数字；查不到就写明没查到和原因。出题前对最新基准再核一次，前提变了就重写或撤掉。
- **比对类证据在同条件下做**：同语言、同数据、同版本、同设备。条件对不上，就不拿来比。
- **复现才是证据。** 凭读代码写出来的根因是猜测；用户看得见的问题，按用户的操作把路径真的走一遍；后端和数据的问题，原样贴查询结果、日志、接口响应，标上条件和时间。没复现的写明没复现、卡在哪、依据是什么。
- **证据取自要判断的那个东西本身**：判断问题，取自复现；判断设计，取自冻结画布；判断交付，取自实现。原样取用。

## 整体风格

- **结论在前。** 先说对读者来说什么变了（用户看到什么、哪条规则改了），再讲怎么做的。
- **图文结合，图放在它支撑的那句话旁边**。用能说清要点的最小一种视图；一句话说清的，只写这句话。
- **陌生叫法第一次出现就说清，落到一个具体对象上。** 缩写、内部术语、流程里的叫法（例：「这批题」写成「上周新增的 15 套样题」），说清它是什么、在哪。指它用具体的叫法，不用裸编号；引用编号时带半句内容。
- **叠上去的东西要说明**：为了让人看懂而叠加的光圈、鼠标位置点、角落的秒表不属于产品，在这一组图的开头用一句话说明。

写完逐条对过一遍，每条说得出在哪句话上做到了；这部分没有脚本校验。

## 配什么图：你来判断

看这条证据要人判断的是什么，挑最快能让人看懂的那一种。可用的：

- **UI 页面标注**：截图只截那个组件（必要时连同它弹出的浮层），2 倍像素密度，用产物的主语言，手机宽度默认 390；红色光圈圈出要看的地方，旁边一两句说明。
- **UI flow 标注**：多张截图横排，箭头上写触发条件，截图下一句状态，红色光圈圈出要看的地方；并排对照（之前 / 之后、静止 / 悬停）也用它。拼图只用 `dyna design flow compose`，同一组图才长得一样；构图规则、JSON 格式和命令读 `${CLAUDE_PLUGIN_ROOT}/skills/productivity/decision-rules/references/ui-flow.md`。
- **图表**：用 Skill 工具调 excalidrawer 的入口 skill（`excalidrawer:sequence` 时序、`excalidrawer:tree` 树、`excalidrawer:flowchart` 流程、`excalidrawer:state-machine` 状态、`excalidrawer:comparison` 对比、`excalidrawer:chart` 柱状 / 折线等）。没装 excalidrawer 时用 mermaid。
- **动图**：动起来哪里不对、动效顺不顺。怎么录、怎么转、体积怎么控，读 `${CLAUDE_PLUGIN_ROOT}/skills/productivity/decision-rules/references/gif.md`。
- **表或一行例子**：规则覆盖了谁（场景 × 有没有覆盖），数值对不对（输入 → 之前的结果 → 现在的结果），直接写进正文。

图放在哪、文件怎么起名、要不要上传，由调用你的 skill 定，这里不管。
