## 核心

按 spec 的方案解决 spec 提出的问题。每个处置先问：它是不是在解决这份 spec 的问题、是不是照 spec 的方案。spec 之外的事不在这次做，交回调用方自己的流程。

## 依据只认三种

都要具体，能让人一眼核对：

- **仓库写下来的规则原文**：`CODING_STANDARDS.md`、`REVIEW.md`、`AGENTS.md` / `CLAUDE.md`、它们链接到的文档、lint 与 typecheck 的配置。引得出原文、指得出出处。
- **人已经做过的决定**：原话，来自 spec、工单或这个 PR 的 review loop 文件里人的批示。
- **产品里已有的做法**：指得出至少一处现存实例。「大概是这样」不算。

## 依据明确、没冲突：照标准做

照依据做，不问人。汇报里在别的内容之前单列一节「已按规则处理」，每条一句：做了什么、依据本身（原文、出处、实例，不只是一句「按规则」）、提交或 issue 链接。

人说一句「推翻某条」，就是一条新的人的决定：按人的意思改回或改做，之后不再按同一依据把它标成照规则。

## 依据冲突或没有：停下问人

下面这些都不算依据明确，停下，摆成一道题给人：

- 两条依据冲突，或一条规则两种读法都说得通。
- 指不出现存实例。
- 人的决定只覆盖了相邻的情形，要靠推断才能套到这一条上。
- 三种依据都没有。

宁可多问，也不靠推断凑出一个依据：核对不了的依据比没有更糟。人当场的判断会纠正项目的上下文。

## 护栏

下面这些只由人定，没有「照规则」这个处置：

- 术语：起名、改名、定稿（新词只在 `idea-loop:grill` 里加）
- 动生产数据
- 真实支付
- 对外发布
- 合并改了代码的 PR。只改 `docs/` 的 PR（spec PR、设计 PR）检查全过就合并：它们只是把这一段定下的东西放进主分支，让下一段从主分支接着做

## 要人定的写成一道题

- 选项之间差在读者能感到的地方；只差内部结构的是实现细节，自己定。
- 每个选项配一个真实例子：一个真实的输入，走一遍，看到什么、本该看到什么；能从项目已有材料取就取。
- 给推荐和一句理由。
- 要人评判文案或素材时，先给评判标准：评判什么、好和不好各长什么样。
- 题里的现状和证据照 `idea-loop:evidence` 写。
