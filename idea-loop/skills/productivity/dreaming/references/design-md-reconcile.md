# `DESIGN.md` 对账：dreaming 特有的部分

候选蒸馏是把候选往 `DESIGN.md` 里收；对账方向相反：拿 `DESIGN.md` 现有的内容去量代码，再按写入标准体检。判据、对账表、写入流程都在 design-modeling：用 Skill 工具调 `idea-loop:design-modeling`，看它的「五条写法规则」「各章写什么」「准入分层表」「明确不进 DESIGN.md 的内容」「对账」「一次写入怎么走」「新建」。对账表的每一行怎么判，只按「对账」。这份只写 dreaming 特有的：只出提议、怎么落进提议表。

## 先找文件

照「一次写入怎么走」的「找文件」：`git ls-files | grep -i 'DESIGN.md$'`。一份就地对；多份（多个 app）就问人这次对哪一份，没人可问时每一份各出一组行，对象列写清路径。

**一份都没有**：这里兜底新建（第一份通常由 `/idea-loop:uiux-imagine` 开工时写），先判来源（「新建」）：

- 项目有线上 UI → 提议段照「新建」里的「有线上 UI：从代码量」，量出的三桶（一致 / 不一致 / 偶然）分开写进「证据」，`DESIGN.md 条目` 一行，处置 `新建 DESIGN.md`，起草的整份文件放进 Artifact 或证据格里指向的文件。
- 没有 UI 或 UI 还是占位 → 不写，也不进表；在会话汇报里提一句「项目没有 `DESIGN.md`，也没有可量的 UI」。

## 提议段：量，不写

对账只读：读 `DESIGN.md`、读代码、在 `DESIGN.md` 上跑官方 lint（`npx -y @google/design.md@latest lint <路径>`，只报告，不改文件）。把「对账」的发现落进 `DESIGN.md 条目` 一节，每处一行：

| 「对账」的发现 | 提议表里 | 处置 |
|---|---|---|
| 法和代码对不上 | 一行写法与代码各是什么；法错了还是代码错了由人判 | `交人裁决`；「选项」写 A 改法 / B 代码错。选 B 时在 `缺陷` 一节起草一行（`法对代码错：…`，处置 `开 issue`） |
| 不该在文件里的内容（「明确不进 DESIGN.md 的内容」表里的各行） | 点名是哪一行、属于哪一类 | 页面决定 `移出`（留在档案）；历史叙事、划掉的条目 `删除`；缺陷 → `缺陷` 一节起草 issue |
| 先例 / 判例 / 带日期的条目 | 点名那一条的日期或判例结构 | 被多处遵循的 `改写为全局规则`（证据格写出无日期的新文，并入哪一章）；其余 `移出` 或 `删除` |
| 被取代的内容 | 点名取代它的是哪一条 | `删除` |
| 同一规则的两种写法 | 点名两处位置 | `合并为一条` |
| 官方 lint 的 warning | 原文 warning | `处理 lint 警告`（改 token / 补 `omitted` 说明 / 交人裁决三选一写在「选项」里） |

- **证据格放旧文与新文并排**，写「依据：」点名标准，要求见 [proposal-table.md](proposal-table.md) 的「证据格要有的东西」。依据只认三种：design-modeling 的具体一节或一条，官方 design.md 规范的某一条，或这次 lint 实际输出里的规则名（如 `orphaned-tokens`、`contrast-ratio`）。说不出依据的修改不提：那是品味，不是维护。
- **交给人时出维护卡**：格式见 [review-page.md](review-page.md) 的「维护卡」；法和代码对不上时必须带取自实现的实测截图。
- 「法对代码错」的缺陷起草成目标仓库的 GitHub issue（哪条规则、现在是什么样、本该是什么样、一段引文），怎么开见 [proposal-table.md](proposal-table.md) 执行段的 `缺陷` 一行。
- **健康信号**（「对账」末段）：这份文件变短的次数应该和变长一样多。一次对账提议全是加、没有减，多半是把盘点当成了法，回头再过一遍。

## 执行段

人批了的行，照「一次写入怎么走」落笔：备份 → 起草 → 人确认措辞 → 只改批过的 → lint 与 diff。提议段永远不写 `DESIGN.md`；人在会话里批过、又确认了措辞，才写。人拒绝写文件，就把内容以文字交回。落笔后的 `DESIGN.md` 随执行段那个只改知识库的 PR 提交。
