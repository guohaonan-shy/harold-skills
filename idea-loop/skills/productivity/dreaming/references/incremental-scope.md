# 对账范围：截图对账这次对哪些状态

dreaming 每周由桌面 app 的定时任务自己跑一次（`/idea-loop:setup` 建的）。截图对账要把档案里的状态一个个重新驱动、拍图、比对，状态多了很贵，所以**只对上次以来代码动过的状态做**；档案对象的源码检查不开浏览器，每次都是全量。

只在项目有设计档案、`prod/` 里有对象、要起 ui-reviewer 的时候做这一步。项目没有设计档案、或 `prod/` 为空（走全站初扫），这一步和提议表开头的那一行都不用写。

## 先定全量还是增量

按顺序，第一条成立就停：

| 条件 | 范围 | 提议表那一行写的原因 |
|---|---|---|
| 人调用时明确说了「全量」 | 全量 | 人说了全量 |
| 取不到定时任务（会话里没有 `mcp__scheduled-tasks__list_scheduled_tasks`，或没有 `dreaming-<仓库名>` 这个任务） | 全量 | 没有定时任务 |
| 定时任务没有一次状态为 `succeeded` 的执行 | 全量 | 定时任务还没有成功跑过 |
| 找不到基准提交（见下） | 全量 | 找不到那一刻的提交，并写出为什么 |
| 以上都不是 | 增量 | 自哪天的哪个提交起 |

**手敲的那次用同一个基准，不推进基准**：基准只取定时任务自己的执行记录，人手敲的 dreaming 不在这个任务的记录里，所以它不会让下一次定时执行的起点往前走。

## 基准提交

1. 任务 id 是 `dreaming-<仓库名>`，仓库名取主 checkout 的目录名（`git rev-parse --show-toplevel` 的最后一段），跟 `/idea-loop:setup` 建任务时用的一样。`list_scheduled_tasks` 里没有这个 id，不去猜别的任务，按上表走「没有定时任务」。
2. `mcp__scheduled-tasks__list_task_runs`，`taskId` 填上面的 id，`limit` 取 50，从新到旧找第一条 `status` 是 `succeeded` 的，记下它的 `started_at`。这一次自己若就是定时任务起的，它的状态是 `running`，不会被选中。
3. 起环境时已经 `git fetch`。找 `origin/<基准分支>` 在那一刻的提交：`git rev-list -1 --first-parent --before="<started_at>" origin/<基准分支>`。输出为空（那一刻之前基准分支上还没有提交）就走「找不到基准提交」。

得到的提交就是**基准提交**。

## 挑状态

增量时，在这次的 worktree 里跑档案查询的 `affected`：

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/design-archive-query.mjs" <worktree 根> affected <基准提交>
```

它交回从基准提交到现在（这个 worktree 的 HEAD 就是 `origin/<基准分支>`）受影响的状态清单：改过的文件是某页面登记的代码，这页的全部状态都算；是某组件登记的代码，用到它的状态都算（列在状态里的、边上用到的、页面区域里摆着它的）；被这些页面或组件的代码直接 import 的数据、样式、静态资源改了，也算它们改了（只追一跳、只认相对路径）。返回里的 `states` 就是交给实时波的清单，`totalStates` 是档案一共多少个状态；MCP 里同一个问法叫 `design_affected`。

这个清单**只用来定实时波对哪些状态拍图比对**：

- 清单为空：实时波一个状态都不跑，提议表那一行写「改过的代码没有牵到任何状态」。起 ui-reviewer 的第一批照旧（源码波每次全量，只在第一批跑），状态清单给空。
- 清单不空：照 [archive-reconcile.md](archive-reconcile.md) 的「实时波」派工，状态清单就是它；状态多要分批时，也只在这份清单里分。
- 全量：清单取自 `prod/index.md` 的页面清单，对每页跑 `query page <页面名>` 拿它的状态，原来怎么做还怎么做。

## 提议表开头那一行

不管全量还是增量，提议表标题下面第一行写这次的范围（给人看，也让人知道下一次可以怎么补）：

```markdown
对账范围：增量——自 2026-10-12 的提交 a1b2c3d 起，改过的代码牵到 3 个状态（档案共 42 个）
对账范围：全量——人说了全量，对了 42 个状态
对账范围：全量——没有定时任务，对了 42 个状态
```

三样都要有：全量还是增量、为什么、对了几个状态。增量写基准提交的日期与短 SHA 和「档案共几个」，让人看得出省了多少。

## 两个例外

- **上一张提议表还没批又到点了**：照常跑，不合并两张表。新提议表在范围那一行后面再写一行「上一次（<日期>）的提议表还没处理」。怎么知道还没处理：每次的提议表放在各自 worktree 的 `.tmp/dreaming/<日期>/proposal.md`，处理完（执行了批了的行，或人把每一行都回了「不批」）就删掉那个日期目录，空表交出「这次无事」后也删；所以在 `git worktree list` 列出的别的 worktree 里，`.tmp/dreaming/<别的日期>/proposal.md` 还在、跑 `proposal-table-check.mjs --json` 的 `empty` 是 `false`，就是上一张还没处理，日期取目录名。多张取最近一张。没有就不写这一行。
- **没跑成的批**：实时波交回 `incomplete` 的批，写在提议表末尾（见 [archive-reconcile.md](archive-reconcile.md)「实时波」第 3 步），后面附一句「下次可说全量补上」。基准是按定时任务「成功」前推的，一次执行成功了但这一波没跑成，基准照样往前走：这是已知缺口，靠这一行让人看到，下次调用时说「全量」补上。
