# 候选蒸馏：dreaming 特有的部分

把设计档案里的「设计法候选」收进项目的 `DESIGN.md`。判据、写入流程、单条蒸馏的步骤都在 design-modeling：用 Skill 工具调 `idea-loop:design-modeling`，看它的「五条写法规则」「维护原则：整改优先于追加」「准入分层表」「明确不进 DESIGN.md 的内容」「蒸馏」「设计法候选的形态」，判断一条候选该不该进、进哪，只按那几节。这份只写 dreaming 多出来的：候选从哪找、对账时怎么出提议、批了之后怎么收尾。

## 三种来源

| 来源 | 怎么找 | 提议表里写什么 |
|---|---|---|
| **对象正文里的候选** | 设计档案里 page / component / motion / journey 文件的固定一节「## 设计法候选」；档案还没落地的项目，找冻结记录 `docs/design/tmp/<slug>/canvas/<slug>-design.md` 的同名一节。整节只有一行「无」就跳过 | 候选原文（一句规则 + 并进 / 为什么 / 证据，「设计法候选的形态」的形态） |
| **多个档案组件重复的做法** | 对账的源码波顺带数：同一种配方（内边距、圆角、状态处理）出现在多个组件对象里 | 次数和重复它的组件名，先补成「设计法候选的形态」那样的一条候选 |
| **被多处引用的动效** | 查询入口反查每个动效对象被多少节点、边引用；档案没落地时数 wikilink | 引用次数和引用方，补成一条候选（该并进 Motion 章的哪条全局原则） |

后两种不设阈值：档案刚建时次数都很小，定死的数字要么永远不触发，要么一建好就全触发。次数和引用方摆给人，由人判。

## 提议段：每条候选一行

每条候选在 `候选` 一节占一行（行的形状见 [proposal-table.md](proposal-table.md)），逐条做：

1. **过分层表**：「准入分层表」，说出去向和一句理由。拿不准落在哪两层，就把两个候选层和各自的理由写进「选项」，由人选。
2. **先整改后追加**（「维护原则：整改优先于追加」）：在 `DESIGN.md` 里先找受它影响的已有内容：矛盾、过时、已覆盖。能改写或删除的就提议改写或删除；已覆盖的什么都不加；只有缺这一处才提议追加，追加时同步 front matter 的 token。所以建议处置的次序是：`改写已有规则` 优先，其次 `已覆盖不加`，最后才是 `追加新规则`。「发现」格写清楚找过哪些已有内容。
3. **证据格放图、去处和旧文新文并排**：这条规则说的那块界面的截图（先从设计档案取，没有再从实现截，见 [review-page.md](review-page.md) 的「全页共用」）；进 `DESIGN.md` 的写「并进：<章 · 条>」和 `旧：「…」→ 新：「…」`（追加写 `旧：无 → 新：「…」`）。
4. **交给人时出候选卡**：格式见 [review-page.md](review-page.md) 的「候选卡」。

不进 `DESIGN.md` 的候选，按「蒸馏」的去向分走，落到表里是这几个：

| 去向 | 建议处置 |
|---|---|
| 页面或组件自己的「决定」 | `留在原处` |
| 通用设计原则（换个产品也成立） | `起草通用原则 issue`（标题 + 原则 + 来源 + 建议落点，写在「证据」格） |
| 现状、缺陷（说的是「现在什么样」） | `起草缺陷 issue`：起草成目标仓库的 GitHub issue，同时在 `缺陷` 一节有对应的一行；design-modeling 里这一类若仍指向别处，以这里为准 |
| 驳回 | `驳回`，一句理由 |

**默认等那一页上线**（「蒸馏」）：页面对象还在 `tmp/`、没进 `prod/` 的候选不进表，它们还没合并，归各自的需求。人要求提前的，在「发现」里注明「未经线上验证」。

## 执行段

人批了、在会话里确认了措辞的行，逐条照 `idea-loop:design-modeling` 的「一次写入怎么走」落笔（备份 → 旧新并排 → 人确认措辞 → 只改批过的 → lint + diff）。提议段只出提议。

- 一批候选里有几条要进 `DESIGN.md`，合成一次写入、一次 lint。
- **处理完的候选从档案对象里删掉**（经 `delta/` 加归档脚本，见 [proposal-table.md](proposal-table.md) 的「执行段」），去向（落进哪一章 / 开了哪个 issue / 留在原处 / 驳回理由）记在这次 PR 的正文里。
- 整节删空时写一行「无」：空着分不清是没有还是漏了。
- 两种 issue 都是人批了才开：通用原则 issue 的命令照「蒸馏」，缺陷 issue 照 [proposal-table.md](proposal-table.md) 执行段的 `缺陷` 一行。
- 不批的候选原样留着，下一次对账再出现，这是正常的。

## 单条蒸馏

人在会话里口述一条视觉规则、调用时带上它：只处理这一条，不开浏览器、不起开发服务、不跑其它任何一部分、不出提议表。步骤逐字照 design-modeling「蒸馏」指到的「单条蒸馏」（补成「设计法候选的形态」→ 过分层表 → 先整改后追加 → 旧新并排 → 等人确认 → lint 与 diff）。

- 补不出「证据」就问人。
- 人确认之后，在一个从 `origin/<基准分支>` 新切的 worktree 里落笔，开只改 `DESIGN.md` 的 PR，跟对账的执行段一个去处。
