# design-modeling

**项目 `DESIGN.md` 只有一个写入者，就是你。** 它写的是这个产品的视觉语言：用自然语言写，跨页都必须服从。它不是「关于设计的一切」的收件箱。

> 先读一次 `../../references/wiki-conventions.md`（`docs/` 的目录与状态约定）。
>
> **格式只认官方 spec，每次运行现读**：`npx -y @google/design.md@latest spec`。不在本 skill 里复述它——复述的那份会落后于 CLI，而 hook 和收尾校验用的都是最新版。本 skill 只写 spec 管不到的东西：什么该进（§2）、内容怎么写（§7）、候选长什么样（§8）。

为什么只有一个写入者：一份真实项目的 `DESIGN.md` 曾经有六个以上的写入口，每个入口判断「该不该进」的标准都不一样，最后它长到六百多行，混进了代码行号、已知缺陷、迁移计划和历史叙事。唯一写入者的作用不是拦截（格式有 hook 里的官方 lint 管），而是让「该不该进」的判断标准只有一份。

## 0 谁调、什么时候调

- **`uiux-imagine` 选定语言之后**，在同一个会话里调你的新建模式。选定的色彩角色、字体、实测对比度都还在上下文里，这正是要在这里接住的原因。
- **人直接调**，通常是蒸馏（「把这几页的候选处理一下」）或对账（「DESIGN.md 跟代码还对得上吗」）。
- **别的 skill 或会话想改 `DESIGN.md`**，都应该转到这里。

你是模型可调用的，这意味着你可能在人没盯着的时候被调起来。所以**每一次写入都停下来等人确认措辞**（§5），模型可以起草，不能自己落笔。

## 1 先找文件，再判模式

**找文件**：`git ls-files | grep -i 'DESIGN.md$'`。

- 只有一份，就地维护，不搬家。
- 有好几份（monorepo 的多个 app），问人这次动哪一份。
- 没有，新建在仓库根，除非人指定了某个 app 目录。refine 和 imagine 都从项目根或 app 根读它。

**判模式**，判完先说出来再动手：

| 项目状态 | 模式 |
|---|---|
| 没有 `DESIGN.md` | **新建**（§3） |
| 有，且冻结记录里有未处置的候选，或人口述了一条规则 | **蒸馏**（§4） |
| 有，人要求核对，或这份文件不是你写的、你第一次接手 | **对账**（§6） |

一次运行可以先对账再蒸馏，但两种模式的写入分开确认。

## 2 准入分层表——每条内容都先过它

从上往下问，**第一个命中的就是去处**：

| 层 | 去处 | 判据 |
|---|---|---|
| 工作流 | idea-loop plugin 的 `skills/*/SKILL.md` | 说的是环怎么跑 |
| 通用设计原则 | idea-loop plugin 的 `references/design/` | **换一个产品照样成立** |
| 产品视觉语言 | 项目 `DESIGN.md` | 只对这个产品成立，**而且跨页都要服从** |
| 页面决定 | 那一页的冻结记录 `docs/design/<slug>/` | 只对这一页成立 |
| 现状、缺陷、迁移 | `docs/quality-backlog.md` / spec | 说的是「现在什么样」，不是「应该什么样」 |

两个用来校准的判例：

- **「营销页的图像语言是无人静物摄影」被判错。** 同一页就用了静物照、线稿、生成插图、代码动效四种，图像风格是按每页内容选的。这是页面决定，不是产品视觉语言。
- **所有介绍页共用的收尾渐变从没进过 DESIGN.md，是漏了。** 它跨页、只属于本产品，正好在产品视觉语言那一层。

产品视觉语言这一层还收一类常被漏掉的内容：**页面家族的复用机制**，比如一组同类页面共用的构图顺序。它跨页、只属于本产品、能被检查。

拿不准落在哪一层时，把两个候选层和各自的理由摆给人，由人定。不要为了让文件看起来完整而往 DESIGN.md 里塞。

## 3 新建

先判是哪一种来源，并说出来：

### 3.1 有线上 UI——推断

**量，不凭印象。** 从代码与真 DOM 的 computed style 读出字阶、间距节奏、圆角、边框粗细、阴影、颜色在实际用法里的角色，以及实测对比度。浏览器怎么读见 `../../references/design/browser-usage.md`，对比度判据见 `../../references/design/accessibility-baseline.md`。

量出来的值分三桶，**分开报告**：

- **一致的**：候选底线。
- **不一致的**：开放问题，交人裁决，裁决之前不入法。
- **偶然的**：没人选过的框架默认值，不入法。

把一个不一致的值写成底线，等于把一次意外冻结成法。三个占位页面量出来的「语言」也不是语言——UI 还是占位的项目按 3.2 走。

### 3.2 没有 UI——接 imagine 的选择

只接 `uiux-imagine` 语言高度已经选定的东西。缺任何一样就问，不猜不补：

- 色彩角色：ground / ink / accent / 语义状态色，每个角色一句用途；
- 字体与字阶：每个字体家族承担的角色；
- 形状语言：圆角、边框、层次；
- register：这个产品有几个 register，各自多安静或多活；
- 每一对角色色的**实测**对比度；
- 锚点（可选）：imagine 选定的 brand board 路径。有就在 Overview 里指过去，你不负责产出它。

**单独被调用、项目既没有 UI 也没走过 imagine：拒绝，指回 `uiux-imagine` 的语言高度。** 从零立一套视觉语言需要先出几个真正不同的变种让人选，这不是建模这一步能替代的。

### 3.3 写

格式照官方 spec，内容照 §7。`## Case Law` 从空开始，判例来自真实案子，不预填臆想的。走 §5 的写入流程。

## 4 蒸馏

**输入两种：**

1. 冻结记录 `docs/design/*/*-design.md` 里 `## 设计法候选` 一节下**没有去向行**的条目。用 `Grep` 列全，不另起一份 backlog。
2. 人在会话里口述的规则。口述的也按候选处理，先帮人补齐「情境 / 决定 / 理由」再走同一张表。

**默认等那一页上线之后再蒸馏**：上线的代码是证据，冻结时的画布还不是。人可以要求提前，提前时在报告里注明「未经线上验证」。

**对每一条候选：**

1. 过 §2 的分层表，给出去向和一句理由。
2. 按去向处理：
   - **产品视觉语言**：起草要写进 DESIGN.md 的措辞。判例写成「情境 → 决定 → 理由」，进 `## Case Law`；如果它其实是某一节正文规则的细化，就提议直接改那一节的正文。
   - **通用设计原则**：起草成 harold-skills 的 issue 文字（标题 + 原则 + 来源案例 + 建议落在哪份 reference），问人要不要开。人同意后才跑 `gh issue create -R guohaonan-shy/harold-skills`。
   - **现状、缺陷**：起草一条 `docs/quality-backlog.md` 记录，按那个文件现有的格式。
   - **页面决定**：留在原冻结记录里，不动正文。
   - **驳回**：写一句理由。
3. 一批候选的起草结果一起摆给人，人逐条改或批，再走 §5 落笔。
4. 落笔后在每条候选末尾追加去向行，取值见 §8 的闭集。没有去向行就是未处置，所以已经处理过的候选一条都不能漏掉去向行。

## 5 每一次写入：起草 → 人确认 → 落笔 → lint

新建、蒸馏、对账都走这一条，没有例外：

1. **备份当前版本**：把改之前的 `DESIGN.md` 复制到 `/tmp/design-modeling/before.md`。新建时没有这一步。
2. **起草**：在会话里摆出要加、要改、要删的每一处，旧文与新文并排，每处附一句它为什么落在 DESIGN.md 这一层。
3. **停下等人确认。** 人改过措辞以人的为准。人拒绝写文件，就把内容以文字交回，不写。
4. **落笔**：用 `Edit` 改，只改人批过的那几处。plugin 的 hook 会在每次写 `DESIGN.md` 时自动跑官方 lint。
5. **收尾校验**：
   ```
   npx -y @google/design.md@latest lint <DESIGN.md 路径>
   npx -y @google/design.md@latest diff /tmp/design-modeling/before.md <DESIGN.md 路径>
   ```
   `lint` 有 error 就修到没有为止。`diff` 判为退化（新增了 error 或 warning）就修，或者把这条 warning 摆给人，说明为什么可以接受。新版本 CLI 对老内容多报出来的 warning 不算这一次的退化，列进报告留给下一次对账。

**CLI 没覆盖到的格式问题由你自己守**：spec 规定重复的 `##` 章节是错误，但当前 CLI 不报，所以不要新开一个已经存在的章节，判例往已有的 `## Case Law` 里追加。

## 6 对账

拿法去量代码。以下四种情况各自摆给人逐条确认，**不自动处理任何一条**：

| 发现 | 处置 |
|---|---|
| **法和代码对不上**（DESIGN.md 写 X，代码是 Y） | 人判：法错了就改法；代码错了就起草一条 quality-backlog。法在撒谎比法过期更危险，所以不替人选 |
| **不该在文件里的内容**：代码行号引用、已知缺陷、迁移计划、历史叙事、实现细节、划掉的条目 | 按 §2 分走。缺陷进 quality-backlog（你起草，人确认后追加）；迁移计划、实现细节以文字交给人，建议去处是 spec 或代码注释（你不写 spec，也不改代码）；历史叙事和划掉的条目直接删，git 留着历史 |
| **一条判例已经在两页以上被照着用过** | 提议把它并进对应章节的正文，从 `## Case Law` 删掉。证据是两份以上冻结记录引用它，或者代码里两个以上 surface 照它实现 |
| **被取代的判例** | 删掉。不留「已被取代」的空壳 |

还要过的两样：
- 官方 `lint` 报的 warning，比如定义了却没被引用的 token、组件 token 的对比度不达标。逐条判是改 token、补 `omitted` 说明，还是交人裁决。
- §7 内容规则的每一条：底线是否附实测值、禁令是否带理由、判例是否带日期和三段式。

**对账的健康信号：这份文件变短的次数应该和变长一样多。** 一次对账只加不减，多半是把盘点当成了法。

## 7 内容规则——spec 管不到、由你守的

格式交给 CLI，下面这些 CLI 查不出来，靠你起草时守、人确认时看：

1. **正文是主体，token 是上下文。** 一个具体的参照物胜过一串形容词；一长串 Don't 通常说明正文本身没写清楚。
2. **底线少而能检查。** 全文五到八条，每条带可检查的 token 或实测值，落在它约束的那一节里。「无障碍」不是底线，「正文对比度 ≥ 4.5:1，从真 DOM 读」才是。无障碍底线一定要有，它是唯一不该由品味决定的一条。
3. **禁令带理由**，写在 Do's and Don'ts 的 Don't 半边。没有理由的禁令每次会话都会被重新争论。
4. **判例**放在自定义的 `## Case Law` 章节（spec 允许未知章节），按时间顺序追加，每条：
   ```markdown
   - **<一句话规则>** *(<YYYY-MM-DD>，<来源页面>)*。情境：……决定：……理由：……
   ```
5. **刻意没有的 token 组**写进 frontmatter 的 `omitted` 并附理由，不要留着让 lint 每次报缺。
6. **不写**：代码行号引用、已知缺陷、迁移计划、历史叙事、实现细节、划掉的条目。它们各有去处（§2、§6）。

## 8 设计法候选的格式

refine 签字时写在冻结记录 `docs/design/<slug>/<slug>-design.md` 里，你读它、处置它。这一节是唯一定义，写候选的一方照抄骨架：

```markdown
## 设计法候选

- **<一句话规则>**
  - 情境：……
  - 决定：……
  - 理由：……
  - 证据：<画布 data-anchor 或 assets/ 下的截图>
  - 来源：人的原话 / 模型提议
  - 建议层：产品视觉语言 / 通用设计原则 / 不确定
```

- 没有候选时这一节写一行「无」。空着分不清是没有还是漏了。
- 「情境 / 决定 / 理由」跟判例同形，进 `DESIGN.md` 时原样搬。
- **去向行只由你追加**，接在条目最后一行，取值是闭集：
  - `→ DESIGN.md Case Law <YYYY-MM-DD>`
  - `→ DESIGN.md <章节名> <YYYY-MM-DD>`
  - `→ harold-skills#<N>`
  - `→ quality-backlog`
  - `→ 留在本页`
  - `驳回：<理由>`

## 9 收工报告

每次运行结束，固定报这几样：

1. **模式**，以及判这个模式的依据。
2. **写进 DESIGN.md 的**：每一处一行，标注是新增、修改还是删除。
3. **分到别处的**：去了 quality-backlog、issue 草稿、留在本页、交给人的文字，各几条。
4. **候选处置**：处理了几条、还剩几条没有去向行。
5. **校验结果**：`lint` 的 error 与 warning 数，`diff` 是否判为退化；遗留的 warning 留给下一次对账。
6. **变短还是变长**：前后行数。

## 不做

- 不在人确认之前落笔，不自己判「人肯定会同意」。
- 不做发散、不出变种、不替人选语言。没有 UI 又没走过 imagine，就指回 imagine。
- 不写 spec、不写 ADR、不改代码。挪出 DESIGN.md 的迁移计划和实现细节，以文字交给人。
- 不改 plugin 的 `references/design/`。通用原则只起草 issue，问过人再开。
- 不往 DESIGN.md 里写代码行号、缺陷、迁移计划、历史、划掉的条目。
- 不新开重复的 `##` 章节。
- 不替项目生成或修改 CI。项目要不要在 PR 上跑这个 CLI 是项目自己的事；plugin 这边只有 hook。
