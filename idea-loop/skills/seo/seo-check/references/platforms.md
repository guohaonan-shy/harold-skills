# Google 与 Bing 的标准

两个平台读同一份 HTML，但一个只报状态，一个会逐页挑内容的毛病。设计新路由的 head 标签、或平台后台报了脚本没报的东西时，按下面判。

## 报告方式就不一样

- **Google（Search Console）**：只给抓取、收录、富结果资格的**状态**，没有内容检查器，不会告诉你标题太短。
- **Bing（Webmaster Tools）**：「站点扫描」本身就是一个内容检查器，长度类的警告都来自它。

所以看到长度警告，它来自 Bing。为了 Bing 报告干净可以照它改，但不要把它当成 Google 的规则。

## 一样的地方

| 项 | 两边的共同要求 |
|---|---|
| 标题 | 必须有；结果页按显示宽度截断，要紧的放前面 |
| canonical | 每页恰好一个；出现多个时 Google 全部忽略 |
| hreflang | 两边读法相近：每个语言版本列出整组、包括自己，整组互相指向，并给一个 `x-default` |
| 仍有效的结构化数据 | Article、BreadcrumbList、Organization 仍会被用到；内容要和页面上看得见的一致 |
| 图片 alt | 爬虫和 AI 抓取器只能从 alt 和正文里知道图里有什么 |

## 不一样的地方

| 项 | Google | Bing | 怎么做 |
|---|---|---|---|
| 标题长度 | 没有长度规则，不警告；按设备宽度截断，常常自己改写 | 查长度，推荐 50–60 字左右，报「太短」「太长」 | 长度是 Bing 的卫生信号；按字宽控制在可见范围内 |
| 描述长度 | 没有长度规则；经常不用你的描述，自己写摘要 | 查长度，推荐 150–160 字左右 | 写满但不超；超宽两边都截断 |
| 缺描述 | 容忍 | 报错 | 每个可收录页都写 |
| CJK 页面的长度 | 不适用 | 按原始字数算，不给 CJK 折算，写满的中文标题仍报「太短」 | 已知误报，不凑字 |
| FAQPage、HowTo 结构化数据 | 已不再产生富结果，标记是惰性的 | 看重页面上**可见**的 FAQ 段落，AI 回答会引用它 | 留着无害；不为 Google 富结果新加；可见的 FAQ 照常写 |
| 站内搜索框（`WebSite` + `SearchAction`） | 已不再使用 | — | 不依赖它，也不必删 |
| hreflang 的反馈 | Search Console 不报告 hreflang 错误，只能自己验 | 同样读 hreflang | 靠检查脚本的互指检查 |
| 即时收录通知（IndexNow） | 不接收；靠 sitemap 发现，收录请求在 Search Console 里手动提 | 接收，提交后按信号重新抓取（接入 IndexNow 的其他引擎也会收到） | 新页、改过的页推给 IndexNow；Google 那边保证 sitemap 是新的 |

## 和 AI 引用有关的 Bing meta 指令

这几个不检查，但设了会直接影响页面能不能被 AI 回答引用，没想清楚就不要设：

| 指令 | 效果 |
|---|---|
| `NOARCHIVE` | 页面不进 Copilot 的回答和引用依据 |
| `NOCACHE` | Copilot 只能用标题和摘要 |
| `NOSNIPPET`、`data-nosnippet` | 降低被引用的质量 |
| `data-snippet` | 指定一段可以被引用的文字 |

## AI 搜索喜欢的页面

Bing 的站长指南已经把面向 AI 的内容写进规则，奖励的是：事实直接陈述、可核实；实体名称前后一致；一个网址一个主题；关键信息靠前；清楚的标题层级、表格、FAQ 段落；说法有数据或来源支撑；写明更新时间。写正文时按 seo-writing 的规则落实，这里只是说明检查之外它们为什么重要。
