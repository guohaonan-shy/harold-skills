# SEO 审计

## 目标

审计一个域名，交付一页 HTML 报告：任何人（包括完全不懂 SEO 的人）读一遍就能照做。整份报告只为支撑**一件**站长这周就能做的事；其余都是佐证。

调用方提示的第一行是「无人值守，交回发现清单。」时交付的是发现清单，不是报告：先读 [references/unattended.md](references/unattended.md)，它改写下面的输入、项目上下文、工作流收尾，并定清单的格式。

## 必需输入

- 要审计的域名：SEO.md「站点」节的域名，人点名别的域名时以人为准。
- `projectId`：SEO.md「OpenSEO」节的项目。没有 SEO.md 时用 `list_projects` 找；找不到匹配的，建一个（`create_project`）。

## 项目上下文

项目上下文工具免费，和 OpenSEO 应用、其它 agent 共用。

1. 读项目目录的 `SEO.md`：`dyna seo parse <项目目录>/SEO.md` 读出各节。竞品和重点页面以 SEO.md 为准，和 OpenSEO 项目上下文不一致时听 SEO.md 的。没有 SEO.md：人在场时在收尾建议人跑一次 `/idea-loop:setup`（SEO 模块），照常往下做。
2. 调 `get_project_context`，报告以它为根：业务是做什么的，决定哪些发现要紧、那「一件事」该是什么。
3. 这个 skill 需要 `business_overview`。它写着「无」（人明确说过不需要）时，当作没有这项信息：不推断、不问、不写回，人在场、无人值守都一样；说明没法按业务判断哪些发现要紧、那「一件事」该是什么，只交回核实过的问题，人在场就写在报告里。其余为空时：
   - 人在场：做最小的现场补齐：从站点推断业务，用一个问题和人确认，用 `update_project_context` 写回，再继续审计。收尾时建议人跑 `/idea-loop:setup`（SEO 模块）补其余。
   - 无人值守：缺了不推断，写法见 `references/unattended.md`。
4. 花 credits 之前查研究日志：30 天内跑过同样的研究，就复用那次结果并说明。
5. 收尾时（只限人在场）写回经得住时间的东西：修正过的 `business_overview`；报告单独点名的页面，经人同意先加进 SEO.md 的「重点页面」，再用 `addKeyPages` 写进项目上下文，两边一致；并追加一条研究日志：`{ appendResearchLog: { summary: "Site audit: <domain>. Verdict: <conclusion>" } }`。

完成条件：知道业务和 SEO.md 的重点页面；缺的项已补齐，或已说明因此没做的部分。

## OpenSEO MCP 工具

- `whoami`：花钱前确认连接和剩余 credits。OpenSEO 没连上：停下请人连接。
- `list_projects` / `create_project`：解析 `projectId`。
- `run_site_audit`：开始抓取（默认页数预算）。Lighthouse 保持关闭（它的默认值）：它要多花好几分钟，这份报告用不上；只有人要性能 / Core Web Vitals 深度时才传 `runLighthouse: true`。然后查 `get_audit_status`（抓取要一两分钟，两次查之间等一等），读 `get_audit_issues`。逐页证据有用时调 `get_audit_pages`。
- `get_backlinks_overview`：外链和引用域名的全貌；通常是决定「那一件事」的数据。
- `get_domain_overview`：估算的自然流量和自然关键词数。站点明显已死时跳过。
- `research_keywords`：带搜索量和难度的关键词点子，用来提出一个起步的重点方向。一次调用，1–3 个种子词取自站点真正讲的东西。站点挂了就跳过。

总花费保持克制：一次审计、一次外链概览、至多一次域名概览、至多一次关键词研究。只有概览和关键词查询花 credits。

## 工作流

1. **取数**：`whoami`，解析 `projectId`；对域名 `run_site_audit`，抓取期间取 `get_backlinks_overview`；抓取结束后读 `get_audit_issues`，站点活着的话再取 `get_domain_overview`。
   完成条件：手上有审计问题清单和外链概览（站点活着时还有域名概览）。
2. **核实**：审计结果坏掉或几乎为空（证书错误、5xx、只抓到一页）时，动笔前先调查：自己查证书和各种跳转写法，并在网上搜这家业务。死掉的域名常常有一个活着的继任站，那会把整个建议翻成「把旧域名跳转过去」。打算报告的每条发现，都自己抓线上页面的 HTML 核过。
   完成条件：每条要报告的发现都有线上页面证据；没见到证据的一律不报。
3. **定方向**：
   - 定下那一件事：从数据推出来，不从泛泛的建议推。常见模式：
     - 站点干净、没有外链：联系客户、合作方或目录站，附一封可以直接发的消息。
     - 域名已死、继任站活着：通过主机商支持做永久跳转，附要发给他们的整段文字。
     - 页面被屏蔽或 noindex：去掉屏蔽。
   - 站点健康时提出一个起步的重点方向：调一次 `research_keywords`，种子取自站点真实的主题，选一个主题和 3–5 个站点能实际排上去的低难度关键词，每个配上要做的页面或文章。这是起步方向，不是关键词策略；完整流程请人用 `keyword-research`。站点挂了整步跳过：那时只有那一件事要紧。
   完成条件：那一件事是一个不懂技术的人这周就能做完的事，带着能直接复制粘贴的操作细节。
4. **写报告**：用 `references/template.html`（见「输出格式」）。
   完成条件：模板里的占位和示例行都换成了本站的内容。
5. **交付前 review**：环境里有第二个 agent 或模型就做一轮对抗式审查，没有就重新自审一遍。把核实过的事实交给审查者，让它攻击四点：超出事实的说法、没解释的术语、对新手负担过重的内容、夸张的措辞。审查者也可能指出你没给它的真实事实；拿你的证据去核，而不是去「修」它们。
   完成条件：四点都有结论，改完了该改的。
6. **交付**：用『发布审阅页』（做法照 `dyna runtime show 发布审阅页`）。

## 输出格式

读 `references/template.html`：只填内容，CSS 和结构保持原样（只用浅色调色板，不做深色模式）。

- 页头：域名作标题，下一行单独写审查日期，再写 2–3 句全文摘要（总体状况；主要缺口和那一件事；报告覆盖了什么）。
- 小节顺序：结论、那一件事、小修复（最多 5–10 条，按影响排序）、先从哪儿着手（只限健康站点）、已经做对的、方法说明页脚。
- 每条修复都给出确切证据（引用的标签或数字），和不懂技术的人能照做的具体步骤。
- 「先从哪儿着手」点名一个主题方向和 3–5 个关键词，每个用大白话写搜索量，并写要做的页面或文章。站点挂了就省掉这一节。

## 护栏

- 语气平静、平实：去掉感叹号、夸张词、破折号、「不是 X，是 Y」式对照和填充话。严重程度的词只在字面成立时用（站点挂了是严重的；title 太长不是）。
- 每个术语第一次出现时用大白话解释：canonical、meta description、alt text、爬虫、301、结构化数据。
- 报告只放对这个站点要紧的发现，一份新手报告列二十条发现就是失败。
- 缺外链或排名数据意味着「没有记录到数据」，不是惩罚；照实说，别渲染。
- 偏向站点现在就能赢的关键词：意图具体、难度低；新站还排不上的头部大词不列。
- 区分工具报出来的和你自己核实的，两者都写进方法说明页脚（无人值守时写进 `evidence`）。
