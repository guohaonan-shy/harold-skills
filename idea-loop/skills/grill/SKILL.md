# Grill

把需求当成一棵**决策树**来拷问：每个决策都分叉出挂在它下面的决策。

按**轮次**推进。**frontier** = 所有前置已经落定、现在就能问的决策——也就是不需要先猜别的答案就能回答的问题。**一次问完整个 frontier**：每题编号，每题附上你推荐的答案。然后停下来等人回答。

**用纯 chat markdown 问，不要用 `AskUserQuestion`。** 那个工具限 2–4 个选项的卡片，对设计 fork 太窄；参考项目全仓也没有这个 tool，它靠的是下面这个格式加纪律，不是靠工具。

每题格式：

```
❓ **Q1** - **<问题标题>**：<问题正文，可以多段，可以带选项>

➡️ <你推荐的答案>
```

人每答完一轮，树就重塑一次：落定的决策把 frontier 往外推，解锁依赖它们的问题。重算 frontier，问下一轮。**一个问题如果依赖本轮还开着的另一个问题，它属于下一轮，不属于这轮。**

## 事实是你的活，决策是人的活

需要环境事实（文件里写了什么、代码是否已存在、哪个 PR 合了、生产数据长什么样）时，**自己去查，或者派 subagent 去查——绝不拿这种问题问人**。

别为此阻塞：正在跑的探查是一个未落定的前置，所以只有依赖它的问题要等；frontier 上其余的现在就问。

判断题是人的：摆到人面前，然后等。

### 事实核实的一种：问题要走一遍

人描述的问题、你读代码推出来的根因，都还是事实层面的猜测——核实它们跟查文件、查 PR 是同一个动作，只是从「读」升级成「真的操作一遍」。不问人「要不要复现」，直接复现（或派 subagent），只有依赖这条根因的问题等它。

走一遍有两个用处，所以放在这里做，不留给 `to-spec`：

- **核实根因。** 复现经常推翻读代码得出的根因——以为是 A，走一遍发现 A 根本不发生，是 B。根因一变，挂在它下面的决策全要重问；等到 `to-spec` 才发现，就得回头重新 grill。所以在相关决策落定之前做。
- **顺手留下 spec 第一章的证据。** 复现时截的图、记的时间线，挑出来标注好，就是 `to-spec` §1 给人 review 的图；`to-spec` 不再复现，只负责排版。新功能没有根因要核实，只剩这个用处：截现在的 UI、圈出它不够用的地方。

仪器和证据形式照 `../../references/spec-figures.md` §1：

- 用户可见的问题：本地开发环境里用浏览器自动化走一遍用户路径，慢网络用请求延迟、失败用请求拦截模拟；截图、标注、需要时记下每步的毫秒数。
- 纯后端、埋点、数据问题：查询结果、日志、接口响应。
- 新功能：截现在的 UI，标出它在哪里不够用——新需求也是从旧页面满足不了什么里来的。

**文件分两处放**（spec-figures §1「放哪」）：复现过程中的一切——每次尝试的截图、网络日志、trace、没用上的半成品——放在当前 worktree 的临时目录 `<worktree 根>/.tmp/grill/<YYYY-MM-DD>-<topic>/`，生命周期跟着 worktree，grill 收工时删；**挑出来当证据、标注好的那几张**落进这场讨论的 raw 桶 `docs/raw/<topic>/assets/`，`to-spec` 从那里取。

复现的结果当成本轮的事实摆出来：复现了什么、推翻了什么先前的说法。

**没能复现的，不是贴个「未复现」就算完。** 说清楚卡在哪——本地没有那份数据、要登录的账号没有、那个状态触发不出来、只在生产的网络或设备上出现——以及要复现还缺什么。然后把它当成**一道题**放进本轮 frontier：「这条没能复现，卡在 X；你能给我 Y（账号 / 数据 / 操作路径 / 一段录屏）吗？还是就以读代码的结论为准？」➡️ 附上你推荐的选项。人给了复现方式就再走一遍；人确认不复现，才落成「未复现」，原因跟着一起写。这跟「事实不问人」不冲突：问的不是事实本身，是你自己拿不到的复现条件。

## 术语

先读一次 `../../references/glossary.md`。目标项目根有 `GLOSSARY.md`（或 `GLOSSARY-MAP.md`）就每轮开问前读一遍，没有就跳过。

**定一个叫法是决策，是人的活。** 下面三种情况各出一道术语题，跟别的题一起放进当轮 frontier，附推荐叫法：

- 人用的词跟术语表冲突；
- 人用的词模糊或一词多用；
- 人说某个东西怎么运作，你去代码里核实（这是事实，你的活）发现对不上。

讨论概念之间的关系时，自己编具体场景去压边界，逼出两个概念的分界。

人答了术语题，**算下一轮 frontier 之前当场写进 `GLOSSARY.md`**，格式和收什么照 glossary.md；
第一个词定下来时才建文件。没答的推荐叫法不写。写入后 plugin 的 hook 会跑 `glossary-check`，报错就当场改。

## PRODUCT.md 缺口

目标项目缺 `PRODUCT.md` 时，把"建立 PRODUCT.md 需要拍板的核心判断"当成新解锁的 frontier 节点问出来——这跟这次改动要不要碰 UI 无关，纯后端项目一样需要产品真相支撑决策。不要悄悄推迟到后面另起一次交互。（把答案落成 `PRODUCT.md` 文件是另一个 codebase 初始化 skill 的事，grill 只负责把问题问出来。）

## 设计子树

设计形状不是一条独立的、每次都要单独走一轮的轨道——它是挂在某个产品决策节点下面的子树：只有当某个产品决策需要设计层面的取证才能给出靠谱推荐答案时，这棵子树才长出来，不是每次涉及 UI 就强制拉一轮。

子树长出来之后，看这条 frontier 问题**缺的是事实还是结构**，取证形态不同：

**缺事实**（视觉方向 / 具体 UI 模式 / 多步骤流程的既有惯例）→ 跟上面"事实是你的活"是同一个动作，只是核实对象换成了设计事实：派一个纯研究、不需要人介入的 subagent 去查，结果回到主会话，用来支撑这条问题的 ➡️ 推荐答案。**设计相关的推荐必须有真实取证支撑，不能是凭印象编的。**

**缺结构或行为**（文字怎么写都定不下来——这个状态机该长什么样、这个 surface 该按什么结构组织，得看到、点到才能选）→ 走这条动作链：

1. **把这条 frontier 问题压成一句话。** 一句话说不清，就是它还没拆干净——回去拆，不要把一整个 surface 甩过去。
2. **调 `prototype`**（同 plugin 内 Skill 调用），把那一句话交给它。
3. **人在原型里选。** 选的是结构或模型，不是视觉——原型是刻意灰盒的。
4. **答案回决策树。** 人的裁决就是这条 frontier 的落定，它把 frontier 往外推，解锁依赖它的问题；重算 frontier，继续问下一轮。

裁决和那份 HTML 由 `prototype` 自己落进 raw 桶，`grill` 不写这些文件。人对原型出的几个选项都不满意时，**回新一轮 grill 重新审视相关的产品决策**，不是让原型原地再出一批变体——"不满意"优先当成"某个产品判断需要重新审"来处理。

纯技术修改、埋点、bug fix 这类全程没有任何产品决策需要设计取证的改动，子树根本不长出来，frontier 清空就直接收工进 `to-spec`。不要因为改动技术上碰了某个 UI 文件就补跑一次没有实质问题的原型。

`DESIGN.md` **不由 grill 问**。项目缺它是设计发散那一段（`uiux-imagine`）的活——视觉语言在那里被选出来并写成文件。访谈阶段不要因为项目缺 `DESIGN.md` 单独开一轮；这跟上面 `PRODUCT.md` 那条不对称是有意的：产品真相是决策的前置，视觉语言不是。

## 什么时候算完

frontier 空了——决策树每个分叉都走到过，没有任何东西是暗中假设的。每个问题都有复现证据；没能复现的，卡在哪已经问过人，人确认了不复现（原因记下来）。**在人确认达成共识之前，不要动手做任何事。**

## 收工

共识达成后，需要落盘就调 `to-spec`（它会写 raw transcript + spec）。`grill` 自己只写两样东西：`GLOSSARY.md`（只写人答过的术语题），和复现证据图（raw 桶的 `assets/`）。证据图落定之后，删掉 `<worktree 根>/.tmp/grill/<YYYY-MM-DD>-<topic>/`。
