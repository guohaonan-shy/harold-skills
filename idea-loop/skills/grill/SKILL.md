# Grill

把需求当成一棵**决策树**来拷问：每个决策都分叉出挂在它下面的决策。

按**轮次**推进。**frontier** = 所有前置已经落定、现在就能问的决策——也就是不需要先猜别的答案就能回答的问题。**一次问完整个 frontier**：每题编号，每题附上你推荐的答案。然后停下来等人回答。

**用纯 chat markdown 问，不要用 `AskUserQuestion`。** 那个工具限 2–4 个选项的卡片，对设计 fork 太窄；参考项目全仓也没有这个 tool，它靠的是下面这个格式加纪律，不是靠工具。

每题格式：

```
❓ **Q1** - **<问题标题>**：<问题正文，可以多段，可以带选项>

➡️ <你推荐的答案>
```

人每答完一轮，树就重塑一次：落定的决策把 frontier 往外推，解锁依赖它们的问题。重算 frontier，问下一轮。**一个问题如果依赖本轮还开着的另一个问题，它属于下一轮，不属于这轮。**

## 事实是你的活，决策是人的活

需要环境事实（文件里写了什么、代码是否已存在、哪个 PR 合了、生产数据长什么样）时，**自己去查，或者派 subagent 去查——绝不拿这种问题问人**。

别为此阻塞：正在跑的探查是一个未落定的前置，所以只有依赖它的问题要等；frontier 上其余的现在就问。

判断题是人的：摆到人面前，然后等。

## 设计子树

设计形状不是一条独立的、每次都要单独走一轮的轨道——它是挂在某个产品决策节点下面的子树：只有当某个产品决策需要设计层面的取证才能给出靠谱推荐答案时，这棵子树才长出来，不是每次涉及 UI 就强制拉一轮。

需要取证时，跟上面"事实是你的活"是同一个动作，只是核实对象换成了设计事实：派一个纯研究、不需要人介入的 subagent 去查（视觉方向 / 具体 UI 模式 / 多步骤流程——取哪层看这条 frontier 问题实际需要哪层的事实）。取证结果回到主会话，用来支撑这条问题的 ➡️ 推荐答案。**设计相关的推荐必须有真实取证支撑，不能是凭印象编的。**

frontier **完全清空**（产品决策和设计的结构选择都已经拍板）之后，才一次性 handoff 给 `design`（设计总入口，跨 plugin Skill 调用）——这时已经没有需要问的东西了，构建段本身不需要中途交互。`design` 被这样嵌套调用时跳过它自己原生那轮"确认要设计什么"的澄清问答：那轮问答视为已经被这里的 frontier 覆盖了，避免访谈中途从连续编号问答切换成另一种问答格式。人直接单独调用 `design`（不经过 grill）不受这条影响，仍走它原生的完整流程。

`design` 收工带回来的答案是**预览 HTML 路径 + 冻结状态摘要**。人来判定这份产物满不满意：

- 满意 → 这条分叉清空，继续问 frontier 剩下的部分。
- 不满意 → 回到新一轮 grill，重新审视相关的产品决策——不是回 `design` 内部原地调视觉细节。把"不满意"当成"可能是某个产品判断需要重新审"来处理，不要默认当成"视觉细节没调好"。

目标项目缺 `DESIGN.md` / `PRODUCT.md` 时，把"建立这两份文档需要拍板的核心判断"当成新解锁的 frontier 节点问出来，不要悄悄推迟到后面另起一次交互。

## 什么时候算完

frontier 空了——决策树每个分叉都走到过，没有任何东西是暗中假设的。**在人确认达成共识之前，不要动手做任何事。**

## 收工

共识达成后，需要落盘就调 `to-spec`（它会写 raw transcript + spec）。`grill` 自己不写任何文件。
