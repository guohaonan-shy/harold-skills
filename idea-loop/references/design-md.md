# DESIGN.md 写入标准

项目根的 `DESIGN.md` 是这个产品**设计系统本身**的写法。这份 reference 回答四件事：它是什么、每章写什么不写什么；一条内容该不该进、不该进去哪；一次写入怎么走；一条「设计法候选」长什么样。**判断「这条该不该进 `DESIGN.md`」只读这一份**——规则不散在别处。

> 依据：Google `design.md` 规范，加对公开的 84 份 `DESIGN.md` 样本（VoltAgent/awesome-design-md）的阅读；条文由 Harold 定稿。本文里的样本品牌都是公开的外部分析，不是本插件的服务对象。
>
> **格式只认官方 spec，每次运行现读**：`npx -y @google/design.md@latest spec`。本文不复述它——复述的那份会落后于 CLI，而 hook 与收尾校验用的都是最新版。本文只写 spec 管不到的：什么该进、怎么写、怎么维护、候选长什么样。

## 1 是什么

`DESIGN.md` 由两部分组成：YAML front matter（机器可读的全部数值，即 token）和 Markdown 正文（给人和 agent 读的理由与用法）。Google 的说法是：token 是规范性的数值，正文提供怎么用的上下文。

我们的落地理解：

- 它是**设计系统本身**的自然语言加 token 表达，是 living source of truth，描述「现在是什么、必须怎么做」。
- 它**不收设计过程**：某天做了什么改动、做了什么决策、某个页面或某个组件在某个场景里的具体样子，都是过程，不是系统。
- 它是**被整理的**，不是被追加的（§4）。

## 2 结构

front matter 之后，正文用 `##` 二级标题，按下面的顺序（出现的章按此顺序，重复标题是错误）：

| 章 | 内容 | 来源 |
|---|---|---|
| 1 Overview | 品牌气质与设计立场 | Google 规范 |
| 2 Colors | 色板与每色的用途、限制 | Google 规范 |
| 3 Typography | 字阶与排版原则 | Google 规范 |
| 4 Layout | 间距、栅格、留白 | Google 规范 |
| 5 Elevation & Depth | 层级怎么表达 | Google 规范 |
| 6 Shapes | 圆角与形状规则 | Google 规范 |
| 7 Components | 组件配方（含状态） | Google 规范 |
| 8 Do's and Don'ts | 可判定的约束 | Google 规范 |
| 9 Responsive Behavior | 断点、折叠、触控尺寸 | 扩展：样本里 61/84 份有 |
| 10 Motion | 动效的全局原则与禁令 | 扩展：规范与全部样本都没有，我们自设 |
| 11 Known Gaps | 没覆盖什么 | 扩展：样本里 43/84 份有 |

- 不需要的章用 front matter 的 `omitted:` 声明并写原因，**不留空标题**。
- **不设 Iteration Guide**：它与 Do's 容易重复。
- 三个扩展章不在 Google 规范里，lint 对未知章节只保留不报错，所以它们的形态（不带日期、不枚举、不写判例）**靠写的人守**。

## 3 五条写法规则

对每一章都生效，也是样本里好文件和坏文件的分界。

1. **准入判据。** 只收设计系统本身的信息：全局的、当前生效的、下一个 agent 可以直接照做的规则与数值。凡是「某天做了什么改动」「做了什么决策」「某个特定组件或页面的具体描述」都不进（§8）。
2. **一条规则只写一处。** 样本里最常见的缺陷是自相矛盾（84 份里约 57 份）：同一规则在 Overview、Do's、各组件条目里各写一遍，改一处漏另一处。坏例：lamborghini 的颜色章列了三个强调色，Don'ts 却写只许金色一个；ferrari 的层级表给了柔和阴影，Do's 写「不加阴影」。
3. **数值只在 front matter，正文用名字引用。** 正文写 `{colors.primary}`，不重抄 hex。坏例：airtable 的 Colors 章逐条重复 hex，违反了它自己写的「hex 至多出现一次」。
4. **每条规则带「为什么」或「边界」。** 只给数值不给理由，agent 遇到没覆盖的情况无法推断。好例：mastercard 解释了为什么跳过 8–12px 圆角（要么小、要么大、要么全圆，中间档不存在），比单给一张圆角表有用得多。
5. **只写当前状态，不写演进。** 不写「从 X 改成了 Y」「某月某页确认」。

## 4 维护原则：整改优先于追加

靠**整理**保持可维护，不靠追加。每次有新内容要改动，按顺序：

1. **先找已有内容里受影响的部分。** 在所有章节和 front matter 里找：这条新内容是否与已有规则矛盾、是否让已有规则过时、是否已经被某条已有规则覆盖。
2. **能整改就整改。** 过时的改写或删除，矛盾的统一成一条，已覆盖的什么都不加。
3. **只有已有内容没有覆盖某个缺口时才新增。** 新增时仍写成全局规则，放进最合适的一章，并同时更新 front matter 里对应的 token。
4. **改完读一遍相关章节**，确认没有留下同一规则的两种写法。

判断标准：文件即使被反复修改，行数也不应随改动次数单调增长；它的大小由「设计系统有多少缺口」决定，不由改了多少次决定。

## 5 Front matter（token）

- **定义**：文件开头 `---` 包起来的 YAML，是设计系统的全部**数值**，也是唯一的数值来源。
- **写什么**：`colors`、`typography`、`rounded`、`spacing`、`components` 五组，加 `name`、`description`、`version`，必要时 `omitted`。颜色用 CSS 颜色串（hex 为默认）；字阶含 `fontFamily / fontSize / fontWeight / lineHeight / letterSpacing`；组件的值用 `{colors.primary}` 这类引用，不写裸值；**状态拆成独立条目**（`button-primary`、`button-primary-hover`、`button-primary-pressed`）。
- **不写什么**：理由、用途说明、日期——这些在正文里。
- **好例**：linear.app 的 `button-primary` / `-hover` / `-pressed` 三个条目都只引用 token，改一个色值全局生效（74/84 份样本这样写）。
- **坏例**：ibm 把 `button-tertiary` 的边框只写在正文括号里，配方里没有，只读 token 的 agent 会漏掉；opencode.ai 同类（正文里的 1px 边框、2px 下划线在 YAML 里缺字段）。
- **强制规则：凡是影响渲染的属性，必须在 front matter 的 token 里有。** 正文只负责解释怎么用、为什么，不能成为某个渲染属性的唯一出处。新增内容同样要同步 token。

## 6 各章写什么、不写什么

### 6.1 Overview

- **定义**：一屏以内的设计立场，用来在「没有具体规则覆盖」时指导取舍。
- **写什么**：品牌气质（克制或活泼、紧凑或舒展）；最多 5–8 条关键特征，每条能转成可检查的判断。
- **不写什么**：不重复后面各章的规则；不用「signature / engineering-grade / elegant」这类没有可执行含义的修辞。
- **例**：好——tesla 一句话点明立场（radical subtraction），特征全可检查：整页一个强调色、没有阴影、没有渐变、没有边框。坏——linear、mongodb、framer、clay 的 Overview、Key Characteristics 与 Do's 三处重复同一条规则。

### 6.2 Colors

- **定义**：色板，以及**每个颜色什么时候用、什么时候不能用**。
- **写什么**：按角色分组（品牌、表面、文字、语义）；每色一行：名字、token 引用、用途、限制。
- **不写什么**：不贴采集来源页面，不逐条重抄 hex。
- **例**：好——stripe 的 Ruby 一行写明「渐变强调与图表高亮；永远不是按钮」；tesla「没有第二强调色」。「限制」比「颜色本身」更有价值：agent 最容易犯的错是把强调色用到不该用的地方。

### 6.3 Typography

- **定义**：字阶表加排版原则。
- **写什么**：字阶按语义命名（`display-xl`、`body-md`、`label-caps`），建议 9–15 级；每级的用途；原则——字重范围、行高与字号的关系、字体缺失时的替代。
- **不写什么**：不写页面里某个标题具体多大。
- **例**：好——hashicorp「紧的展示行高配松的正文行高，这个对比就是品牌的声音」；vodafone 说明 -1px 字距是为 144px 字号校准的。坏——figma 的 Do's 规定字重只许 320/330/340/480/540/700，Overview 里却用了 450。

### 6.4 Layout

- **定义**：间距刻度、栅格、容器宽度，以及留白的理由。
- **写什么**：间距 token、最大内容宽度、栅格列数与间隙、留白原则、图片比例。
- **不写什么**：断点与折叠（放 6.9）。
- **例**：好——tesla 把留白写成原则：每个主要内容块占满一屏高，一屏只传达一条信息。

### 6.5 Elevation & Depth

- **定义**：层级关系怎么表达。有阴影就写阴影参数，没有阴影就写替代手段。
- **写什么**：层级表（层级 / 处理方式 / 用在哪），明确禁用的手段。
- **不写什么**：不生成示例块。
- **例**：好——linear.app 用底色阶梯加 1px 边框表达，第 0 到第 4 层逐级写明处理方式和用在哪，并写明「在深色上基本不用投影」。坏——aljazeera、nerdwallet、wired、vodafone 等自动生成的示例块（`ex-modal-card`、`ex-toast`）写了阴影，与本章「无阴影」直接矛盾。

### 6.6 Shapes

- **定义**：圆角刻度和形状规则。
- **写什么**：圆角 token、每档用在哪、图片几何、**为什么没有某一档**。
- **不写什么**：不写某个组件在某个页面的圆角。
- **例**：好——mastercard「要么 ≤6、要么 20–40、要么全圆，8–12 这个中间档刻意缺席」。

### 6.7 Components

- **定义**：设计系统里**可复用的基础组件**的配方：外观属性加全部状态，是 agent 可以直接抄的一章。
- **写什么**：系统级的通用组件（按钮、输入框、卡片、徽章、导航、列表项、对话框等）；每个组件用 token 引用写颜色、字阶、圆角、内边距、尺寸，一句用途，以及状态（default / hover / pressed / focused / disabled）。
- **不写什么**：不写某个特定组件在某个页面或场景里的具体描述；不写页面级结构（「首页 hero 的布局」「分析页的进度列表」）；不写某个页面特有的组件；不写生成的示例块。判别方法：**这个组件的配方换到任何一个页面都成立，才进这一章**。
- **例**：好——framer、mongodb 把 pressed、focused 单列成条目，便于机械校验。坏——kraken 只给默认态；intercom 的 `text-input-focused` 与默认态取值完全相同，焦点态没有可见差异；mydealz 的示例引用了文件里不存在的 token。

### 6.8 Do's and Don'ts

- **定义**：可判定的约束。读完这一章，agent 能判断「这样做算不算违规」。
- **写什么**：每条做 / 不做加一句理由；引用 token，不写裸值。
- **不写什么**：「应该美观」「保持一致」这类无法判定的话。
- **例**：好——tesla「不要加 scale / translate 的 hover 动画，交互只有颜色过渡」「每屏至多两个行动按钮」；hashicorp 的产品专属色只能用在该产品语境里。坏——slack 的 Do's 规定按钮内边距不得低于 14px 28px，secondary pill 却写 10px 30px。

### 6.9 Responsive Behavior（扩展）

- **定义**：断点、折叠策略、触控尺寸。
- **写什么**：断点表（名称 / 宽度 / 变化）、折叠规则、触控目标最小尺寸、图片处理。
- **不写什么**：不重述断点数值——**断点数值只能出现一次**。
- **例**：好——airtable 用表格写断点，触控尺寸直接引用组件 token 并对照 WCAG 的 44px。坏——apple 的断点表写 736/834，末尾却列了 734、833、480；expo 的 Mobile 写 <640px，折叠段却写 768px 以下汉堡菜单。

### 6.10 Motion（扩展）

- **定义**：动效的**全局通用规则**：全站原则和禁令。不是动效清单，不是先例库，不是具体动画的枚举。
- **写什么**：统一时长和缓动（一个或一小组，作为 token）；可以动什么、不可以动什么（禁令）；reduced-motion 要求；产品有多个调性时，「安静」与「活泼」场景之间怎么取舍。
- **不写什么**：不写某个页面做了什么动画、什么时间定的；不枚举具体的动效模式（「滑动指示器」「处理中的光扫」「重试光环」这类逐条列举，会让这一章只增不减）。多个具体动效背后有共同规律的，把规律抽成一条原则写进来，不把各个动效都留着。具体参数留在冻结记录里。
- **例**：唯一的好范本是 tesla——原则「0.33s cubic-bezier 是所有交互状态变化的统一时长」，要求「所有过渡保持 0.33s」，禁令「不加 scale / translate 的 hover 动画，交互只有颜色过渡」，全文没有一条带日期的先例。theverge、starbucks 同类（starbucks 有真实的 duration token）。其余约 80 份样本没有动效数值，所以这一章的形态要靠我们自己守。

### 6.11 Known Gaps（扩展）

- **定义**：这份文件**没有覆盖什么**，以及已知的数据局限。是对读者的诚实声明，**不是变更日志**。
- **写什么**：未覆盖的范围（暗色模式、错误态样式）；数值是估测还是权威；缺口的临时处理。
- **不写什么**：不写「某日做了什么改动」，不写决策历史。
- **例**：好——hashicorp「暗色是唯一的营销模式，亮色适配未记录」；airtable 说明颜色取自截图采样，可能随季节换色。

## 7 准入分层表——每条内容都先过它

从上往下问，**第一个命中的就是去处**：

| 层 | 去处 | 判据 |
|---|---|---|
| 工作流 | idea-loop 插件的 `skills/*/SKILL.md` | 说的是环怎么跑 |
| 通用设计原则 | idea-loop 插件的 `references/design/` | **换一个产品照样成立** |
| 产品设计系统 | 项目 `DESIGN.md` | 只对这个产品成立，**而且跨页都要服从**，并且已经能写成全局规则（无日期、无页面名、可照做） |
| 页面或组件的决定 | 设计档案里对应对象的「决定」（需求进行中写在 `tmp/<spec-slug>/delta/` 的对象文件里，归档时进 `prod/`） | 只对这一页、这个组件成立 |
| 现状、缺陷、迁移 | `docs/quality-backlog.md` / spec | 说的是「现在什么样」，不是「应该什么样」 |

两个用来校准的判例：

- **「营销页的图像语言是无人静物摄影」被判错。** 同一页就用了静物照、线稿、生成插图、代码动效四种，图像风格是按每页内容选的。这是页面决定，不是产品设计系统。
- **所有介绍页共用的收尾渐变从没进过 `DESIGN.md`，是漏了。** 它跨页、只属于本产品，正好在产品设计系统这一层。

产品设计系统这一层还收一类常被漏掉的内容：**页面家族的复用机制**，比如一组同类页面共用的构图顺序。它跨页、只属于本产品、能被检查。

拿不准落在哪一层时，把两个候选层和各自的理由摆给人，由人定。**不要为了让文件看起来完整而往 `DESIGN.md` 里塞。**

## 8 明确不进 `DESIGN.md` 的内容

| 内容 | 为什么不进 | 样本里的情况 |
|---|---|---|
| 判例（情境 → 决定 → 理由，带日期） | 是决策与过程，不是设计系统；随时间只增不减，把文件变成决策堆叠 | 0/84 份有 |
| 带日期的先例（「某月某日，某页」） | 同上 | 0/84 份有 |
| 具体动效的枚举（逐条列各种动画） | 只增不减，无法维护；Motion 章只收全局原则 | 除 tesla 外都没有动效规则 |
| 单个页面的设计决定、特定组件在特定场景的具体描述 | 属于页面，不属于设计系统 | 样本都不含 |
| 某天的快照、变更记录 | `DESIGN.md` 描述当前状态 | 0/84 份有 |
| 采集来源页面清单、脚本生成说明 | 是取证说明，对自己维护的项目没有意义 | 59 份有来源说明，15 份残留脚本痕迹 |
| 自动生成的示例块（`ex-*`、`TO_FILL`） | 几乎不增加信息，还引入错误引用 | 约 15 份残留 |
| 代码行号引用、已知缺陷、迁移计划、历史叙事、划掉的条目 | 各有去处（§7） | — |
| 被多处遵循的先例 | 应先改写成无日期的全局规则，再并入对应章节；原始判例留在别处 | — |

## 9 一次写入怎么走

新建、蒸馏、对账都走这一条，没有例外。**模型可以起草，不能自己落笔。**

0. **找文件**：`git ls-files | grep -i 'DESIGN.md$'`。只有一份就地维护，不搬家；有好几份（monorepo 的多个 app）问人这次动哪一份；没有就在仓库根新建，除非人指定了某个 app 目录。
1. **备份**当前版本到 `/tmp/design-md/before.md`。新建时没有这一步。
2. **起草**：在会话里摆出要加、要改、要删的每一处，旧文与新文并排，每处一句它为什么落在这一层。按 §4 先找受影响的已有内容，能整改的整改，缺口才追加。
3. **停下等人确认。** 人改过措辞以人的为准。人拒绝写文件，就把内容以文字交回，不写。
4. **落笔**：只改人批过的几处。插件的 hook 会在每次写 `DESIGN.md` 时自动跑官方 lint。
5. **收尾校验**：

   ```
   npx -y @google/design.md@latest lint <DESIGN.md 路径>
   npx -y @google/design.md@latest diff /tmp/design-md/before.md <DESIGN.md 路径>
   ```

   `lint` 有 error 就修到没有为止。`diff` 判为退化（新增了 error 或 warning）就修，或把这条 warning 摆给人并说明为什么可以接受。新版本 CLI 对老内容多报出来的 warning 不算这一次的退化，列进报告留给下一次对账。
6. **CLI 没覆盖到的由写的人自己守**：重复的 `##` 章节在 spec 里是错误但当前 CLI 不报，所以不要新开已经存在的章节；三个扩展章的形态（不带日期、不枚举、不写判例）同理。
7. **报告**：模式与依据；写进 `DESIGN.md` 的每一处（新增 / 修改 / 删除）；分到别处的各几条；校验结果；前后行数。

## 10 新建

先判是哪一种来源，并说出来。**两种都不预填 `## Case Law`**——文件里没有这一节。

### 10.1 有线上 UI——从代码量

**量，不凭印象。** 从代码与真 DOM 的 computed style 读出字阶、间距节奏、圆角、边框粗细、阴影、颜色在实际用法里的角色，以及实测对比度。浏览器怎么读见 `design/browser-usage.md`，对比度判据见 `design/accessibility-baseline.md`。

量出来的值分三桶，**分开报告**：

- **一致的**：候选底线，进。
- **不一致的**：开放问题，交人裁决，裁决之前不入法。
- **偶然的**：没人选过的框架默认值，不入法。

把一个不一致的值写成底线，等于把一次意外冻结成法。三个占位页面量出来的「语言」也不是语言——UI 还是占位的项目按 10.2 走。

### 10.2 没有 UI——接 `uiux-imagine` 选定的语言

只接语言高度已经选定的东西。缺任何一样就问，不猜不补：

- 色彩角色：ground / ink / accent / 语义状态色，每个角色一句用途；
- 字体与字阶：每个字体家族承担的角色；
- 形状语言：圆角、边框、层次；
- register：这个产品有几个 register，各自多安静或多活；
- 每一对角色色的**实测**对比度；
- 锚点（可选）：选定的 brand board 路径，有就在 Overview 里指过去。

**项目既没有 UI 也没走过语言高度：不写。** 从零立一套视觉语言需要先出几个真正不同的变种让人选，这不是写文件这一步能替代的，回 `uiux-imagine`。

### 10.3 写

结构照 §2，每章照 §6，front matter 照 §5，不需要的章写进 `omitted` 附理由。走 §9。写完 `Known Gaps` 如实写下没覆盖的东西。

## 11 蒸馏

**输入**：设计法候选（§13 的形态），和人在会话里口述的规则。口述的也按候选处理，先帮人补成 §13 的形态再过同一张表。

**默认等那一页上线之后再蒸馏**：上线的代码是证据，冻结时的画布还不是。人可以要求提前，提前时在报告里注明「未经线上验证」。

**对每一条候选**：

1. 过 §7 的分层表，给出去向和一句理由。
2. 按去向处理：
   - **产品设计系统**：按 §4 落——先在已有章节里找被它影响的内容，矛盾的统一、过时的改写、已覆盖的不加，只有缺口才新增，新增时同步 front matter 的 token；候选里的「并进」是建议，不是命令。
   - **通用设计原则**：起草成 harold-skills 的 issue 文字（标题 + 原则 + 来源 + 建议落在哪份 reference），问人要不要开；人同意后才跑 `gh issue create -R guohaonan-shy/harold-skills`。
   - **页面或组件的决定**：留在原处（档案里的「决定」），不动正文。
   - **现状、缺陷**：起草一条 `docs/quality-backlog.md` 记录，按那个文件现有的格式。
   - **驳回**：写一句理由。
3. 一批候选的起草结果一起摆给人，人逐条改或批，再走 §9 落笔。
4. **处理完的候选删掉**，去向（落进哪一章 / 开了哪个 issue / 留在原处 / 驳回理由）记在这次执行的结果里，不留在候选上。

### 单条蒸馏

人在会话里说「以后这类卡片都用 X」，手动调一次 `dreaming` 并带上这条规则时，**只处理这一条**，不跑全量对账：

1. 读本文（尤其 §3、§4、§7、§8）。
2. 把口述的话补成 §13 的形态：一句话规则、并进哪一章、为什么、证据。补不出「证据」就问人，不编。
3. 过 §7 的分层表。不是产品设计系统层的，按 §11 的对应去向处理，到此为止。
4. 是产品设计系统层的：按 §4 找受影响的已有内容，起草旧文与新文并排的改动（§9 第 2 步）。
5. 停下等人确认措辞，再落笔。
6. 跑 `lint` 与 `diff`（§9 第 5 步）。

人不调，这条规则就记成候选，等 `dreaming` 的下一次定期处理。

## 12 对账

拿法去量代码。以下情况各自摆给人**逐条**确认，**不自动处理任何一条**：

| 发现 | 处置 |
|---|---|
| **法和代码对不上**（`DESIGN.md` 写 X，代码是 Y） | 人判：法错了就改法；代码错了就起草一条 quality-backlog。法在撒谎比法过期更危险，所以不替人选 |
| **不该在文件里的内容**：§8 表里的各行 | 按 §7 分走。缺陷进 quality-backlog（起草，人确认后追加）；迁移计划、实现细节以文字交给人，建议去处是 spec 或代码注释；历史叙事和划掉的条目直接删，git 留着历史 |
| **先例 / 判例 / 带日期的条目** | 被多处遵循的，先改写成无日期的全局规则并入对应章节，原条目删掉；其余移出（页面决定留在档案）或删除 |
| **被取代的内容** | 删掉。不留「已被取代」的空壳 |
| **同一规则的两种写法** | 统一成一条，只保留一处（§3 规则 2） |

还要过的两样：官方 `lint` 报的 warning（定义了却没被引用的 token、组件 token 的对比度不达标），逐条判是改 token、补 `omitted` 说明，还是交人裁决；以及 §3 五条写法规则的逐条检查（底线是否附实测值、禁令是否带理由、影响渲染的属性是否都在 token 里）。

内容规则里还有两条 CLI 查不出来：**底线少而能检查**（全文五到八条，每条带可检查的 token 或实测值，「无障碍」不是底线，「正文对比度 ≥ 4.5:1，从真 DOM 读」才是；无障碍底线一定要有，它是唯一不该由品味决定的一条）；**禁令带理由**（没有理由的禁令每次会话都会被重新争论）。

**对账的健康信号：这份文件变短的次数应该和变长一样多。** 一次对账只加不减，多半是把盘点当成了法。

## 13 设计法候选的形态

除了 `uiux-imagine`（项目开工时没有 `DESIGN.md`）和 `dreaming` 之外，**任何地方想改 `DESIGN.md` 都只写一条候选**。一条候选长这样：

```markdown
- **<一句话规则，已经是 DESIGN.md 能收的形态：无日期、无页面名、可照做>**
  - 并进：<章名>（新增 / 整改哪一条）
  - 为什么：……
  - 证据：<哪些对象这样做，wikilink>
```

- 没有候选时这一节写一行「无」。空着分不清是没有还是漏了。
- **没有「情境 / 决定 / 理由」三段式，也没有去向行**：`dreaming` 处理完就删，去向记在那次的执行结果里。
- 写的是背后的**规律**，不是具体一次的参数。一个新动效模式，写成可并进 Motion 章的全局原则；具体参数留在动效对象里。
- 候选的住处：它出自的档案对象（页面、组件、动效、用户路径）正文的 `## 设计法候选` 一节；需求进行中写在 `docs/design/tmp/<slug>/delta/` 的对象文件里，归档时随对象进 `prod/`。冻结记录（`tmp/<slug>/canvas/<slug>-design.md`）的同名一节只列一份汇总，每条一行，写明挂在哪个对象上，不重写全文。
- 写不成这个形态（带着日期、页面名，或只对这一页成立）的，不是候选，留在对象的「决定」里。

## 14 谁写、谁读

**写 `DESIGN.md` 的只有两处，都先读本文、都把措辞交人确认：**

| 谁 | 写什么 |
|---|---|
| `uiux-imagine` | **只新建**：开工时项目没有 `DESIGN.md`，选定语言后在同一会话里写第一份（有线上 UI 照 §10.1，没有照 §10.2）。项目已有 `DESIGN.md` 时「重探语言」只产出候选，不改文件 |
| `dreaming` | 新建（定期对账时发现项目没有）/ 蒸馏 / 对账，含单条蒸馏 |

**其余一律写候选**：designer 的动效段签字后的新模式、静态设计签字时的 Distill-back、`uiux-imagine` 的修订提案、实现时冒出来的新 token——都是一条 §13 形态的候选，等 `dreaming` 处理。

**读**：所有设计侧 skill 与 agent，在判断「这条该不该进 `DESIGN.md`」时只读本文。读 `DESIGN.md` 本身（当作项目的设计法）是另一回事：`designer`、各 protocol 和实现标准都读它，但不写它。
