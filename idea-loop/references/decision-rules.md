# 决策规则：什么 agent 自己定，什么交给人

插件里每个角色（起草方、执行方、审查者、编排者）碰到一个「这条该怎么处置」的问题，先对着这份文件。它分两半：

- **自己定**（§1–§4）：能从规则推出处置的，直接照办，不问人。
- **交给人时**（§7）：依据不成立、真要人拍板的题，摆给人之前要先做完的功课。

> 为什么要有这份文件：一轮 review 或一次停下里摆给人的决定，大部分是重复的——有明文规则的违规、说明文字跟已定做法对不上、跟这次无关的存量问题，人每次都定成同一个答案。每一次都走一遍人，是把「按推荐」的力气花在不需要判断的事上，真正要人定的事反而被淹没。所以先写下「什么算判得出来」，判得出来的立即办、单列出来让人能推翻，其余才问人。

**现在读它的地方**：`agents/pr-reviewer.md` 与 `references/review-standards.md`（每条候选标处置）、`skills/engineering/pr-review/SKILL.md`（照规则的条目在贴汇报之前就处理，满足条件时自己起下一轮）、`skills/engineering/to-spec/SKILL.md` 与它的 `references/backlog-mode.md`、`agents/issue-explorer.md`（起草 spec：§4 先自己定、交给人的题按 §7 写）、`agents/implementer.md` 与 `skills/engineering/implement/SKILL.md`（执行方沿用现有做法、存量按依赖分流，停下汇报单列「已按规则处理」，决定题按 §7 写）。别处不再各写一份「谁来定」「题怎么写」的判断，要写就引用这里。

## 1 自己定的四条

一条处置能从下面推出来，就照办，不问人：

1. **有依据就照办。** 依据只认三种，缺一不可具体：
   - **仓库写下来的规则原文**：`REVIEW.md`、`AGENTS.md` / `CLAUDE.md`、它们链接到的约定文档、lint 与 typecheck 的配置。能引原文、指出出处。
   - **人在这份 spec 或这个 PR 里已经做过的决定**：原话，来自 spec、工单（`人的决定`）或这个 PR 的 review loop 文件里人的批示。
   - **产品里已有的统一做法**：能指出至少一处现存实例。「大概是这样」不算。

   由此推出的处置：
   - 有明文规则、没有歧义的 Standards 违规：**修**。
   - spec、工单、说明文字跟已定的做法对不上：**本次同步改**。spec 里交代由来的历史段落保留，标明后来改了。
   - spec 没说的界面细节（文案写法、颜色规则等），产品已有统一做法：**沿用**。
   - 执行方超出范围的删除：删掉的东西没有调用方、也没人读，**接受并补记**进工单；删掉的是有人读的信息，或改变了行为，**恢复**。
2. **归不归这次，看依赖。** 这次引入的，这次修。存量问题**开 issue**；例外是它让这次改动拿到错的数据、让这次的结论站不住、或让 CI 变红——这次修。**谁去找、谁来开**分开看：
   - **审查者不去找存量问题**。它只在存量污染了这次改动、或让 CI 变红时才报（处置是修）；跟这次无关的存量，它不找、不报，更不处置。
   - **跟这次无关的存量，开 issue 由编排者做**，对象是执行方交回的「顺手发现」：`implement` 的编排者逐条在目标仓库开 issue（不加 `status:*` 标签，没标签就是待办，`issue-dispatch` 会接手），写进停下汇报的「已按规则处理」，第 1 轮 review 汇报的「已按规则处理」里也带上这几条；人一句话可推翻（`skills/engineering/implement/SKILL.md` §6）。
3. **代价跟用户会失去的东西相称。** 会丢用户已交的内容、数据、钱：修。只在兜底路径或罕见异常里出现、又不丢东西：接受，写成已知限制。等待时间、体验上的小代价：接受，上线后看数据。**在 PR 流程里这一条只用来定推荐**，见 §3。
4. **默认改动最小。** 结构性的重排（目录重构、换框架）不顺手并进来，要做就单独起。

## 2 依据不成立：照旧交给人

下面这些都不算「判得出来」，处置写成「要你决定」：

- 规则有歧义，两种读法都说得通。
- 两条规则冲突。
- 要引的「产品已有做法」，找不到现存实例。
- 人的决定只覆盖了相邻的情形，要靠推断才能套到这一条上。

**宁可多问，不要靠推断凑出一个依据。** 依据是用来让人一眼核对的，核对不了的依据比没有更糟。

## 3 PR 流程里「代价相称」只决定推荐

第 3 条在起草 spec 时由起草方直接按它定（人审 spec 时会看到）。到了 PR 流程（停下汇报和 review 轮次），边缘情形——只在兜底路径或罕见异常里出现、不丢东西——**照旧是「要你决定」**，这条只用来定推荐，**不进「已按规则处理」**。

理由：这类判断（用户会不会丢东西）本身可能判错，判错的代价是丢用户的数据；而且被推翻的记录还不多。等推翻记录积累得够多（`dreaming` 回看已合并的 PR 时会沉淀），再考虑升级成自动处置。

## 4 不自动的

下面这些照旧只由人定，没有「照规则」这个处置：

- 起名定稿（新词只在 `grill` 里加）
- 人验素材
- 分类体系怎么切
- 方案形状被人提出第三条路的
- 对外发布
- 动生产业务数据
- 合并（下一轮 review 只在 `skills/engineering/pr-review/SKILL.md` §5 写明的条件下自动起，其余照旧由人触发）

## 5 照规则的处置，人能推翻

照规则处理掉的条目，**不等于人不能管**：

- 会话里的汇报在 Spec 与 Standards 之前单列一节「已按规则处理」，每条一句：做了什么、依据是什么、提交或 issue 链接（写法见 `pr-description.md` §5）。
- 人说一句「推翻某条」，编排者当作一条新批示：原话逐字记进 review loop，按人的意思改回或改做；下一轮的审查者读到这条记录，**不再按同一依据**把它标成照规则。
- 所以每条照规则的处置都要留得下依据：原文、出处、实例，不能只留一句「按规则」。

## 6 校验

审查者交回的候选，处置与依据由 `scripts/review-check.mjs` 机械校验：「照规则」必须带依据（三种之一，原文要在出处里找得到）和动作（修 / 同步改 / 接受并补记 / 恢复 / 开 issue），不写选项和建议；依据是规则原文的，原文不在规则文件里就丢弃。形状见 `review-standards.md` §4。

## 7 交给人时

依据不成立、真要人拍板的题——起草 spec 时落进 §4 的选项、`implement` 停下汇报里的决定题、review 汇报里的「要你决定」——摆给人之前，先做完下面三条功课。目的只有一个：人读一遍就懂、答一次就完，不用回头追问「现在到底是怎么做的」「有多少」「这个记号是什么意思」。

### 7.1 现状先查清

- 题里每句关于**现状**的话，都核过代码、数据或文档，能说出出处（在哪、什么时候查的）。「应该是」「大概」不进题。
- 讲影响，带规模数字：不写「不少用户会遇到」，写「最近 30 天 12 次」。查不到数字，写明没查到和原因，不估。
- 同一行为的**其他入口**查过：同一个能力还有哪些页面、接口、调用方走同一条路。写明每个是纳入还是排除，排除的给一句理由。
- **相邻在飞**的 spec、issue 查过，写明有没有重叠；有的，写明谁先谁后、互相依不依赖。
- 出题前对着**最新的基准分支**再核一次。别人刚合进去的改动，可能让题的前提过期；前提已变，题重写，或者撤掉。

### 7.2 先写交付物，再列做法

- 先写用户最终得到什么、由哪些输入决定，再列实现方式。方案的形状是在这一步定的，写反了，选项就会落在错的层次上。
- 选项之间要有**用户能感到的差别**。只差在内部结构、用户感觉不到的，不是选项，是实现细节——按 §1 第 4 条自己定。
- 每个选项牵出的后续写全：选了它，哪些中间状态要处理（做到一半被打断、取消后回到哪一步、已经产生的数据怎么办）。
- 改了 spec 的文字，图和测试表同步改。图停在审核前的版本，等于让人在对不上的两份东西之间选。

### 7.3 每个问题、每个选项配具体例子

- 每个问题、每个选项各配**一个具体例子**：一个真实的输入，走一遍，看到什么、本该看到什么。
- **陌生记号先解释**。题里用到的缩写、内部术语、符号，第一次出现时说清它是什么。
- **不用裸编号指代选项**，也不用 R1 / R2 这类别处定义的编号指代内容：写出它是什么。选项自己的 A / B 标签可以用，引用时带上半句内容。
- **比对类证据在同条件下做**：同语言、同数据、同版本、同设备。条件对不上，证据不能拿来比。
- **要人评判文案或素材时，先给评判标准**：评判什么、好和不好各长什么样；没有标准的评判题，人只能凭感觉答，下一次又得再答一遍。

### 7.4 怎么校验

这一半没有脚本校验，靠写题的人逐条自核、审的人逐条核对。起草这一侧，`agents/issue-explorer.md` 的自检把它写成了可以逐条核对的句子。
