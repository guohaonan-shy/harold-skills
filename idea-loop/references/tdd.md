# TDD —— red → green 循环，以及怎么让它产出值得留的测试

`implement` 在写测试前读这份。它不是"要不要写测试"的说明书——**该用哪种仪器验，spec 的 §5 已经答过了**。这份只管：既然这一刀落在 TDD 那几行上，怎么把循环跑对。

---

## 好测试是什么

**测试通过公共接口验证行为，不验证实现细节。** 实现可以整个换掉，测试不该动。

好测试读起来像一份规格——`user can checkout with valid cart` 一眼看出存在什么能力——并且能活过重构，因为它不关心内部结构。

## seam —— 测试落在哪

**seam** 是你能观察行为、而不必伸手进内部的那个公共边界。测试住在 seam 上，永远不测内部。

**只在事先谈拢的 seam 上测。** 写任何测试之前，seam 已经在 spec 的 §5 写下来并经人确认了。**没有确认过的 seam，不写测试。**

你测不了所有东西。提前谈拢 seam，就是让力气落在关键路径和复杂逻辑上，而不是每一个边界情况。

> 顺带：先写测试的动作**本身就是接口设计的动作**——这是 TDD 作为设计工具的那一面，也是为什么 seam 必须在写代码前定。

## 三种反模式

- **耦合实现** —— mock 了内部协作者、测了私有方法、或者绕过接口从侧门验证（去查数据库而不是用接口读回来）。**判别标志：重构了、行为没变，测试却红了。**
- **同义反复** —— 期望值是按代码同样的方式算出来的（`expect(add(a,b)).toBe(a+b)`、手工照着实现推出来的快照、常量等于自己），于是它天生就过，永远不可能跟代码唱反调。**期望值必须来自独立的真相源**：一个已知的字面量、一个手算的例子、spec 的原文。
- **横向切片** —— 先写完所有测试再写所有实现。批量写出来的测试验的是**想象中的**行为：你测的是形状而不是用户可见的行为，测试对真实改动变得不敏感，而且你在理解实现之前就把测试结构锁死了。要**纵向**走——一个测试 → 一段实现 → 重复，每个测试是一颗**曳光弹**，回应上一轮教给你的东西。

## 循环的规矩

- **先红后绿。** 先写会失败的测试，再写刚好让它过的代码。不要预判后面的测试，不要加投机性功能。
- **一次一刀。** 一个 seam、一个测试、一段最小实现。
- **重构不属于这个循环。** 它属于 review 阶段，不属于 red → green。

## mock 只在系统边界

可以 mock：**外部 API**（支付、邮件）、**数据库**（有时候——**优先用测试库**）、**时间/随机数**、**文件系统**（有时候）。

不要 mock：**你自己的类/模块**、**内部协作者**、**任何你控制得了的东西**。

为可 mock 性设计：依赖注入（把外部依赖传进去，别在里面 new）；SDK 式接口优于万能 fetcher（每个外部操作一个具体函数，mock 时不用在里面写条件分支）。

> **存量代码大概率不符合这条，这是常态，不是要你回头重写。** 典型违规形态是 `patch("app.services.X.SomeRepository.get_by_id")` —— 把自己的类替换在**另一个自己模块的 import 点**上，正是上面那条判别标志的教科书案例；这种 mock 在真实代码库里往往成百上千处，一次扫清不现实。
>
> **实用政策：只约束新增。** 新写的测试守这条边界，存量不用倒查、不用一次扫完。如果发现某类 mock 其实是被环境问题逼出来的（比如某个模块一 import 就有副作用，测试环境又没配好那个依赖），那是环境缺陷不是测试哲学问题——单独登记单独修，环境修好之后那批 mock 会自己消失。

## 什么时候不该用 TDD

spec §5 的仪器矩阵已经划好了。判据是**能不能先写出一个会红的测试**：

- **LLM 输出质量** —— 输出非确定，无从写红 → **eval**（promptfoo + 确定性 assert）
- **视觉正确性** —— 感知性判断 → **截图对比**（`design-port`）
- **端到端流程** —— 跨系统，红了也定位不到 → **`qa:*` 浏览器测试**

缝里的情况：**prompt 改动本身走 eval，但 prompt 产出的结构**（schema、字段存在性、枚举闭集）**走 TDD**。
