# 术语表（GLOSSARY.md）

目标项目根目录的 `GLOSSARY.md` 存什么、长什么样、谁来写、怎么读。新增和改名只在 `grill` 里写，`dreaming` 经人同意做订正和删除；
其余产出命名的 skill（`to-spec` / `to-ticket` / `implement` / `pr-review`）只读。**每一次写入都以 Harold 当场的拍板为真相源。**

> 来源：改写自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `domain-modeling`
> （`skills/engineering/domain-modeling/`，v1.3），MIT License，Copyright (c) Matt Pocock。
> 跟上游不同的地方有四处，都是有意的，列在文末。

---

## 1 它是什么，不是什么

**一份术语表，别的什么都不是。** 每条只回答两件事：这个东西在本项目里叫什么，它是什么。

它不是 spec，不是草稿本，不是实现说明，不是调研笔记。上游作者报告的头号失效就是膨胀：模型把「写进术语表」
当成「把每个答案都存下来」，几个月后文件变成一份 spec。下面每条规则都是为了挡住这一点。

## 2 收什么：三问全过才收

1. **换实现测试**：把实现整个换掉（改表名、换语言、重写这段代码），这句话还对吗？不对就是实现细节，不收。
2. **项目特有**：这是本项目（或它所在业务领域）的概念，还是通用编程概念？超时、错误类型、工具模式这类，项目用得再多也不收。
3. **真被当名字用，且会叫歧**：它在对话、代码或 spec 里被当成名字使用，**并且**存在不止一种叫法，或者容易跟另一个概念混。
   只有一种叫法、也不会跟别的概念混的词，收了也没用。

### 不收的东西去哪

| 内容 | 去处 |
|---|---|
| 字段取值、枚举编码（`1=active`、`category=2`）、表结构、存储位置 | 目标项目的 `AGENTS.md`（表结构那节）或代码本身 |
| 代码约定（命名风格、下划线还是连字符） | 最近的 `AGENTS.md`，能 lint 就写成 lint |
| 指向代码常量或文件的「以 X 为准」 | 对应的 `docs/domain/` 文档或模块 `AGENTS.md` |
| 机制、调研、分类体系、「它怎么运作」 | `docs/domain/` |
| 决策和它的理由 | spec，了结后进 ADR（归 `dreaming`，见 `wiki-conventions.md` §1） |

方向是单向的：其他文档用术语表里的叫法，术语表不链回它们。

## 3 文件与结构

### 位置

- 单一上下文（多数项目）：仓库根目录一份 `GLOSSARY.md`。
- 多上下文：根目录一份 `GLOSSARY-MAP.md`，指向各上下文自己的 `GLOSSARY.md`。**先拿子标题分组撑着**，
  只有当文件已经精简、仍然覆盖两块读者不会同时需要的领域时才拆。一份膨胀的文件拆开，只会得到几份膨胀的文件。
- **按需创建**：第一个术语定下来时才建文件，不提前建空壳，不因为文件不存在去提醒人。
- 它在 `docs/` 之外，不是 vault 的一部分：**不带 frontmatter**，不参与 `wiki-conventions.md` 的 slug 唯一性。

### 格式

```md
# {上下文名}

{一到两句：这个上下文是什么，为什么存在。}

## 术语

### {分组，可选}

**Practice**：
学生可以做的一条练习，属于四种题型之一。
_Avoid_: exercise, drill

**Cause layer**：
一个错词被归到的错误发生位置，三层之一：发音、听力、表达。
_Avoid_: error type, category（Issue 上另有一个也叫 category 的分类，指的是别的东西）

## 歧义词

- **status**：代码里有至少六套互不相关的 status。单独说 status 不成立，必须带上实体名（Practice status、Session status……）。
```

### 词条规则

- **词条名**用项目里实际流通的写法——代码和对话里都这么叫的那个，英文就写英文。
- **定义一到两句，写它是什么，不写它做什么。**
- **要有主见**：一个概念只留一个标准叫法，其余叫法进 `_Avoid_`。`_Avoid_` 里的词可以带一个括号，说清它其实指什么。
- **正文里不出现**：反引号、文件路径、链接、「数字=含义」这类取值映射。出现了，几乎一定是第 2 节该挪走的东西。
- 自然成簇就用 `###` 分组，否则平铺。二级标题只有 `## 术语` 和 `## 歧义词` 两个。
- 定义用目标项目文档的语言写。

### 歧义词规则

`_Avoid_` 只能表达「这个概念别用那个词叫」，是一个概念对多个词。**一个词对多个概念**挂在哪个词条下都不对，所以单独一节。

- 只有一个词能指**两个以上**概念时才进这一节；只指一个概念的，写成那个概念的 `_Avoid_`。
- 每条一到两句：这个词可能指哪几样，单独出现时该怎么说。

这些格式规则由 `glossary-check` 机械校验，见第 7 节。它不判断内容该不该收——那是第 2 节和人的事。

## 4 写：人拍板之后当场写

**只有两个入口能写，而且每次都要 Harold 当场拍板。** 入口收窄是有意的：每个 skill 都能写，术语表就没人管得住。

| 入口 | 写什么 | 时机 |
|---|---|---|
| `grill` | 新增、改名 | 访谈中，人答了术语题当场写（见下） |
| `dreaming` | 订正、删除 | 对账发现词条过时或跟代码对不上，逐条问人，人同意了才改 |

`to-spec` / `to-ticket` / `implement` / `pr-review` 一律不写（第 5 节）。没有拍板的，谁都不写。

### 什么时候出术语题

`grill` 每轮开始前读一遍术语表（不存在就跳过）。下面三种情况，各当成一道 frontier 题问出来，附上推荐叫法：

- **跟术语表冲突**：「术语表里 cancellation 定义为 X，你这里说的像是 Y，是哪个？」
- **叫法模糊或一词多用**：「你说的 account 是 Customer 还是 User？这是两样东西。」
- **跟代码对不上**：人说某个东西怎么运作，去代码里核实；矛盾就摆出来——「代码里取消的是整个 Order，你刚说可以部分取消，哪个对？」

讨论概念之间的关系时，**自己编具体场景去压边界**，逼出两个概念的分界在哪。

### 什么时候写

**人回答了术语题之后、算下一轮 frontier 之前，当场写。** 不攒到收工再写——攒到最后写出来的是一份总结，会漏。
没回答的推荐叫法不写。人没拍板的词，写进去就是一份听起来很确定的 agent 臆测，后面的会话会把它当真——
**一份没人审过、由 agent 写的术语表比没有更糟**。

### 每次写都是改，不是追加

- 新增一个词，同时处理被它取代的那个：挪进 `_Avoid_`，或者删掉。**不留「旧版」小节。**
- 一个词条的概念在项目里已经没了，删掉它。
- 健康的术语表**变短的次数和变长的一样多**。只增不减，就是在膨胀。

## 5 读：所有产出命名的地方

产出里要给领域概念起名时——spec 标题、ticket 标题、测试名、PR 描述、review finding——读术语表：

- 用标准叫法，不用 `_Avoid_` 里的词。
- 碰到歧义词，按那一条说的带上限定。
- 需要的概念术语表里没有：先想一下是不是在造项目里不存在的说法（是就换个说法）；是真缺口，按下面的分工处理。

### 缺词怎么收

- **`grill` 里**：就是一道术语题，人答了当场写。
- **`to-spec` / `to-ticket` / `implement` 里**：不问、不写，用一个描述性的说法先把活干完。
- **`pr-review` 里**：只报不写。Spec 轴对着 diff、spec 和 ticket 找「用到了、但术语表里没有」的领域概念，
  连同上面三步留下的描述性说法，一起列进轮次帖的「缺词」栏，每条写清概念和推荐叫法。主会话向人汇报时把这一栏念出来，
  要不要补、怎么叫，由人决定开一轮 `grill` 定。轮次帖留在 PR 上，这份清单不会随会话结束而丢。

术语表不存在就照常干活，不提醒、不建议创建。

### 目标项目里怎么接

读取规则落在目标项目根的 `AGENTS.md`，用普通 markdown 链接，不依赖 `@` 导入（那是 Claude Code 专有写法，Codex 不展开）。模板：

```md
## 领域词汇

[GLOSSARY.md](GLOSSARY.md) 是本项目的术语表。给领域概念起名前先读它：用标准叫法，不用 `_Avoid_` 里的词，
歧义词按它说的带限定；缺词不自己造词，在产出里说明缺了什么。
```

## 6 一致性：谁来发现它烂了

- **`dreaming`**：对账时查两件事——`_Avoid_` 里的词有没有出现在新代码或新文档里；词条说的概念在代码里是不是已经没了。
  每条订正或删除都先摆给人，人同意了才改，不批量默认执行。
- **`pr-review` 的 Spec 轴**：PR 新增或改名了一个领域概念，术语表却没动，进「缺词」栏（第 5 节）。

## 7 机械校验：hook 管写入，CI 兜底

`scripts/glossary-check.mjs` 是一个 lint：只查第 3 节的格式规则，不调模型，退出码 0 通过、2 有违规、1 读不了文件。
它在两个地方跑，**skill 里不需要手动调用**：

- **plugin 的 PostToolUse hook**：任何 Write/Edit 落到一个名为 `GLOSSARY.md` 的文件上就跑，违规写到 stderr、退出码 2，
  直接反馈给正在写的模型，当场改。别的文件一律静默放过。
- **目标项目的 CI**：挡住绕过 hook 的改动（人手改、别的工具改）。脚本是单文件、零依赖，本仓库公开，CI 按 commit sha 钉版本直接拉，
  不往目标项目里复制一份。升级就是改 sha。

```yaml
name: Glossary check
on:
  pull_request:
    paths: ['**/GLOSSARY.md']
jobs:
  glossary:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: |
          curl -fsSL https://raw.githubusercontent.com/guohaonan-shy/harold-skills/<sha>/idea-loop/scripts/glossary-check.mjs -o /tmp/glossary-check.mjs
          git ls-files | grep -E '(^|/)GLOSSARY\.md$' | xargs -r -n1 node /tmp/glossary-check.mjs
```

## 跟上游的差异

| 上游 | 这里 | 为什么 |
|---|---|---|
| 独立 skill `domain-modeling`，模型可自动调用 | 一份 reference，写入和读取的 skill 都显式读 | 上游自认最大的失效是被别的 skill 调用时漏加载；写死在 SKILL.md 里的必读项不会漏 |
| 同一个 skill 管 ADR，会话中满足三条件就提议写 | 不管 ADR | ADR 在 idea-loop 里只由 `dreaming` 在删 spec 前写，状态闭集也不同 |
| 只有 `_Avoid_` | 加一节「歧义词」 | 一个词对多个概念的情况 `_Avoid_` 表达不了 |
| 「不写实现细节」靠模型自觉 | 第 2 节三问 + 不收清单的去处 + `glossary-check` 机械校验 | 膨胀是上游报告最多的问题，给想多写的内容一个明确去处，比单靠「不许写」管用 |
