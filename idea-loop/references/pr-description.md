# PR 页面——人审一次交付的地方

一份 spec 的所有工单共享**一条集成分支、一个 PR**。这个 PR 只写给一个读者：要判断这次交付能不能合并的那个人。他每次打开都要能马上知道两件事：**要我决定什么，要我看什么。**

> 曾经的 PR 描述把 spec 的「为什么」和每张工单的改动重写了一遍，再附上给 review agent 读的验收契约；轮次帖里是复现命令和检查日志。一个 PR 加起来四五万字，真正要人做的那一件事埋在中间。这份文件就是为了不再那样写。

## 1 PR 描述是总览，thread 是对话

| 阶段 | PR 状态 | 要人决定、要人看的东西 | 谁写 |
|---|---|---|---|
| **实现中**：工单没全部落地，或还有等决定的事 | draft | 每次停下开一个**停下汇报 thread**（§4） | `implement` 的编排者 |
| **review**：全部落地、没有等决定的事 | open | 每一轮开一个 **review thread**（§5） | `pr-review` 的审查者 |

人在 thread 里回答、批示、追问，**以他自己的身份**。Claude 的汇报和回复**以项目 bot 的身份**（§2）。

PR 描述本身是常驻的总览。读它的人**打开时没有上下文**：活是委托出去的，spec 他可能只记得个大概。所以描述从「这是什么」往下读到「要我做什么」，越往下越可以不读；只为查证的东西折叠在最后。**描述里不放 review**：每一轮 review 都有自己的 thread，描述里再放一份摘要只会重复。

| 节 | 标题 | 写什么 | 写入方 |
|---|---|---|---|
| `summary` | 一句话 | 这个 PR 让谁能做什么，或者修好了什么。只读这一句也知道它是干嘛的 | `implement`：开 draft 时写，转 open 前按落地结果重写 |
| `changes` | 改了什么 | 按点分块：碰页面的，每个页面端到端变了什么，加上后端流程变了什么；没碰页面的，只写后端流程的变化。**每一块里**放之前 → 之后的对照、替你做的决定、怎么验证的和验证了哪些点 | `implement` 转 open 前写，对照图专门拍 |
| `your-todo` | 要你做的事 | 要你审的、要你决定的、上线前要你注意的 | `implement` 转 open 前写；`pr-review` 的编排者每轮之后更新 |
| `reference` | 参考 | 折叠：按模块的改动地图、spec 和工单链接、执行记录、合并后 Claude 做的清理 | `implement`：开 draft 时写，每次停下更新 |

**整个描述是给人读的。** 折叠的「参考」以外，不写代码行、变量名、函数名、文件路径、提交号、spec 或工单的章节编号，说页面、流程、行为和后果。`pr-body.mjs` 写入前会机械地查这一条，查到就拒写；图片和链接的地址不算。

每节的格式见 §6。每节夹在隐藏标记之间，由 `scripts/pr-body.mjs` 按固定顺序写入，**标题由脚本加**，内容文件里不用写：

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-body.mjs" set <owner/repo> <PR 号> <节名> <内容文件>
```

每个写入方只重写自己负责的节。标记以外的文字（人手写的说明、署名行）会被保留，放在所有节的下方。**不要直接 `gh pr edit --body` 整体覆盖**，那会把别人的节一起冲掉。PR 描述本身由 gh 当前登录的账号写：它是 PR 的一部分，不是一条发言。

## 2 Claude 的帖子：bot 身份，一次报告一个 thread

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-thread.mjs" open  <owner/repo> <PR 号> <pause|review> <轮次> <正文.md> <锚定的工单文件>...
node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-thread.mjs" read  <owner/repo> <PR 号> <thread 首条评论 id>
node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-thread.mjs" reply <owner/repo> <PR 号> <thread 首条评论 id> <回复.md>
node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-thread.mjs" edit  <owner/repo> <PR 号> <评论 id> <新正文.md>
node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-thread.mjs" list  <owner/repo> <PR 号>
```

- **一次报告，一个新 thread。** 停下汇报和 review 轮次都这样。下一次停下、下一轮 review，再开新的，**不在旧 thread 里接着汇报**。轮次取 `list` 输出的 `next.pause` / `next.review`。
- **为什么是 review 评论**：GitHub PR 的 Conversation 评论是平铺的，不能回复某一条；能接着回复、能 Resolve 的只有 review 评论。所以每份报告是一条 **file 级的 review 评论**，锚在 PR diff 里的某个工单文件上（脚本只会锚在 diff 里有的工单文件上）。它照样显示在 Conversation 里。
- **以 bot 的身份发。** 仓库在 `~/.idea-loop/github-apps.json` 里配了 GitHub App（通常叫 `<project>-claude`）时，脚本用它的安装令牌发帖。令牌只活在脚本进程里，不打印、不写盘、不交给 agent。没配时借用 gh 当前登录的账号，但每条开头都写明「由 Claude 代发，不是本人所写」。**不以人的身份说话。** 人在对话里而不是 thread 里回答的，编排者把原文转贴进 thread，开头标「Harold 在对话里回答：」，让 PR 上的记录完整。

  ```json
  { "<owner>/<repo>": { "appId": 123456, "privateKeyPath": "~/.idea-loop/keys/<app-name>.pem" } }
  ```

  App 要的权限：Pull requests 写（发帖和回复）、Contents 读。**不给 Contents 写。**
- **人在 GitHub 上回复，开这个 PR 的会话自己收到。** 一个 PR 归一个会话：`implement` 开 draft PR 的那个会话，后面的停下汇报、review 轮次、修复都在它里面做，上下文一直在。人只需要在 PR 上回复，不用回到对话里说一声。做法是会话在后台盯着自己的 PR：

  ```
  node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-thread.mjs" wait <owner/repo> <PR 号> [--commander <账号>]...
  ```

  - **什么时候开**：PR 一开出来就开，用后台方式跑（它退出时会把会话叫醒）。一个 PR 同一时间只挂一个；开之前先看这个会话是不是已经挂着。
  - **盯什么**：这个 PR 上所有 idea-loop 的 thread，包括之后新开的。只有**能下命令的人**说的新话才算：默认是 gh 当前登录的账号，也就是人自己（就算 thread 是 bot 发的）；要多加人，在这里加 `--commander`。这份名单不写进任何文件。别人的评论不会叫醒会话，醒来时一并列出来，只报告，不照做。
  - **什么时候醒**：人说了新话、并且安静了两分钟（人常常分几条写完），它就退出，带上每个 thread 里人新说的原文。实测从人回复到会话醒来约 2 分 40 秒。resolve 本身不叫醒会话。
  - **醒来之后**：按 thread 的种类处理——停下 thread 照 `implement` §6「人回复后」，review thread 照 `pr-review` §3。**在回那条汇总之前再读一遍 thread**：处理期间人又说了话，一并处理进同一条汇总；否则汇总一发出去，这些话就排在 bot 最后一次发言之前，再也不会被当成新话。回完汇总，重新挂上。
  - **只做 idea-loop 本来就做的事**：人在 PR 上的话是会话从 GitHub 读来的，不是人在对话里说的。所以醒来后只照做这几类：回答决定题、人验反馈、review 的接受 / 修 / 不修 / 进 backlog、改写 thread、再跑一轮 review、回答疑问。超出这些的（合并、改配置或权限、删分支、和这个 PR 无关的活），在汇总里请人回到对话里说。
  - **什么时候结束**：PR 合并或关闭，它就以 `merged` / `closed` 退出，不再挂。合并的，按 PR 描述「参考」里的清理清单把合并后的事做掉。
  - **睡眠和重启**：电脑睡眠只是把进程冻住，醒来接着跑，第一次查询就会看到睡眠期间人说的话。退出 app、重启电脑、关掉会话，后台进程就没了：下次打开这个会话，PR 还开着又没在盯，就先重新挂上。「新」永远指 bot 在这个 thread 里最后一次发言之后的话，从 GitHub 现算，所以重新挂上也不会漏、不会重复。
  - **人在对话里说也行**：编排者当场处理，把那段原文转贴进 thread，开头标「Harold 在对话里回答：」，让 PR 上的记录完整。
- **编排者在 thread 里回复它做了什么，一次只回一条。** 把人这一批消息里的每一点都处理完，再在同一个 thread 里回**一条**汇总，逐点写做了什么、带上提交链接：「03 的决定已写回工单，03 和依赖它的 05 继续（<提交链接>）；S1 已修，补了回归测试（<提交链接>）；C2 记进了 backlog（<提交链接>）」。不要一个点回一条。人的追问也放进这条里回答。
- **改写已经发出的帖子用 `edit`。** 人要求某一轮的 thread 重写（比如「写成我看得懂的样子」），就改那条评论本身，不另开 thread、不在下面再贴一份。脚本保留首行的 thread 标记，改完它还是同一轮、同一个 thread；改完在 thread 里回一句改了什么。
- **resolve 是人的签收，不是 bot 的。** 一个 thread 里的事都处理完了，编排者回一句「都处理完了，确认无误请 resolve」，由人点 resolve，人也可以随时重新打开。编排者从 `list` 读每个 thread 的状态，把「都已 resolve」当作人签收的信号。另外，GitHub App 要有 Contents 写权限才能 resolve review thread，bot 不该为此拿到能改代码的权限。

## 3 不写什么

- **不复述 spec 和工单。** 「为什么」在 spec §1，每刀做了什么在工单里，`reference` 里给链接就够。
- **不写给 agent 看的东西。** 验收契约就是分支上的工单文件，review 的 agent 直接去读，不在 PR 里另抄一份。复现命令、检查日志、修复前后对比这些过程材料，不出现在 PR 上。
- **描述里不放 review。** 结论、条目、图都在各轮的 thread 里。
- **review thread 的正文不出现代码层面的指称**（§5）：变量名、函数名、「文件:行号」、提交号、spec 或工单的章节编号（「§4.7」）都不写。读 thread 的是拍板的人，这些他看了也不知道是什么意思。代码位置只给修复方，放进 thread 最后的折叠区。

## 4 停下汇报（`pause` thread）

`implement` 每次停下（没有能做的工单了）就开一个，汇报这一次停下之前发生的事。

```markdown
## 第 N 次停下 · 落地 <K> 张，等你决定 <M> 件

> <一句话说明叠加层：光圈 / 蓝点 = 鼠标位置，角落秒表 = 从某事件起计时，都不属于产品>

### 需要你决定

#### <工单号 · 一句话说卡在哪>
<两三句：缺的是什么，为什么查代码定不了>

![<图说>](<素材 URL>)        ← 有助于理解时才放：分支逻辑一张 flowchart，界面行为一张流程图

- **A**：<做法>——<代价>
- **B**：<做法>——<代价>

推荐 A：<一句理由>。在等它的工单：<编号列表>

### 交付验收

#### 03 · <工单标题>

**流程**
- [ ] <看什么>

  ![..](<URL>)

**动效**
- [ ] <看什么>

  ![..](<URL>)

**执行方替你做的取舍**
- <取舍>：<为什么这样选>；不同意就说，改起来是 <小 / 中 / 大>

---
在这个 thread 里回复就行：决定写「03 选 A」，人验项不对就说哪一项、哪里不对，有疑问直接问。
```

- 只写**本次停下之前新落地**的工单，上一个 thread 里交过的不重复。
- 素材的做法与形态见 `evidence.md`。每项是复选框 + 一句「看什么」+ 素材。人在 GitHub 上直接勾选：bot 发的评论，有写权限的人也能勾。
- **只放要人判断的**：逐格比对已经全绿的格、单测覆盖的逻辑都不放。一张工单没有人验项，也没有取舍，就只写一行「无需人看」。
- 没有等决定的事，就不写「需要你决定」这一节。

## 5 review 轮次（`review` thread）

`pr-review` 每跑一轮，开一个 `review` thread 放这一轮的全部结论，**PR 描述不动**。人在 thread 里批示，编排者按批示修，修完在同一个 thread 里回复；下一轮由人触发，开新的 thread。

**这个 thread 写给拍板的人看。** 他要的是：问题是什么、跟 main 有什么不同、用户会感受到什么区别、要他定什么。范围说明、审法、spec 原文、提交号、代码路径堆在前面，他看完描述和图还是不知道问题是什么。所以开头只有一句结论，每条固定几段，其余的收进最后的折叠区。

### thread 正文

```markdown
## Review 第 N 轮

**结论**：<有没有把已有功能改坏>。Spec <K> 条、Standards <M> 条<，都是要你拍板的事，不是 bug>。机械检查<全绿 / 有 X 处没过>。

---

### Spec：代码有没有按 spec 做

#### S1 · <后果：用户能感到的那句话>

<问题：一两句，是什么、跟 main 哪里不一样>

**对用户的影响**：<谁、在什么情况下、多常见会碰到；碰不到就写「用户感受不到」>

<证据：最快能让你看懂的那种——截图、带标注的截图流程、动图、时序图、一张小表、一行例子；非行为问题没有这一块>

**要你决定**：<一句前提：和 spec 或工单的哪条规定对不上，那条规定是干什么用的>。<选项 A>，还是 <选项 B>？建议 <A>：<一句理由>。

---

### Standards：代码有没有守仓库写下来的规则

#### C1 · <违反了什么>

- **规则**：<规则原文>（<哪份文档，用文档的名字说>）
- **现状**：<代码现在怎么做，用话说>
- **影响**：<现在会怎样；现在没事就说以后在什么情况下出事>
- **建议**：<一个改法>

---

### 术语表缺的词（不阻塞）

| 概念 | 推荐叫法 | 代码里现在的名字 |
|---|---|---|

<details><summary>本轮审了什么、没审什么、丢弃的候选，以及给修复方的位置</summary>

**审的版本**：<短 SHA>，基准 <基准分支>
**核对过、没有问题的**：<一两行>
**没覆盖到的**：<哪些没看，由谁补>
**机械检查**：<每条命令一行：命令 | 结果（只算这次改动过的行）>
**丢弃 K 条**：<每条一行：是什么，为什么丢（没复现 / 规则原文找不到 / 不在 diff 里 / 人上一轮说过不修）>
**规则有歧义、没当违反**：<每处一句>
**给修复方的位置**：<S1 → 文件:行号、提交号；C1 → 文件:行号，以及违反规则的那几行代码>

</details>

---
在这个 thread 里逐条回复就行，比如「S1 接受，C1 修，C2 进 backlog」，有疑问直接问。
```

### 每条怎么写

- **标题就是后果。** 用用户能感到的话说（「连续失败几次的学生会提前用完当天的练习次数」），不用代码视角的说法（「重试路径扣了配额」）。不是 bug、只是和 spec 对不上的，标题就说是什么（「修了一个 spec 说这次不修的 bug」）。
- **对用户的影响要具体**：谁、在什么情况下、多常见。用户感受不到就直说，这种通常是要你拍板的事，不是 bug。
- **说行为和后果，不说代码。** 正文（开头结论、问题、影响、证据、要你决定）不写变量名、函数名、「文件:行号」、提交号、spec 或工单的章节编号。要指 spec 的某条规定，就把那条规定用话说出来。代码位置只放折叠区最后的「给修复方的位置」，审查者交回编排者的报告里也有。`review-check.mjs` 会机械地查这一条（`review-standards.md` §4）。
- **「要你决定」的前提要说清那条规定是干什么用的。** 例：「工单把报告取音频的总时长上限定为 5 秒，用来让报告最多等 5 秒就出现。」规则覆盖了一部分的，直接写覆盖了谁、漏了谁，选项就是要不要补。
- **至少两个选项，并给出建议。** 不是 bug 的，选项通常是「接受，把它补进 spec 或工单」与「拆出去」。
- **Standards 的「规则」引原文**，来源说文档的名字（「后端的 AGENTS.md」）。违反规则的那几行代码放进折叠区，不放正文。

### 证据：选最快能让人看懂的那种

不规定图种，按「人需要看见什么」选。一句话就说清了的，不配图。

| 人需要看见的 | 最快的形式 |
|---|---|
| 界面上哪里不一样 | 之前 / 之后两张截图并排，差别处画红圈 |
| 走到第几步分叉、出错 | 截图拼的流程（`evidence.md` §3），带标注，出错那一步画红圈 |
| 动起来哪里不对 | 动图（`evidence.md` §4） |
| 谁先谁后、等了多久（多为后端） | 时序图（excalidrawer `sequence`），main 和本分支的结局并排；两种实现规则不一致的，同一张图里用虚线框标出不一致的那一段 |
| 规则覆盖了谁、漏了谁 | 一张小表：场景 × 有没有覆盖 |
| 数值或计算不对 | 一行具体例子：输入 → main 的结果 → 本分支的结果 |

非行为问题（多了 / 少了一个文件、路径和 spec 写的不一致）没有证据块，diff 本身就是证据。图的地址用 `evidence.mjs publish` 给的地址，点开能在浏览器里看原图（`evidence.md` §2）。

### 规则

- **行为问题必须复现，并带上复现证据**（图、表或例子）。复现不了的，放进「丢弃的候选」，只记一行。
- **Standards 的问题必须引用规则原文，而且违反的代码必须在这次的 diff 里。** 对不上的同样丢弃。机械检查（lint、typecheck、仓库声明的检查命令）的结果并入 Standards，只计这次改动过的行；挂在改动行上的诊断才成为 `C` 条目。
- 编号 `S1` / `C1` 只在这一轮内有效，方便人批示时引用。
- **缺词**：这次 PR 引入或改名、但目标仓库 `GLOSSARY.md` 没收的领域概念，用表格写概念、推荐叫法、代码里现在的名字（这一列本来就是代码里的名字，不受上面「不说代码」的限制）。不是问题，不阻塞，loop 不写术语表（新词只在 `grill` 里加，见 `glossary.md`）。没有就不写这一节。
- 两轴分开写，**不合并、不跨轴排序**：一处代码可以守规矩却做错了事，也可以做对了事却破了规矩，分开报才不会互相掩盖。

## 6 描述的四节

```markdown
## 一句话

<谁现在能做什么 / 修好了什么>。

## 改了什么
```

- **一句话**写结果，不写过程。
- **改了什么按点分块，每块自成一体。** 碰了页面的，一个页面一块，写这个页面从进入到离开端到端变了什么，再写它背后的后端流程变了什么；没碰页面的，一个后端流程一块。读完一块，人就知道这一点改成了什么样、Claude 在这一点上替他定了什么、凭什么说它是对的。
  - **之前 → 之后**在转 open 前**专门拍**，不复用人验素材（那些是为验收拍的，角度不一定是对照）。同一组操作在基准分支和本分支上各走一遍，取同样的组件、同样的宽度。前端用截图、动图或带标注的截图流程，后端用时序图；具体哪种按「最快能让人看懂」选（原则同 §5「证据」）。文件名以 `pr-` 开头，用 `evidence.mjs publish` 上传。用户感觉不到的改动，写一句「用户看不到变化」再加一句换来了什么。
  - **替你做的决定**只收工单实现过程中执行方自己定的事（大部分决定在 `grill` 和 `to-spec` 里已经由人定了，那些不再列）。每条写决策背景、定成了什么、对用户的影响。这一点上没有就不写这一行。
  - **怎么验证的**写方式、验证了哪几个点、结论。不写风险。
- **要你做的事**只有三类：要你审的（还没勾的人验素材、最新一轮 review thread）、要你决定的（review thread 里等批示的条目、替你做的决定里建议你确认的）、上线前要你注意的（生产配置、手动迁移、真实服务的冒烟）。Claude 自己能做的不列。做完的勾上，不删。
- **参考**整节折叠，只给想追溯的人看；提交号这类查证用的东西只放这里。
