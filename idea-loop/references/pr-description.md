# PR 页面与汇报——人审一次交付时读的东西

一份 spec 的所有工单共享**一条集成分支、一个 PR**。PR 描述和过程中的汇报只写给一个读者：要判断这次交付能不能合并的那个人。他每次看都要能马上知道两件事：**要我决定什么，要我看什么。** 这份文件规定 PR 描述怎么写（§1、§6），以及停下汇报和 review 轮次怎么写（§4、§5）；汇报放在哪、人怎么回复、怎么归档，见 `review-loop.md`。

> 曾经的 PR 描述把 spec 的「为什么」和每张工单的改动重写了一遍，再附上给 review agent 读的验收契约；轮次帖里是复现命令和检查日志。一个 PR 加起来四五万字，真正要人做的那一件事埋在中间。这份文件就是为了不再那样写。

## 1 PR 描述是总览，汇报在会话里

| 阶段 | PR 状态 | 要人决定、要人看的东西 | 谁写 |
|---|---|---|---|
| **实现中**：工单没全部落地，或还有等决定的事 | draft | 每次停下一份**停下汇报**（§4） | `implement` 的编排者 |
| **review**：全部落地、没有等决定的事 | open | 每一轮一份 **review 汇报**（§5） | `pr-review` 的审查者 |

汇报在会话里给人看、人在会话里回复，同样的内容记进本地的 review loop 文件，PR 合并时按停下和轮次归档成 PR 上的评论（`review-loop.md`）。

PR 描述本身是常驻的总览。读它的人**打开时没有上下文**：活是委托出去的，spec 他可能只记得个大概。所以描述从「这是什么」往下读到「要我做什么」，越往下越可以不读；只为查证的东西折叠在最后。**描述里不放 review**：review 在会话里进行，合并时整份记录贴在 PR 的评论里，描述里再放一份摘要只会重复。

| 节 | 标题 | 写什么 | 写入方 |
|---|---|---|---|
| `summary` | 一句话 | 这个 PR 让谁能做什么，或者修好了什么。只读这一句也知道它是干嘛的 | `implement`：开 draft 时写，转 open 前按落地结果重写 |
| `changes` | 改了什么 | 按点分块：碰页面的，每个页面端到端变了什么，加上后端流程变了什么；没碰页面的，只写后端流程的变化。**每一块里**放之前 → 之后的对照、怎么验证的（一个验证点一条：验了什么行为、用什么方式、结论） | `implement` 转 open 前写，对照图专门拍 |
| `your-todo` | 要你做的事 | 要你审的、要你决定的、上线前要你注意的 | `implement` 转 open 前写；`pr-review` 的编排者在人的批示带出新事项时更新 |
| `reference` | 参考 | 折叠：按模块的改动地图、spec 和工单链接、执行记录、合并后 Claude 做的清理 | `implement`：开 draft 时写，每次停下更新 |

**整个描述是给人读的。** 折叠的「参考」以外，不写代码行、变量名、函数名、文件路径、提交号、spec 或工单的章节编号，说页面、流程、行为和后果。`pr-body.mjs` 写入前会机械地查这一条，查到就拒写；图片和链接的地址不算。

每节的格式见 §6。每节夹在隐藏标记之间，由 `scripts/pr-body.mjs` 按固定顺序写入，**标题由脚本加**，内容文件里不用写：

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/pr-body.mjs" set <owner/repo> <PR 号> <节名> <内容文件>
```

每个写入方只重写自己负责的节。标记以外的文字（人手写的说明、署名行）会被保留，放在所有节的下方。**不要直接 `gh pr edit --body` 整体覆盖**，那会把别人的节一起冲掉。PR 描述本身由 gh 当前登录的账号写：它是 PR 的一部分，不是一条发言。

## 2 汇报在哪、人怎么回复

见 `review-loop.md`：会话里给人看、人在会话里回复，每次处理完只回一条汇总，内容逐字记进 `.tmp/review-loop/<PR 号>.md`，合并时归档成 PR 评论。PR 上不开 thread，不在 PR 上和人往来。

## 3 不写什么

- **不复述 spec 和工单。** 「为什么」在 spec §1，每刀做了什么在工单里，`reference` 里给链接就够。
- **不写给 agent 看的东西。** 验收契约就是分支上的工单文件，review 的 agent 直接去读，不在 PR 里另抄一份。复现命令、检查日志、修复前后对比这些过程材料，不出现在 PR 上。
- **描述里不放 review。** 结论、条目、图都在各轮的汇报里。
- **汇报的正文不出现代码层面的指称**（§5）：变量名、函数名、「文件:行号」、提交号、spec 或工单的章节编号（「§4.7」）都不写。读汇报的是拍板的人，这些他看了也不知道是什么意思。代码位置只给修复方，放进汇报最后的折叠区。

## 4 停下汇报

`implement` 每次停下（没有能做的工单了）就开一个，汇报这一次停下之前发生的事。

```markdown
## 第 N 次停下 · 落地 <K> 张，已按规则处理 <J> 件，等你决定 <M> 件

> <一句话说明叠加层：光圈 / 蓝点 = 鼠标位置，角落秒表 = 从某事件起计时，都不属于产品>

### 已按规则处理（不同意的，说「推翻某条」）

- **<工单号> · <标题>**：<做了什么，一句>。依据：<产品里已有的哪处做法，指到现存实例；或这个存量问题怎么污染了这张工单、让 CI 变红>
- **<工单号> · <标题>**：<顺手发现的存量问题是什么，一句>，这次没动，已开 issue <链接>。依据：它跟这张工单无关（`decision-rules.md` §1 第 2 条）

---

### 需要你决定

#### <工单号 · 一句话说卡在哪>
<两三句：缺的是什么，为什么查代码定不了>

![<图说>](<素材的本地路径>)        ← 有助于理解时才放：分支逻辑一张 flowchart，界面行为一张流程图

- **A**：<做法>——<代价>
- **B**：<做法>——<代价>

推荐 A：<一句理由>。在等它的工单：<编号列表>

### 交付验收

#### 03 · <工单标题>

**流程**
- [ ] <看什么>

  ![..](<URL>)

**动效**
- [ ] <看什么>

  ![..](<URL>)

---
直接回复就行：决定写「03 选 A」，人验项看过了说一声，不对就说哪一项、哪里不对，「已按规则处理」里不同意的说推翻某条，有疑问直接问。
```

- 只写**本次停下之前新落地**的工单，上一次停下交过的不重复。
- 素材的做法与形态见 `evidence.md`。每项是复选框 + 一句「看什么」+ 素材。人看过、觉得对，回一句就行，编排者在文件里把那一项勾上。
- **只放要人判断的**：逐格比对已经全绿的格、单测覆盖的逻辑都不放。一张工单没有人验项，就只写一行「无需人看」。
- 没有等决定的事，就不写「需要你决定」这一节；没有按规则处理的事，就不写「已按规则处理」。
- **「已按规则处理」放在「需要你决定」之前，每条一句：做了什么 + 依据。** 只放三类：执行方**按产品已有做法定的**（工单和 spec 没说的界面细节，沿用现存做法；依据写它沿用的那一处）、**本次修的存量问题**（污染了这张工单的输入或结论、或让 CI 变红；依据写它怎么污染的）、**顺手发现的跟这次无关的存量问题**（`implement` 的编排者已逐条在目标仓库开了 issue，写清是什么、链接；依据写它跟这张工单无关）。判断规则在 `decision-rules.md` §1，人说「推翻某条」：前两类 `implement` 当作一条人的决定写回工单，开了 issue 的那类关掉那个 issue 或按人的意思改做（`skills/implement/SKILL.md` §6）。边缘情形（只在兜底路径里出现、不丢东西）不放这里，是决定题，规则只用来定推荐（`decision-rules.md` §3）。
- **决定题的写法按 `decision-rules.md` §7「交给人时」**：现状先查清、先写交付物再列做法、每个问题和选项配具体例子；选项仍然至少两个，推荐按「代价相称」「改动最小」给。
- **不写执行方替你做的取舍。** 实现时工单没说、只影响代码怎么写的细节，执行方自己定，人不需要知道，也不知道看完要做什么。会改变用户看到什么的事，要么已经在工单里定了，要么按产品已有做法定、列进「已按规则处理」让人能推翻，要么是决定题，没有第四种。

## 5 review 轮次

`pr-review` 每跑一轮，写一份汇报放这一轮的全部结论，**PR 描述不动**。照规则能处理的条目编排者在贴汇报之前就处理掉，汇报里单列出来让人看一眼；剩下的人在会话里批示，编排者按批示修，修完回一条汇总。下一轮在满足条件时由编排者自己起，否则由人触发（`skills/pr-review/SKILL.md` §5）。

**这份汇报写给拍板的人看。** 他要的是：问题是什么、跟 main 有什么不同、用户会感受到什么区别、要他定什么。范围说明、审法、spec 原文、提交号、代码路径堆在前面，他看完描述和图还是不知道问题是什么。所以开头只有一句结论，每条固定几段，其余的收进最后的折叠区。

### 汇报正文

```markdown
## Review 第 N 轮

**结论**：<有没有把已有功能改坏>。Spec <K> 条、Standards <M> 条，其中 <X> 条已按规则处理，<Y> 条要你拍板<，都是要你拍板的事，不是 bug>。机械检查<全绿 / 有 X 处没过>。

---

### 已按规则处理（不同意的，说「推翻某条」）

- **C1** · <标题>：<做了什么，一句>。依据：<依据是什么，一句：哪条规则 / 你在哪次定过的原话 / 产品里已有的哪处做法>。<提交或 issue 链接>
- **S2** · <标题>：……

---

### Spec：代码有没有按 spec 做

#### S1 · <后果：用户能感到的那句话>

<问题：一两句，是什么、跟 main 哪里不一样>

**对用户的影响**：<谁、在什么情况下、多常见会碰到；碰不到就写「用户感受不到」>

<证据：界面上看得到的问题，用取自实现的截图——之前 / 之后、带标注的截图流程或动图，表格只作补充；界面上看不到的，用时序图、一张小表或一行例子；非行为问题没有这一块>

**要你决定**：<一句前提：和 spec 或工单的哪条规定对不上，那条规定是干什么用的>。<选项 A>，还是 <选项 B>？建议 <A>：<一句理由>。

---

### Standards：代码有没有守仓库写下来的规则

#### C1 · <违反了什么>

- **规则**：<规则原文>（<哪份文档，用文档的名字说>）
- **现状**：<代码现在怎么做，用话说>
- **影响**：<现在会怎样；现在没事就说以后在什么情况下出事>
- **建议**：<一个改法>

---

### 术语表缺的词（不阻塞）

| 概念 | 推荐叫法 | 代码里现在的名字 |
|---|---|---|

<details><summary>本轮审了什么、没审什么、丢弃的候选，以及给修复方的位置</summary>

**审的版本**：<短 SHA>，基准 <基准分支>
**核对过、没有问题的**：<一两行>
**没覆盖到的**：<哪些没看，由谁补>
**机械检查**：<每条命令一行：命令 | 结果（只算这次改动过的行）>
**丢弃 K 条**：<每条一行：是什么，为什么丢（没复现 / 规则原文找不到 / 不在 diff 里 / 人上一轮说过不修）>
**规则有歧义、没当违反**：<每处一句>
**给修复方的位置**：<S1 → 文件:行号、提交号；C1 → 文件:行号，以及违反规则的那几行代码>

</details>

---
逐条回复就行，比如「S1 接受，C1 修，C2 开 issue」；「已按规则处理」里不同意的，说「推翻某条」；有疑问直接问。<第 2 轮及以后加一句：已跑满两轮，要再跑或合并请直接说。>
```

### 每条怎么写

- **「已按规则处理」放在最前，在 Spec 与 Standards 之前，每条一句。** 说三样：做了什么（用话说）、依据是什么、提交或 issue 链接。依据只会是三种：仓库写下来的规则（说文档的名字，不贴路径）、你在这份 spec 或这个 PR 里做过的决定（引原话）、产品里已有的统一做法（说在哪一处）。做了什么的类别：修了、同步改了说明文字、接受并补记进了 spec 或工单、恢复了被删的东西、开了 issue。**第 1 轮还带上 `implement` 期间为执行方顺手发现的存量问题开的 issue**（那几条不是审查者的条目，没有 S / C 编号，标题写存量问题是什么，依据写它跟这次改动无关）。这一节只写做完的事；没有就不写这一节。要你拍板的条目不进这里，也不在下面重复。
- **标题就是后果。** 用用户能感到的话说（「连续失败几次的学生会提前用完当天的练习次数」），不用代码视角的说法（「重试路径扣了配额」）。不是 bug、只是和 spec 对不上的，标题就说是什么（「修了一个 spec 说这次不修的 bug」）。
- **对用户的影响要具体**：谁、在什么情况下、多常见。用户感受不到就直说，这种通常是要你拍板的事，不是 bug。
- **说行为和后果，不说代码。** 正文（开头结论、问题、影响、证据、要你决定）不写变量名、函数名、「文件:行号」、提交号、spec 或工单的章节编号。要指 spec 的某条规定，就把那条规定用话说出来。代码位置只放折叠区最后的「给修复方的位置」，审查者交回编排者的报告里也有。`review-check.mjs` 会机械地查这一条（`review-standards.md` §4）。
- **「要你决定」的前提要说清那条规定是干什么用的。** 例：「工单把报告取音频的总时长上限定为 5 秒，用来让报告最多等 5 秒就出现。」规则覆盖了一部分的，直接写覆盖了谁、漏了谁，选项就是要不要补。
- **至少两个选项，并给出建议。** 不是 bug 的，选项通常是「接受，把它补进 spec 或工单」与「拆出去」。
- **Standards 的「规则」引原文**，来源说文档的名字（「后端的 AGENTS.md」）。违反规则的那几行代码放进折叠区，不放正文。

### 证据：选最快能让人看懂的那种

先分**界面上看不看得到**：

- **看得到**（页面、按钮、提示、播放、录音状态的变化）：**必须有取自实现的截图**。单点差别用之前 / 之后截图，多步流程用截图拼的流程（`evidence.md` §3），动起来的用动图。拍板的人要看见学生看见的东西，一张表格或一段文字时间线只会让他猜，所以表格、时序图、例子只能放在截图后面作补充。确实拍不到的（比如只有真机能复现），写一句为什么。
- **看不到**（纯后端、埋点、数据）：按下表选最快能看懂的那种。一句话就说清了的，不配图。

| 人需要看见的 | 最快的形式 |
|---|---|
| 界面上哪里不一样 | 之前 / 之后两张截图并排，差别处画红圈 |
| 走到第几步分叉、出错 | 截图拼的流程（`evidence.md` §3），带标注，出错那一步画红圈 |
| 动起来哪里不对 | 动图（`evidence.md` §4） |
| 谁先谁后、等了多久（多为后端） | 时序图（excalidrawer `sequence`），main 和本分支的结局并排；两种实现规则不一致的，同一张图里用虚线框标出不一致的那一段 |
| 规则覆盖了谁、漏了谁 | 一张小表：场景 × 有没有覆盖 |
| 数值或计算不对 | 一行具体例子：输入 → main 的结果 → 本分支的结果 |

非行为问题（多了 / 少了一个文件、路径和 spec 写的不一致）没有证据块，diff 本身就是证据。图在汇报里写本地路径，在会话里紧跟着它那一条的文字、单独用发送文件的工具发给人；合并归档时才上传到素材分支、换成点开能看原图的链接（`review-loop.md` §4）。

### 规则

- **行为问题必须复现，并带上复现证据**：界面上看得到的用截图，看不到的用图、表或例子。复现不了的，放进「丢弃的候选」，只记一行。
- **Standards 的问题必须引用规则原文，而且违反的代码必须在这次的 diff 里。** 对不上的同样丢弃。机械检查（lint、typecheck、仓库声明的检查命令）的结果并入 Standards，只计这次改动过的行；挂在改动行上的诊断才成为 `C` 条目。
- 编号 `S1` / `C1` 只在这一轮内有效，方便人批示时引用。
- **缺词**：这次 PR 引入或改名、但目标仓库 `GLOSSARY.md` 没收的领域概念，用表格写概念、推荐叫法、代码里现在的名字（这一列本来就是代码里的名字，不受上面「不说代码」的限制）。不是问题，不阻塞，loop 不写术语表（新词只在 `grill` 里加，见 `glossary.md`）。没有就不写这一节。
- 两轴分开写，**不合并、不跨轴排序**：一处代码可以守规矩却做错了事，也可以做对了事却破了规矩，分开报才不会互相掩盖。

## 6 描述的四节

```markdown
## 一句话

<谁现在能做什么 / 修好了什么>。

## 改了什么

### <页面或流程：一句话说它现在怎么走>

<之前 → 之后：前端放截图对照、动图，或截图拼成的流程（带标注和注释）；后端放时序图，之前和之后并排>

**后端流程**：<这个页面背后的流程变了什么，一两句；没变就写「没变」>

**怎么验证的**
- <验证了什么行为>：<方式>，<结论>
- <没验成的行为>：没验成，<为什么>；<谁补、什么时候补>

### <下一个页面或流程>
……

## 要你做的事

**要你审的**
- [ ] <看什么>（在会话里看过、回一句就行）

**要你决定的**
- [ ] <要定什么，一句>（在会话里回答）

**上线前要注意的**
- [ ] <事>——<为什么要人来做>

## 参考
```

- **一句话**写结果，不写过程。
- **改了什么按点分块，每块自成一体。** 碰了页面的，一个页面一块，写这个页面从进入到离开端到端变了什么，再写它背后的后端流程变了什么；没碰页面的，一个后端流程一块。读完一块，人就知道这一点改成了什么样、凭什么说它是对的。
  - **之前 → 之后**在转 open 前**专门拍**，不复用人验素材（那些是为验收拍的，角度不一定是对照）。同一组操作在基准分支和本分支上各走一遍，取同样的组件、同样的宽度。**碰了页面的块，「之前」从设计档案 `prod/` 取**：用档案的「单个状态」查询拿进入方式（入口地址、前置条件、沿途每一步，`design-archive-query.mjs … state <状态名>`），在基准分支上照它走进去拍，不凭记忆摸路；`prod/` 里存着的主视口截图用来核对拍对了页面，对照图本身仍在同样的宽度下重拍。档案里还没有这个页面（首次初扫之前），照旧在基准分支上手动走。前端用截图、动图或带标注的截图流程，后端用时序图；具体哪种按「最快能让人看懂」选（原则同 §5「证据」）。文件名以 `pr-` 开头，用 `evidence.mjs publish` 上传。用户感觉不到的改动，写一句「用户看不到变化」再加一句换来了什么。
  - **怎么验证的**一个验证点一条：验了用户能感到的哪个行为、用什么方式（单元、组件、浏览器端到端、测量比对、真实前后端、手动）、结论。没验成的照样列，写原因和谁补，不藏、不当成通过。不写风险，不写执行方实现时自己定的细节：给足验证，细节交给执行方。
- **要你做的事**只有三类：要你审的（还没看过的人验素材）、要你决定的（会话里还没批示的事）、上线前要你注意的（生产配置、手动迁移、真实服务的冒烟）。Claude 自己能做的不列。做完的勾上，不删。
- **参考**整节折叠，只给想追溯的人看；提交号这类查证用的东西只放这里。
