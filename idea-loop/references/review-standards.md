# Review standards —— Standards 轴的依据

`pr-review-round` 的 Standards 轴读这份。它回答的问题只有一个：

> **这段 diff 符不符合本仓库写下来的规范？**

它**不找 bug**（那是 Correctness 轴），也**不问建的对不对**（那是 Spec 轴）。

---

## 三条约束

1. **仓库文档覆盖 baseline。** 下面的 smell 清单是兜底；只要仓库某处写明了相反的做法，以仓库为准，并把 smell 压掉。
2. **smell 永远是判断题。** 报告时说「疑似 Feature Envy」，不说「违反规范」。写下来的规范可以是硬违规，smell 不行。
3. **工具已经查的，跳过。** 这条最重要——见下。

---

## 工具层：查得了的别让 LLM 查

Standards 轴分两层。**下层是确定性工具，上层才是判断。**

具体是哪些工具、覆盖哪些语言，**由这个仓库自己有什么决定，不是固定的**——见 `pr-review-round.mjs` 里的探测逻辑（走到每个改动文件最近的 `pyproject.toml`/`ruff.toml`/`tsconfig.json` 或仓库自己文档里点名的配置）。两者在 review 里的待遇**不同**，这是本轴唯一要紧的区分，跟具体工具是谁无关：

- **CI 已经拦的那部分，一条都不报。** 查一眼 `.github/workflows/*.yml`（或等价的 CI 配置）——如果这项检查已经在阻塞合并，作者自己会修，跑它只是为了知道 CI 会说什么。
- **CI 没管的那部分要报，而且可以阻塞。** 没有任何东西在执行这项检查，所以 review 是它唯一的关口。工具没有意见，只有事实——按真实影响定级（可到 `high`），标 `fromTool: true`，计入合并门禁。

**判断题（成文规范 + Fowler smell）永不阻塞**，封顶 `medium`，纯风格一律 `low`。它们负责让代码库长期诚实，不负责拦住一个能跑且做对了事的 PR。

**不要重复报工具已经报过的东西**，只查工具查不了的：设计意图、抽象是否恰当、改动是否外科手术式、命名是否诚实。

> 为什么这样分：一个永远是红的门什么都拦不住，而让 LLM 去查类型错误既贵又不如编译器准。工具负责「客观错了」，LLM 负责「这样写好不好」。

---

## 本仓库的成文规范

来源是**这个仓库自己**的 `CLAUDE.md`（或等价的顶层约定文档）——先读那份，把它写的原则渲染成对着 diff 能问出的具体问题；它没写清楚的地方，才落回下面这 8 条。下面这套是从 idea-loop 最初写出来那个项目的 `CLAUDE.md` 原样带过来的默认值，写得足够通用，多数仓库能直接当起点用，但**不是本仓库的规范**，只是没有更贴切的东西时的兜底。**别为它另建一份 `CODING_STANDARDS.md`——当前仓库的 `CLAUDE.md` 就是，新建平行文档只会又造一个漂移源。**

| 原则 | 对着 diff 问什么 |
|---|---|
| **1 Think before coding** | 有没有在需求含糊时静默替人选了一个解释？有没有更简单的做法没被提出来？ |
| **2 Simplicity first** | 有没有为"以后可能用得上"加的抽象、配置开关、参数？200 行能不能是 50 行？**新抽象必须消除已经存在的重复，而不是想象中的重复。** |
| **3 Surgical changes** | 有没有顺手重构与本次任务无关的代码？风格/命名/惯用法跟周围一致吗？删掉的东西是不是真的因本次改动而不再被用？ |
| **4 Goal-driven execution** | 有没有可运行的成功判据（构建过、路由渲染、schema 校验），还是只靠"看起来对"？ |
| **5 Read clusters as systemic** | 同一处收到一串细粒度修正时，有没有找出背后那**一条**规则并顺带审同类，还是打了 N 个单点补丁？ |
| **6 Verify with a falsifiable signal** | 「已验证」建立在什么**本可以失败**的信号上？（in-flight CSS transition 用 `getComputedStyle` 读到的是目标值——冻结的动画也显示正常，那不算验证） |
| **7 Responsive by default** | 碰了公开/营销面吗？有没有 390px 和 360px 的截图证据？固定宽度 `w-[Npx]`、绝对定位装饰、`min-h-screen` 居中这些在手机上会坏的模式出现了吗？ |
| **8 Ground decisions in evidence** | 根因是**实际取证**来的还是听着合理的猜测？两种"证据说谎"的方式：**取样不全**冒充全貌；**权威来源与自己的观察矛盾**时编个故事把它们圆上（那是要挖得更深的信号，绝不是编故事的许可）。 |

如果这个仓库自己另外维护了专门领域的规范文档（设计系统、API 契约、数据模型约定……），碰到对应文件时同样要读、同样优先于下面的兜底——这份文件不可能穷举每个仓库会有哪些领域文档，找它们的方式是看仓库自己的 `CLAUDE.md`/`README.md` 有没有点名。

## Smell baseline —— Fowler《重构》第 3 章

仓库什么都没写时也适用。每条读作 *它是什么* → *怎么修*，逐条对照 diff：

- **Mysterious Name** —— 函数/变量/类型的名字没有揭示它做什么或存什么。→ 改名；起不出诚实的名字，说明设计本身是糊的。
- **Duplicated Code** —— 同一个逻辑形状出现在本次改动的多个 hunk 或文件里。→ 抽出共享形状，两边都调它。
- **Feature Envy** —— 一个方法访问别的对象的数据多过自己的。→ 把方法移到它羡慕的数据那边。
- **Data Clumps** —— 同几个字段/参数总是一起出现（一个想诞生的类型）。→ 打包成一个类型，传那个。
- **Primitive Obsession** —— 用基本类型或字符串代替一个配得上自己类型的领域概念。→ 给这个概念一个小类型。
- **Repeated Switches** —— 同一个类型上的 `switch`/`if` 级联在改动里反复出现。→ 换成多态，或一张两边共用的映射表。
- **Shotgun Surgery** —— 一个逻辑改动逼你在 diff 里改很多个文件。→ 把一起变的东西收进一个模块。
- **Divergent Change** —— 一个文件/模块因为好几个互不相干的理由被改。→ 拆开，让每个模块只因一个理由变。
- **Speculative Generality** —— 为 spec 没有的需求加的抽象、参数或钩子。→ 删掉；内联回去，等真需求出现再说。
- **Message Chains** —— 长长的 `a.b().c().d()` 导航，调用方本不该依赖这条链。→ 用第一个对象上的一个方法把整条走法藏起来。
- **Middle Man** —— 一个类/函数大部分只是在往下转发。→ 砍掉，直接调真正的目标。
- **Refused Bequest** —— 子类/实现者忽略或覆盖了它继承来的大部分东西。→ 放弃继承，改用组合。

---

## 报告格式

每条发现必须带**出处**，二选一：

- 写下来的规范：**文件 + 具体那条规则**（如 `CLAUDE.md 原则 3 Surgical changes`）
- baseline smell：**smell 名字 + 引用 hunk**

并区分**硬违规**（违反了成文规范）与**判断题**（baseline smell 一律是判断题）。

工具已经报过的不要重复。
