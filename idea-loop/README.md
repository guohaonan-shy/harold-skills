# idea-loop plugin

> The domain glossary (`GLOSSARY.md`, `skills/productivity/glossary/SKILL.md`) adapts the `domain-modeling` design from
> [mattpocock/skills](https://github.com/mattpocock/skills) (MIT).

Closed loop from idea to shipped engineering, backed by the `docs/` Obsidian
vault as its knowledge base. Each spec lives in its own directory,
`docs/spec/<slug>/<slug>.md`, with its tickets under `docs/spec/<slug>/tickets/`;
the directory's existence says the spec is not settled yet, and its frontmatter
`issues:` lists the issues it covers: the spec is settled once they are all closed (see
`skills/productivity/wiki-conventions/SKILL.md`). A spec has no status of its own.

## Install

```
/plugin marketplace add guohaonan-shy/harold-skills
/plugin install idea-loop@harold-skills
```

Then run `/idea-loop:setup` in the target repo.

## Skills

| Skill | Stage | Coverage |
|---|---|---|
| `/idea-loop:setup` | Setup | Run once per target repo, by hand. Checks `gh`, `origin/HEAD`, Codex and Mobbin read-only, asks only what the repo does not already say, and writes the project files the other skills read: `DEVELOPMENT.md` (base branch, merge method, worktree preparation, dev server), `REVIEW.md` (verification commands), `CODING_STANDARDS.md` (skeleton; the rules are the project's), an `## idea-loop` block in `CLAUDE.md` / `AGENTS.md`, the `docs/` skeleton only when the human keeps the knowledge base in the repo (kept outside — a directory or repo of its own — it only records where, and the spec, design and dreaming flows are unavailable in that repo), an `## issue 分类` section in `AGENTS.md` (the `type:*` categories and the other labels to keep), the `docs/` skeleton and local excludes. It creates the `status:*`, `kind:*`, `type:*` and `priority:*` labels, moves labels still in use onto categories, and prunes the rest once the human has seen the list. It also asks (the "asking the human" capability) whether to install the weekly scheduled task `dreaming-<repo name>` that starts `idea-loop:dreaming` (minute off 0 and 30; a runtime without the "scheduled task" capability gets the prompt handed over to be created by hand; what a missed run does is the runtime's, in `idea-loop:runtime`), creating it only on a yes. The same way it offers the weekly `triage-<repo name>` task that starts `idea-loop:issue-triage`, and (`references/dispatch.md`) creates the hourly `dispatch-<repo name>` task (each round is a new session) and prints the allow rule the runtime needs for it, and its label step also creates the `priority:P0` / `priority:P1` / `priority:P2` labels. It also asks where the issues live, GitHub or Linear: a Linear project gets connected through the Linear MCP (the "install and settings" capability tells the human how in the current runtime; the address is `https://mcp.linear.app/mcp`), the chosen team's states, Triage setting and label groups are laid out as a table for the human to confirm and written into a Linear-flavoured `ISSUE_TRACKER.md` (first heading `# Issue tracker：Linear`; template `references/issue-tracker-linear.md`), and the GitHub label steps are skipped. It also asks whether the team uses triage and writes the answer (`triage：用` or `triage：跳过`) into `ISSUE_TRACKER.md`; labels left over from the old Chinese state names are listed by `issues.mjs migrate` and changed only after the human confirms. A skill or agent that needs one of these files and finds none stops and asks for `/idea-loop:setup` |
| `/idea-loop:issue-dispatch` | Intake | The issue dispatcher, started once with `/idea-loop:issue-dispatch` (no interval: it runs every hour). Each round first asks `issues.mjs queues` what the time of day is for: the `调度` table of `ISSUE_TRACKER.md` (default: 09:00–19:00 hands out `triage`, 22:00–08:00 hands out `todo`, 3 at most each, nothing in the gaps) gives `dispatch` and `limit`. The body holds what is the same everywhere: every round runs `issues.mjs reconcile`, counts the open issue sessions (the child sessions an issue session spawns, e.g. parallel imagine sessions, take no slot and are reported as a separate count; every issue is in this one queue, whatever its category), reports issues in in-progress or in-review with no session of that number, and hands over only the kind the period says: in a `triage` period one session per `triage` issue (`issues.mjs candidates --state=triage`) for `limit` minus the sessions in the triage sidebar section; in a `todo` period one per `todo` issue for `limit` minus the in-progress sessions with activity in the last 2 hours (in-review sessions do not count, and a session idle for 2 hours gives its slot back without being touched), the prompt ending in 「夜间模式」; in a gap nothing is handed over. At most 3 a round. The first round after a `todo` period ends adds a morning summary read from `~/.idea-loop/dispatch/<repo name>.json` (one line per issue opened overnight: PR link, review result, how many things 「夜里替你定的」, or where it stopped) and pushes one line. Candidates come from `issues.mjs candidates` (no open blocked-by), ordered by whose they are first: issues assigned to the current `gh` login alone (P0 → P1 → P2 → no priority, oldest first within a level), the unassigned ones only when none of those can go (also P0 → P1 → P2 → no priority first, then the longest in `todo` first within a priority, by when the state's label was last added), and issues assigned to someone else never; on Linear the same order through `assignee: "me"` / `"null"`, with `updatedAt` standing in for the time in Todo. Three things are the runtime's, in `idea-loop:runtime` ("session management", the dispatch part): how the rounds are run (on the desktop an hourly scheduled task `dispatch-<repo name>`; magi's `magi cron` the same), how open sessions are counted, how an issue is handed over (on the desktop: a worktree outside the main checkout, `desktop-handoff.mjs` opens the session with `claude -p` and hands it to Claude Desktop, the dispatcher titles it, moves it into its sidebar section and only then sends the task; in magi: first a worktree on `issue/<n>-<slug>` outside the main checkout, then a session started in it with `--cap` for `magi`, the issue platform's MCP server (Linear: `linear`) and `browser`). Nobody has to click anything: a triage session stops at the first thing it needs the human for |
| `idea-loop:issue-session` | Intake → Merge | One issue's session, one spec and one branch `issue/<n>-<slug>`, the human's window for grilling and decisions. Two routes, chosen by the issue's state when it claims it. A **triage session** (opened by the human or the dispatcher; claims `triage`) reads the issue and the triage evidence comment, drafts the spec through `to-spec` and `references/draft-spec.md` (self-check, grilling what needs the human; a `type:seo/*` issue whose spec has no 「前端交互」 section is not stopped for the human: each 「待定」 is settled by its recommendation with the basis written 「AI 照推荐定：<reason>」, 「需要 grill」 is answered from the spec and the `SEO.md` 「内容原则」 section, and the draft is committed with no push notification and no stop; one with a 「前端交互」 section still goes to the human), then design (`/idea-loop:uiux-imagine` → `uiux-refine`, started by the human), pushes the branch, flips the issue to `todo` with a comment naming the branch, and closes itself out (the runtime's "session wrap-up"). A **todo session** (opened by the dispatcher; claims `in-progress`) picks up the branch (or drafts the spec itself with `to-spec`; if something needs the human it flips the issue back to `triage` with a comment and closes itself out), then cuts tickets (`to-ticket`; tickets already cut are not cut again, so re-typing the command works), implements (`implement`) and reviews (`pr-review`) in this same session, opening a worktree on the same-named branch in every other repository the issue touches (the ISSUE_TRACKER.md 「仓库」 section), until all PRs merge and the issue is `done`. When the task says 「夜间模式」 (the dispatcher's night rounds) nobody is there to answer, so `references/night-mode.md` applies: everything that would stop for the human is settled by its recommendation and listed in the PR description's 「夜里替你定的」 section (what was picked, why, the other option); the session stops only at merging a PR, deleting a branch or data, force-pushing, sending mail out or commenting in someone else's repository, or touching a project other than this issue's (written under 「等你定的」 where the session stopped); it works through `pr-review`'s first stop with the PR ready and the session placed in the in-review section, and does no retro and no archiving (left for the daytime). On a Linear project it reads and flips the issue the Linear way (`idea-loop:issues`), not with `gh` and `issues set`. A worktree the dispatcher already cut on `issue/<n>-<slug>` (magi) is used as is. On start it places itself by its state where the runtime has such placement (the desktop sidebar sections triage / in-progress / in-review) and titles itself `<repo>#<n> <title>`. "Put aside" is `issues.mjs set … backlog --comment=<where it stopped, the branch>`; the next session reads that comment. It closes itself out at the end (desktop: archives itself, which removes its worktree; magi: stops itself, since a session cannot archive itself) |
| `idea-loop:issue-triage` | Intake | Sorts the backlog. Without arguments (the weekly scheduled task `triage-<repo name>`, installed by `setup`) it takes the oldest 15 backlog issues from `issues.mjs backlog` and starts one `idea-loop:issue-triager` per issue, at most 5 at a time; each checks for a duplicate, the `docs/records/out-of-scope/` list, whether it is already implemented, reproduces it (output in `.tmp/triage/<n>/`), sets its category and posts one evidence comment through `issues.mjs note`. The session does not wait for the human: it flips each issue straight to the route its triager suggested (`todo` or `triage` with P1/P2, `canceled`, or stay in backlog; a project that skips triage has no `triage` route). `canceled` only comes from a duplicate, an out-of-scope hit, already implemented or not reproducible; an issue it cannot judge worth doing goes to `triage`, never `canceled`. It pushes only when an issue stays in backlog waiting for the human to add information, or a suspected P0 is found, naming those numbers. The `out-of-scope` record is written in the triage session where the human decides not to do a request (`idea-loop:issue-session`), not here. `全部` runs the existing backlog in batches of 15, one batch after another with no table to approve; `P0 <n>` (called by 「开一个 issue」 for a suspected P0) starts a single triager, and on a reproduction flips the issue to `todo`, sets `priority:P0` and notifies the human |
| `/idea-loop:grill` | Idea | Design-tree interview, one round of open questions at a time — facts are the agent's job, decisions are the human's |
| `idea-loop:retro` | Retro | Run at the end of an issue session (`issue-session`'s 「收尾」, before it closes itself out) or by the human saying "retro". Reads this session's own transcript file — not its context, which compaction has already thinned — squeezed by `scripts/session-digest.mjs` into every human utterance plus the conclusion of the AI reply before it (no tool calls or output). Finds three signals: the human's corrections and follow-up questions (one occurrence is enough), the human's choices on posed questions (the same kind at least twice across issues, no counter-example, counted from `docs/raw/decisions/` in the target repo), and directions the human volunteers (one occurrence; the human is asked which layer). Each candidate is shown with the verbatim words, where it happened, the layer (plugin skill / the target repo's rule files / a mechanical check), old and new wording side by side, how to verify afterwards that the change fixed that moment (a replay case's three parts, a check's name, or "can't verify" with the reason), and — when the retro reads the candidate pool (`docs/records/retro-candidates/`, harold-skills' pool read remotely with `gh` when it runs elsewhere) and finds the same kind already there — "this is the N-th time, merged into <that file>". The human answers approve-into-the-pool / approve-and-open-an-issue / reject / change; the retro recommends a home with each candidate — the pool while the kind has come up once or twice (counting this one), an issue from the third time, the pool's threshold — and the human still chooses; a bare "approve" follows the recommendation. It edits no rule file: an issue-bound candidate becomes a to-be-verified issue (plugin problems to harold-skills, project ones to the target repo); a pool-bound one is written into the pool by landing (plugin skill / agent / reference / script candidates go to harold-skills' pool, the target repo's own rule-file candidates to its own; a new file, or one more line in an existing file's 出现 section), where `dreaming` counts it. The questions put to the human and each candidate's outcome (`批·进候选池（<link>，第 N 次）` / `批·开 issue（<link>）` / …) are recorded in the target repo's `docs/raw/decisions/<issue>.md`, committed on the issue's branch when its PR is still open, else through a docs-only PR; a pool write into harold-skills from another repo is a second docs-only PR opened remotely with `gh` (no checkout), merged when checks pass |
| `/idea-loop:to-spec` | Spec | Turns the current context (a `grill` conversation, or an issue `issue-triage` has already reproduced) into one spec readable by humans as well as agents: one quoted line per covered issue saying whether it exists, the problem statement with its reproduction evidence, the plan (opening with an interaction sequence diagram; backend, front-end-internal and front-end-interaction sub-sections as needed), user stories as one tree per scenario (one expected behaviour per problem for pure fixes), implementation decisions, and testing decisions with agreed seams. Every section opens with one line saying what it gives the reader. A conversation also lands as a raw transcript. Settles what the written rules can settle (`idea-loop:decision-rules`), and gives every statement about the present state a source (the shared writing rules in `idea-loop:evidence`). When the issue is about a document an agent reads, it first diagnoses that document with `idea-loop:writing-for-agents` and lists its callers; the plan follows from both, each change naming the lever. A spec has no status: its frontmatter lists the issues it covers (`issues:`), and a spec that still has a 「需要 grill」 line or a 「待定」 fork keeps its issue in `triage` until the human settles it. The spec is committed on the work's branch and reaches main with the code PR (a spec that covers no issue: with the human present it is opened as a `todo` issue through `issues.mjs new`, otherwise the skill stops and asks). Figure rules: `idea-loop:evidence` |
| `/idea-loop:uiux-imagine` | Design · diverge | The skill runs the process; `idea-loop:uiux-imaginer` (latest Opus via the `opus` alias, effort high) does the work, one task at a time. It opens only the altitude that is still undecided and renders every round straight into a clickable comparison board with real motion, at the lowest fidelity that tells the variants apart. The skill shows each round to the human (the "browser" capability's show-the-human section), sorts the human's reply into a task (steer / apply to the picked variant / park for refine / reopen the language), and proposes wrapping up once nothing directional is left; the human declares it. Wrap-up hands ONE direction note (seven sections, a composition list per chosen variant, each item marked human-chosen or model-filled) plus a handoff canvas to `uiux-refine` via `docs/design/tmp/<spec-slug>/imagine/` under the worktree root (`git rev-parse --show-toplevel`; local, not in git) — no critic, no scoring. The imaginer does not research: a UX question it can only guess at goes back as a suggested research question with its recommended answer; the human decides whether to run `uiux-research`. When the project has no `DESIGN.md`, the imaginer drafts the first one and the skill writes it only after the human confirms the wording **Shelved designs**: before starting, it looks in the main checkout's (the first line of `git worktree list`) `docs/design/pending/` for a design of the same screen and asks the human whether to carry on from it; if yes it is copied back into this worktree's `docs/design/tmp/<spec-slug>/` and resumed from the interruption-and-resume path. When the human says "not building this screen yet", the orchestrator moves the whole `tmp/<spec-slug>/` untouched to the main checkout's `docs/design/pending/<spec-slug>/` (local only, never committed, skipped by the design-archive check) and leaves a pointer and the reason in the spec (`idea-loop:wiki-conventions`). |
| `/idea-loop:uiux-refine` | Design · converge | The skill runs the process; two plugin agents do the work, and the human decides every round. `idea-loop:designer` (latest Opus via the `opus` alias, effort high) delivers the next canvas version (`v1`, `v2`, …) from the handoff canvas `uiux-imagine` leaves behind (or from the direction note alone when there is none) and hands back a **change set** with each version, every entry tied to a decision number; it only does what the decisions and the ledger say, and hands back "stuck" (what it is stuck on) when two decisions collide or a decision conflicts with the design laws. Each round the session has a fresh `idea-loop:ui-master` (latest Fable via the `fable` alias, effort high, Read-only — it never sees the canvas code) act as an **advisor**: it hands back opinions (each with a one-line description of the real screen that would explain it), an assessment of each of the human's lines of reasoning, and a score, and `critic-score.mjs` only checks the shape (it decides nothing about stopping). The session compares this version with the last with `ui-measure` (what changed without being declared in the change set), starts the researcher's light use for a user path and Mobbin reference pictures per opinion, and assembles one **design review report** with `design-review-report.mjs`, sent through the runtime's "publish a review page" capability; the chat gets the report link, the score and what needs attention (each may carry a sentence or two of why it is recommended, plus a line on how to answer). The human answers in the chat by number and every item needs an answer before the designer moves: what they do not mention, the session asks again instead of deciding for them; once confirmed, the decisions go into the **ledger** (`canvas/work/ledger.md`), the only record of what the human settled. There is no pass and no bottleneck: the human's signature freezes, and before it the session lists the direction-level opinions nobody has resolved. When the judge names a direction-level opinion about a block the human has already said they dislike in this refine, the report recommends going back to imagine for that block instead of keeping it. Motion is one kind of decision, and the subtraction and AI-tells checks are standing angles of the judge and a self-check of the designer, not rounds; after "static is settled" only the asset list (marketing register only) and the pre-sign-off check remain. The designer does not research: a question it cannot settle becomes a "suggested research question", worked from its recommendation. Freezes (fully or partly) on the human's signature and writes interaction flows back into the spec; what it tells the human after the freeze depends on the session type: a triage session goes back to `issue-session`'s 「交给调度」 (push, flip to `todo`, wrap up; no tickets), a todo session to its 「实现」 (draft PR first, then tickets), outside an issue session the human decides; the design PR carries only the signed canvas, the freeze record and the flows, no `delta/`. After the freeze the canvas is the one design truth: when the human later accepts something that differs from it (accepting the implementation in review, accepting an implementer's way out of a stop, or changing their mind), the orchestrating session of that stage (`implement` before the PR opens, `pr-review` after) runs the shared `design-change-sync` skill (the steps are written once there, not in `uiux-refine`), which starts a `designer` on the task "design change" — it edits only the affected cells and hands back the next canvas version — and a fresh `ui-master` gives opinions on only those cells and the human decides whether to commit (the judge is an advisor, not a gate); once the human says commit, the session commits and pushes the canvas, adds one row to the freeze record's section "changes after the freeze", and sends an implementer after any ticket whose code now disagrees. The human has already seen the redrawn cells at that decision Shelving a design ("not building this screen yet") and carrying on from a shelved one follow the same rule as `uiux-imagine`: `docs/design/pending/<spec-slug>/` in the main checkout, `references/after-freeze.md` has the steps. |
| `/idea-loop:uiux-research` | Design · research | Two branches. **Full-page research** is run by the **human**, whenever they want to see how other products do something (no spec needed; model-invocable, so "look up how others do the leave-confirmation dialog" in plain conversation starts it). The skill turns the ask into one named question, picks the drop directory, and starts a fresh `idea-loop:uiux-researcher` (latest Opus via the `opus` alias, effort medium; tools: the plugin's Mobbin MCP (`mcp__plugin_idea-loop_mobbin__*`), `curl`, writing files in the drop directory). The researcher downloads the reference screenshots and writes one `index.html` (relative paths only, opened through a static server and shown to the human the way the "browser" capability's show-the-human section says) — at the top the named question, a 「研究问题」 block with the human's own words and the context handed to the researcher, and what these products agree on; then per source a flow of screenshots (click to enlarge) with scene and design logic only; and last, after the final source, the questions the human must decide once all of that is read against our needs — checked by `scripts/research-check.mjs`; the caller only receives the page's path and one sentence, never Mobbin calls or whole screenshots. Files go to `docs/design/tmp/<spec-slug>/research/<question>/` (with a spec) or `docs/design/tmp/research/<question>/` (without), local and never in git. UX patterns, flows, usual page structure and copy tone only — never visual style. The data source is Mobbin (screens, flows and website sections; needs a paid Mobbin plan and a one-time OAuth login); with Mobbin not connected the research stops and says how to connect it, and nothing else is affected. The orchestrator of `uiux-imagine` / `uiux-refine` calls it only when the human says to, and forwards conclusions to the executor only when the human says which, as text (never the pictures). **Light use** is the other branch: the design-convergence session starts the researcher itself every round, with no approval from the human, after the judge's opinions come back. It hands over the round's per-state screenshots, the numbered judge opinions, the human's intent and thinking and the ledger; the researcher covers only what those opinions touch and returns one structured file, `research-light.json` (not a page), next to the screenshots it downloaded: per opinion (or per group of opinions about the same thing) a user path — each step says what is seen, what is done, what comes next, with 1–2 Mobbin pictures and a one-line reading — and one sentence of new design intent, plus an `overturns` entry (ledger number and reason) when the path argues a ledger decision should change, and `uncovered` for opinions it found no reference for. With Mobbin not connected the file says so (「这一轮没有参考图：Mobbin 没连上」) and is still valid. `research-check.mjs --light` checks the file; its format is in `skills/design/uiux-research/references/light-return.md`, apart from the full-page contract. The designer and the judge still never research, and the reference pictures go to the human only |
| `/idea-loop:to-ticket` | Plan | Slices a spec with nothing left for a human (no 「需要 grill」, no 「待定」; design frozen if it touches UI) into tracer-bullet vertical cuts with blocking edges. Before cutting it `git fetch`es and reads `origin/<base branch>`: from the entry the user comes in by (a URL, a command) it walks the real call chain hop by hop to the data source (route → page → API in a web app), saying what each hop does now, including hops the spec does not name, and reads the commits on the base branch that touched the chain since the spec file's last commit; a stretch the spec does not cover counts as "spec not clear" and goes through the same stop rule below. Inside an issue session (called by `issue-session`) it stops when the issue is still in `triage` (state read with `issues show`, not the label) and points back to 「交给调度」; called directly by the human it does not check the state. It writes the tickets and commits them onto the current branch (the implementers' worktrees are cut from it) without waiting for a nod. The cut (title / blocked by / end-to-end behaviour per ticket) goes into the final review report; it stops only when slicing surfaces a real decision question for the human. A ticket that changes skills, agent definitions or skill reference files (by path: `SKILL.md`, any `.md` under `skills/`, a `.md` directly under `agents/`) ends its acceptance list with three fixed acceptance cells: `writing-for-agents` called with one lever line per changed file in the hand-back, the `SKILL.md` body inside the limit, and a proof that the rule really changed |
| `/idea-loop:implement` | Build | Runs a whole spec: the calling session orchestrates, dispatching `idea-loop:implementer`s in parallel along the `Blocked by` frontier (up to three at once by default, each in its own worktree and a fresh context the first time; the pending ledger records each stopped ticket's implementer agent id, and once the human has decided, the orchestrator calls that same implementer back with `SendMessage` — pointers only, plus the integration branch's latest commit to merge first — and starts a new one from the half-finished branch only if that fails or no id was recorded; a ticket that has already landed is always redone by a fresh one, since its worktree is gone; an `idea-loop:explorer` writes shared pointer-only notes first; one ticket → one commit the orchestrator fast-forwards onto the integration branch (before landing it saves the hand-back to a file and runs `ticket-ledger.mjs skill-edit <commit> <file>`: a commit that changed skill-like files needs the standards line's method to say it called `writing-for-agents` (the template's own "读 / 调" left as is does not count) and a lever line for each file, otherwise the hand-back goes back to the implementer), then reclaims the worktree; an implementer always calls `decision-rules` first, picks any other skill from what the ticket asks for, reads the whole spec as background (the ticket sets the scope) and, before writing, reads the target repo's written standards — `CODING_STANDARDS.md`, `REVIEW.md`, `AGENTS.md` / `CLAUDE.md` and what they link to — the same set the review's Standards axis judges by, picking the entry in `CODING_STANDARDS.md`'s links that governs the files the ticket changes and reading or calling it before writing, and listing which standards it read in the hand-back's `verified`; for a ticket that changes skills, agent definitions or skill reference files it calls `writing-for-agents` directly (no hop through `CODING_STANDARDS.md`) and adds one lever line per changed file to `verified`; TDD at the agreed seams, human-verify flows and GIFs recorded from the implementation). Stops only for the human — a Review 汇报 (from implementation) shown in the session and kept in the PR's local review-loop file: what the implementers already settled by the existing way of the product or by fixing a legacy problem that spoiled the ticket (listed first, the human overturns any with one sentence), then the decisions that really need a human. When nothing waits for the human (no pending decision), the report is still written to the review-loop file with a closing "what was done", nobody is waited for, and the PR turns ready and goes into `pr-review` at once (large rule replays still to run, or a replay result not yet handled, keep it draft; the orchestrator runs them on the spot). The PR turns ready once everything has landed; the orchestrator then waits for CI on the head (`gh pr checks --watch`) before `pr-review` starts — red goes back as a new box on the ticket that introduced the failing test, and a PR with no checks gets one local full run instead. When the human accepts a design that differs from the frozen canvas at a stop, it runs the same design-change-sync route as above (designer edits the affected cells, a fresh `ui-master` gives opinions on them and the human decides, commit and push to the integration branch, freeze-record row, implementer redispatched for any code that disagrees) |
| `/idea-loop:pr-review` | Review | One round per call on the open PR: an `idea-loop:pr-reviewer` reads the head's CI result for the full test suite (CI must be green first; with no checks on the PR it runs the suite locally), runs typecheck and lint itself (changed lines only) and two read-only Codex processes — Spec and Standards — reproduces every behavioural Spec finding and shows it in whatever form is fastest to grasp, checks every quote and the wording mechanically, marks every finding with a disposition (by rule / the human decides, `skills/productivity/decision-rules/SKILL.md`), and writes the round's report, which the session shows the human and keeps in the review-loop file. Findings the written rules already settle are handled before the report is shown and listed first under "handled by rule"; the human can overturn any of them with one sentence. The rest the human rules on in the session; fixes go back through the tickets and the implementer; accepting the implementation where it differs from the canvas (or the human changing the design) goes through the design-change-sync route — a `designer` edits the affected cells of the canvas, a fresh `ui-master` gives opinions on only those cells and the human decides whether to commit, the session commits and pushes to the PR branch and records a freeze-record row, and nothing is hand-edited in `delta/`; when a round had fixes, they have landed and the next round number is at most 5, the session starts the next round itself (the fifth round's fixes go unreviewed: the session stops and says so); before every round the session first merges the latest base branch into each PR branch (merge, not rebase; generated files such as the spec index are regenerated, not hand-merged), and again on the human's word to merge. ### The forward loop is not the maintenance sweep

`grill → to-spec → [uiux-imagine → uiux-refine] → to-ticket → implement →
pr-review` runs once per piece of work, on one working branch: the spec, the frozen design and the
tickets are committed there next to the code, and one PR takes them all to main (no separate spec or
design PR; `skills/productivity/wiki-conventions/SKILL.md`, section 知识库落地). Only work with no code
to ride along — a parent issue once it is split, an issue found absent, a dreaming run — lands through
its own docs-only PR.
**One state, on the issue** (`skills/engineering/issues/SKILL.md`): backlog → triage → todo →
in-progress → in-review → done, plus canceled. backlog is an open issue with no `status:*` label;
triage is the human's evaluation (grill, design), and the dispatcher opens a session for each triage issue in the daytime periods; `todo` is dispatched in the night periods; a todo session opens a
draft PR as soon as the spec is committed, one per repository the issue touches, turns them ready
for in-review, and the issue is done once every PR is merged. A team without triage says so in
`ISSUE_TRACKER.md` and goes backlog → todo. Besides its status an issue carries `type:*` category
labels, defined in the project's `AGENTS.md`. **A spec is a document, not a second state**: its
frontmatter only lists `issues:`, `scripts/spec.mjs` reads it, and `scripts/issues.mjs` is the only
writer of an issue's status and checks the precondition before writing (for triage → todo: nothing
in the spec waits for a human, and a spec that touches UI has its freeze committed on the working
branch). Issues are not grouped by parent and child: one issue, one session, one spec.
**Issues on Linear** are supported: the project's `ISSUE_TRACKER.md` says `# Issue tracker：Linear`, sessions, the dispatcher and triage read and write the issue through the Linear MCP as `skills/engineering/issues/references/linear.md` lays out (in-progress is flipped at claiming, in-review and done are pushed by the GitHub integration), the `issues.mjs` commands that write GitHub issues refuse there, `issues check --from=<current state>` still checks every flip's precondition, and a spec's `issues:` may list keys like `ENG-123` (`spec.mjs` reads them as strings; an opening verdict line reads `> ENG-123 存在：…`). `issues new` takes `--repo=<owner/repo>` to open the issue in another repository.
`dreaming` is a **batch reconciliation** over the whole vault: the docs, the design archive and
`DESIGN.md`. It runs weekly from the scheduled task `/idea-loop:setup` creates, or by hand. It is not the
next step after `implement`.

**No stage in the forward loop writes an ADR.** ADRs are produced only in Maintain,
which is also where a finished spec is deleted (the contract's invariant: never delete
a spec before its ADR exists). So a spec sitting in `docs/spec/` with its work already
merged is a **normal state**, not an oversight — it is waiting for the next sweep.

| Model-invocable | Human-invoked only (`disable-model-invocation`) |
|---|---|

`grill` is model-invocable so that "grill this idea" in an ordinary conversation starts it; it is still an
interview, so it only means something with a human answering. `uiux-imagine` is human-invoked: it steers on a human's directional
reaction each round, and a human is the one who declares the direction done.
`uiux-research` is model-invocable because looking up "how do others do this" is an ordinary thing to ask for in any conversation — but the *decision* to run a full-page research stays with the human: inside imagine / refine the orchestrator calls it only when the human says to. The one exception is its light use, which the design-convergence session starts every round on its own (the researcher stays a separate agent, so the session only receives a file). `uiux-refine` stops on a human at every round — the human decides by number what each opinion becomes, and
only the human's signature freezes — and wants a fresh window so it starts from the handoff canvas and
direction note instead of continuing the diverge session it cannot see. `dreaming` proposes
destructive disposals.

The project's `DESIGN.md` is written from exactly two places, `uiux-imagine` (only when the
project has none at the start) and `dreaming`; both read `skills/design/design-modeling/SKILL.md` and wait for the
human to confirm the wording before every write. Everything else on the design side — `designer`'s
motion sign-off, the Distill-back at the end of a freeze, an implementer meeting a value `DESIGN.md`
lacks — only writes a *design-law candidate* for `dreaming` to process.

The execution two were human-only until the caller-dispatch model landed: a ticket needs a
context holding nothing but itself, and `/clear` is a human action. Dispatching a fresh agent
satisfies that precondition too — more strictly, in fact — so `implement` became an orchestrator
that dispatches one `idea-loop:implementer` per ticket. What the lock was protecting did not come
off: the ticket must still be self-contained (no file paths, no code snippets, behaviour not
procedure), and the implementer must still **stop and report** when a behaviour is undecided
rather than guessing its way onward. See `to-ticket` §6 for where each of the original reasons
now lives.

### Delivery: implement → draft PR → review

```text
/idea-loop:implement <spec-slug>
```

One spec, one integration branch, one PR. The PR description is the **review
report**, written for a reader who never followed the work (it was delegated) and meant to be enough to
decide the merge: one sentence; the problem (what was seen, with numbers); how it was fixed (the
rules applied and their grounds, the slicing into tickets with what blocks what, each page or flow
end to end with its before → after shot); how it was verified (what was verified, what was not and
why, what the review rounds concluded); whether it can be rolled back (how, what it touches, what to
prepare before going live, the issues filed on the way); and what the human has to do (review the
human-verify material, decide, then say "merge"); plus a folded reference. No code lines,
variable names or paths outside that reference — `scripts/pr-body.mjs` refuses them. When a review round has
nothing for the human to decide and nothing left to fix, the orchestrator does not wait: it pushes the
docs-only "spec done, tickets deleted" commit, waits for its CI, writes the report and stops there; merging
afterwards needs no further CI wait. Layout: `skills/engineering/pr/SKILL.md`.

**The review loop lives in the session, not on GitHub** (`skills/engineering/pr/SKILL.md`, section "review loop 文件"). Only one
person reads the reports and decides, and they are already in the Claude session (desktop or
phone), so every Review 汇报 (implementation stops and review rounds are the same kind of report) is shown there, with figures sent as files and a push
notification; the human replies there; the orchestrator handles the batch and answers in one reply.
The same words — report, the human's rulings verbatim, what was done — go into one local file per PR
(`.tmp/review-loop/<PR>.md`, `scripts/review-loop.mjs`), the loop's memory across compaction or a new
session. When the human says merge, each report is posted to the PR as one plain comment
(figures uploaded and linked), then the PR merges and the file is deleted. No threads, no bot
waiting on GitHub. (Tried first: threads on the PR with a background watcher waking the session;
it worked, but carried one person's words from GitHub back into the session they were already in.)

| Phase | PR | Who talks | Where the human answers |
|---|---|---|---|
| Implementing | draft | `implement`'s orchestrator, in the session | A **Review 汇报 per stop** (the same report as a review round, "from implementation"; written for the record but not waited on when it has no decision): first what was **handled by rule** (details the spec left open that the product already answers, legacy problems fixed because they spoiled the ticket's input or turned CI red, and unrelated legacy problems the implementer noticed, for which the orchestrator already opened an issue (no status label) — one line each with its basis; overturn any with one sentence, which the orchestrator writes into the ticket as the human's decision), then what needs deciding, then whether what landed can be rolled back, then the human-verify material (flows and GIFs recorded from the implementation, one checkbox each) |
| Review | open | `pr-review`'s orchestrator, in the session | A **Review 汇报 per round**, written for the person who decides: a one-line verdict, then **handled by rule** (what was done, on what basis, with a commit or issue link — overturn any with one sentence), then each thing to decide in one format whichever axis it comes from — titled by its consequence, with the situation now (a Standards finding quotes the rule here), the user impact, whatever evidence makes it fastest to grasp (screenshots, an annotated flow, a GIF, a sequence diagram, a small table, a worked example), options that each say what they cost and whether they can be undone, and a recommendation — then whether the change can be rolled back; no variable names, file:line, commit hashes or section numbers in the body — code locations go in a folded block for the fixer |

- **Ticket done = every acceptance box has evidence or names who takes it over** (a later ticket,
  or the PR's delivery check), the tests the ticket wrote or touched, the API tests of the interfaces it touches, the selected regressions, typecheck and lint are green; the full suite runs once, in CI, after the PR turns ready — then one
  commit carrying a `Ticket: <NN>-<slug>` trailer. Git is the ledger; nothing else counts tickets.
- **Stop vs defer.** A behaviour nobody decided stops that ticket (and what depends on it) — unless the
  product already has one way of doing it (name an existing instance): then the implementer follows it
  and says so in its hand-back; a legacy problem that spoils the ticket's input or turns CI red is
  fixed in this ticket and reported as such, while an unrelated one becomes an issue the orchestrator opens (the reviewer does not hunt for legacy problems) (`skills/productivity/decision-rules/SKILL.md` 的「核心」). Everything else keeps going. A behaviour that is decided but cannot be proven inside this ticket
  is deferred to a named receiver; no receiver means it was undecided after all.
- **Posting identity.** The archive comments posted at merge come from the repository's GitHub App
  when `~/.idea-loop/github-apps.json` configures one (Pull requests write, Contents read); otherwise
  from the gh login; neither adds a signature line to the body.
- **Delivery evidence never enters the code branch or `docs/`.** It lives on one orphan branch per
  PR (`scripts/evidence.mjs`), never merged, deleted when the PR merges, and is embedded as
  `blob/<branch>/<file>?raw=true` so clicking an image opens it full size instead of downloading it
  (`skills/engineering/pr/references/delivery-evidence.md`). Knowledge-base images — spec figures, frozen canvases — stay in `docs/`.
- **Two axes, reported apart** (`skills/engineering/pr-review/references/review-standards.md`). The reviewer runs the repo's
  declared checks and keeps only diagnostics on changed lines (`scripts/changed-lines.mjs`); each
  Codex process sees only its own question. A behavioural Spec finding that cannot be reproduced
  and drawn, or a Standards finding whose rule text or code is not where it claims, is discarded by
  `scripts/review-check.mjs` and listed in one folded line; a finding that stands but is missing a
  part or speaks in code terms is sent back for rewording before the report is shown.
- **What the agents settle themselves, and what they ask** (`skills/productivity/decision-rules/SKILL.md`). The
  core is solving the spec's problem with the spec's plan. A basis is one of three things — the
  text of a written rule, the human's own words already given, an existing practice with a named
  instance; when the basis is clear and nothing conflicts, the agent follows it and lists it first
  under "handled by rule" (`review-check.mjs` finds that text where it says it is), and an overturn is
  one more ruling, recorded verbatim. When bases conflict or there is none, it stops and asks. The
  guardrails — naming, production data, real payments, publishing, merging a PR that changes code —
  are always the human's (spec and design ride in the code PR; a docs-only
  PR for work with no code is merged once its checks pass). The same
  file says how a question for the human is written: options that differ where the reader feels it,
  a real example each, a recommendation. For a scope question (fold a surfaced change into the
  current PR, or open it separately) the recommendation follows delivery, not PR size: a problem
  that affects this spec's implementation, or has an effect once shipped, is recommended into the
  current PR; the rest is not, and goes back to the caller's own process. How each flow disposes of findings (the reviewer's
  disposition table, the implementer's stop-or-defer table) lives with that flow. `skills/productivity/evidence/SKILL.md`
  says what counts as evidence (source, time, version, numbers, like-for-like comparisons) and the
  overall style (conclusion first, figure beside the sentence it supports); which figure to draw is
  left to the model, and where it goes is up to the caller (`to-spec`'s `references/figures.md`,
  `pr`'s `references/delivery-evidence.md`). Section 4 of a drafted spec keeps what the
  rules can settle as decisions with their basis; only the choices whose basis does not hold are
  left as options, and every "suggest closing" entry says what was claimed, why it no longer holds,
  and how that was checked.
- **Fixes go back through the tickets.** A finding fixed — by rule or by the human's word — becomes a
  new acceptance box on the ticket that introduced it (found by the quote, or by `git blame` →
  `Ticket:` trailer), and a fresh implementer does it. **The next round starts itself** when
  this round had at least one fix, every item is handled and the fixes are pushed, and the next
  round number is at most 5 (it says so and sends a push notification first); with no fix it stops
  and waits for the word to merge, after the fifth round's fixes it stops and says they went
  unreviewed. The cap binds only the automatic start — the human can ask for another round any time. Merging is the human's order.

The old loop (up to two automatic rounds of three-axis review → fix → re-verify, one round post per
round, a mergeReady verdict) and its design record [`docs/pr-review-loop.md`](./docs/pr-review-loop.md)
are superseded; the record stays as history.

### The blog workflow: brief → writing loop → publish

An SEO article (an issue labelled `type:seo/*` whose spec is a content brief) goes through three steps,
all inside the issue session; the angle is the only thing a human has to pick, and when nobody is there
(night mode) the session follows the recommendation and writes the basis 「AI 照推荐定」 into the spec.

1. **Brief, with images** (`seo-brief`, triage session). After the angle and the title are settled the
   brief gets a 「配图」 section: cover-subject candidates per angle and the OG headline taken from the
   title. `idea-loop:cover` (the article-list cover and the top image) and `idea-loop:og` (the 1200×630
   share card) make the two images; they are committed on the issue branch next to the spec. A human in
   the session answers angle and cover subject in one question; a project with no 「出图配方」 gets the default
   and the brief says so in one sentence.
2. **Draft, then a revision loop** (`seo-writing`, todo session). The draft follows the brief and the
   project's voice files. Then, every language version, up to three rounds: `scripts/writing-lint.mjs`
   (configured by `SEO.md` 「lint 配置」) and the project's own 「补充 lint」, then a 「写作评委」 (writing judge)
   sub-agent scoring 13 dimensions (plus 「第二评委」, a second model's command, when the project set one).
   Lint hits and `local` findings are fixed by the writer; what is still not clean goes into the handback.
   A `premise` finding (the thesis, the sections or the factual claims would change) is never fixed by the
   writer: the committed work is pushed and the issue goes back to triage with the writing judge's own words, in
   the day and in night mode alike (`skills/engineering/issue-session/references/night-mode.md`), because
   the angle is the human's. A changed title or thesis re-runs `cover` and `og`.
3. **Publish** (`seo-writing` handback, then the existing flow). Build the site: the post-build hook runs
   `seo-check` on the changed routes and hands any error back. The handback lists the files, the lint
   result, the writing judge rounds, what is not clean and any `premise`. The draft PR, the auto-merge for
   content-only SEO PRs and the post-deploy check are the flow described above under "Delivery".

What a project writes to use it (the format is `skills/seo/seo-setup/references/seo-md.md`; `seo-setup`
asks for each key with a recommendation):

| Where | What | Read by |
|---|---|---|
| `SEO.md` 「写作」 | voice file, failure-case file, page-type field and map, `lint 配置`, `补充 lint`, `第二评委` (`无` skips the last two) | `seo-writing`, the writing judge |
| `SEO.md` 「配图」 | image directory (must sit inside 「内容路径」), image-generating tool, cover field, OG field, `DESIGN.md` path when the repo has several | `cover`, `og`, `seo-brief` |
| `DESIGN.md` | `colors` / `typography` tokens, and optionally a `blog-cover` component (logo, base colour, subject style, prompt skeleton) and an `og-card` component (layout, `titleSize`, logo) | `cover`, `og` |

Any of these missing is not a stop: `cover` and `og` fall back to a neutral default 「出图配方」 and say so in the
handback, and a skipped lint or second judge is skipped, not an error. See also `skills/seo/README.md`.

## Tests

Node unit tests across this whole repo (every plugin's `scripts/`) run under **one
command**, from the repo root:

```
node --test '*/scripts/*.test.mjs'
```

Node's own test runner, no test framework and no `package.json` — the glob is
what keeps the command stable as plugins add suites, and the leading `*` is what
keeps it out of `.claude/` worktrees. Today it covers the design-lint rules,
the two UI-loop comparators and the two-canvas-version diff logic (`ui-canvas-diff`), the critic score check, the design review report builder, the direction
note's seven-section shape, the glossary lint, the seo scripts (SEO.md parsing, the missing-facts check, budget, context sync, audit regressions, issue planning against a fake gh, the two-platform check and its post-build hook), the DESIGN.md lint hook (against a fake CLI, no
network), and a tripwire that keeps `skills/` free of the source project's
names and examples, all living in this plugin's `scripts/`; new
deterministic scripts get picked up by putting their tests next to them as
`<name>.test.mjs`.

One file is the exception: `scripts/design-archive-sections-browser.test.mjs` opens a real
Chromium for every case and takes about 6 minutes, so the command above skips all of its
cases unless `IDEA_LOOP_BROWSER_TESTS=1` is set. Run it on its own, in the background, when
`design-archive-sections.mjs`, the `ui-png-compare.mjs` it imports or the test file itself changes:

```
IDEA_LOOP_BROWSER_TESTS=1 node --test idea-loop/scripts/design-archive-sections-browser.test.mjs
```

Each case times out after 120 seconds and the browser start-up after 60, so a stuck browser
fails that one case and the file still ends.

Only the deterministic cores are unit-tested. The playwright shell
(`scripts/ui-measure.mjs`) is the browser boundary and has no unit tests on
purpose — mocking a browser would test the mock. The CLI tails on
`critic-score.mjs` and `glossary-check.mjs` are the same kind of thin
shell — argv, a file read, an exit code — and are verified by being run, not
by a spawned-process test. (`direction-note-check.mjs` and `flow-compose.mjs` also have spawned-process
tests for the paths they are called on and the state-id file contract.) The glossary **hook**
(`scripts/glossary-check-hook.mjs`) has no unit test either — it is verified by
actually writing a broken `GLOSSARY.md` anywhere and confirming it reports; that is the falsifiable signal, not a mocked stdin payload.
`scripts/design-lint-hook.mjs` is tested by spawning it with a real payload on real files, because what it must get
right is *which paths it watches* (only HTML directly in `docs/design/tmp/<spec-slug>/canvas/`).
`scripts/design-md-hook.mjs` is the exception: its whole job is shelling out to an external CLI, so
its tests swap in a fake CLI to pin the exit-code contract (error blocks, warning passes, an
unreachable CLI never blocks), and one real run against the official CLI was the falsifiable check.

## Baseline: `uiux-research`

`evals/uiux-research/` is the plugin's baseline, and it is deliberately not a pass/fail eval.
What the researcher's page should contain is still being settled with the human, so it asserts no content and gives no
score. It pins **six default prompts taken from real design sessions** (leave confirmation, resuming after a
pause, failure card or not, error-title tone, where a failed list item goes, pausing under a modal), each with one line
on what that research actually helped or did not help with last time, plus a minimal product context
(`DESIGN.md`, `PRODUCT.md`). One command runs all or some of them; each page is left at a fixed place and each case has its
own `annotations.md` where the human records what is wrong with it. Annotations are kept, and they are what the page's
shape converges on over time.

```
node idea-loop/evals/uiux-research/run.mjs --list                  # cases and prompts
node idea-loop/evals/uiux-research/run.mjs --only leave-confirm    # one case
node idea-loop/evals/uiux-research/run.mjs                         # all six (calls Mobbin for real — run it at night)
```

Output lands in `/tmp/idea-loop-uiux-research/<case>/output/index.html`. Details: `evals/uiux-research/README.md`.

## Replay: proving a rule change took effect

A rule written into a skill, agent or reference is only a claim until the skill is seen behaving differently. A rule that can be
decided mechanically becomes a check (a script or a validator test) that is first seen **failing** on the input that reproduces
the old mistake. A rule that needs judgement gets a **replay case** in `evals/retro/cases/<case>/`: the commit the decision
happened at, the prompt that made the skill produce the thing, where it stops (the moment it hands the thing to the human; only
the judging session is told), a yes/no question written from what the human said back then (with the words quoted), and its size
(small or large) with the basis.

```
node idea-loop/evals/retro/retro-replay.mjs --list                      # cases, sizes, format problems
node idea-loop/evals/retro/retro-replay.mjs --case <name> [--base main] # one small case: pre-change vs post-change plugin
node idea-loop/evals/retro/retro-replay.mjs --settle <name> --run <dir> # re-decide after the human overruled a judgement
```

The runner copies the project as of the case's commit into a temp dir, runs `claude -p` with `--plugin-dir` pointing at the base
branch's plugin and again at this working tree's plugin (a sub-agent cannot do this: it loads the installed copy), then has a
judge read both products anonymously and answer the question with a quote. **The judge is Codex** (a different model family from
the two runs), run through the Codex companion's `task` (found the way `pr-review` finds it; read-only, never `--write`), with the
products lettered A and B in a random order each time; the order is recorded as `afterIs` in `result.json` and turned back into
pre-change / post-change when the answers are read, and `result.json`, the terminal report and the review loop entry all say who
judged (`judge: codex` or `judge: claude`). It uses no Claude quota (the cost estimate printed up front still follows the old
formula and says the judge runs on Codex). When no Codex is found, the runner prints 没找到 Codex，评委用 Claude before it starts
and judges with `claude -p` as before (a Codex that gives nothing at judging time falls back the same way, said out loud); a
replay is an acceptance check, not a gate, so it falls back instead of stopping, and the entry shows it (with `RETRO_CLAUDE_BIN` set to a stand-in `claude` and `RETRO_CODEX_COMPANION` not set, the runner does not look for a real Codex at all: the stand-in judges). **The input is only the human's
words**: each run is given exactly the case's `prompt` (nothing added, no note that it is a test, no stop point: an agent that hands
its work to the human ends its turn, and the timeout is the backstop) and works in `<tmp dir>/<random>/<project name>`, a path with
nothing about retro, replay, before or after in it, and the plugin it loads is copied to `<tmp dir>/<random>/<plugin dir name>`
first (`--plugin-dir` points there, so a skill's "Base directory" shows no such word either) and the copy is deleted afterwards;
what the runs leave behind is kept under the run dir, where the agent does not look. **The plugin files the change touched are put into the project copy in each side's own version**: when the case's commit holds this plugin at its place in the repository (a `.claude-plugin/plugin.json` there with the same `name`; a plugin outside a git repo is taken to sit at `<repo root>/<its dir name>`), every file that differs between the base branch's plugin and this working tree's (added, edited or deleted, anywhere in the plugin dir except its top-level `evals/`, which holds the replay cases and eval material themselves and is never swapped in) is written from the side being run, or removed when that side lacks it, before the project's initial commit, so a run that reads the plugin straight out of the project reads that side's rule and the swapped files do not show up as something the run wrote; the other plugin files and the rest of the project stay as the commit had them, and a commit with no such plugin (a case from another repository) is unpacked as it was. **No process the runner starts has a `gh` login**: the two runs, the Claude judge and the Codex judge get the runner's own environment without `GH_TOKEN` / `GITHUB_TOKEN` / `GH_ENTERPRISE_TOKEN` / `GITHUB_ENTERPRISE_TOKEN` and with `GH_CONFIG_DIR` pointing at an empty dir under the run dir, so a `gh` read (an issue or PR as it is now, not as of the case's commit) fails as not logged in; the runner's own environment and the machine's login are untouched, and reading the public repository's web pages (WebFetch, `curl`) is not stopped. A case whose `prompt` contains 回放, eval, judge, rubric, benchmark, 评测, 评委 or 判定 (any case) is malformed: `--list`
reports it and `--case` / `--run-large` exit 2 without starting a session. **Before the judge, the runner checks that the post-change run used
the change.** The change set is the files added or modified under `skills/` and `agents/` between the base branch's plugin and this
working tree's; the run used it when its event stream (main session and sub-agents) reads one of them (a Read, or a Bash command naming
its full path or its path relative to the project; the project's own copy of the plugin counts as a place the post-change plugin sits), calls a skill one of them belongs to (the Skill tool, or a prompt that starts with that skill's slash command, which the
harness loads without a tool call), or starts an agent one of them defines (the Agent tool), or when one of them is a file the SessionStart hook injects (`decision-rules`, `runtime`, and the reference of the runtime the replayed session runs in, found by the detection rule on the runner's environment, which the session inherits; the other runtime's reference is not injected and still has to be read or called to count: the session has it from the start and nothing in the stream shows it; reported as `injected`, after any read or call that is). Used: the judge's answer decides as before and
`result.json` records what was hit (`exercised`). Not used: the judge still runs and its answers stay in the result, but the outcome is
`not-exercised` (用例没测到改动), exit 1, listed in the review loop entry like any case that did not pass; a skill that was never loaded
cannot show that its rule works. An empty change set (only scripts changed) is recorded as 不适用 and the judge decides. Pre-change "no" and post-change
"yes" is a pass; pre-change "yes" is reported as "the case did not catch the problem". It does not score anything. Details and
the exit codes: the header of `evals/retro/retro-replay.mjs`.

**Who runs what, and when.** There is no night queue and no scheduled task: replays are run on the spot, by whoever has the
change in hand. The implementer runs a small case itself (`--case`). A large case (it starts a plugin agent, opens a browser or
calls a paid service) is not run by `--case`: the runner exits with code 3, and a small case that turns out to start a plugin
agent or open a browser is stopped and relabelled large in its `case.json` the same way. The implementer only writes and commits
such a case and hands back "大用例待跑：<case>". Once the PR is open, the orchestrator of `idea-loop:implement` tells the human how
many cases, how long (at most 3×45 minutes each) and what it expects to spend (about $1.05–3.50 per case, more when agents are
started), does not wait for a nod, and runs `retro-replay.mjs --cases a,b --run-large --pr <N> --worktree <dir>` in the
background (a foreground Bash call is cut at 10 minutes). The runner runs the cases one after the other in any hour, nothing is
stopped for starting an agent or opening a browser (the session timeout is 45 minutes unless `--timeout-min` says otherwise),
and appends one `replay` entry to the PR's review loop file (`review-loop.mjs check` reads it; a case that did not pass leaves it
unsettled). It sends no session message and no notification: the orchestrator waits for the exit, reads the output and the file,
and handles the result as `idea-loop:implement`'s `references/replay-result.md` says: first it reads the two products itself, answers
the case's yes/no question on each, and compares with the judge; a disagreement stops the run and goes to the human (a small
case's implementer does the same and hands a disagreement back as `blocked`). The PR stays a draft until the replays
are handled. Exit codes: 0 all passed, 1 some did not, 2 no `--pr` / no case / a case that is missing or malformed (no session
is started). A runner copy at `~/.idea-loop/bin/` from before this option does not know it: run `scripts/retro-install.mjs` again (that is, `/idea-loop:setup`'s runner step: the installed copy only changes when setup is run again). The Codex lookup script (`scripts/codex-companion.mjs`) is installed with the runner, so a machine that has not run setup again has no Codex lookup either and cannot use the Codex judge; the same goes for the exercised check, which also needs the runtime detection script (`scripts/runtime-detect.mjs`, installed with the runner too) to tell which runtime the checked session ran in.

`/idea-loop:setup` does the machine-level part once: `scripts/retro-install.mjs` copies the runner to `~/.idea-loop/bin/` (a fixed
path) and prints the permission rule `Bash(node ~/.idea-loop/bin/retro-replay.mjs:*)` for the human to add to
`~/.claude/settings.json` (setup never changes permission settings); on a machine that had the night queue, setup also deletes the
old scheduled task `idea-loop-retro-replay` and the old queue directory.

## Runtimes

idea-loop runs in two runtimes: the Claude desktop app (`claude-desktop`) and a Claude Code session started by magi (`magi`). The Claude command line and IDE plugins are not separate runtimes: they are detected as `claude-desktop`, and the capabilities they lack take the fallback. The capability list and one reference per runtime live in `skills/productivity/runtime/`; adding a runtime means one more reference and one more known name in `scripts/runtime-detect.mjs`. Force a runtime with `IDEA_LOOP_RUNTIME=claude-desktop|magi`; any other value is an error.

## Portability

Project rules and verification tools come from the current repository's root files written by
`setup` — DEVELOPMENT.md, REVIEW.md, CODING_STANDARDS.md — plus AGENTS.md / CLAUDE.md and what they link to. No rule is inherited from
any particular project. Plugin paths go through `${CLAUDE_PLUGIN_ROOT}` rather than being hardcoded,
so this plugin should survive being copied to another project or machine as-is. The
`openai-codex` companion script is found the same way: walk up from `${CLAUDE_PLUGIN_ROOT}`
to the plugins root and look under either the marketplace clone or the versioned cache.
There is no fallback for it on purpose — a hardcoded default is what made this unportable,
and a review that silently points at a nonexistent script is worse than one that refuses
to start.

## The design side

Design used to be its own installable plugin. It isn't any more — every stage of it
consumed or produced an `idea-loop` artifact (a spec, the freeze a ticket
reads, the instrument `implement` runs), so keeping it addressable across a plugin
boundary only bought two version numbers that could drift apart. It now lives here,
with **no alias, no compatibility shim, and no transitional double install**.

**Why the refine models are pinned in the agent definitions.** Once the executor was swapped for a
weaker model and the same baseline went from freezing to three rounds in a row stuck for rounds — splitting
the roles fixed the structure, not the model. The critic (`ui-master`, `fable`) and the executor
(`designer`, `opus`) run on different models so they don't share one blind spot. The definitions use
aliases, so a new model arrives with a Claude Code upgrade; to pin a version for a while, override the
alias mapping with an environment variable (e.g. `ANTHROPIC_DEFAULT_OPUS_MODEL`) instead of editing the
definition.

What came across:

| Piece | Where it lives now |
|---|---|
| The taste/craft references | `skills/design/uiux-refine/references/design/` |
| The two former design skills | `skills/design/uiux-refine/references/design/static-protocol.md` (surface, module and component altitudes in one file), `skills/design/uiux-refine/references/design/motion.md` — demoted to on-demand protocols |
| The `DESIGN.md` spec | Format: the official `@google/design.md` spec, read at run time (`npx -y @google/design.md@latest spec`). What may enter, how to write it, the candidate format, who may write: `skills/design/design-modeling/SKILL.md`; how a write goes: `skills/design/design-modeling/references/write.md` |
| The lint hook + rules + their unit tests | `hooks/hooks.json`, `scripts/design-lint*.mjs` |
| The browser | the "browser" capability, done as the current runtime says (`skills/productivity/runtime/references/`; on the desktop a user-level `playwright` MCP, headless and isolated, checked by `setup`; in magi `magi browser`); how to use it: `skills/engineering/browser/SKILL.md` |
| The design archive's lookups | `.mcp.json` (`design-archive`, `scripts/design-archive-mcp.mjs`) |
| Design research | the plugin's own `mobbin` MCP (remote, the human logs in once through `/mcp`), checked by `setup` |

The design critic (`agents/ui-master.md`) is an advisor and has no separate rubric: it judges the gap to what a top
studio would ship, lists the biggest gaps first (each routed by `kind`: direction / pattern / craft, each with a
`reference` sentence), assesses every one of the human's numbered lines of reasoning, and scores 1–10 as a reference.
It asks "what could go" and looks for AI tells on every round. Whether the loop stops is the human's signature, not
the score. `scripts/critic-score.mjs` only checks the shape (against the canvas's state list and the reasoning ids the
human wrote this round) and points out the direction findings; it prints no stop verdict.

Nothing in `skills/design/uiux-refine/references/design/` is an entry point. They are loaded on demand by whichever
step is running; the hooks are the only pieces that fire on their own. One fires only on a
`Write`/`Edit` whose path lands in a canvas HTML — `docs/design/tmp/<spec-slug>/canvas/*.html`, or the legacy
`design-preview/` / `design-motion-preview/` scratch dirs; the other only on a write to a file named
`DESIGN.md`, where it runs the official `@google/design.md` lint at `@latest` and hands any error
back to the model. There is no pre-merge hook: the design archive is a step of `pr-review`'s merge flow
(`skills/engineering/pr-review/references/merge.md`). The known gap is that clicking merge on the web, or merging from a session
other than the issue session, skips the archive; the weekly `dreaming` backstops it, so merges go through the issue session.

What retired outright, because its content was already relocated: the `design` entry skill,
the port-verification skill
(→ `skills/engineering/implement/references/ui-tickets.md` and the `ui-measure` skill, which generalized it past React), and the
`wireframe-candidates` workflow (its structural-divergence audit moved into `prototype`, which was later removed too).
