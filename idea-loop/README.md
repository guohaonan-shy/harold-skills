# idea-loop plugin

> The domain glossary (`GLOSSARY.md`, `skills/productivity/wiki-conventions/references/glossary.md`) adapts the `domain-modeling` design from
> [mattpocock/skills](https://github.com/mattpocock/skills) (MIT).

Closed loop from idea to shipped engineering, backed by the `docs/` Obsidian
vault as its knowledge base. Each spec lives in its own directory,
`docs/spec/<slug>/<slug>.md`, with its tickets under `docs/spec/<slug>/tickets/`;
the directory's existence says the spec is not settled yet, and its frontmatter
`issues:` lists the issues it covers: the spec is settled once they are all closed (see
`skills/productivity/wiki-conventions/SKILL.md`). A spec has no status of its own.

## Install

```
/plugin marketplace add guohaonan-shy/harold-skills
/plugin install idea-loop@harold-skills
```

Then run `/idea-loop:setup` in the target repo.

## Skills

| Skill | Stage | Coverage |
|---|---|---|
| `/idea-loop:setup` | Setup | Run once per target repo, by hand. Checks `gh`, `origin/HEAD`, Codex and Mobbin read-only, plus whether the project is already connected (`dyna home where`: a 0.1.x project, one with idea-loop's files or a `docs/` holding a `spec/` or `adr/` in the code repository, stops at "this project has to be migrated" and nothing is written; the migration steps are still to come), asks only what the project does not already say, and writes the project files the other skills read into the project directory in home (`~/home/projects/<name>/`; nothing of idea-loop is written into the code repository, and a new project gets no `## idea-loop` block in its `AGENTS.md`; the project map takes its place): `DEVELOPMENT.md` (base branch, merge method, worktree preparation, dev server), `REVIEW.md` (verification commands), `CODING_STANDARDS.md` (skeleton; the rules are the project's), `ISSUE_TRACKER.md` (its `分类 label` section holds the `type:*` categories and the other labels to keep), the `docs/` skeleton and the Git LFS rule for design assets, then commits them to home with `dyna home commit`, plus the local excludes in the code repository. After that it asks, once per module, whether to connect it ("yes" / "later"); SEO is the only module so far, see the next row. It creates the `status:*`, `kind:*`, `type:*` and `priority:*` labels, moves labels still in use onto categories, and prunes the rest once the human has seen the list. It also asks (the "asking the human" capability) whether to install the weekly scheduled task that starts `idea-loop:dreaming` — one per device, id `dreaming-home`, directory home, created after the home step (a second project's setup finds it and only reports it as already there; minute off 0 and 30; a runtime without the "scheduled task" capability gets the prompt handed over to be created by hand; what a missed run does is the runtime's, in `dyna runtime show`), creating it only on a yes. The same way it offers the weekly `triage-<repo name>` task that starts `idea-loop:issue-triage`, and (`references/dispatch.md`) reports whether this device has `dispatch-home` (the one 30-minute dispatch task, each round a new session) and, when it has none, asks whether to create it (the same steps as starting the dispatch) and prints the allow rule the runtime needs for it, and its label step also creates the `priority:P0` / `priority:P1` / `priority:P2` labels. It also asks where the issues live, GitHub or Linear: a Linear project gets connected through the Linear MCP (the "install and settings" capability tells the human how in the current runtime; the address is `https://mcp.linear.app/mcp`), the chosen team's states, Triage setting and label groups are laid out as a table for the human to confirm and written into a Linear-flavoured `ISSUE_TRACKER.md` (first heading `# Issue tracker：Linear`; template `references/issue-tracker-linear.md`), and the GitHub label steps are skipped. It also asks whether the team uses triage and writes the answer (`triage：用` or `triage：跳过`) into `ISSUE_TRACKER.md`; labels left over from the old Chinese state names are listed by `dyna issues migrate` and changed only after the human confirms. It also has a `home` step for `~/home` (`references/home.md`, run before the project files are written, because the project directory is made there): it builds the repo when the device has none (a private git repo with the device map, the project list and the fixed text (思考与决策, 沟通, 证据: the principles, who decides, how to talk to a human: the three-sentence frame and a decision written as a question; what evidence is; one copy in `references/home-rules.md`) in `AGENTS.md`, `memory/`, `projects/`; asks once whether to push it to a private GitHub repo), adds the current repo as one line of the project list and drafts its project map from a template (`projects/<name>/AGENTS.md`, at most 2000 characters), and then puts the four user-level changes (`dyna home config`: enable idea-loop in `settings.json`, point `autoMemoryDirectory` at `~/home/memory/`, link `~/.claude/CLAUDE.md` to `~/home/AGENTS.md`, bring the three fixed sections in `AGENTS.md` up to the plugin's copy — `--only rules`) to the human together, once, and lists the paragraphs of the human's own sections that repeat the fixed text (the human deletes them; setup never edits what the human wrote); whoever agrees gets all that are still to do after a backup into `~/home/.backup/`, those already in place are not asked about, so a second project on the same device only gets registered. The same step picks the device's runtime (`references/runtime-env.md`): it lists the descriptions the plugin and `<home>/runtime/` have (name and marker), says which one `dyna runtime name` finds in this session, and asks which one this machine uses by default; a runtime with a marker variable is found by it, so the pick only covers sessions with no marker, and it is written to `<home>/runtime/selected` and committed with `dyna home commit`. When the runtime the human uses is not in the list, the human gives its documentation (a link, a file, or text pasted into the chat), Claude writes a description from the capability template, one capability section at a time, the human approves each section, it is written to `<home>/runtime/<name>.md`, and `dyna runtime check` has to pass before `dyna home commit`. Adding a runtime this way changes no dyna code. A skill or agent that needs one of these files and finds none stops and asks for `/idea-loop:setup` |
| `/idea-loop:issue-dispatch` | Intake | The issue dispatcher, one per device, started once with `/idea-loop:issue-dispatch` from any directory (no interval: it runs every 30 minutes). Starting it creates the scheduled task `dispatch-home` in home (cron `7,37 * * * *`; the skill does not pin a model or effort in its front matter; the start report reminds the human to pick Sonnet for `dispatch-home` by hand in the desktop app), writes `DISPATCH.md` in home from the defaults when there is none (an old `调度` section in a project directory's `ISSUE_TRACKER.md` is shown before/after and merged in only on the human's yes), disables the old `dispatch-<repo name>` tasks, and runs the first round. Each round reads `dyna home dispatch` (the device's one table: periods with what each hands out and how many sessions a round may open at most, the cap on sessions open at once per state, projects to skip; default: 09:00–19:00 `triage`, 22:00–08:00 `todo`, `triage` 3 a round and `todo` 1 a round, triage capped at 6, in-progress and in-review not capped, nothing in the gaps) and `dyna home projects` (every project in the list), counts the open issue sessions in the three sidebar sections across all projects (the child sessions an issue session spawns take no slot and are reported as a separate count; a same-numbered session only blocks the issue of the project whose repo name it carries), then goes through the projects in the list's order: one that cannot run (not in home, no local clone, clone not on the default branch, fast-forward pull fails) is skipped and named in the report; for each of the others it runs `dyna issues reconcile`, reports issues in in-progress or in-review with no session of that number, and takes that state's candidates (`dyna issues candidates`) minus the issues that already have a session. The number to open is min(max per round, the state's cap − the sessions open in that state), no cap meaning the per-round number; the candidates of all projects form one table, ordered by whose they are first: issues assigned to the current `gh` login alone (P0 → P1 → P2 → no priority, oldest first within a level), the unassigned ones only when none of those can go (also by priority, then the longest in the state first), and issues assigned to someone else never; the first that many are handed over, the prompt ending in 「夜间模式」 in a `todo` period. In a gap nothing is handed over and the round only reconciles. The first round after a `todo` period ends adds a morning summary read from `~/.idea-loop/dispatch/<repo name>.json` (one line per issue opened overnight, in a section per project: PR link, review result, how many things 「夜里替你定的」, or where it stopped) and pushes one line; the report is one for the whole device and the push one sentence of totals. On Linear the same order through `assignee: "me"` / `"null"`, with `updatedAt` standing in for the time in the state. Three things are the runtime's, in `dyna runtime show 会话管理` ("session management", the dispatch part): how the rounds are run (on the desktop the scheduled task `dispatch-home`; magi's `magi cron` the same, working directory home), how open sessions are counted, how an issue is handed over (a worktree outside the project's local clone (on magi on the issue's branch: attached when the branch is already local, tracked from `origin` when only the remote has it, cut from the base branch when neither does), then the session is opened with the runtime's own commands, written in its description (on the desktop `claude -p` creates the session and `claude --desktop --resume <id>` hands it to Claude Desktop, and the dispatcher titles it, moves it into its sidebar section and only then sends the task; in magi `magi sessions start` takes the task as its last argument, with `--cap` for `magi`, the issue platform's MCP server (Linear: `linear`) and `browser`), and one runtime-independent command, `dyna runtime record`, writes the dispatch record the morning summary reads). Nobody has to click anything: a triage session stops at the first thing it needs the human for |
| `idea-loop:issue-session` | Intake → Merge | One issue's session and one spec; the branch `issue/<n>-<slug>` is for code only and is cut when the first line of code is written, not in triage. The human's window for grilling and decisions. Two routes, chosen by the issue's state when it claims it. A **triage session** (opened by the human or the dispatcher; claims `triage`) reads the issue and the triage evidence comment, drafts the spec through `to-spec` and `references/draft-spec.md` (self-check, grilling what needs the human; a `type:seo/*` issue whose spec has no 「前端交互」 section is not stopped for the human: each 「待定」 is settled by its recommendation with the basis written 「AI 照推荐定：<reason>」, 「需要 grill」 is answered from the spec and the `SEO.md` 「内容原则」 section, and the draft is committed with no push notification and no stop; one with a 「前端交互」 section still goes to the human), then design (`/idea-loop:uiux-imagine` → `uiux-refine`, started by the human), commits the spec and the frozen design to home, flips the issue to `todo` with a comment naming the spec's commit in home (`spec 已提交到 home <sha>`), and closes itself out (the runtime's "session wrap-up"). A **todo session** (opened by the dispatcher; claims `in-progress`) reads the spec in home (or drafts the spec itself with `to-spec`; if something needs the human it flips the issue back to `triage` with a comment and closes itself out), then cuts tickets (`to-ticket`; tickets already cut are not cut again, so re-typing the command works), implements (`implement`) and reviews (`pr-review`) in this same session, opening a worktree on the same-named branch in every other repository the issue touches (the ISSUE_TRACKER.md 「仓库」 section), until all PRs merge and the issue is `done`. When the task says 「夜间模式」 (the dispatcher's night rounds) nobody is there to answer, so `references/night-mode.md` applies: everything that would stop for the human is settled by its recommendation and listed in the PR description's 「夜里替你定的」 section (what was picked, why, the other option); the session stops only at merging a PR, deleting a branch or data, force-pushing, sending mail out or commenting in someone else's repository, or touching a project other than this issue's (written under 「等你定的」 where the session stopped); it works through `pr-review`'s first stop with the PR ready and the session placed in the in-review section, and does no retro and no archiving (left for the daytime). On a Linear project it reads and flips the issue the Linear way (`idea-loop:issues`), not with `gh` and `issues set`. A worktree the dispatcher already cut on `issue/<n>-<slug>` (magi) is used as is. On start it places itself by its state where the runtime has such placement (the desktop sidebar sections triage / in-progress / in-review) and titles itself `<repo>#<n> <title>`. "Put aside" is `dyna issues set … backlog --comment=<where it stopped, the branch if there is one>`; the next session reads that comment. It closes itself out at the end (desktop: archives itself, which removes its worktree; magi: stops itself, since a session cannot archive itself) |
| `idea-loop:issue-triage` | Intake | Sorts the backlog. Without arguments (the weekly scheduled task `triage-<repo name>`, installed by `setup`) it takes the oldest 15 backlog issues from `dyna issues backlog` and starts one `idea-loop:issue-triager` per issue, at most 5 at a time; each checks for a duplicate, the `docs/records/out-of-scope/` list, whether it is already implemented, reproduces it (output in `.tmp/triage/<n>/`), sets its category and posts one evidence comment through `dyna issues note`. The session does not wait for the human: it flips each issue straight to the route its triager suggested (`todo` or `triage` with P1/P2, `canceled`, or stay in backlog; a project that skips triage has no `triage` route). `canceled` only comes from a duplicate, an out-of-scope hit, already implemented or not reproducible; an issue it cannot judge worth doing goes to `triage`, never `canceled`. It pushes only when an issue stays in backlog waiting for the human to add information, or a suspected P0 is found, naming those numbers. The `out-of-scope` record is written in the triage session where the human decides not to do a request (`idea-loop:issue-session`), not here. `全部` runs the existing backlog in batches of 15, one batch after another with no table to approve; `P0 <n>` (called by 「开一个 issue」 for a suspected P0) starts a single triager, and on a reproduction flips the issue to `todo`, sets `priority:P0` and notifies the human |
| `/idea-loop:grill` | Idea | Design-tree interview, one round of open questions at a time — facts are the agent's job, decisions are the human's |
| `idea-loop:retro` | Retro | Run at the end of an issue session (`issue-session`'s 「收尾」, before it closes itself out) or by the human saying "retro". Reads this session's own transcript file — not its context, which compaction has already thinned — squeezed by `dyna retro digest` into every human utterance plus the conclusion of the AI reply before it (no tool calls or output). Finds three signals: the human's corrections and follow-up questions (one occurrence is enough), the human's choices on posed questions (the same kind at least twice across issues, no counter-example, counted from `docs/raw/decisions/` in the target repo), and directions the human volunteers (one occurrence; the human is asked which layer). Each candidate is shown with the verbatim words, where it happened, the layer (plugin skill / the target repo's rule files / a mechanical check), old and new wording side by side, how to verify afterwards that the change fixed that moment (a replay case's three parts, a check's name, or "can't verify" with where it is stuck), and — when the retro reads the candidate pool (`docs/records/retro-candidates/`, harold-skills' pool read from its project directory in home when it runs elsewhere) and finds the same kind already there — "this is the N-th time, merged into <that file>". The human answers approve-into-the-pool / approve-and-open-an-issue / reject / change; the retro recommends a home with each candidate — the pool while the kind has come up once or twice (counting this one), an issue from the third time, the pool's threshold — and the human still chooses; a bare "approve" follows the recommendation. It edits no rule file: an issue-bound candidate becomes a to-be-verified issue (plugin problems to harold-skills, project ones to the target repo); a pool-bound one is written into the pool by landing (plugin skill / agent / reference / script candidates go to harold-skills' pool, the target repo's own rule-file candidates to its own; a new file, or one more line in an existing file's 出现 section), where `dreaming` counts it. The questions put to the human and each candidate's outcome (`批·进候选池（<link>，第 N 次）` / `批·开 issue（<link>）` / …) are recorded in the project directory's `docs/raw/decisions/<issue>.md`, committed straight to home; a pool write into harold-skills from another project goes into harold-skills' project directory the same way |
| `/idea-loop:to-spec` | Spec | Turns the current context (a `grill` conversation, or an issue `issue-triage` has already reproduced) into one spec readable by humans as well as agents: one quoted line per covered issue saying whether it exists, the problem statement with its reproduction evidence, the plan (opening with an interaction sequence diagram; backend, front-end-internal and front-end-interaction sub-sections as needed), user stories as one tree per scenario (one expected behaviour per problem for pure fixes), implementation decisions, and testing decisions with agreed seams. Every section opens with one line saying what it gives the reader. A conversation also lands as a raw transcript. Settles what the user's rules (`~/.claude/CLAUDE.md`) and the four kinds of basis in `pr-review`'s review standards can settle, and gives every statement about the present state a source (the shared writing rules in `idea-loop:evidence`). When the issue is about a document an agent reads, it first diagnoses that document with `idea-loop:writing-for-agents` and lists its callers; the plan follows from both, each change naming the lever and ending with one 「验证：」 line (a check that was first seen red on the historical error / a replay case / a goal case written from the spec's own expected behaviour / "behaviour unchanged" with why / "can't verify" with where it is stuck); a skill change in the testing table's LLM-output row reads 「见杠杆诊断各处的验证」, not 「不涉及」. A spec has no status: its frontmatter lists the issues it covers (`issues:`), and a spec that still has a 「需要 grill」 line or a 「待定」 fork keeps its issue in `triage` until the human settles it. The spec is committed straight to home, not to a branch (a spec that covers no issue: with the human present it is opened as a `todo` issue through `dyna issues new`, otherwise the skill stops and asks). Figure rules: `idea-loop:evidence` |
| `/idea-loop:uiux-imagine` | Design · diverge | The skill runs the process; `idea-loop:uiux-imaginer` (latest Opus via the `opus` alias, effort high) does the work, one task at a time. It opens only the altitude that is still undecided and renders every round straight into a clickable comparison board with real motion, at the lowest fidelity that tells the variants apart. The skill shows each round to the human (the "browser" capability's show-the-human section), sorts the human's reply into a task (steer / apply to the picked variant / park for refine / reopen the language), and proposes wrapping up once nothing directional is left; the human declares it. Wrap-up hands ONE direction note (seven sections, a composition list per chosen variant, each item marked human-chosen or model-filled) plus a handoff canvas to `uiux-refine` via `docs/design/tmp/<spec-slug>/imagine/` under the project directory in home (`<project directory>/docs/design/tmp/…`, absolute path handed to the imaginer; local, not in git) — no critic, no scoring. The imaginer does not research: a UX question it can only guess at goes back as a suggested research question with its recommended answer; the human decides whether to run `uiux-research`. When the project has no `DESIGN.md`, the imaginer drafts the first one and the skill writes it only after the human confirms the wording. **Shelved designs**: before starting, it looks in the project directory's `docs/design/pending/` for a design of the same screen and asks the human whether to carry on from it; if yes it is copied back into `<project directory>/docs/design/tmp/<spec-slug>/` and resumed from the interruption-and-resume path. When the human says "not building this screen yet", the orchestrator moves the whole `tmp/<spec-slug>/` untouched to `<project directory>/docs/design/pending/<spec-slug>/` (local only, never committed, skipped by the design-archive check) and leaves a pointer and the reason in the spec (`idea-loop:wiki-conventions`) |
| `/idea-loop:uiux-refine` | Design · converge | The skill runs the process; two plugin agents do the work, and the human decides every round. `idea-loop:designer` (latest Opus via the `opus` alias, effort high) delivers the next canvas version (`v1`, `v2`, …) from the handoff canvas `uiux-imagine` leaves behind (or from the direction note alone when there is none) and hands back a **change set** with each version, every entry tied to a decision number; it only does what the decisions and the ledger say, and hands back "stuck" (what it is stuck on) when two decisions collide or a decision conflicts with the design laws. Each round the session has a fresh `idea-loop:ui-master` (latest Fable via the `fable` alias, effort high, Read-only — it never sees the canvas code) act as an **advisor**: it hands back opinions (each with a one-line description of the real screen that would explain it), an assessment of each of the human's lines of reasoning, and a score, and `dyna design critic round` only checks the shape (it decides nothing about stopping). The session compares this version with the last with `ui-measure` (what changed without being declared in the change set), starts the researcher's light use for a user path and Mobbin reference pictures per opinion, and assembles one **design review report** with `dyna design report`, sent through the runtime's "publish a review page" capability; the chat gets the report link, the score and what needs attention (each may carry a sentence or two of why it is recommended, plus a line on how to answer). The human answers in the chat by number and every item needs an answer before the designer moves: what they do not mention, the session asks again instead of deciding for them; once confirmed, the decisions go into the **ledger** (`canvas/work/ledger.md`), the only record of what the human settled. There is no pass and no bottleneck: the human's signature freezes, and before it the session lists the direction-level opinions nobody has resolved. When the judge names a direction-level opinion about a block the human has already said they dislike in this refine, the report recommends going back to imagine for that block instead of keeping it. Motion is one kind of decision, and the subtraction and AI-tells checks are standing angles of the judge and a self-check of the designer, not rounds; after "static is settled" only the asset list (marketing register only) and the pre-sign-off check remain. The designer does not research: a question it cannot settle becomes a "suggested research question", worked from its recommendation. Freezes (fully or partly) on the human's signature and writes interaction flows back into the spec; what it tells the human after the freeze depends on the session type: a triage session goes back to `issue-session`'s 「交给调度」 (push, flip to `todo`, wrap up; no tickets), a todo session to its 「实现」 (draft PR first, then tickets), outside an issue session the human decides; the signed canvas, the freeze record and the flows are committed straight to home, no `delta/`. After the freeze the canvas is the one design truth: when the human later accepts something that differs from it (accepting the implementation in review, accepting an implementer's way out of a stop, or changing their mind), the orchestrating session of that stage (`implement` before the PR opens, `pr-review` after) runs the shared `design-change-sync` skill (the steps are written once there, not in `uiux-refine`), which starts a `designer` on the task "design change" — it edits only the affected cells and hands back the next canvas version — and a fresh `ui-master` gives opinions on only those cells and the human decides whether to commit (the judge is an advisor, not a gate); once the human says commit, the session commits the canvas to home, adds one row to the freeze record's section "changes after the freeze", and sends an implementer after any ticket whose code now disagrees. The human has already seen the redrawn cells at that decision. Shelving a design ("not building this screen yet") and carrying on from a shelved one follow the same rule as `uiux-imagine`: `<project directory>/docs/design/pending/<spec-slug>/`, `references/after-freeze.md` has the steps. |
| `/idea-loop:uiux-research` | Design · research | Two branches. **Full-page research** is run by the **human**, whenever they want to see how other products do something (no spec needed; model-invocable, so "look up how others do the leave-confirmation dialog" in plain conversation starts it). The skill turns the ask into one named question, picks the drop directory, and starts a fresh `idea-loop:uiux-researcher` (latest Opus via the `opus` alias, effort medium; tools: the session's tools minus a deny list, found by short name; it uses the Mobbin MCP's search tools, `curl` and writing files in the drop directory). The researcher downloads the reference screenshots and writes one `index.html` (relative paths only, opened through a static server and shown to the human the way the "browser" capability's show-the-human section says) — at the top the named question, a 「研究问题」 block with the human's own words and the context handed to the researcher, and what these products agree on; then per source a flow of screenshots (click to enlarge) with scene and design logic only; and last, after the final source, the questions the human must decide once all of that is read against our needs — checked by `dyna research submit`; the caller only receives the page's path and one sentence, never Mobbin calls or whole screenshots. Files go to `<project directory>/docs/design/tmp/<spec-slug>/research/<question>/` (with a spec) or `<project directory>/docs/design/tmp/research/<question>/` (without), local and never in git. UX patterns, flows, usual page structure and copy tone only — never visual style. The data source is Mobbin (screens, flows and website sections; needs a paid Mobbin plan and a one-time OAuth login); with Mobbin not connected the research stops and says how to connect it, and nothing else is affected. The orchestrator of `uiux-imagine` / `uiux-refine` calls it only when the human says to, and forwards conclusions to the executor only when the human says which, as text (never the pictures). **Light use** is the other branch: the design-convergence session starts the researcher itself every round, with no approval from the human, after the judge's opinions come back. It hands over the round's per-state screenshots, the numbered judge opinions, the human's intent and thinking and the ledger; the researcher covers only what those opinions touch and returns one structured file, `research-light.json` (not a page), next to the screenshots it downloaded: per opinion (or per group of opinions about the same thing) a user path — each step says what is seen, what is done, what comes next, with 1–2 Mobbin pictures and a one-line reading — and one sentence of new design intent, plus an `overturns` entry (ledger number and reason) when the path argues a ledger decision should change, and `uncovered` for opinions it found no reference for. With Mobbin not connected the file says so (「这一轮没有参考图：Mobbin 没连上」) and is still valid. `dyna research submit --light` checks the file; its format is in `skills/design/uiux-research/references/light-return.md`, apart from the full-page contract. The designer and the judge still never research, and the reference pictures go to the human only |
| `/idea-loop:to-ticket` | Plan | Slices a spec with nothing left for a human (no 「需要 grill」, no 「待定」; design frozen if it touches UI) into tracer-bullet vertical cuts with blocking edges. Before cutting it fetches the remote and reads `origin/<base branch>`: from the entry the user comes in by (a URL, a command) it walks the real call chain hop by hop to the data source (route → page → API in a web app), saying what each hop does now, including hops the spec does not name, and reads the commits on the base branch that touched the chain since the spec file's last commit; a stretch the spec does not cover counts as "spec not clear" and goes through the same stop rule below. Inside an issue session (called by `issue-session`) it stops when the issue is still in `triage` (state read with `dyna issues show`, not the label) and points back to 「交给调度」; called directly by the human it does not check the state. It writes the tickets and commits them to home (the implementers' worktrees are cut from the code branch and cannot read home, so dispatch hands them the tickets' absolute paths) without waiting for a nod. The cut (title / blocked by / end-to-end behaviour per ticket) goes into the final review report; it stops only when slicing surfaces a real decision question for the human. A ticket that changes skills, agent definitions or skill reference files (by path: `SKILL.md`, any `.md` under `skills/`, a `.md` directly under `agents/`) ends its acceptance list with three fixed acceptance cells: `writing-for-agents` called with one lever line per changed file in the hand-back, the `SKILL.md` body inside the limit, and, one per change, the spec's own 「验证：」 line copied in (the executor does not pick the proof; a change whose spec has no such line sends the cutting back to the spec) |

### The forward loop is not the maintenance sweep

`grill → to-spec → [uiux-imagine → uiux-refine] → to-ticket → implement →
pr-review` runs once per piece of work. Everything it writes into the knowledge base — spec, frozen
design, tickets, the design archive after the code PR merged — is committed straight to home's main with
`dyna home commit`, which stages only the files it is given; the issue's branch and the code PR carry
code only (`skills/productivity/wiki-conventions/SKILL.md`, section 知识库落地). Triage cuts no branch: the
branch comes with the first line of code.
**One state, on the issue** (`skills/engineering/issues/SKILL.md`): backlog → triage → todo →
in-progress → in-review → done, plus canceled. backlog is an open issue with no `status:*` label;
triage is the human's evaluation (grill, design), and the dispatcher opens a session for each triage issue in the daytime periods; `todo` is dispatched in the night periods; a todo session opens a
draft PR as soon as the issue's branch has its first commit (an issue touches one repository, so it has one PR), turns it ready
for in-review, and the issue is done once that PR is merged. A team without triage says so in
`ISSUE_TRACKER.md` and goes backlog → todo. Besides its status an issue carries `type:*` category
labels, defined in the `分类 label` section of the project directory's `ISSUE_TRACKER.md`. **A spec is a document, not a second state**: its
frontmatter only lists `issues:`, `dyna spec` reads it, and `dyna issues` is the only
writer of an issue's status and checks the precondition before writing (for triage → todo: nothing
in the spec waits for a human, and a spec that touches UI has its freeze committed straight to home). Issues are not grouped by parent and child: one issue, one session, one spec.
**Issues on Linear** are supported: the project's `ISSUE_TRACKER.md` says `# Issue tracker：Linear`, sessions, the dispatcher and triage read and write the issue through the Linear MCP as `skills/engineering/issues/references/linear.md` lays out (in-progress is flipped at claiming, in-review and done are pushed by the GitHub integration), the `dyna issues` commands that write GitHub issues refuse there, `issues check --from=<current state>` still checks every flip's precondition, and a spec's `issues:` may list keys like `ENG-123` (`dyna spec` reads them as strings; an opening verdict line reads `> ENG-123 存在：…`). `issues new` takes `--repo=<owner/repo>` to open the issue in another repository. Every other `dyna issues` command works on the project's own repository, taken from the project list in home (not from the directory it runs in), and `ISSUE_TRACKER.md` has no 「仓库」 section any more: an issue changes one repository.
`dreaming` is a **batch reconciliation** over the whole vault: the docs, the design archive and
`DESIGN.md`. It runs weekly from the scheduled task `/idea-loop:setup` creates, or by hand. It is not the
next step after `implement`.

**No stage in the forward loop writes an ADR.** ADRs are produced only in Maintain,
which is also where a finished spec is deleted (the contract's invariant: never delete
a spec before its ADR exists). So a spec sitting in `docs/spec/` with its work already
merged is a **normal state**, not an oversight — it is waiting for the next sweep.

Which skills the model may invoke itself:

| Model-invocable | Human-invoked only (`disable-model-invocation`) |
|---|---|
| `grill`, `retro`, `issue-triage`, `to-spec`, `to-ticket`, `implement`, `pr-review`, `uiux-research`, `writing-for-agents`, `seo-scan`, the SEO method and solve skills | `uiux-imagine`, `uiux-refine`, `dreaming`, `setup`, `agent-builder` |

`grill` is model-invocable so that "grill this idea" in an ordinary conversation starts it; it is still an
interview, so it only means something with a human answering. `uiux-imagine` is human-invoked: it steers on a human's directional
reaction each round, and a human is the one who declares the direction done.
`uiux-research` is model-invocable because looking up "how do others do this" is an ordinary thing to ask for in any conversation — but the *decision* to run a full-page research stays with the human: inside imagine / refine the orchestrator calls it only when the human says to. The one exception is its light use, which the design-convergence session starts every round on its own (the researcher stays a separate agent, so the session only receives a file). `uiux-refine` stops on a human at every round — the human decides by number what each opinion becomes, and
only the human's signature freezes — and wants a fresh window so it starts from the handoff canvas and
direction note instead of continuing the diverge session it cannot see. `dreaming` proposes
destructive disposals.

The project's `DESIGN.md` is written from exactly two places, `uiux-imagine` (only when the
project has none at the start) and `dreaming`; both read `skills/design/design-modeling/SKILL.md` and wait for the
human to confirm the wording before every write. Everything else on the design side — `designer`'s
motion sign-off, the Distill-back at the end of a freeze, an implementer meeting a value `DESIGN.md`
lacks — only writes a *design-law candidate* for `dreaming` to process.

The execution two were human-only until the caller-dispatch model landed: a ticket needs a
context holding nothing but itself, and `/clear` is a human action. Dispatching a fresh agent
satisfies that precondition too — more strictly, in fact — so `implement` became an orchestrator
that dispatches one `idea-loop:implementer` per ticket. What the lock was protecting did not come
off: the ticket must still be self-contained (no file paths, no code snippets, behaviour not
procedure), and the implementer must still **stop and report** when a behaviour is undecided
rather than guessing its way onward. See `to-ticket` §6 for where each of the original reasons
now lives.

### Delivery: implement → draft PR → review

```text
/idea-loop:implement <spec-slug>
```

One spec, one integration branch, one PR. The PR description is the **review
report**, written for a reader who never followed the work (it was delegated) and meant to be enough to
decide the merge: one sentence; the problem (what was seen, with numbers); how it was fixed (the
rules applied and their grounds, the slicing into tickets with what blocks what, each page or flow
end to end with its before → after shot); how it was verified (what was verified, what was not and
why, what the review rounds concluded); whether it can be rolled back (how, what it touches, what to
prepare before going live, the issues filed on the way); and what the human has to do (review the
human-verify material, decide, then say "merge"); plus a folded reference. No code lines,
variable names or paths outside that reference — `dyna pr body set` refuses them. When a review round has
nothing for the human to decide and nothing left to fix, the orchestrator does not wait: it waits for the
PR's CI, writes the report and stops there; merging afterwards needs no further CI wait, and the tickets are
deleted from home (and the design archive written) only once the code PR has merged. Layout: `skills/engineering/pr/SKILL.md`.

**The review loop lives in the session, not on GitHub** (`skills/engineering/pr/SKILL.md`, section "review loop 文件"). Only one
person reads the reports and decides, and they are already in the Claude session (desktop or
phone), so every Review 汇报 (implementation stops and review rounds are the same kind of report) is shown there, with figures sent as files and a push
notification; the human replies there; the orchestrator handles the batch and answers in one reply.
The same words — report, the human's rulings verbatim, what was done — go into one local file per PR
(`.tmp/review-loop/<PR>.md`, `dyna pr loop`), the loop's memory across compaction or a new
session. When the human says merge, each report is posted to the PR as one plain comment
(figures uploaded and linked), then the PR merges and the file is deleted. No threads, no bot
waiting on GitHub. (Tried first: threads on the PR with a background watcher waking the session;
it worked, but carried one person's words from GitHub back into the session they were already in.)

| Phase | PR | Who talks | Where the human answers |
|---|---|---|---|
| Implementing | draft | `implement`'s orchestrator, in the session | A **Review 汇报 per stop** (the same report as a review round, "from implementation"; written for the record but not waited on when it has no decision): first what was **handled by rule** (details the spec left open that the product already answers, legacy problems fixed because they affect the change (they spoiled the ticket's input or conclusion, turned CI red, or state a fact — a count, name, path or structure — that this change just made out of date), and legacy problems that do not affect the change, which the implementer noticed, for which the orchestrator already opened an issue (no status label) — one line each with its basis; overturn any with one sentence, which the orchestrator writes into the ticket as the human's decision), then what needs deciding, then whether what landed can be rolled back, then the human-verify material (flows and GIFs recorded from the implementation, one checkbox each) |
| Review | open | `pr-review`'s orchestrator, in the session | A **Review 汇报 per round**, written for the person who decides: a one-line verdict, then **handled by rule** (what was done, on what basis, with a commit or issue link — overturn any with one sentence), then each thing to decide in one format whichever axis it comes from — titled by its consequence, with the situation now (a Standards finding quotes the rule here), the user impact, whatever evidence makes it fastest to grasp (screenshots, an annotated flow, a GIF, a sequence diagram, a small table, a worked example), options that each say what they cost and whether they can be undone, and a recommendation — then whether the change can be rolled back; no variable names, file:line, commit hashes or section numbers in the body — code locations go in a folded block for the fixer |

- **Ticket done = every acceptance box has evidence or names who takes it over** (a later ticket,
  or the PR's delivery check), the tests the ticket wrote or touched, the API tests of the interfaces it touches, the selected regressions, typecheck and lint are green; the full suite runs once, in CI, after the PR turns ready (a repository with no checks runs it once locally per head and records it with `dyna pr full-suite record`, and pr-review reuses a green record of the same head via `dyna pr full-suite show`) — then one
  commit carrying a `Ticket: <NN>-<slug>` trailer. Git is the ledger; nothing else counts tickets.
- **Stop vs defer.** A behaviour nobody decided stops that ticket (and what depends on it) — unless the
  product already has one way of doing it (name an existing instance): then the implementer follows it
  and says so in its hand-back; a legacy problem that affects the change (it spoils the ticket's input or conclusion, turns CI red, or states a fact — a count, name, path or structure — that this change just made out of date, even in explanatory text or a file the ticket does not name) is
  fixed in this ticket and reported as such, while one that does not affect the change becomes an issue the orchestrator opens, after the orchestrator re-checks the stated reason and sends a mis-sorted one back to the same implementer (the reviewer does not hunt for legacy problems, and reports only the same three kinds). Everything else keeps going. A behaviour that is decided but cannot be proven inside this ticket
  is deferred to a named receiver; no receiver means it was undecided after all.
- **Posting identity.** The archive comments posted at merge come from the repository's GitHub App
  when `~/.idea-loop/github-apps.json` configures one (Pull requests write, Contents read); otherwise
  from the gh login; neither adds a signature line to the body.
- **Delivery evidence never enters the code branch or `docs/`.** It lives on one orphan branch per
  PR (`dyna pr evidence`), never merged, deleted when the PR merges, and is embedded as
  `blob/<branch>/<file>?raw=true` so clicking an image opens it full size instead of downloading it
  (`skills/engineering/pr/references/delivery-evidence.md`). Knowledge-base images — spec figures, frozen canvases — stay in `docs/`.
- **Two axes, reported apart** (`skills/engineering/pr-review/references/review-standards.md`). The reviewer runs the repo's
  declared checks and keeps only diagnostics on changed lines (`dyna pr diagnostics filter`), and lists the SKILL.md files and agent definitions whose body length changed, before → after (`dyna pr skill-growth <merge-base>`, facts only; Standards judges the growth); each
  Codex process sees only its own question. A behavioural Spec finding that cannot be reproduced
  and drawn, or a Standards finding whose rule text or code is not where it claims, is discarded by
  `dyna pr candidates submit` and listed in one folded line; a finding that stands but is missing a
  part or speaks in code terms is sent back for rewording before the report is shown.
- **What the agents settle themselves, and what they ask** (the user's rules, `~/.claude/CLAUDE.md`, and
  `skills/engineering/pr-review/references/review-standards.md`). `setup` writes one fixed text into
  `~/home/AGENTS.md` (sections 思考与决策, 沟通, 证据; the one copy is
  `skills/engineering/setup/references/home-rules.md`, written by `dyna home config` as its fourth item), so
  every session and general-purpose sub-agent loads the same four working principles (confirm the problem,
  name the goal, push one step further, goal before convenience). The text says what is the human's alone
  (merging a PR that changes code, production data, real payments, publishing, naming terms) and when to stop
  and ask (a silent error, no goal to name, the shape of the plan); anything else the agent decides and lists
  first under "handled by rule", and an overturn is one more ruling, recorded verbatim. In the PR flow a basis
  is one of four things — the text of a written rule, the human's own words already given, an existing practice
  with a named instance, or a goal (a line of this spec, with a verdict: met, met in part, not met; only "met"
  is followed by rule); `dyna pr candidates submit` finds the text where it says it is (a goal's quote must come
  from the spec passed with `--spec`). When bases conflict or there is none, the finding goes to the human.
  For a scope question (fold a surfaced change into the current PR, or open it separately) the recommendation
  follows delivery, not PR size: a problem that affects this spec's implementation, or has an effect once
  shipped, is recommended into the current PR; the rest is not, and goes back to the caller's own process. How
  each flow disposes of findings (the reviewer's disposition table, the implementer's stop-or-defer table)
  lives with that flow. `idea-loop:evidence` takes the fixed "Evidence" section in home as the overall rule and
  writes only what is outside it: what counts as evidence (re-checking the baseline, like-for-like comparisons,
  reproduction, evidence taken from the thing being judged) and the overall style (the smallest view that makes
  the point, names taken from the glossary or the conversation and explained only when neither has them, overlays
  declared); an overview of the six forms says what each lets the human see (annotated screenshot: one screen's
  problem; UI flow: the whole user path; chart; GIF: an interaction while designing or changing it; screen
  recording: the end-to-end delivery, checked in the PR; table or one-line example), each with its own how-to file, and a recording is an H.264 mp4 under the same 10MB limit
  (split into segments when over); where it goes is up to the caller (`to-spec`'s
  `references/figures.md`, `pr`'s `references/delivery-evidence.md`). Section 4 of a drafted spec keeps what the
  rules can settle as decisions with their basis; only the choices whose basis does not hold are
  left as options, and every "suggest closing" entry says what was claimed, why it no longer holds,
  and how that was checked.
- **Fixes go back through the tickets.** A finding fixed — by rule or by the human's word — becomes a
  new acceptance box on the ticket that introduced it (found by the quote, or by `git blame` →
  `Ticket:` trailer), and a fresh implementer does it. **The next round starts itself** when
  this round had at least one fix, every item is handled and the fixes are pushed, and the next
  round number is at most 5 (it says so and sends a push notification first); with no fix it stops
  and waits for the word to merge, after the fifth round's fixes it stops and says they went
  unreviewed. The cap binds only the automatic start — the human can ask for another round any time. Merging is the human's order.

The old loop (up to two automatic rounds of three-axis review → fix → re-verify, one round post per
round, a mergeReady verdict) and its design record [`docs/pr-review-loop.md`](./docs/pr-review-loop.md)
are superseded; the record stays as history.

### The blog workflow: brief → writing loop → publish

An SEO article (an issue labelled `type:seo/*` whose spec is a content brief) goes through three steps,
all inside the issue session; the angle is the only thing a human has to pick, and when nobody is there
(night mode) the session follows the recommendation and writes the basis 「AI 照推荐定」 into the spec.

1. **Brief, with images** (`seo-writing`'s brief branch, triage session). After the angle and the title are settled the
   brief gets a 「配图」 section: cover-subject candidates per angle and the OG headline taken from the
   title. `idea-loop:cover` (the article-list cover and the top image) and `idea-loop:og` (the 1200×630
   share card) make the two images; they are committed with the spec. A human in
   the session answers angle and cover subject in one question; a project with no 「出图配方」 gets the default
   and the brief says so in one sentence.
2. **Draft, then a revision loop** (`seo-writing`, todo session). The draft follows the brief and the
   project's voice files. Then, every language version, up to three rounds: `dyna seo writing lint`
   (configured by `SEO.md` 「lint 配置」) and the project's own 「补充 lint」, then a 「写作评委」 (writing judge)
   sub-agent scoring 13 dimensions (plus 「第二评委」, a second model's command, when the project set one).
   Lint hits and `local` findings are fixed by the writer; what is still not clean goes into the handback.
   A `premise` finding (the thesis, the sections or the factual claims would change) is never fixed by the
   writer: the committed work is pushed and the issue goes back to triage with the writing judge's own words, in
   the day and in night mode alike (`skills/engineering/issue-session/references/night-mode.md`), because
   the angle is the human's. A changed title or thesis re-runs `cover` and `og`.
3. **Publish** (`seo-writing` handback, then the existing flow). Build the site: the post-build hook runs
   `dyna seo check` on the changed routes and hands any error back. The handback lists the files, the lint
   result, the writing judge rounds, what is not clean and any `premise`. The draft PR, the auto-merge for
   content-only SEO PRs and the post-deploy check are the flow described above under "Delivery".

What a project writes to use it (the format is `skills/engineering/setup/references/seo/seo-md.md`; setup's SEO module
asks for each key with a recommendation):

| Where | What | Read by |
|---|---|---|

## Command line: `dyna`

`dyna` is idea-loop's command line: skills and agents write `dyna <module> <command>` and look the arguments up
with `--help`, instead of calling scripts by full path. It is written in Go, lives in the repository's `dyna/`
directory (not a plugin), and is released on its own as packages on GitHub Releases; the plugin only carries
the skill text and a launcher.

- **`bin/dyna`** (this plugin) is a short `sh` launcher; Claude Code puts the plugin's `bin/` on the session's
  PATH, so a session just types `dyna …`. It hands the call to the installed binary, `~/.idea-loop/bin/dyna`,
  together with the plugin's directory (`IDEA_LOOP_PLUGIN_ROOT`) and the version range from **`dyna-version`**
  (`IDEA_LOOP_CLI_RANGE`). The binary refuses to run outside that range and says what to run: `/idea-loop:setup`
  to upgrade it when it is too old, `/plugin` to update the plugin when the binary is too new; with no binary
  installed the launcher says to run `/idea-loop:setup`. A call with `--hook` is never stopped by any of this:
  one line on stderr and exit 0.
- **`dyna self install` / `dyna self upgrade`** are handled by the launcher itself, so they work before any binary
  is installed: they download this machine's package, check its sha256 against the release's checksum file, and put
  the binary in `~/.idea-loop/bin/`.
- **`dyna-version`** is raised only when a skill starts using a command or flag a newer dyna added, and only after
  that dyna is released and its command registry is stored in `dyna/registry/`. `scripts/dyna-scan.test.mjs`
  (repository root) reads every `dyna <module> <command>` written in the skills, agents, this README, `hooks/hooks.json`
  and `.mcp.json` against the registry of the lowest accepted version and goes red on a command or flag that is not
  there, on a hook-only command written outside `hooks.json`, and on a floor that is not released.
- **`dyna registry --json`** prints the command registry: each command with its arguments, one-line summary, who
  may call it (a session, only a hook, only tests) and the next command to run when it fails.
- **`runtime/`** (this plugin) is the data the `runtime` module reads: `capabilities.md` (the capability list, its fallbacks, and the capability template: per capability the items a flow asks of it, each with what goes in, what comes back and what to do when it cannot be done; `runtime inject` leaves the template out, `dyna runtime check [<file>]` checks a description against it)
  and one `<environment>.md` per runtime environment, each with one `## <capability>` section. `runtime show
  <capability>` prints the current environment's section, `runtime inject` (only the SessionStart hook calls it) prints

The text lives in the plugin, so

## Tests

Node tests across this whole repo (every plugin's `scripts/`) run under **one
command**, from the repo root:

```
node --test '*/scripts/*.test.mjs' 'scripts/*.test.mjs'
```

Node's own test runner, no test framework and no `package.json` — the glob is
what keeps the command stable as plugins add suites, and the leading `*` is what
keeps it out of `.claude/` worktrees. This plugin's `scripts/` holds only tests now, of
two kinds: tripwires on the text of skills, agents and references (the `*-doc.test.mjs` files, and
the tripwire that keeps the plugin free of the source project's names and examples), and tests of how the plugin
reaches the command line (the launcher `bin/dyna`, the commands `hooks/hooks.json` and `.mcp.json` call, the two
eval runners against a fake `claude`). Anything that has to ask `dyna` something builds the binary from the
repository's own `dyna/` once per test file (`scripts/dyna-test-bin.mjs`), never the installed one.

What the deterministic scripts used to do is `dyna` code now, and its tests are Go tests: `cd dyna && go test ./...`
(`go vet ./...` and `gofmt -l .` are its typecheck and lint). The browser boundary (`dyna ui measure`) has no
unit test on purpose, as before — mocking a browser would test the mock; the sections shooting's generated code is run
in a real Chromium by a Go test that runs only with `IDEA_LOOP_BROWSER_TESTS=1` (and skips when no Chromium is found), so the full
`go test ./...` leaves it out. It takes about 5 minutes; run it on its own, in the background, when the sections shooting's browser code, the screenshot
compare it uses or the test itself changes:

```
cd dyna && IDEA_LOOP_BROWSER_TESTS=1 go test ./internal/design/sections -run TestBrowserCodeRunsInARealBrowser -timeout 15m
```

## Replay: proving a rule change took effect

A rule written into a skill, agent or reference is only a claim until the skill is seen behaving differently. A rule that can be
decided mechanically becomes a check (a script or a validator test) that is first seen **failing** on the input that reproduces
the old mistake. A rule that needs judgement gets a **replay case** in `evals/retro/cases/<case>/`: the commit the decision
happened at, the prompt that made the skill produce the thing, where it stops (the moment it hands the thing to the human; only
the judging session is told), a yes/no question written from what the human said back then (with the words quoted, `quote`), and its size
(small or large) with the basis. A new ability has no history and no words to quote: its case is a **goal case**, which names in
`goal_from` the spec and the User Story or expected behaviour the question was written from, instead of `quote` (one of the two,
never both, never neither). It runs the same way, on both plugins with the same judge; the judge is told the question came from
that spec expectation, and a pre-change "yes" reads 不过：改前就做得到 (the human decides whether to change the case or drop the rule).

```
node idea-loop/evals/retro/retro-replay.mjs --list                      # cases, sizes, format problems
node idea-loop/evals/retro/retro-replay.mjs --case <name> [--base main] # one small case: pre-change vs post-change plugin
node idea-loop/evals/retro/retro-replay.mjs --settle <name> --run <dir> # re-decide after the human overruled a judgement
```

The runner copies the project as of the case's commit into a temp dir, runs `claude -p` with `--plugin-dir` pointing at the base
branch's plugin and again at this working tree's plugin (a sub-agent cannot do this: it loads the installed copy), then has a
judge read both products anonymously and answer the question with a quote. **The judge is Codex** (a different model family from
the two runs), run through `dyna agent codex run` (the `codex` command on PATH; read-only, never write access), with the
products lettered A and B in a random order each time; the order is recorded as `afterIs` in `result.json` and turned back into
pre-change / post-change when the answers are read, and `result.json`, the terminal report and the review loop entry all say who
judged (`judge: codex` or `judge: claude`). It uses no Claude quota (the cost estimate printed up front still follows the old
formula and says the judge runs on Codex). When no Codex is found, the runner prints 没找到 Codex，评委用 Claude before it starts
and judges with `claude -p` as before (a Codex that gives nothing at judging time falls back the same way, said out loud); a
replay is an acceptance check, not a gate, so it falls back instead of stopping, and the entry shows it (with `RETRO_CLAUDE_BIN` set to a stand-in `claude` and `RETRO_CODEX_BIN` not set, the runner does not look for a real Codex at all: the stand-in judges). **The input is only the human's
words**: each run is given exactly the case's `prompt` (nothing added, no note that it is a test, no stop point: an agent that hands
its work to the human ends its turn, and the timeout is the backstop) and works in `<tmp dir>/<random>/<project name>`, a path with
nothing about retro, replay, before or after in it, and the plugin it loads is copied to `<tmp dir>/<random>/<plugin dir name>`
first (`--plugin-dir` points there, so a skill's "Base directory" shows no such word either) and the copy is deleted afterwards;
what the runs leave behind is kept under the run dir, where the agent does not look. **The plugin files the change touched are put into the project copy in each side's own version**: when the case's commit holds this plugin at its place in the repository (a `.claude-plugin/plugin.json` there with the same `name`; a plugin outside a git repo is taken to sit at `<repo root>/<its dir name>`), every file that differs between the base branch's plugin and this working tree's (added, edited or deleted, anywhere in the plugin dir except its top-level `evals/`, which holds the replay cases and eval material themselves and is never swapped in) is written from the side being run, or removed when that side lacks it, before the project's initial commit, so a run that reads the plugin straight out of the project reads that side's rule and the swapped files do not show up as something the run wrote; the other plugin files and the rest of the project stay as the commit had them, and a commit with no such plugin (a case from another repository) is unpacked as it was. **No process the runner starts has a `gh` login**: the two runs, the Claude judge and the Codex judge get the runner's own environment without `GH_TOKEN` / `GITHUB_TOKEN` / `GH_ENTERPRISE_TOKEN` / `GITHUB_ENTERPRISE_TOKEN` and with `GH_CONFIG_DIR` pointing at an empty dir under the run dir, so a `gh` read (an issue or PR as it is now, not as of the case's commit) fails as not logged in; the runner's own environment and the machine's login are untouched, and reading the public repository's web pages (WebFetch, `curl`) is not stopped. A case whose `prompt` contains 回放, eval, judge, rubric, benchmark, 评测, 评委 or 判定 (any case) is malformed: `--list`
reports it and `--case` / `--run-large` exit 2 without starting a session. **Before the judge, the runner checks that the post-change run used
the change.** The change set is the files added or modified under `skills/` and `agents/` between the base branch's plugin and this
working tree's; the run used it when its event stream (main session and sub-agents) reads one of them (a Read, or a Bash command naming
its full path or its path relative to the project; the project's own copy of the plugin counts as a place the post-change plugin sits), calls a skill one of them belongs to (the Skill tool, or a prompt that starts with that skill's slash command, which the
harness loads without a tool call), or starts an agent one of them defines (the Agent tool), or when one of them is a file the SessionStart hook injects (`runtime` and the reference of the runtime the replayed session runs in, found by the detection rule on the runner's environment, which the session inherits; the other runtime's reference is not injected and still has to be read or called to count: the session has it from the start and nothing in the stream shows it; reported as `injected`, after any read or call that is). Used: the judge's answer decides as before and
`result.json` records what was hit (`exercised`). Not used: the judge still runs and its answers stay in the result, but the outcome is
`not-exercised` (用例没测到改动), exit 1, listed in the review loop entry like any case that did not pass; a skill that was never loaded
cannot show that its rule works. An empty change set (only scripts changed) is recorded as 不适用 and the judge decides. Pre-change "no" and post-change
"yes" is a pass; pre-change "yes" is reported as "the case did not catch the problem". It does not score anything. Details and
the exit codes: the header of `evals/retro/retro-replay.mjs`.

**Annotated samples.** A skill whose products are judged by feel rather than by a single rule (so far `evidence`) keeps a group of
real scenes where the human once asked for the evidence, in `evals/<skill>/cases/<name>/`: the same `case.json` format as a replay
case, plus `sample.md` (the original text, what the human pointed at, what good looks like, and which scene was swapped in and
why when the original input could not be had) and `annotations.md` (where the human overrules a judgement). The retro runner runs
them as it runs any case, with `--cases-root`:

```
node idea-loop/evals/retro/retro-replay.mjs --worktree "$PWD" --cases-root "$PWD/idea-loop/evals/evidence" --list
node idea-loop/evals/retro/retro-replay.mjs --worktree "$PWD" --cases-root "$PWD/idea-loop/evals/evidence" --case <name> --base <before>
```

Nothing is scored; the output is the two products and the judge's answer for the human to annotate. Run the group after changing the
skill. The rule for adding a group is in the repository `AGENTS.md`, "Eval 策略".

**The temporary home.** The knowledge base lives in idea-loop's home (`projects/<名字>/docs/`, `IDEA_LOOP_HOME` points at it), and the
post-change plugin reads only home. So every session the runner starts gets its own temporary home (a git repo in a temp dir, a copy kept
under the run dir as `<side>/home`) and `IDEA_LOOP_HOME` points at it; nothing of the machine's own home is reachable. An **old case**
(no `home_commit`: its commit is from before the knowledge base moved) gets one built out of that commit: its `docs/` and bootstrap
files copied into `projects/<名字>/`, the project list naming the project (the case repository's `origin`, the checkout the run works
in); the post-change run gets it, and so does a pre-change plugin that already reads the knowledge base from home (its `hooks/hooks.json`
has the `home map` SessionStart hook: the plugin of 0.2.0's line); a pre-change plugin from before 0.2.0 reads the same files from the code
repository and gets an empty home. A
case with the optional field **`home_commit`** (a commit of the home repository) gives both runs a copy cut from it, and
`--home-repo <dir>` says where the home repository is (required for such a case). The judge sees the files a run wrote in its home as well
as in the workspace. The conversion from `docs/` to a home lives only in the runner.

**The fixed text, per side.** A side whose plugin has `skills/engineering/setup/references/home-rules.md` gets its temporary home written
the way `/idea-loop:setup` writes a real one (`dyna home config apply --only rules`, run with that plugin and a throwaway `HOME` so nothing
lands in the machine's own `~/.claude`), so the home has the sections 思考与决策 / 沟通 / 证据; the pre-change plugin has no such file and its
home has none. A replayed session cannot be given another `~/.claude/CLAUDE.md`, which is where a real session reads home's `AGENTS.md`
from, so the three sections are also put in the project copy's `.claude/CLAUDE.md` (committed into the starting state, so the run is not
credited with them); the machine's own `~/.claude/CLAUDE.md` still reaches both sides. The check that the post-change run used the change
counts that file as injected. `--before-dyna <bin>` / `--after-dyna <bin>` set the `dyna` each side's session runs with
(`IDEA_LOOP_DYNA_BIN`): a plugin calls the command line it was written against, and a hook of the pre-change plugin that
injects a skill the change deleted only works with the `dyna` of an earlier version; `--after-dyna` is also the one that writes the sections (0.0.9 or newer).

**Guard cases.** A case with `"guard": true` watches that a rule does not reach too far (what the human decides stays with the human): the
old behaviour already answers "yes", so the runner passes it on the post-change "yes" alone.

**Who runs what, and when.** There is no night queue and no scheduled task: replays are run on the spot, by whoever has the
change in hand. The implementer runs a small case itself (`--case`). A large case (it starts a plugin agent, opens a browser or
calls a paid service) is not run by `--case`: the runner exits with code 3, and a small case that turns out to start a plugin
agent or open a browser is stopped and relabelled large in its `case.json` the same way. The implementer only writes and commits
such a case and hands back "大用例待跑：<case>". Once the PR is open, the orchestrator of `idea-loop:implement` tells the human how
many cases, how long (at most 3×45 minutes each) and what it expects to spend (about $1.05–3.50 per case, more when agents are
started), does not wait for a nod, and runs `retro-replay.mjs --cases a,b --run-large --pr <N> --worktree <dir>` in the
background (a foreground Bash call is cut at 10 minutes). The runner runs the cases one after the other in any hour, nothing is
stopped for starting an agent or opening a browser (the session timeout is 45 minutes unless `--timeout-min` says otherwise),
and appends one `replay` entry to the PR's review loop file (`dyna pr loop check` reads it; a case that did not pass leaves it
unsettled). It sends no session message and no notification: the orchestrator waits for the exit, reads the output and the file,
and handles the result as `idea-loop:implement`'s `references/replay-result.md` says: first it reads the two products itself, answers
the case's yes/no question on each, and compares with the judge; a disagreement stops the run and goes to the human (a small
case's implementer does the same and hands a disagreement back as `blocked`). The PR stays a draft until the replays
are handled. Exit codes: 0 all passed, 1 some did not, 2 no `--pr` / no case / a case that is missing or malformed (no session
is started). A runner copy at `~/.idea-loop/bin/` from before this option does not know it: run `dyna retro install` again (that is, `/idea-loop:setup`'s runner step: the installed copy only changes when setup is run again). The runner starts every `claude -p` and `codex exec` through `dyna agent claude run` / `dyna agent codex run` (the `dyna` at `IDEA_LOOP_DYNA_BIN`, else `~/.idea-loop/bin/dyna`, else on PATH), so a machine without the command line cannot run a replay at all; the exercised check asks `dyna runtime name` which runtime the checked session ran in.

`/idea-loop:setup` does the machine-level part once: `dyna retro install` copies the runner to `~/.idea-loop/bin/` (a fixed
path) and prints the permission rule `Bash(node ~/.idea-loop/bin/retro-replay.mjs:*)` for the human to add to
`~/.claude/settings.json` (setup never changes permission settings); on a machine that had the night queue, setup also deletes the
old scheduled task `idea-loop-retro-replay` and the old queue directory.

## Runtimes

idea-loop ships descriptions for two runtimes: the Claude desktop app (`claude-desktop`) and a Claude Code session started by magi (`magi`). The Claude command line and IDE plugins are not separate runtimes: they have no reliable marker, so they land on `claude-desktop`, and the capabilities they lack take the fallback. The capability list and one description per runtime live in `runtime/` (read by `dyna runtime`), plus `<runtime>-<topic>.md` detail files a section points at (the injected data has a size cap; today `claude-desktop-mic.md`). A description starts with one marker line above its first `## ` section: `标记：` followed by the environment variable, in backticks, that only a session of that runtime has (`magi` writes `MAGI_SESSION_ID`), or `标记：没有` when there is none (`claude-desktop`). A file without a marker line (`capabilities.md`, the detail files) is not a description. dyna keeps no list of runtimes: the known ones are the plugin's descriptions with a marker line, plus the ones in `<home>/runtime/` with a marker line that the plugin has no file of the same name for (a runtime of the user's own, a whole description; a home file with the name of a plugin description stays the section-by-section local override). The runtime is found in this order: `IDEA_LOOP_RUNTIME` (a known name; any other value is an error that lists the known names); the first known runtime, by name, whose marker variable has a value (when more than one does, the first is used and `inject reference` starts with a line saying so); the runtime the human picked, one name in the plain-text file `<home>/runtime/selected` (a name that is not known counts as none, with a line at the top of `inject reference`); `claude-desktop`. Adding a runtime means one more description with a marker line, in the plugin or in home, and no change to dyna (`dyna runtime --help` says how).

## Portability

Project rules and verification tools come from the current repository's root files written by
`setup` — DEVELOPMENT.md, REVIEW.md, CODING_STANDARDS.md — plus AGENTS.md / CLAUDE.md and what they link to. No rule is inherited from
any particular project. Plugin paths go through `${CLAUDE_PLUGIN_ROOT}` rather than being hardcoded,
so this plugin should survive being copied to another project or machine as-is. Codex is
reached the same way on every machine: `dyna agent codex run` starts the `codex` command found on `PATH`, with no
path lookup into another plugin's directory and no fallback for it on purpose — setup's preflight checks that
`codex` is there and says so when it is not, and a review that silently points at a nonexistent command is worse than
one that refuses to start.

## The design side

Design used to be its own installable plugin. It isn't any more — every stage of it
consumed or produced an `idea-loop` artifact (a spec, the freeze a ticket
reads, the instrument `implement` runs), so keeping it addressable across a plugin
boundary only bought two version numbers that could drift apart. It now lives here,
with **no alias, no compatibility shim, and no transitional double install**.

**Why the refine models are pinned in the agent definitions.** Once the executor was swapped for a
weaker model and the same baseline went from freezing to three rounds in a row stuck for rounds — splitting
the roles fixed the structure, not the model. The critic (`ui-master`, `fable`) and the executor
(`designer`, `opus`) run on different models so they don't share one blind spot. The definitions use
aliases, so a new model arrives with a Claude Code upgrade; to pin a version for a while, override the
alias mapping with an environment variable (e.g. `ANTHROPIC_DEFAULT_OPUS_MODEL`) instead of editing the
definition.

What came across:

The design critic (`agents/ui-master.md`) is an advisor and has no separate rubric: it judges the gap to what a top
studio would ship, lists the biggest gaps first (each routed by `kind`: direction / pattern / craft, each with a
`reference` sentence), assesses every one of the human's numbered lines of reasoning, and scores 1–10 as a reference.
It asks "what could go" and looks for AI tells on every round. Whether the loop stops is the human's signature, not
the score. `dyna design critic round` only checks the shape (against the canvas's state list and the reasoning ids the
human wrote this round) and points out the direction findings; it prints no stop verdict.

Nothing in `skills/design/uiux-refine/references/design/` is an entry point. They are loaded on demand by whichever
step is running; the hooks are the only pieces that fire on their own. One fires only on a
`Write`/`Edit` whose path lands in a canvas HTML — `docs/design/tmp/<spec-slug>/canvas/*.html`, or the legacy
`design-preview/` / `design-motion-preview/` scratch dirs; the other only on a write to a file named
`DESIGN.md`, where it runs the official `@google/design.md` lint at `@latest` and hands any error
back to the model. There is no pre-merge hook: the design archive is a step of `pr-review`'s merge flow
(`skills/engineering/pr-review/references/merge.md`). The known gap is that clicking merge on the web, or merging from a session
other than the issue session, skips the archive; the weekly `dreaming` backstops it, so merges go through the issue session.

What retired outright, because its content was already relocated: the `design` entry skill,
the port-verification skill
(→ `skills/engineering/implement/references/ui-tickets.md` and the `ui-measure` skill, which generalized it past React), and the
`wireframe-candidates` workflow (its structural-divergence audit moved into `prototype`, which was later removed too).
