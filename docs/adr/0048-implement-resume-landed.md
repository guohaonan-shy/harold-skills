# ADR-0048 — implement：会话断了以后，已做完的工单先落地

> 由 spec `implement-resume-landed` 蒸馏而来，该 spec 已删除。

## 1 背景（why）

编排者（调 `idea-loop:implement` 的会话）派出的执行方，各在自己的 worktree 里做一张工单，做完交回 `landed`，编排者核对后 fast-forward 落地。会话在「执行方已交回、编排者还没落地」这一刻断掉（进程结束、会话压缩），重进来时只剩 `git worktree list` 里那个执行方 worktree，上面已有一个带 `Ticket:` 的完成提交。

当时 `implement` 的「账本」只给一条路：`git worktree list` 里 pending 没记着的执行方 worktree 照「回收」收掉后重派。「回收」第 4 步是 `git worktree remove --force` 再 `git branch -D`，已做完的提交连分支一起删，同一张工单从头再做；「核对与落地」只在「一次处理一个交回」时触发，断会话之后没有一句让编排者先看看这个 worktree 是不是已经做完。同一份文件里「回收」又写着「只在工单落地之后做」，跟这句自相矛盾。

真实例子：harold-skills#125（spec `design-archive-skill-length`）。工单 01 落地成 `4e42c73` 后，工单 02 的执行方在上一个进程结束前交回了 `landed`，它的提交 `6becd9e`（「拍档案截图改写成按情形排步骤的参考，删掉 sections.md」）比集成分支只多这一个。编排者没在那时落地；人问「工单02搞定了吗」时，编排者临场先查了提交再落地，没照规则走。照规则走的话，`6becd9e` 会被删掉、工单 02 重做一遍。

根因是「账本」写会话断了的处理时，把 pending 没记着的执行方 worktree 一律当成半途而废，没区分「已做完、只差落地」；而「已落地」的账只认集成分支上的提交，执行方分支上的完成提交在账上看不见。

## 2 决策（how）

- **断会话重进后，编排者先逐个看 pending 没记着的执行方 worktree：** 分支上有一个带这张工单 `Ticket:` 的提交、比集成分支只多这一个、工单格全勾或带 `⏭ 延后`，就当它交回了 `landed`，照「核对与落地」落地再回收；不是这样的，才照「回收」收掉后重派。然后重算可派的工单。
- **判「已做完」不新增判据**：这三条就是「核对与落地」表里 `landed` 那一行已有的机械核对。落地照那一节走，ff 不了、核对不过的处理也照它（退回执行方；执行方已不在就算没做完，回收重派）。
- **文字照 retro 里人批过的新文，一字不改**（依据是批过的原文）。只改这一句，不加脚本、不改「核对与落地」、不改「回收」；按 `writing-for-agents` 的杠杆，缺的是一个分支，补在「会话断了」这个入口原处，不另开一节。
- **取舍：** 没把执行方分支上的完成提交记进账本（比如让 `ticket-ledger.mjs` 也扫执行方分支），已有的机械核对就能判；没做回放用例：用 #125 工单 02 的现场跑了两次，改前、改后编排者都答「是」（改前它看出这句跟「回收」的「只在落地之后做」打架，自己选了落地），按仓库 `AGENTS.md` 改前就「是」的用例没抓住问题、不算过，人定「I1 选 B，删掉」，验收只靠文档测试。
- **已知限制：** 会话断后补落地的那张工单，执行方交回时报的东西（验证记录、按现有做法定的事、spec 缺口、无关存量、人验清单）随会话一起没了、找不回来；素材文件照常从它的目录拷出。只在会话恰好断在交回之后、落地之前才碰到，比改前整张工单删掉重做好。人定「S2 选 A」。
