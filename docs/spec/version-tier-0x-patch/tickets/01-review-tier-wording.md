# 01 — 版本三档的 minor / patch 改成「0.x 期间改流程行为算 patch」

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

会话给一个改了插件的 PR 定版本档位时读本仓库根目录的 `REVIEW.md`「额外要求」里的三档。现在 minor 写着「改了流程的行为但老用法照样能用」，所以每个改已有流程行为的 PR 都被判 minor，人合并前再改回 patch（8 次）。这张工单把 minor、patch 两条换成 spec「实现决策」里人已定的新文（逐字照抄），之后同一类 PR 照新文判出 patch。major 一条、「三档取最高」、版本号从 main 往上升、漏升测试那几句都不动。不碰任何插件目录，不升版本。

顺带：retro 候选池里这条候选（标题「插件还在 0.x 时，改一个已有流程的行为升 patch…」）的状态改成已落地，注明 minor 用的是本 spec 的新文、不是候选里写的那版。

## 验收标准

- [ ] `REVIEW.md`「额外要求」里 minor 一条与 spec「实现决策」给的 minor 新文逐字一致。
- [ ] `REVIEW.md`「额外要求」里 patch 一条与 spec「实现决策」给的 patch 新文逐字一致。
- [ ] major 一条、「三档取最高」、「定了哪一档写进参考」「版本号从 main 往上升」「漏升测试守着」这几句与改前逐字一致。
- [ ] 对着改后的三档，逐个判 spec「问题陈述」表里 8 次 PR 的改动描述，8 行都判 patch，跟「人定」一列一致；判档结果逐行写进交回。
- [ ] 候选池那条的状态写成已落地，并写明 minor 用的是本 spec 的新文。
- [ ] 全量测试（`REVIEW.md`「验证命令」）全绿，其中漏升版本的测试不因这次红（没碰插件目录）。

## 选中的存量回归

- 漏升版本的测试（`plugin-version.test`）：它按「改了哪个插件目录」判要不要升版本；这次只改仓库根和 `docs/`，它应该照样绿，红了说明改动越界进了插件目录。
