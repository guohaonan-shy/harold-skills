# 设计档案：首屏以下会连出边的组件，要出现在截图里

> #69 存在：一打开就要请求数据的长页面（报告页），加载完那个状态比主视口高，但档案只给它拍一张主视口图；首屏以下的按钮、链接连出去的边，在任何截图里都看不到出发的组件。分段那条路也走不通：它只许入口状态声明，而入口是加载中骨架。详情在「问题陈述」

## 问题陈述

### 首屏以下的组件连出边，截图里却看不到它

先说清几个叫法（都在 `idea-loop:design-archive`）：

- **状态**：页面上的一屏，比如「加载中」「加载完」「某段展开」，是档案图里的节点。
- **边**：从一个状态到另一个状态的一次触发。`user` 边是用户在某个组件上的一次操作，写了组件（`component`）和用可访问性树定位它的方式（`locate`）。
- **截图**：每个状态在 `assets/` 里有图，审设计、对账（拿实现拍的图跟档案比）都对着图看。不分段的状态只拍一张主视口大小的图，用 `screen` 命令拍，叫 `<状态 id>.png`。
- **分段（`sections`）**：营销页那种长页面的入口状态从上到下切成几段（hero、faq、footer……），每段一张图。分段页上每个可点元素都要归进某一段，所以分段页的组件都在图里。

对着 origin/main `a7c8129`（2026-11-12）查到两条相关规则：

- 「入口是加载中」（`references/writing.md`「建模的取舍」）：页面一打开就发请求的，入口状态是加载中那一屏；加载完是另一个状态，从入口经一条 `system` 边过去。
- 「`sections` 只写在入口状态」（`SKILL.md`「分段」，校验 `design-archive-check.mjs` 规则 7）。

所以报告页的加载完是一个不分段的状态，只有一张主视口图。可它比主视口高得多。Toeflair 2026-10-21 全站初扫的实测（issue 正文）是：写作报告约 3500px，面试报告约 4770px，听后复述报告约 2200px。这三页都只拍到首屏。首屏以下的按钮、链接照样连出边（比如写作报告详评里的「查看范文」、页脚链接），可这些边的组件在哪、长什么样，任何一张图里都没有，只能靠文字描述。这三页不在本仓库，没法在这里核对，数字取自 issue。

本次复现（2026-11-12，对着 `a7c8129`）：把测试夹具里的长营销页 `mkt-pricing` 改成报告页的样子，入口改成加载中骨架，再用一条 `system` 边连到 `mkt-pricing--loaded`。想照现有规则让 `mkt-pricing--loaded` 的组件进图，只有分段这一条路，结果走不通：

- 校验退出码 1，规则 7 报了 9 条违规：`mkt-pricing--loaded` 不是入口，不能写 `sections`，挂在这些段上的 `from`、`section` 也全部失效。
- `measure <仓库根> mkt-pricing--loaded` 退出码 2，提示「不是入口状态：只有入口状态声明 sections」。
- 不分段的话，拍图手册（`references/shooting.md`「单屏状态」）只给 `screen`，拍出来就是一张主视口图。

应该是：首屏以下每一个会连出边的组件，都出现在出发状态的某张截图里，看图就能找到这条边从哪出发。

复现材料：`.tmp/to-spec/design-archive-loaded-sections/repro/`（`repro.mjs`、`check.txt`、`measure.txt`，不提交）。分拣评论：https://github.com/guohaonan-shy/harold-skills/issues/69 （「🤖 idea-loop：」那条）。

### 根因

截图的规则只按页面高度分两种：不比主视口高的拍一张，比主视口高的分段。分段又跟入口状态绑在一起。不是入口、又比主视口高的状态没被想到，实际上落进了「拍一张主视口图」。档案也没有一条规则说「边的组件要在图里」，所以哪条边的组件没拍到，校验和对账都发现不了。

修正：issue 原先想让加载完的状态也能声明分段。人在 2026-11-13 改了方向：分段适合营销页的结构组织，这里真正要守的是会连出边的组件要进截图（原话见「实现决策」）。

## 方案

改完后：一个不分段的状态比主视口高时，除了主视口图，首屏以下每个会连出边的组件都在一张补拍图里。几个组件能同时装进一屏的，共用一张图。每条这样的边写明它的组件在哪张图里，看边就能找到图，校验能查出写错的引用。营销页的分段一点不动。

拿写作报告走一遍。加载完照旧有主视口图 `writing-report--loaded.png`。首屏以下有三处会连出边：详评里的「查看范文」、第二屏的「再练一次」、页脚 6 个链接。新命令定位这 8 个组件，按位置从上往下合成几屏，比如「查看范文」和「再练一次」一屏，页脚一屏，拍成两张：`writing-report--loaded@see-sample.png` 和 `writing-report--loaded@footer-home.png`，用每屏第一条边的 id 命名。这 8 条边各写 `shot:` 指向自己所在的那张。

**哪些状态要补拍**：不声明 `sections`、所在页面比主视口高、并且有 `user` 边的组件落在主视口以外的状态。到底有没有组件落在外面，只有在浏览器里量了才知道，所以由新命令判断；校验只核对写出来的 `shot` 对不对。

**新命令 `cover`**（放在 `design-archive-sections.mjs`，跟 `screen`、`shoot` 同一个文件）：

```
node design-archive-sections.mjs cover <仓库根> <状态 id> --out <目录> [设置]
```

它打印一段浏览器代码，agent 在状态已经走到的那一屏上跑。这段代码：

1. 不重载页面，不拨页面时间（跟 `screen` 一样，加载完、点出来的状态都不会丢）；
2. 读档案里这个状态的每条 `user` 边，用 `locate` 定位组件，量出它在滚动容器里的位置；定位不到或不唯一的，列进 `unlocated`；
3. 落在主视口里的不管；其余从上往下合成几屏：每屏从这一组第一个组件的上沿往上留一点余量开始，高度等于主视口高度，装得下的都归进这一屏，装不下的另起一屏；
4. 每屏滚到位，用 `shoot` 现有的那套方法拍（等内容出齐、两次截图比较、`uncontrolled` 标记），图叫 `<状态 id>@<这一屏第一条边的 id>.png`；
5. 返回每条边该写的 `shot`，加上 `unlocated` 和每张图的 `uncontrolled`；有 `unlocated` 时退出码 1。

**档案里的写法**：`user` 边可写 `shot: <状态 id>@<边 id>.png`，意思是这条边的组件在这张补拍图里。没写 `shot` 的边，组件就在主视口图里。

**校验新加规则 8「边的截图」**：

| 情形 | 判定 |
|---|---|
| `shot` 写法不是 `<出发状态 id>@<边 id>.png` | 违规 |
| `shot` 里的边 id 不是出发状态的某条边 | 违规 |
| 写 `shot` 的状态声明了 `sections` | 违规（分段页用 `from` 挂在段上） |
| `system` 边写了 `shot` | 违规（它不经过组件） |
| 几条边指向同一张图 | 允许（按屏合并） |

图文件在不在，校验照旧不管，跟分段图一样由查询的 `screenshotExists` 报。

**拍图手册与对账**：

- `references/shooting.md` 的「情形怎么选」加一种情形：「比主视口高、不分段的状态」，步骤是先 `screen` 拍主视口，再 `cover` 补拍，按返回给每条边写 `shot`。原先的「单屏状态」说明里补一句，不知道页面高不高时，跑一次 `cover`，返回空就是单屏状态。
- `references/review-reconcile.md`（dreaming 对账）和 `references/review-archive.md`（合并前归档）里拍单屏状态的地方，跟着加 `cover`。补拍图逐张跟 `prod/` 里同名的图比，比法和分段图一样；`cover` 合出来的屏跟 `prod/` 里的分组不一样（内容变了），算「档案过期」，按新的分组重写 `shot`。
- dreaming 初扫（`dreaming` 的 `references/initial-scan.md` 第 7 步）同样加这一步。

**查询**：`state` / `page` 里每条边多带 `shot` 和 `shotExists`。

同一行为的其他入口：

- 分段页（营销页）：排除。每个可点元素已经归进某一段、每段有图，规则 7 已经覆盖。
- 段内交互的状态、滚动驱动的段：排除，它们本来就只拍那一段或那一屏。
- 单屏状态（不比主视口高）：纳入，但没有变化，`cover` 返回空，不多拍。
- `measure` / `attribute` / `shoot`：不改；`cover` 复用 `shoot` 的拍法代码。
- 规则 7 和「`sections` 只写在入口状态」：不改（issue 原先的提议，已撤回）。
- 查询的 `diff`：边的字段逐个比，`shot` 跟其它字段一样会进 `edges[<id>].shot`，不另改。

## User Stories

1. 期望行为：一个不分段、比主视口高的状态（加载完的报告页），首屏以下每条 `user` 边的组件，都在主视口图或某张补拍图里。补拍图按屏合并，每条边的 `shot` 指向它所在的那张，校验能核对 `shot` 的写法和归属。营销页的分段、单屏状态的截图跟现在一样。

## 实现决策

- **方向**：组件进截图，不放开分段。依据是人 2026-11-13 的原话：「我觉的不是分段，分段比较适合marketing部分的结构组织，而这个issue和候选2的核心是，如果有交互导致我们的设计内容需要出边，我觉的截图就是想要包含可交互组件的部分。」以及选题时回的「B 改成组件进截图」。
- **按屏合并，不一条边一张图**：依据是人 2026-11-13 选了「按屏合并」，理由是图少、页脚那种成排链接不会拍出一堆重复图。代价已经说给人：内容变了，分组会跟着变，对账时要重写 `shot`。
- **补拍图的命名**：`<状态 id>@<这一屏第一条边的 id>.png`。用边 id 而不是屏的序号，是因为内容往上加一屏的时候，序号会整体错位，边 id 不会。依据是分段图 `<状态 id>@<段 id>.png` 已经在用这个形状。
- **余量**：每屏起点在第一个组件上沿往上 1/4 主视口高度（主视口 900 就是 225px），让组件上面的上下文也进图；页面底部不够一屏时，起点往上收，让图仍是整屏高。这是按「图跟主视口同尺寸才好逐张比」定的。
- **「在主视口里」怎么判**：组件的盒子整个落在首屏真正露出来的范围里才算：下界取主视口高、内容滚动区的可见下沿、贴在底部的栏（固定在屏幕上、粘在滚动区底部、或叠在内容区上）的上沿三者中最小的。只露出一半、或被底部的栏盖住的，也要补拍。顶部不查：压在贴顶固定栏下、又在页面最顶上的组件，用户在任何滚动位置都看不到、点不到，不会有边从它连出（review 第 2 轮记成已知限制）。（起草时写的是「整个落在页面顶部、主视口高度以内」；review 第 1 轮 S1 查到页面底部有固定栏、或内容区不到屏幕底时，紧贴首屏下沿的组件按这条会被跳过，人 2026-11-13 定「S1 选 A」，改成现在的写法。）
- **`cover` 不重载、不拨时间**：依据是 `screen` / `pinned` 已经这样做，加载完、点出来的状态一重载就丢。页面时间要事先用 `time` 装好，没装的照 `screen` 现有的说法报出来。
- **改的都是现有文件**：新命令放在现有的 `design-archive-sections.mjs`，校验放在现有的 `design-archive-check.mjs`，不新做组件。
- **规则 8 不查图文件在不在**：依据是现在校验对分段图也不查（图可能是 LFS 指针），在不在由查询报。

## 测试决策

| 变的是什么 | 仪器 | 本次 |
|---|---|---|
| 纯逻辑、数据转换、状态机 | TDD 单元测试 | 规则 8 的判定；`cover` 的分屏算法（给一组组件位置和主视口高，算出几屏、每屏起点、每条边归哪张）写成纯函数测；查询多出的 `shot` / `shotExists`。先在现状上红 |
| API 契约（路由、schema、序列化） | TDD API 测试 | 不涉及 |
| DB schema、迁移、并发与事务语义 | 真 DB 测试 | 不涉及 |
| LLM 输出质量（prompt 改动） | eval（确定性断言） | 改了给 agent 读的拍图、对账、初扫说明，加了一种情形和一步命令；验收用文档测试（「情形怎么选」里有这种情形、各处拍单屏的地方都提了 `cover`），不加回放用例 |
| 视觉正确性 | UI 实现环 | 不涉及 |
| 端到端用户流程 | 浏览器端到端测试 | `cover` 打印的浏览器代码：在 `design-archive-sections-browser.test.mjs` 里加一个比主视口高的测试页，有首屏外的按钮和一排页脚链接，断言拍出几张图、每条边的 `shot`。这个文件在 darwin 本机跑全量套件时会卡住（#192），单独跑它 |

- **seam**：
  - `design-archive-check.mjs`：喂档案目录，读违规列表。能抓到 `shot` 写错、写在分段页或 `system` 边上；抓不到组件实际在不在图里。
  - `cover` 的分屏纯函数：喂位置，读分组。能抓到合并、余量、贴底这些算错；抓不到浏览器里的定位。
  - 浏览器测试：喂测试页，读图和 `shot`。能抓到定位和拍图的真实行为；抓不到真实产品页的复杂布局。
- **增量功能测试**：
  - 前置：夹具里一个不分段的状态，三条 `user` 边写了 `shot`，其中两条共用一张图。步骤：跑校验。期望：没有违规。覆盖：期望行为 1。
  - 同一夹具，`shot` 写成别的状态的 id、写在 `system` 边上、写在声明了 `sections` 的状态上，各一个用例。期望：各一条规则 8 违规，点名文件和 `edges[n].shot`。
  - 分屏函数：主视口 900，组件上沿在 1200、1500、3300、3350。期望：两屏，`[1200, 1500]` 一屏，起点 975；`[3300, 3350]` 一屏。页面总高 3500 时，第二屏起点收到 2600。
  - 浏览器：测试页高 3000，首屏外有一个按钮和 4 个页脚链接。期望：`cover` 拍两张图，5 条边的 `shot` 指向对应的图；首屏内的组件不进 `shot`。
  - 现有夹具 `compliantFiles()`、`marketingFiles()`：校验结果跟改前一样。
- **照着谁写**：`idea-loop/scripts/design-archive-check.test.mjs`（规则 7 那组的 `BREAKS` 表）；`design-archive-sections.test.mjs` 里 `screenTargets` 的纯函数用例；`design-archive-sections-browser.test.mjs` 里 `screen` 的浏览器用例；文档测试照 `design-archive-sections-doc.test.mjs`。

## Out of scope

- 让加载完的状态声明分段：issue 原先的提议，人 2026-11-13 撤回了，分段留给营销页的结构组织。
- 没有连出边的组件（纯展示的段落、图表）补拍：人的规则只针对「交互导致出边」的组件。已知限制：首屏以下纯展示的内容仍只能用文字写，没有真实例子说明需要它进图。
- 校验检查图文件在不在：现在对所有截图都不查，由查询报。
