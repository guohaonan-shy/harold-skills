# 01 — 边能写 `shot`，校验规则 8 守住它，查询带出它

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

设计档案（`idea-loop:design-archive`）里，一个状态的 `user` 边可以多写一个字段 `shot: <出发状态 id>@<边 id>.png`，意思是「这条边的组件不在主视口图里，在这张补拍图里」。没写 `shot` 的边，组件就在主视口图 `<状态 id>.png` 里。补拍图按屏合并：几条边可以指向同一张图，图用那一屏第一条边的 id 命名。

这张工单让这个字段在三处生效：

1. **读档案**：读档案的脚本把边的 `shot` 读进来，跟 `component`、`locate` 等字段并列。
2. **校验新加规则 8「边的截图」**（跟现有规则 1–7 同一个校验脚本、同一种违规格式：文件 + `edges[<序号>].shot` + 一句提示）：

   | 情形 | 判定 |
   |---|---|
   | `shot` 写法不是 `<出发状态 id>@<边 id>.png` | 违规 |
   | `shot` 里的边 id 不是出发状态的某条边 | 违规 |
   | 写 `shot` 的状态声明了 `sections` | 违规（分段页的边用 `from` 挂在段上） |
   | `system` 边写了 `shot` | 违规（它不经过组件） |
   | 几条边指向同一张图 | 允许 |

   图文件在不在，规则 8 不查（跟分段图一样，图可能是 LFS 指针，由查询报）。
3. **查询**：查询脚本 `state` / `page` 返回的每条边，多带 `shot`（原样）和 `shotExists`（那张图在出发状态所在对象的 `assets/` 里存不存在；没写 `shot` 的边不带这两个字段）。`diff` 不另改，`shot` 跟其它边字段一样逐个比。

同时更新给 agent 读的文档：
- `design-archive` 的校验说明（check 参考文件）加规则 8 的逐条违规与提示，写法照规则 7 那一节；
- 档案写法说明（writing 参考文件）里边的字段表加 `shot`：什么时候写、写成什么样、没写的意思；
- 查询说明（query 参考文件）里边的返回字段加 `shot`、`shotExists`。
- SKILL.md 里规则编号如有「1–7」之类的总数，跟着改。

## 验收标准

- [ ] 测试先在现状上红：夹具里一个不分段的状态，三条 `user` 边写了 `shot`，其中两条共用一张图；跑校验没有违规（改前：校验不认识 `shot` 或这条用例不存在而红）。
- [ ] 同一夹具上各一个违规用例，各报一条规则 8，点名文件和 `edges[n].shot`：`shot` 写成别的状态的 id；`shot` 里的边 id 不是这个状态的边；写在 `system` 边上；写在声明了 `sections` 的状态上。用例写法照校验测试里规则 7 那组的 `BREAKS` 表。
- [ ] 现有夹具 `compliantFiles()`、`marketingFiles()` 的校验结果跟改前一样。
- [ ] 查询 `state` 一个写了 `shot` 的状态：每条写了 `shot` 的边带 `shot` 和 `shotExists`（图在时 true、不在时 false），没写的边两个字段都没有。
- [ ] 校验说明、写法说明、查询说明三处都写了 `shot` / 规则 8，文档里出现的规则编号跟脚本一致。
- [ ] `idea-loop/scripts` 下设计档案相关的测试全部通过（sections 的浏览器测试除外，它不在这张的范围）。

## 选中的存量回归

- 设计档案校验测试（`design-archive-check.test.mjs`）：规则 7 与边的字段校验在同一个脚本里，加规则 8 可能误伤分段页的边。
- 设计档案查询测试（`design-archive-query.test.mjs`）：边的视图多了字段，`page` / `state` / `diff` 的期望输出可能跟着变。
- 设计档案 MCP 测试（`design-archive-mcp.test.mjs`）：MCP 工具直接转发查询结果。
- 防项目信息泄漏测试（`no-project-leak.test.mjs`）：新写的文档和夹具不能出现真实项目名。
