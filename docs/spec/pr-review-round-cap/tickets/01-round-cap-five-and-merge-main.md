# 01 — pr-review 自动起到第 5 轮，每轮开审前先合入最新主分支

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

编排者在一个 PR 上跑 review 时：

- 一轮有修复，修复落地、CI 绿后自动起下一轮，直到某一轮没有要修的（交审核报告）或有要人定的事（停下）。自动起的上限是第 5 轮：第 5 轮的修复落地后停下，在会话里说「已跑满 5 轮，第 5 轮的修复还没审，要再跑或合并请直接说」。人说「再跑一轮」或手动调 pr-review 不受这个上限约束，但计入轮次。
- 上限只写在 pr-review 的「一轮之后往哪走」一处。审查者（pr-reviewer）的定义和 review 汇报模板里那句「已跑满两轮，要再跑或合并请直接说」删掉：审查者不知道这一轮之后停不停，停下时那句话由编排者说。
- 每一轮开审前（pr-review 的「前提」里，排在等 CI 那条之前），编排者先 `git fetch`，把最新主分支 merge 进每个 PR 分支（不 rebase）；有冲突就解决，由脚本生成的文件（如 spec 索引）重新生成、不手拼；推送后再往下等 CI。已经是最新的就什么都不做。冲突落在编排者判断不了该保留哪边的地方，照 decision-rules 停下问人（已有规则，指过去即可）。
- 人说合并时，合并参考的第 1 步引用「前提」里的这一条，再合入一次最新主分支（报告交出后主分支可能又前进了）。
- 其余提到「两轮」上限的句子同步改：「什么时候跑」的「不受两轮上限约束」改成「不受自动轮数上限约束」；设计变更参考末尾「第 2 轮之后人要核就说『再跑一轮』」删掉；合并参考里「跑满两轮停下后」改成「跑满 5 轮停下后」；SEO 自动合并参考里「现有的『最多两轮』不变」改成跟上限 5 一致的说法。
