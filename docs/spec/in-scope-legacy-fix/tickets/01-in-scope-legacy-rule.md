# 01 — 存量问题按「影响本次改动」判：执行方修、编排者复核、review 照报

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

idea-loop 的实现流程里，判一个存量问题「这次修还是另开 issue」的三道关（工单执行方、实现编排者、PR review）用同一条判据：**影响本次改动**＝污染了这张的输入或结论、让 CI 变红，或它描述、引用的正是这次改的东西（例：这次给配置加了一节，别处写死的节数跟着错）。

- 执行方：影响本次改动的，在这张工单里修，`found` 标「存量本次修」并写清它怎么影响本次改动；不影响的不修，记进 `found`。处置表那一行和交回格式里 `found` 的注释照这条改。新文以 issue #428 正文给的为准：「| **存量问题** | 影响到本次改动的，这次修，标「存量本次修」，理由写清它怎么影响本次改动：污染了这张的输入或结论、让 CI 变红，或它描述、引用的正是这次改的东西（例：这次给配置加了一节，别处写死的节数跟着错）。不影响本次改动的，不修，记进 `found`，由编排者单独开 issue |」
- 编排者（implement）：分拣表的「其余 `found`（跟这次无关的存量）」改成「不影响本次改动的存量」；落地参考那一节改名并加复核：「**不影响本次改动的存量问题自动开 issue**（它不在这份 spec 的问题之内，`idea-loop:decision-rules` 的「核心」）。开之前核一遍理由：写着它描述或引用的正是这次改的东西的，就是影响本次改动，退回同一个执行方在这张工单里修。」implement 正文其余说「无关存量」的地方、停下与续上参考里指向这一节名的指针一并对齐（那里说 CI 失败「跟这次无关」的不动）。
- review（pr-review 的 review 规范）：改动行以外的存量问题要报的例外从两种（污染输入或结论、让 CI 变红）加第三种「它描述、引用的正是这次改的东西」，同一说法；review 校验脚本给 `pollutes` 缺失时的提示语同步加上第三种。
- 说同一件事的其余地方措辞对齐：pr 的审核报告写法里「本次修的存量问题（依据写它怎么污染了这张工单）」改成依据写它怎么影响本次改动、「顺手发现的无关存量问题」改成不影响本次改动的；issues 的「开一个 issue」里「跟这次无关的存量问题」同样改。
- 加一个 retro 回放用例 `implementer-in-scope-legacy`：仓库状态 `2a2f06be`，起执行方做 split-blog-publisher 工单 02（只给指针，照 `implementer-reads-standards` 用例的写法），停在执行方交回；是/否题：「执行方是把其余 seo skill 写『读出八节』当成影响本次改动的存量，在本工单里改了，而不是记成『工单范围以外，没改』吗？」原话取 issue #428 里人的 retro 原话。大小：大。
- idea-loop 插件版本升 patch。

> 人的决定（2026-11-23，夜间模式按推荐定）：规则回放第 1 次没过。改后的执行方读到了新判据，仍把六个 seo skill 的「读出八节」判成不影响，原话「数字只出现在说明文字里，不影响这些 skill 的行为，也不是这次要改的东西，所以没动」：它把「这次改的东西」读成这张工单要改的文件。把第三种情况改锐利，以事实为准、不以文件为准：它写着的事实（数量、名字、路径、结构）正是这次改掉的，这次一改它就过期——哪怕它只是说明文字、在工单没点名的文件里，也算影响本次改动。执行方、编排者复核、review 三处同一说法；回放用例不改，再跑一次。
