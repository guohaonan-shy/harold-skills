# decision-rules：范围题按「影不影响这次交付」推荐

> #313 存在：`idea-loop:decision-rules` 没规定范围题推荐哪一项，会话按「PR 小」推荐拆开，决定记录里同类 6 次人都选了并进当前 PR，详情在「问题陈述」

## 问题陈述

### 范围题推荐拆开，人反复选并进

范围题是会话中途冒出一处改动时摆给人的那道题：并进当前 PR，还是另开。`idea-loop:decision-rules` 的「要人定的写成一道题」只要求「给推荐和一句理由」，没说推荐哪边，会话就按「PR 小、好 review」推荐拆开。

真实例子：#174 的会话里讨论回放怎么验证（参考 poteto 的 eval playbook），冒出四条改进（回放输入不露题、Codex 当评委、核对改后那一遍用上了改动、编排者自己读产物）。题 5 推荐「A：#174 只做取消夜间队列，四条另开 issue」，人选了「B：全部并进 #174」。这四条里的第一条正是 #157 的用例改前改后都答「是」的原因，不改它，#174 交付的回放照样会出同样的错。

同一类选择在决定记录里出现 6 次，人都选了并进当前 PR，没有反例（2026-11-14 对着 origin/main `816d6f2` 逐份读 `docs/raw/decisions/`）：

| 决定记录 | 摆给人的推荐 | 人选的 |
|---|---|---|
| `174.md` 题 5 | 另开 issue | 并进 |
| `55.md`（增量对账） | A 开新 issue | 「增量对账并进这个 PR。」 |
| `149.md` 题 5 | B 另开 issue | 「03 我同意B，但我建议在这个PR里面修复」 |
| `125.md` 题 2 | 并进 | 并进 |
| `266.md` 题 4 | 开成新 issue（todo P2） | 「在这个pr里面一起解决吧」 |
| `180.md` 题 2 | 并进 | 并进并扩大 |

推荐被推翻的有 4 次（#174、#55、#149、#266），都是推荐拆开；推荐并进的 2 次人都照推荐选了。

人在 #174 的 retro 里给出的判据（原话，`docs/raw/decisions/174.md` 候选 1）：「影响这个spec实现的问题在这个pr里修复，上线会有影响的重要问题在pr里修，其余的按照我们的流程进入候选」。

### 根因

`decision-rules` 定了「自己定还是问人」，没定问人时推荐哪一项；会话只能靠「PR 越小越好」这个默认推，跟人看重的「这次交付能不能用」相反。

## 方案

改完：会话摆范围题时，冒出的问题影响这份 spec 的实现、或上线后会有影响的，推荐并进当前 PR；其余的推荐不进，交回调用方自己的流程（issue 会话里是开成 issue）。仍是一道题，由人选。

改动只有一处：在 `idea-loop:decision-rules` 的「要人定的写成一道题」里，「给推荐和一句理由」之后加一条：

> 范围题（冒出的改动并进当前 PR，还是另开）：冒出的问题影响这份 spec 的实现，或者上线后会有影响，推荐在当前 PR 里修；其余的推荐不进当前 PR，交回调用方自己的流程。

对的杠杆（`idea-loop:writing-for-agents`）：这是一条「问人时怎么推荐」的默认值，放在每个停下问人的会话都会读的那一节；`decision-rules` 被 to-spec、implement、pr-review、issue-session 的停下问人处引用，加在这里各处同时生效。

同一行为的其他入口：

- `idea-loop:retro` 摆候选时的推荐：排除。那是「规则候选去哪」，由 #314 管，不是 PR 范围。
- `idea-loop:issue-session` 的「边界」（路上发现的别的问题开出去）：排除，不改。它说的是 spec 之外的问题，跟新文的「其余的」同一个去处，不冲突。

## User Stories

1. 期望行为：会话摆范围题时，影响这份 spec 实现或上线后会有影响的改动，推荐并进当前 PR；其余的推荐不进当前 PR，交回调用方自己的流程。

## 实现决策

- 文字取 issue「新文」，一处改动：issue 写的去处是「照流程进候选池」，改成「交回调用方自己的流程」。依据：人的原话是「按照我们的流程进入候选」，没说候选池；`decision-rules` 的「核心」已有原文「spec 之外的事不在这次做，交回调用方自己的流程」，候选池在 `idea-loop:retro` 里专指规则候选，问题本身的去处是 issue（`idea-loop:issue-session`「边界」）。照已有原文写，不新造一个去处。
- 放在「要人定的写成一道题」一节，不放「核心」：它改的是推荐，不改「范围题要问人」这件事。
- 回放用例 `decision-rules-scope-recommend`：提交 `314a633`（#174 讨论时仓库的样子），输入是 #174 讨论里人的原话加当时的上下文，停在摆出范围题的那一刻。是/否题跟 issue 原文差一处：issue 的问法「被推荐并进当前 PR 的，是不是只有…」在改前一条都不推荐并进时也答「是」，用例抓不住问题（`AGENTS.md`「改前就是的不算过」），所以改成要求影响交付的那条确实被推荐并进。
- 升 idea-loop 的 `version` 一档 minor：改了流程的行为（问人时的推荐方向），老用法照样能用（`REVIEW.md`「额外要求」）。

## 测试决策

| 变的是什么 | 仪器 | 本次 |
|---|---|---|
| 纯逻辑、数据转换、状态机 | TDD 单元测试 | 不涉及 |
| API 契约（路由、schema、序列化） | TDD API 测试 | 不涉及 |
| DB schema、迁移、并发与事务语义 | 真 DB 测试 | 不涉及 |
| LLM 输出质量（prompt 改动） | eval（确定性断言） | 改了 `decision-rules` 的一句规则；验收用回放用例（`idea-loop/evals/retro/`），用例格式由 `retro-case.test.mjs` 校验 |
| 视觉正确性 | UI 实现环 | 不涉及 |
| 端到端用户流程 | 浏览器端到端测试 | 不涉及 |

- **seam**：回放 runner `retro-replay.mjs --case decision-rules-scope-recommend`。能抓到：同一输入下，改前推荐拆开、改后推荐并进；漏掉：别的场景下「影不影响交付」判得对不对。
- **增量功能测试**：前置：分支上的插件和用例。步骤：跑上面的 runner。期望：改前「否」、改后「是」，且改后那一遍读过 `decision-rules`。覆盖：期望行为 1。
- **照着谁写**：`idea-loop/evals/retro/cases/retro-pool-choice`（同样从决定记录里人的原话拼输入）。

## Out of scope

- 「影响 spec 实现」「上线后会有影响」怎么判的细则：先用人的原话，判得不对再从 retro 里收。
