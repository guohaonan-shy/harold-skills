# 调度只数 issue 会话；retro issue 按 plugin 做 retro 整合，一个会话自动做到 PR

> 后来改了（2026-10-26，PR #113 合并当天）：retro 整合部分（`retro` 标签、凑整合的命令、整合卡片、retro-merge skill、retro 第 5 步打标记）已撤回，只保留 #106「调度只数 issue 会话」。原因：人认为 retro 批的候选应先进 `docs/` 的候选池、由 dreaming 判断能不能进 skill，进候选池还是直接开 issue 由人在 retro 里定（#115）。下文是当时的决定，保留作由来。


## 验证

| issue | 结论 | 证据 |
|---|---|---|
| #106 | 存在 | 2026-10-26 按 `issue-dispatch` 现在的第 3 步数了一遍三个 section：数出 10，满额；只数 issue 会话是 5。多出来的 5 个是 Tofelair#407 的 issue 会话开出的 imagine 子会话（详见「问题」1） |
| #108 | 存在 | retro 批了的候选开成普通待验证 issue，跟别的 issue 排同一个主队列；眼下开着 15 个这样的 issue，没有任何标记能把它们和普通 issue 分开（详见「问题」2、3） |

## 问题

### 1. 主队列被 issue 会话开出的子会话占满，十多小时出不了卡片（#106）

**复现到的**（2026-10-26，对 `origin/main` 9d8420a 的 `issue-dispatch`，用 `list_sessions` 按 section 名列没归档的会话）：

| section | 没归档的会话 | 其中标题是「<仓库名>#<号> …」的 |
|---|---|---|
| 审核中 | 3（harold-skills#68、#65、#108） | 3 |
| 设计中 | 6 | 1（Tofelair#407） |
| 实现中 | 1（Tofelair#408） | 1 |
| 合计 | **10** | **5** |

「设计中」另外 5 个是「L&R 介绍页 imagine：首屏 / 三步段 / 题库多场景 / 权威的分数 / 详尽的归因」，`startedBy` 都是 Tofelair#407 的 issue 会话。现在第 3 步把 section 里没归档的会话全加起来，主队列算成 10/10，空位 0；按 #106 的说法，从 10/25 起一张卡片都没出。只数 issue 会话，空位是 5。

另外核到：section 自带的 `session_count`（12 / 7 / 8）含已归档的，第 3 步已经写明不用它，这一点没问题。

### 2. retro 开的 issue 跟正常需求抢同一个上限 10 的队列（#108）

**复现到的**（2026-10-26，`gh issue list --state open`）：harold-skills 开着的 issue 里，正文写明「来自 … 的 retro，人已批」或「人在 … 的 retro 里批的」的有 15 个：#80、#82、#83、#84、#86、#92、#94、#95、#96、#97、#98、#100、#102、#103、#109。15 个全落在 idea-loop 这一个 plugin。

- 它们都没有 `type:*`、没有 `status:*`，在 `issues candidates` 里跟普通 issue 一起按时间排。主队列上限 10、一轮最多出 3 张卡片，照现在的流程它们要一个一个开会话、验证、起草 spec、grill、实现。
- 这些内容人在 retro 里已经批过一遍（retro 第 4 步逐条摆给人、人回「批」才开）。再开会话 grill，是第二次问同一件事。
- 一个 issue 一个 PR，执行方最省事的改法是往 SKILL.md 末尾加一句；15 条下来 skill 会越来越长、越来越针对案例，跟本仓库「description 只做路由、正文只写步骤」（`AGENTS.md` 的 SKILL.md 编写约定 §1，`writing-for-agents`）相反。

### 3. retro 开的 issue 没有任何机器能认的标记

**复现到的**：retro 第 5 步只写「照『开一个待验证的 issue』开（查重、不打 `status:*`）」，不打分类、不打别的 label。上面 15 个是读正文认出来的，正文的形状并不统一：

- 有的带「旧文 / 新文」（#82、#94…），有的没有（#84 只写「落点」与要加的句子）。
- 同样带「候选」字样、讲 retro 的 #87，其实是 `session-digest locate` 的 bug，不是 retro 开的；#99 是会话里发现的 bug，形状也像。
- retro 开的里面也不全是「改一句规则」：#80 正文自己写了「这是插件结构的改动，走正常的审核与实现」；#86 标题带「（待讨论）」，是方向不是规则。

所以「不进队列」要先有一个机器能认的标记，存量的 15 个还得有人认一遍哪些算。

### 根因

1. 问题 1：第 3 步以「在这个 section 里」当「占一个位」，而 issue 会话把自己开出的子会话也留在同一个 section（`start_session` 开的会话嵌在开它的会话下面，sidebar 分组跟着走）。
2. 问题 2、3：retro 的产出只有「开一个待验证的 issue」这一条路，而待验证 issue 只有「一个 issue 一个会话」这一种走法。

## 方案

**人最后得到的**：

- 调度的汇报里，每个队列的「开着的会话」只数 issue 会话；子会话开多少都不占位（#106）。
- retro 批了的规则候选不再一个 issue 一张卡片。调度每天给每个仓库最多出一张「retro 整合」卡片，一次 retro 整合是同一个 plugin 最早的至多 5 个 retro issue。人点开后，整合会话把这几个 issue 合成一份 spec，切工单、实现、开 PR、跑 review 和 skill 测试，全程不停下等人；人第二天在整合会话里看改动、决定合不合（#108）。
- 现在积压的 13 个 retro issue，三次 retro 整合消化完。

**由什么决定**：issue 带不带 `retro` 标记；同一个仓库有没有开着的整合会话；落点 skill 的现有内容（整合并进去，不往后 append）。

**同类入口**（数会话、出卡片、对账都碰「哪些 issue / 会话算数」）：

| 入口 | 纳入 / 排除 |
|---|---|
| `issue-dispatch` 第 3 步「数开着的会话」 | 纳入：只数 issue 会话（#106）；整合会话的标题不是这个格式，不占位 |
| `issue-dispatch` 第 4 步「没有会话的 issue」 | 纳入：标题里列着这个号的整合会话也算有会话 |
| `issue-dispatch` 第 5 步「出卡片」与 `issues candidates` | 纳入：retro issue 不进候选，另出整合卡片 |
| `retro` 第 5 步「开成 issue」 | 纳入：开的时候打上 `retro` 和 plugin 分类，正文写上回放用例要的材料 |
| `issue-session` 的各段 | 纳入：整合会话复用它调的那些 skill（`to-spec`、`to-ticket`、`implement`、`pr-review`），只是不停下等人 |
| `issues queues` 的独立队列（「（独立队列，上限 N）」） | 排除：独立队列仍然一个 issue 一个会话、仍然有上限；#108 要的是按 retro 整合处理，不复用它 |
| 目标仓库里 retro 开出的项目级 issue（开到 Tofelair 等目标仓库的） | 纳入同一套标记和整合卡片；「plugin」换成落点所在的仓库 |

## User Stories

### 场景：调度数空位

1. 作为看调度汇报的人，我想要「开着的会话」只数 issue 会话，以便一个 issue 开再多子会话也只占一个位
2. 作为看调度汇报的人，我想要别的仓库的 issue 会话照样算进共用的 section，以便跨项目共用上限照旧成立

### 场景：retro 开 issue

1. 作为在 retro 里批候选的人，我想要批了的候选开出来就带 `retro` 和 plugin 分类，以便它不占队列、能按 plugin 凑成一次 retro 整合
2. 作为在 retro 里批候选的人，我想要开出的 issue 正文里写好回放用例要的材料（当时的提交、触发 skill 的那句话、停在哪），以便整合会话能写出回放用例

### 场景：调度出整合卡片

1. 作为人，我想要调度每天给每个仓库最多出一张整合卡片，一次 retro 整合取同一个 plugin 最早的至多 5 个，以便积压按天消化
2. 作为人，我想要不满 5 个也出卡片，以便条数少的 plugin 不会一直等
3. 作为人，我想要同一个仓库已经有没归档的整合会话时不再出，以便两次 retro 整合不会同时改同一个 skill

### 场景：整合会话

1. 作为人，我想要点开整合卡片后，这几个 issue 合成一份 spec、切工单、实现、开 PR、跑 review 和 skill 测试，全程不等我，以便我第二天直接看结果
2. 作为人，我想要整合照 `writing-for-agents` 的写法并进现有内容，以便改完的 skill 更通用、更短
3. 作为人，我想要某条的旧文主分支上已经不在、意思已经有了时，不再改并写明证据，以便不重复加
4. 作为人，我想要每条规则都按现有规则证明生效（能机械判定的做成检查，要判断的写回放用例；小的当场跑，大的进夜间队列），以便知道新版 skill 真的解决了那个问题
5. 作为人，我想要拼不出回放材料的那条在 PR 里标「无法回放」，以便我知道哪几条要自己核

### 场景：第二天决定

1. 作为人，我想要第二天打开整合会话就看到改动点和 review、测试结果，以便只需决定合不合
2. 作为人，我想要不要的那条能在会话里说一句就处理掉（不做关成 not planned，要讨论就摘掉 `retro` 回普通队列），以便其余的照常合
3. 作为人，我想要合并时这批 issue 一起关掉，以便不用手动收尾

### 场景：消化存量

1. 作为人，我想要现有的 13 个 retro issue 一次打上标记，以便从下一天起开始按 retro 整合处理

## 实现决策

### #106：只数标题是「<仓库名>#<号> …」的会话

`issue-dispatch`「每一轮」第 3 步改成：每个队列的三个 section 各列出没归档的会话，**只数标题匹配「<仓库名>#<号> …」的**（任何仓库名都算，跨项目共用 section），加起来是这个队列开着的会话数；issue 会话开出的子会话不算占位。

依据：人在调度会话里定的（#106「落点」节）。判别用标题、不用 `startedBy`：点调度卡片开出的 issue 会话，`startedBy` 也是调度会话，分不出来（同节原话）。issue 会话开场第 2 步已经把自己的标题改成这个格式（`issue-session`「开场」第 2 步）。

边缘情形，按规则定：

- issue 会话被人手动改了标题、不再匹配：不数。代价是这个队列可能多出一张卡片（多一个会话，不丢东西），按「代价相称」接受，写成已知限制。
- 汇报里每个队列那一行加「子会话 N 个（不占位）」，让人看得出数字差在哪。依据：#106 的起因就是人看不出 10 是怎么数出来的。

### retro 标记：分类照常按 plugin，加保留 label `retro`

retro 开的 issue 打 `type:<plugin>[/<子类>]` 加 `retro`；`retro` 写进 `AGENTS.md`「issue 分类」一节的「保留的 label」，`issues labels` 才不会把它当多余的。retro 开 issue 时自己知道落点，直接打上分类和 `retro`。依据：grill Q1，人答「同意」（推荐 B）。

带 `retro` 的 open issue：`candidates` 不列它，不算进任何队列的空位；`reconcile` 按它挂着的 spec 照常翻（整合会话起草了 spec 之后它就跟普通 issue 一样有 spec）。

### 整合卡片：每个仓库每天最多一张，至多 5 个

`issue-dispatch` 每一轮在出普通卡片之后：

1. 同一个仓库已经有没归档的整合会话（标题以「<仓库名> retro 整合 」开头），或今天已经出过整合卡片、还没点：不出。
2. 否则按 `type:<父类>` 分组，取最早开的那个 retro issue 所在的 plugin，取这个 plugin 最早的至多 5 个，出一张整合卡片。不满 5 个也出。
3. 卡片标题「<仓库名> retro 整合 #<号> #<号> …」；这个标题不是「<仓库名>#<号>」的格式，按上一节的数法不占位。prompt 让整合会话调 retro 整合的 skill，参数是这几个号。
4. 整合会话开场把自己移进「实现中」section。

调度第 4 步「没有会话的 issue」：标题里列着这个号的整合会话也算它有会话。

依据：grill Q2（不满 5 个也出）、Q3（每天最多一张、已有整合会话不出、标题不占位、放「实现中」），人答「同意」。

### 整合会话：照常走 spec → 工单 → 实现 → review，全程不停下等人

整合会话是一个新的 skill（暂名 `idea-loop:retro-merge`，名字实现时定，可被模型调用：调度出的卡片调它），它：

1. **认领**：这几个 issue 翻成「验证中」。
2. **起草一份 spec**：用 `idea-loop:to-spec`，`issues` 列全这几个号。「验证」表每条核一遍「旧文」还在不在主分支：在，「存在」；旧文已经不在、意思已经有了，「不存在」，证据写出处，这条随 spec 关掉（依据：`issue-verify` 对已经被做掉的 issue 的处置）。spec 经只改 `docs/` 的 PR 检查全过就合并（`decision-rules`「不自动的」里本来就允许）。
3. **切工单、实现**：`idea-loop:to-ticket`、`idea-loop:implement`。一条规则一张工单，落到同一个 skill 同一段的几条合成一张，照 `writing-for-agents` 的写法跟那段现有内容合并，能并进已有规则的不新开一句；改完的 SKILL.md 主体仍 < 5000 字（`AGENTS.md`「标准 plugin 目录结构」），超了的在 PR 里标出。依据：#108「想要的样子」第 3 条。
4. **证明生效**：照 `implementer` 的「改规则的工单：怎么证明 skill 真的变了」——能机械判定的做成检查，要判断的写回放用例；小的当场跑（一个约 $1–3.5），大的进夜间队列。用例的材料（当时的提交、触发 skill 的那句话、停在哪）从 issue 正文、`docs/raw/decisions/<号>.md` 和来源 PR 里拼；拼不出来的那条在 PR 里标「无法回放」，由人在 PR 上核，不硬编用例。依据：grill Q5，人答「同意」。
5. **review**：`idea-loop:pr-review` 跑两轴 review。
6. **停在第二天**：把改动点、review 结果、回放结果摆在会话里，等人决定合不合。

依据：grill Q4，人的原话：「这些 issue 合并成一个 spec -> 拆分工单 -> pr-review / skill test 这些不需要经过我同意，你直接做即可。我第二天在会话 review 改动点即可」。

整合会话不碰 UI，不经过设计段。

### 第二天：不要的条目、合并

人在整合会话里说哪条不要：不做的，`issues drop` 关成 not planned，对应改动撤掉；要讨论的，从 spec 里移出（`issues unhandoff`）、摘掉 `retro`，回普通队列。其余的照常合；合并时这批 issue 跟着 spec 关掉（照现在的 `advance`）。依据：grill Q6，人答「同意」。

### retro 开 issue 时写上回放材料

`retro` 第 5 步开 issue 时，正文除了候选、落点、旧文新文、原话，再写三样：决策发生时的提交、让 skill 产出那个东西的那句话、skill 把东西交给人的那一刻。依据：grill Q5，人答「同意」。

### 存量 13 个打标记

打 `retro`（并按 plugin 打分类）：#82、#83、#84、#92、#94、#95、#96、#97、#98、#100、#102、#103、#109。留在普通队列：#80（正文写明是结构改动）、#86（「待讨论」）、#87 和 #99（bug，不是 retro 开的）。照这个顺序，第一次 retro 整合是 #82、#83、#84、#92、#94。依据：grill Q7，人答「同意」。

### 碰到要人定的事不停，第二天一起确认

全程不停下等人。流程里原本会停的几处（spec 里出现「待定」，例：两条 retro 规则落在同一段、说法相反；implement 有工单要人决定；review 汇报里有「要你决定」）都按推荐先做：spec 里的写成「按推荐先定，待人确认」。这些全部列进第二天摆给人的「要你确认」一节，放在改动点前面；人推翻哪条就照着改。依据：grill Q8，人答「同意」。

### 叫法：retro 整合

同一个 plugin 凑在一起处理的那至多 5 个 retro issue 叫「retro 整合」，处理它们的会话叫「整合会话」，调度出的卡片叫「整合卡片」，标题「<仓库名> retro 整合 #<号> #<号> …」。依据：grill Q9，人的原话：「我倾向于叫 retro 整合」。已写进 `GLOSSARY.md`。

## 测试决策

| 变的是什么 | 仪器 | 本次 |
|---|---|---|
| 纯逻辑、数据转换、状态机 | TDD 单元测试 | 碰到：`issues` 的 `candidates` 跳过 `retro` issue、按 plugin 取至多 5 个凑成一次 retro 整合、`labels` 认 `retro` 是保留 label |
| API 契约（路由、schema、序列化） | TDD API 测试 | 不涉及 |
| DB schema、迁移、并发与事务语义 | 真 DB 测试 | 不涉及 |
| LLM 输出质量（prompt 改动） | eval（确定性断言） | 碰到：`issue-dispatch`、`retro` 的 SKILL.md 改动和新的整合会话 skill；按 `AGENTS.md` §5 不做量化 eval，规则改动照 retro 回放规则验 |
| 视觉正确性 | UI 实现环 | 不涉及 |
| 端到端用户流程 | 浏览器端到端测试 | 不涉及 |

- **seam**：
  - `issues.mjs` 的导出函数（`candidates`、凑批的新函数、`labels`）：喂一组假的 issue（带 / 不带 `retro`、不同 `type:*`、不同开的时间），读它列出什么。抓得到「retro issue 进没进候选、一次 retro 整合取了哪几个」；抓不到调度 SKILL.md 里数会话、出整合卡片那几步（agent 照文字做的）。
  - 数会话、出整合卡片、整合会话一路跑通，没有脚本 seam，靠增量功能测试里的人验。
- **增量功能测试**：
  1. 前置：侧边栏「设计中」里有一个 issue 会话和它开出的 2 个子会话。步骤：调度跑一轮。期望：汇报里主队列只数 1，并写「子会话 2 个（不占位）」。覆盖：调度数空位 1。
  2. 前置：一个带 `retro` 的待验证 issue、一个不带的。步骤：`issues candidates`。期望：只列不带的。覆盖：retro 开 issue 1。
  3. 前置：idea-loop 有 7 个 `retro` issue，没有开着的整合会话。步骤：调度跑一轮，再跑一轮。期望：第一轮出一张整合卡片，列最早的 5 个；第二轮不再出。覆盖：调度出整合卡片 1、3。
