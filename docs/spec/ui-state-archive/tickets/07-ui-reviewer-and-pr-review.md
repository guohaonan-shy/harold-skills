# 07 — UI 审查 agent，接进 pr-review 的每一轮与合并前归档

**Blocked by**：02 — 档案查询模块：六个入口 + 命令行；04 — 归档脚本与合并前钩子
**设计冻结**：不涉及 UI

## 要建什么

一个新的插件 agent「UI 审查」（Sonnet · high），和 pr-review 里调用它的两处，让每次 UI 改动在合并前被对着实现核过、经人审后写进档案。

### UI 审查 agent

输入：spec 名、集成 worktree 路径、分到的端口、模式（「每轮审查」或「归档」）。

- 按 worktree 约定起开发服务器（共用浏览器走已有的浏览器锁），用档案的「需求差异」查询拿 `delta/` 相对 `prod/` 的变化，对每个新增或改动的状态用「单个状态」查询推导出的路径进去，走每条新增或改动的边；画面与 `tmp/<spec-slug>/canvas/` 的冻结画布用已有界面比对脚本的现有容差比对（没有冻结画布的最小差异只核「应看到什么」）。
- **每轮审查模式**：找漏掉的状态与边、走不通的路径、对不上的画面，写成一份发现文件交回（每条带截图证据，格式照 pr-review 汇报 Spec 一节的证据要求）。
- **归档模式**：进不去或对不上就不写，交回失败原因；通过就在实现上重拍精简矩阵（每个状态一张主视口截图、每个动效一张 GIF，放进 `delta/` 各对象的 `assets/`），补齐状态文件的「这一屏」与「应看到什么」，把要写进对象文件的决定与候选整理成一份给人看的草稿，然后交回、停下。
- 不写 `prod/`，不碰 PR，不跟人对话；Codex 不参与，也不读档案。

### pr-review 接线

- **每一轮**：`docs/design/tmp/` 下有这份 spec 的需求目录时，编排者在起 pr-reviewer **之前**先起 UI 审查 agent（每轮审查模式），把发现文件路径交给 pr-reviewer；pr-reviewer 把它并进汇报的 Spec 一节，格式与校验沿用现有的。PR 描述「之前 → 之后」的「之前」从档案 `prod/` 取。
- **合并**（人说合并时）：执行合并命令前先看 `tmp/`；有东西就走归档：起 UI 审查 agent（归档模式）→ 在会话里给人看草稿（人要改就把批示转回同一个 agent）→ 人通过后跑归档脚本 → commit + push 到 PR 分支 → 重新执行合并（合并前钩子这次放行）。审查不通过就回 review loop，不合并。合并前钩子拦下时的提示也指向这条流程。
- review loop 的本地记录里把每次归档的审查结论与人的批示记一笔。

## 验收标准
- [ ] 新 agent 定义存在，模型与思考强度钉在定义里，两种模式的输入、做法、交回物写清楚
- [ ] pr-review 的「跑一轮」写明有 `tmp/` 时先起 UI 审查、发现交给 pr-reviewer；pr-reviewer 的说明里写明怎么并进 Spec 一节
- [ ] pr-review 的「合并」写明归档流程的六步与失败出口
- [ ] PR 描述规范里「之前」的来源写明取自档案
- [ ] 全量 node 测试套件全绿
- [ ] ⏭ 延后 → 集成 PR 的交付验收：在真实项目上走一遍「改一处 UI → 合并被拦 → UI 审查 → 人审 → 并进 prod/ → 放行」

## 选中的存量回归
无 test-cases 库。跑全量 `*/scripts/*.test.mjs`；review-check、pr-body、review-loop 三组必须保持绿。
