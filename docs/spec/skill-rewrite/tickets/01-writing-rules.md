# 01 — 写法规则：重写核对表、命令归类与 4500 线进 writing-for-agents

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

`writing-for-agents` 是后面每张工单照着重写的规则来源。这张工单让它带上四样东西，并且它自己先照这些规则重写（现在主体 4675 字，压到 4500 内）：

1. **重写核对表**：一份 skill 或 agent 定义重写时逐条过的八项：①只有部分运行才走到的分支移出主文件，进这个 skill 自己的参考文件，主文件留一行指针写明什么条件下去读；②开头写目标和交付物，每步结尾一句完成条件；③没有决策历史（日期、人的原话、「当时为什么移到 X」删掉；理由要改变 agent 行为的，留理由本身；原话和日期在知识库的决定记录与 ADR 里，没在的靠 git 历史）；④否定句只用在硬护栏上，后面跟着该做什么；⑤反复出现的长句定义收成一个词（先找现成的词；新词只在一份 skill 内定义、不进术语表；要进术语表的停下问人）；⑥共享的规矩只写一处，别处只指过去，不转述；⑦调命令行用 `dyna <模块> <命令>`，以插件最低版本那份命令登记表为准；⑧不写外部工具的具体命令和次序（见下面的归类）。每项写清怎么验：能机械判的写判法（字数量法、决策历史的搜索、行内命令的搜索），要判断的交给 review 的 Standards 轴。
2. **外部工具命令的归类**：skill 和 agent 定义里每一处 `gh` / `git` 这类外部命令按四类改写：
   - 目标型（拿信息或做一件常规事，换个命令同样拿得到）→ 只写要拿到的东西和完成条件。例：「`gh issue view <号> --comments`」→「读 issue 全文和评论」。
   - 约束型（做法不对会出事：合并方式、只快进、一个 commit、不碰共用 checkout）→ 写成结果约束和理由，不写命令。例：「`git merge --ff-only <commit>`」→「落地只快进，不产生合并提交；快进不了说明集成分支动过，停下」。
   - 坑（不写那个 flag 就会做错，看帮助也想不到）→ 留 flag，旁边一句为什么。例：被本地排除的目录要强制加才进得了提交。
   - 适配层（平台或环境适配参考：issues 的 GitHub 参考、setup 写进目标仓库的模板与前置检查表、运行环境的能力数据）→ 不动。
   工具不可用时 agent 换路（读 prompt 里给的、问人），而不是照一条命令失败。
3. **4500 线**：SKILL.md 与 agent 定义主体都不超过 4500 字，给以后加分支留至少 500 字余量；参考文件不受这条约束，但重写一份 skill 时它指向的参考一起量、一起剪。
4. **规矩的归属表**：依据只认三种、要人定的写成一道题、证据怎么写 → `decision-rules`；知识库落地、项目目录、frontmatter、术语表 → `wiki-conventions`；issue 的状态、正文格式、blocked by → `issues`；PR 描述、汇报、review loop 文件、PR 从 spec 提交就挂着 → `pr`；red → green、什么测试值得留、只在系统边界 mock → `tdd`；运行环境的能力做法 → `dyna runtime show <能力>`；写法本身 → `writing-for-agents`。

这四样放在 `writing-for-agents` 的参考文件里，主文件留指针写明「重写或新写 skill、agent 定义时读」；它本来就有的「剪枝」「步骤与完成条件」「引导词」等节照核对表重写。`evidence` 这时还没并进 `decision-rules`，归属表里证据一项照合并后的名字写 `decision-rules`，别处对 evidence 的引用不在这张工单改（02 号工单统一改）。

改的文件：`writing-for-agents` 的 SKILL.md 与它的参考文件。

## 验收标准

- [ ] 每份改到的 SKILL.md、agent 定义主体不超过 4500 字（量法照仓库 `AGENTS.md`「标准 plugin 目录结构」的要点），交回里贴每份的改前、改后字数。
- [ ] 改到的文件里，决策历史的搜索（日期、「人定」「原话」「依据：」）没有命中；留下的每处在交回里写一行为什么留（例子里的日期、`captured:` 这类格式说明）。
- [ ] 改到的文件里，行内的 `gh` / `git` 命令只剩适配层和标了「坑」的行；能用 `dyna` 子命令的都改成了 `dyna <模块> <命令>`，命令名以插件命令行登记表（当前最低版本那份）为准，`dyna-scan` 测试绿。
- [ ] 照 `writing-for-agents` 的「重写核对表」逐条过（01 号工单写进去的那张），交回的「杠杆」一行写清每份文件对的是哪几条。
- [ ] 改到的文件对应的文档测试同步改：守硬规矩的断言跟着内容挪到新位置；钉决策历史或已删措辞的断言删掉；钉命令原文的改钉结果约束。全量测试绿。
- [ ] 不改任何流程的行为：只改写法和位置。重写中发现行为本身有问题的，在交回的 `found` 里写一行，不在这张工单里改。
- [ ] 调过 `writing-for-agents`，交回 `verified` 里每个改到的 skill、agent 定义、skill 参考文件一行杠杆。
- [ ] 改到的 `SKILL.md` 正文按 `AGENTS.md` 的量法在上限内；超了就把只有部分运行才走到的分支挪进这个 skill 的参考文件，不删工单范围以外的句子。
- [ ] 照执行方定义「改规则的工单：怎么证明 skill 真的变了」选了一种证明并做完：能机械判定的做成检查、先在历史错误上见红；要判断的写回放用例并跑过，大用例写明待跑、由编排者当场跑。只改措辞、行为没变的写「不涉及：只改措辞」。
