# 01 — 执行方开工对齐起点改用不丢东西的写法

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

idea-loop 的工单执行方（implementer 这个 subagent）开工第一步要把自己的新 worktree 对齐到集成分支的起点提交。现在它的定义让它用一条带「丢弃改动」语义的硬重置命令，auto mode 的分类器常把它判成破坏性操作拒掉，执行方要试错几轮才开得了工。

改完：执行方定义里的对齐步骤换成不丢东西的写法——先核工作区为空，再尝试快进到起点提交；快进不了时，把自己这条分支指到起点提交（工作区已核为空，不丢东西）。对齐后照旧核 HEAD 等于起点提交，执行方仍在派给它的那条分支上。定义里其余几处说「在硬重置之后」「不用再重置」的措辞跟着改成「对齐起点之后」「不用再对齐起点」。只正向写出要跑什么，不写「别用某命令」。

idea-loop 插件版本升一档 patch。

## 验收标准

- [ ] 执行方定义里不再出现硬重置（`grep -n 'reset --hard'` 对它无输出）；落地前压成一个 commit 用的软重置不动
- [ ] 开工对齐步骤按顺序写出：核工作区为空 → 快进到起点 → 快进不了时把自己的分支指到起点 → 核 HEAD 等于起点；完成条件不变
- [ ] 定义里原先说「reset 之后」「不用再 reset」的几处措辞改成「对齐起点之后」这类说法，意思不变
- [ ] 有一个文档测试钉住上面三条，改前对着旧定义跑是红的、改后是绿的
- [ ] idea-loop 的 `plugin.json` 版本升一档 patch，README 若提到这一步同步改
- [ ] idea-loop 全部测试照旧绿
- [ ] ⏭ 延后 → 人（PR 交付验收）：合并后下一次 auto mode 下的实现运行里，执行方开工对齐没有被分类器拒绝
