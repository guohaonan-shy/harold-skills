# 01 — PR review 一轮：照规则判得出的条目立即处理，汇报单列「已按规则处理」

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

idea-loop 插件里，一轮 PR review 跑完之后，能从规则推出处置的条目不再等人批示：审查者给每条候选标好处置和依据，编排者在把汇报贴给人之前就把它们处理掉（派修、开 issue、同步改文档），汇报最前面单列「已按规则处理」，每条一句做了什么、依据是什么、带提交或 issue 链接。人说一句「推翻某条」，编排者当作一条新批示改回，并把原话逐字记进 review loop；下一轮审查者读到推翻记录，不再按同一依据自动处理它。这一轮有修复、修复都落地了、还没跑满两轮时，编排者自己起下一轮；跑满两轮就停下等人。

具体要落的东西（按 spec 的 4.1、4.2、4.4、4.5、4.6、4.9、4.10）：

- **新增插件级共享规则文件「决策规则」**，这一张只写「自己定」那一半（spec 4.2 的四条：有依据就照办——依据只认写下来的规则原文、人在这份 spec 或这个 PR 里已做的决定原话、产品里已有的统一做法且能指出现存实例；归不归这次看依赖；代价跟用户会失去的相称；默认改动最小；依据不成立时照旧交给人）。另写清：「代价相称」在 PR 流程里只用来定推荐，边缘情形照旧是「要你决定」（spec 4.9 人的决定）；以及不自动的清单（spec 4.10）。留出「交给人时」那一半的位置，由工单 02 补。
- **review 标准与审查者 agent**：每条 Spec / Standards 候选多一个处置——「照规则」带依据和动作（修 / 同步改 / 接受并补记 / 恢复 / 开 issue），不写要你决定；「要你决定」照旧。有明文规则、没有歧义的 Standards 一律「照规则 · 修」，有歧义的照旧进折叠区。「不报改动行以外的存量」补上例外：污染了本 PR 的输入或结论、或让 CI 变红的存量问题要报，处置为「照规则 · 修」；与本 PR 无关的存量问题照旧不报。审查者读 review loop 里人的推翻记录，不再按同一依据把被推翻的条目标成照规则。
- **review 候选的校验脚本**：认「照规则」形状——必须有依据和动作，不要求选项与建议；依据是规则原文的，照旧要在规则文件里找得到；给人读的字段照旧不许有代码层面的指称。「要你决定」的形状要求不变。补单测。
- **pr-review 编排**：交回后先记文件，再立即处理照规则的条目（修的照现有「修」的路径写进工单、派执行方；开 issue 的在目标仓库开；同步改、补记的直接提交），再在会话里贴汇报；处理推翻；「不做」里的「人批示之前不修任何东西」改为除照规则的条目之外；「进 backlog」改为在目标仓库开 issue。
- **pr-review 编排 · 下一轮由编排者按条件起**（spec 4.6）：三条同时成立才自动起——这一轮有修复（照规则 · 修，或人批了修，至少一条）、这一轮的条目都处理完且修复已落地推送（review loop 的检查没有未处理条目）、这个 PR 还没跑满两轮。起之前在会话里说一句「第 N 轮的修复已落地，自动起第 N+1 轮」并发推送通知。没有修复就不再跑、等人说合并；跑满两轮就停下，汇报末尾写明「已跑满两轮，要再跑或合并请直接说」。上限只约束自动触发，人说「再跑一轮」照旧随时可以跑，人触发的轮次也计入编号。「什么时候跑」一节与「不做」里的「不自己开下一轮」随之改写。
- **review 汇报写法**（PR 描述与汇报写法那份 reference 的 review 轮次一节）：正文结构加「已按规则处理」一节，放在 Spec 与 Standards 之前；末尾告诉人怎么批示的那句加上「不同意的说推翻某条」。
- **同步**：review loop 那份 reference 里提到人批示、进 backlog 的地方；插件 README 与仓库 CLAUDE.md 里对 pr-review 的描述；插件版本号升一个补丁版本。

## 验收标准

- [x] 共享规则文件存在，「自己定」一半写齐 spec 4.2 四条、依据不成立的退路、4.8 的决定和 4.9 不自动清单；review 标准、审查者 agent、pr-review 编排都引用它，而不是各自再写一遍规则
- [x] 校验脚本：一条「照规则」候选（有依据、有动作、没有要你决定）校验通过；缺依据或缺动作的进改写；依据为规则原文但规则文件里找不到的被丢弃；正文带代码指称的进改写——各有单测，改前红、改后绿
- [x] 校验脚本：现有「要你决定」形状的单测全部照旧通过
- [x] 审查者 agent 的说明里写明每条候选要标处置，Standards 默认照规则 · 修，存量依赖例外，读推翻记录
- [x] pr-review 编排的说明里写明：照规则条目在贴汇报之前处理、汇报单列「已按规则处理」且在最前、推翻的处理方式与原话记录、「进 backlog」改为开 issue；「不做」一节与之不矛盾
- [x] 汇报写法里有「已按规则处理」一节的模板，每条一句做了什么 + 依据 + 链接
- [x] pr-review 编排写明自动起下一轮的三个条件、起之前的那句话与推送、两种停下（没有修复 / 跑满两轮）的处理，以及人手动再跑不受上限约束；「什么时候跑」与「不做」两节和它不矛盾
- [x] 插件里不再有把「进 backlog」写成追加到待办文件的地方（全文搜索为空，或只剩明确说明它已改为开 issue 的历史说明）
- [x] README、仓库 CLAUDE.md 对 pr-review 的描述与新行为一致；插件版本号已升
- [x] 插件全部脚本单测通过（含防止泄漏目标项目细节的那条测试）

## 选中的存量回归

无 test-cases 库。这个仓库真实存在的套件是 idea-loop 插件脚本旁的 node 内置测试（`node --test` 跑插件 scripts 下全部测试文件）：
- review 候选校验脚本的单测——这张直接改它，原有形状规则不能被改坏。
- review loop 脚本的单测——推翻记录写进同一份文件，条目解析不能被改坏。
- 防止插件文字泄漏某个具体项目细节的测试——新写的规则文件和说明里不能出现目标项目专有的名字。
