# 02 — 起草：交给人的题先做完功课

**Blocked by**：01 — PR review 一轮：照规则判得出的条目立即处理（共享规则文件由它新建，这张补另一半）
**设计冻结**：不涉及 UI

## 要建什么

人审一份新起草的 spec 时，不再需要一条条追问现状、问例子、补范围：起草方（to-spec 的两种模式，以及从 issue 起草的 issue-explorer agent）在落盘之前，把能按规则定的事定掉，把留给人的题按「交给人时」三条写好。

具体要落的东西（按 spec 的 4.3、4.7）：

- **共享规则文件补「交给人时」一半**（spec 4.3 的三条）：现状先查清（出处、规模数字、同类入口、相邻在飞的 spec 与 issue、出题前对最新基准分支再核）；先写交付物再列做法（选项差在用户能感到的地方、后续写全、改 spec 同步图与测试表）；每个问题和选项配具体例子（陌生记号先解释、不用裸编号指代选项、比对同条件、评判文案先给标准）。
- **to-spec（两种模式共用的写法）**：§1 根因与正文里关于现状的陈述带出处、讲影响带规模；§2 之前写清交付物与它依赖的输入；§4 先按「自己定」处置能判的、写成已定决定并注明依据，只把依据不成立的写成选项，边缘情形按「代价相称」在 spec 里定好；范围写明同类入口纳入还是排除，相邻在飞的 spec 与 issue 进 §8；改 spec 文字时图和测试表同步改。
- **to-spec 的 backlog 模式**：「§4 只写修法有分歧的条目」改成上面的写法；「建议关闭」每条带三样——现象、现状证据（为什么现在不成立）、怎么验证的。
- **issue-explorer 的自检**加三项：§4 每个选项都说明了为什么依据不成立；范围一节写明了同类入口；「建议关闭」每条带现象、现状证据和验证方式。
- **同步**：README 与仓库 CLAUDE.md 里对 to-spec、issue-explorer 的描述（如有需要）。

## 验收标准

- [ ] 共享规则文件「交给人时」一半写齐 spec 4.3 三条，与 01 写的「自己定」一半同在一个文件里
- [ ] to-spec 的说明在 §1、§2、§4、范围、§8 与改 spec 的地方都引用了共享规则，不再各自重写规则
- [ ] backlog 模式的章节取舍表与「建议关闭」写法按上面改了
- [ ] issue-explorer 自检清单多出三项，每项写成可逐条核对的句子
- [ ] 用这份 spec 自己当样例对照一遍：它的 §1 现状陈述有出处、§4 只剩一个真分歧并已由人定、「建议关闭」带现象 / 现状证据 / 验证——说明新写法写得出来（在交回里写对照结果）
- [ ] 插件全部脚本单测通过（含防泄漏测试）

## 选中的存量回归

无 test-cases 库。这个仓库真实存在的套件是 idea-loop 插件脚本旁的 node 内置测试：
- spec 状态脚本的单测——起草写法变了，spec 状态与移交标记的检查不能被改坏。
- issue 状态脚本的单测——issue-explorer 的流程描述改了，handoff 的行为不能变。
- 防止插件文字泄漏某个具体项目细节的测试。
