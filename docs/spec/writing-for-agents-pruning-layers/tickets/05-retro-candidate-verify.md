# 05 — retro：候选多一栏「验证」，写清改完怎么证明它治好了当时的问题

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

`idea-loop:retro` 的每条候选现在有七栏（信号、原话、落点、旧文、新文、归并、同类）。「归并」管新内容和已有原则怎么结合；没有一栏回答：这条改完之后，怎么在当时出问题的那一刻证明它真的让 skill 变了。回放用例要到实现时才由 implementer 写，人批候选时看不到它将来怎么验。人的原话：「要结合candidate分析，这个内容到底可以和现有的skill怎么结合，以及这块内容要如何验证这个改动确实对于之前的问题解决了」。

在候选格式里加一栏「验证」，写验收的形状（用例文件仍由实现时写）：

- 要判断的规则：回放用例的三样——当时的提交、让 skill 产出东西的那句 prompt、一道从人原话写出的是/否题；
- 能机械判定的：检查的名字，并写「先在历史错误上看它红」；
- 两样都写不出的：写「判不了」和原因，人批的时候就知道它没法验。

验收方式的依据是仓库 `AGENTS.md` §5 的第二个例外（改前「否」、改后「是」才算规则真的让 skill 变了），格式写进 retro，不复述那一节。同步改：

- retro 的「做完的条件」（现在写「八项都填了」）改成九项，并要求「验证」一栏写的提交在仓库里存在、是/否题能从原话推出；
- 同一个候选格式在别处还有副本，一起加：retro 的候选池参考里规定的池文件字段、retro 的决定记录参考（`decision-record`）里的候选块、仓库 `docs/records/index.md` 写的池形状契约；dreaming 读候选池的地方核一遍不受影响。
- 现有的 27 份池文件不回填（默认改动最小）：读池的脚本和 dreaming 要容得下没有「验证」的旧文件。

照「先归并」：先看「做完的条件」和候选格式说明里已有的句子能不能改写来容纳它，不另起一节。
