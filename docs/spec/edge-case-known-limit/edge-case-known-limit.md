# PR 流程里看得见、不丢东西的边缘情形，照规则接受成已知限制

> #280 存在：现行 review 标准把「只在兜底路径或罕见异常里出现、不丢东西的边缘情形」一律标成「要你决定」；决定记录里碰到时看得见、不丢东西的 3 道，人每次都选接受、从未推翻，详情在「问题陈述」

## 问题陈述

### 1. 看得见、不丢东西的边缘情形，每次都停下问人

现状（对着 main `a032e45` 查，2026-11-16）：

- `idea-loop:decision-rules` 没有覆盖这类题的规则；`pr-review` 的 review 标准处置表里有一行写死：「只在兜底路径或罕见异常里出现、不丢东西的边缘情形 → **要你决定**，推荐接受（接受它没有依据）」。`pr-review` 的 SKILL 和 `pr` 的汇报写法两处也重复写了「边缘情形是决定题」。
- 这一行是 ADR-0035 剪枝时有意留下的：原来的「PR 流程里『代价相称』只定推荐」一节删掉，边缘情形改指「停下问人」，处置仍是「要你决定」。原节的理由是「判断不丢东西可能判错，判错的代价是丢用户数据」。所以这次是在放宽一个当时有意设的保险，不是补遗漏。

复现：决定记录（`docs/raw/decisions/`）里标了「边缘情形」类别的题共 11 道，逐条按「碰到时会怎样」重新归类：

| 碰到时会怎样 | 题 | 人当场的处置 | 后来 |
|---|---|---|---|
| **看得见、不丢东西**（有注记，或这一步不执行、原样交给人，或指错位置但信息都在） | #68 题 3（拍图结果带注记，切两段就拍全）、#55 题 17（这一行不执行、原样交给人）、#80 题 9（关闭评论指到 spec 开头，证据在「验证」表） | 3 道全接受 | 没有推翻 |
| **悄悄出错**（没有提示、没人会发现） | #108 题 9、题 10（调度悄悄卡住）、#68 PR #114 S1（悄悄缺图） | 3 道全修 | — |
| | #51 题 11（开场任务提示被当成人的发言）、#55 题 16（别名 import 悄悄漏挑） | 2 道接受 | **都被人推翻**：#108 回看时人说前者应该修，后者「需要讨论」 |
| | #65 题 7（窄栏「滚一下换一张」检不出，没有真实实例） | 接受 | 没有推翻 |
| **会丢东西** | #157 题 2（断会话后执行方交回的验证记录找不回来） | 接受（窗口很窄） | — |
| **没有实例、说不清碰到时怎样** | #108 题 8（分类是独立队列时整合会话放哪） | 接受 | — |

例子（#68，PR #114 第 1 次停下）：一段横跨滚动容器顶边时只拍到首屏那截，拍图结果带注记，切成两段就能拍全。摆给人的是 A 记成已知限制 / B 给这种段也做拼接，推荐 A；人回「01 选 A：记成已知限制，分段参考里加一句在容器顶切成两段。」

本该是：表里第一行这一类照规则接受，列进「已按规则处理」，人扫一眼、想推翻再说，不用停下等一句「选 A」。

复现材料：`docs/raw/decisions/{51,55,65,68,80,108,157}.md` 里「类别：边缘情形」的各题；分拣评论 https://github.com/guohaonan-shy/harold-skills/issues/280 （2026-11-13）；候选的来历 `docs/records/retro-candidates/retro-candidate-102.md`。

### 根因

接受一条边缘情形，三种依据（规则原文、人的决定、现存实例）都给不出：人每次的「接受」只覆盖那一条，套到下一条要靠推断（「人的决定只覆盖了相邻的情形」），于是每次都落到「停下问人」。缺的是一条写下来的规则，把人反复做的同一个选择变成规则原文。

## 方案

改完人得到什么：PR 流程（停下汇报、review 轮次）里，碰到时看得见、不丢东西、能具体说出碰到时会怎样的边缘情形，不再出现在「要你决定」里，而是出现在「已按规则处理」里，一句话写它碰到时会怎样、补记进了 spec 的哪里；人说一句「推翻」就改回问题处理。决定由两样输入定：执行方能不能具体说出「碰到时会怎样」，以及说出来的结果属不属于「看得见」的三种且不丢东西。

全貌：`decision-rules` 的「依据明确、没冲突：照标准做」一节下有一个小列表「这几类也照规则处置」（跟 #276 共用，#276 写它那一条），#280 在里面写一条；`pr-review` 的处置表那一行拆开，看得见的改成「照规则 · 接受并补记」、依据引这条原文；另外两处「边缘情形是决定题」的重复句改成指向它。review 的准入脚本已经支持「照规则」带依据（种类「规则原文」、出处、原文），依据文件用插件里 `decision-rules` 的绝对路径，脚本按路径读得到，不用改脚本。

```
审查者交回一条边缘情形
  ├─ 说得出碰到时会怎样？── 否 ──→ 要你决定（同现在）
  └─ 是
      ├─ 看得见（三种之一）且不丢东西 ──→ 照规则 · 接受并补记（新）→ 「已按规则处理」
      ├─ 悄悄出错 ──→ 见「待定：悄悄出错的怎么处置」
      └─ 会丢东西 ──→ 要你决定（同现在）
```

同一行为的其他入口：

- **纳入**：`pr-review` 的处置表、`pr-review` 的 SKILL 里「留给人」那两句、`pr` 的汇报写法里「边缘情形不放这里」那句——都是同一条规则的落点。
- **纳入**：`implement` 停下汇报时的同类题（它读同一份 `decision-rules`，规则写在那里就覆盖）。
- **排除**：`to-spec` 的「边缘情形在这里定好，不留给 implement 停下」——起草时人在场，本来就该当场定，不受这条影响。
- **排除**：#276 的「两种都行、执行方已做好一种」——触发条件不同，由 #276 自己的会话写进同一个列表。

## User Stories

只修问题，不加能力：

1. **期望行为**（对应问题 1）：PR 流程里，审查者或执行方交回一条边缘情形，能具体说出碰到时产物带注记、或这一步不执行原样交给人、或信息都在只是位置或指向不对，且不丢东西的，汇报里它出现在「已按规则处理」，一句话写依据（碰到时会怎样）和动作（接受并补记，补到 spec 的 Out of scope 或工单），不出现在「要你决定」；说不出碰到时会怎样的、会丢东西的，仍在「要你决定」。

## 实现决策

- **规则的形状与落点**：只管边缘情形的一条，不跟 #276 合成一条更宽的原则；写进 `decision-rules`「依据明确、没冲突：照标准做」一节下的小列表「这几类也照规则处置」，与 #276 那条并列，各自的反例仍回「依据冲突或没有：停下问人」。列表标题与引导句以 #276 先写的为准，后合并的一方 rebase 进同一列表（依据：#276 会话 2026-11-16 的提议，分支 `issue/276-keep-done-alternative` 提交 `2883a80` 已写入标题；两条的判据不在一个轴上——#276 看「不削弱 spec 目标」，这里看「碰到时看得见、不丢东西」）。`pr-review` 处置表、`pr-review` SKILL、`pr` 汇报写法三处只引它，不各写一遍（依据：ADR-0035「『一道题』只在 decision-rules：单一事实来源」的同一做法）。
- **处置的动作**：用准入脚本已有的「接受并补记」，补记进 spec 的 Out of scope（或工单），写成已知限制；不新增动作（依据：现存实例——#68 题 3、#157 题 2 的做法都是「spec 的 Out of scope 记已知限制」）。
- **依据的种类**：「规则原文」，出处为插件里 `decision-rules` 的那一句。
- **「看得见」的判法**写成具体的三种，不留给推断：碰到时（a）产物里带注记，（b）这一步不执行、原样交给人，（c）信息都在、只是位置或指向不对。说不出属于哪一种，就不算（依据：上表第一行三道题恰好各是一种）。
- **人推翻**：照 `decision-rules` 已有的「人说一句『推翻某条』」，不另写。

### 待定：悄悄出错的边缘情形怎么处置

依据为什么冲突：issue 提议「碰到时会悄悄出错的，照规则修」；但上表里悄悄出错的 6 道，人选修或事后改成修的 4 道，接受且没推翻的 1 道（#65 题 7，没有真实实例），事后说「需要讨论」的 1 道（#55 题 16）。

- **A 照规则修**（issue 原提议）：#108 题 9 这类直接修、进「已按规则处理」。代价：#55 题 16 那种「该不该管」本身要讨论的，会被直接修掉，人得在「已按规则处理」里发现并推翻。
- **B 仍是「要你决定」，推荐写「修」**：处置表那一行拆开——看得见的照规则接受，悄悄出错的照旧问人、推荐修。代价：这类题每次仍停一次（证据里 6 道）。

**推荐 B**：6 道里有 2 道人没有选修，「修」不是人一贯的选择，够不上规则；这一类停下来的代价也是有意的——它正是 ADR-0035 保险要拦的「判错」。
