# 思考与决策写进 home 的固定文案，插件删掉 decision-rules

> #280 存在：现行 review 标准把「只在兜底路径或罕见异常里出现、不丢东西的边缘情形」一律标成「要你决定」；决定记录里碰到时看得见、不丢东西的 3 道，人每次都选接受、从未推翻，详情在「问题陈述」1

> #276 存在：「两种都行、执行方已做好一种」的条目每次都摆成「要你决定」；决定记录里 5 次，人 4 次回「保持现状 / 选已做的」，详情在「问题陈述」2（2026-11-13 分拣对着 main a7c8129 核过，2026-11-16 #276 会话对着 main a032e45 复核；#276 已按人的决定并进本 issue，关成重复）

#427（交给人的消息缺「问题」「解法」，人得先追问）2026-11-22 按人的决定并进本 issue、以 canceled 关闭，内容在「问题陈述」4。

## 问题陈述

### 1. 看得见、不丢东西的边缘情形，每次都停下问人

现状（对着 main `a032e45` 查，2026-11-16）：`pr-review` 的 review 标准处置表里有一行写死「只在兜底路径或罕见异常里出现、不丢东西的边缘情形 → **要你决定**，推荐接受（接受它没有依据：`idea-loop:decision-rules` 的『依据冲突或没有：停下问人』）」，`pr-review` 的 SKILL 和 `pr` 的汇报写法两处重复了这句。这一行是 ADR-0035 剪枝时有意留下的保险，理由是「判断不丢东西可能判错，判错的代价是丢用户数据」。

复现：决定记录（`docs/raw/decisions/`）里标「边缘情形」的题共 11 道，按「碰到时会怎样」重新归类：

| 碰到时会怎样 | 题 | 人当场的处置 | 后来 |
|---|---|---|---|
| **看得见、不丢东西**（有注记，或这一步不执行、原样交给人，或指错位置但信息都在） | #68 题 3、#55 题 17、#80 题 9 | 3 道全接受 | 没有推翻 |
| **悄悄出错**（没有提示、没人会发现） | #108 题 9、题 10、#68 PR #114 S1 | 3 道全修 | — |
| | #51 题 11、#55 题 16 | 2 道接受 | **都被人推翻**（#108 回看：前者应该修，后者「需要讨论」） |
| | #65 题 7（没有真实实例） | 接受 | 没有推翻 |
| **会丢东西** | #157 题 2 | 接受（窗口很窄） | — |
| **说不清碰到时怎样** | #108 题 8 | 接受 | — |

例子（#68，PR #114 第 1 次停下）：一段横跨滚动容器顶边时只拍到首屏那截，拍图结果带注记，切成两段就能拍全。人回「01 选 A：记成已知限制，分段参考里加一句在容器顶切成两段。」

### 2. 执行方已做好一种、另一种也说得通的小题，每次都停下问人

例子（#148，PR #274 第 1 轮 review 的 C1）：新加的自校验句写了「两个选项各配例子和代价」，「例子」跟它指向的决策规则重复。改要动三处文字、再花约 $7.4 重跑规则回放；不改只是多两个字。人回「C1 选 B，保持现状」。

决定记录里同一类（类别「改动最小-沿用已做的」）5 次：沿用 4 次（`51.md` 题 12、`55.md` 题 9、`55.md` 区域组件、`148.md` 题 1），不沿用 1 次（`55.md` 题 10「我倾向于选择B。」：执行方把档案对账不开浏览器的一半留在 dreaming，spec 要的是对账都交给钉了模型的 agent，只达成一半）。

### 3. 规则穷举不完

两类题都是同一个形状：插件里的 `decision-rules` 默认「三种依据都给不出就停下问人」，人每多批一类，就要多写一条例外。全局量：决定记录 36 份、181 道题（2026-11-17 数）；人改了或推翻推荐的 26 道，其中 25 道出在起草 spec、grill、审 spec 初稿时，PR 流程里只有 #311 题 2（版本档位）1 道。

### 4. 交给人的消息缺「问题」或「解法」，人得先追问一句

#164 的会话（2026-11-20）里，人两次得先追问才能做决定：

- 理解解法：grill 第一轮题里直接用了 `disallowedTools`，没说它是什么。人：「disallowed tool是指不被允许的工具吗？」
- 理解问题：一道「要不要改『Mobbin MCP』这类叫法」的题，没说这个叫法在哪、做什么用。人：「Mobbin MCP 这类叫法是在哪里？做什么用的」

同一场会话里，第 2 次实现落地后全量测试在后台跑完（1724 过、0 失败），agent 没说，人来问「测试完成了吗」。同类追问此前还有 Toeflair#577、#731（候选池 `docs/records/retro-candidates/2026-10-31-handing-to-human-name-references.md`），共 3 场会话。

现状（对着 `release/idea-loop-0.2.0` 的 `f12f7edc` 和这台设备的 `~/home/AGENTS.md` 查，2026-11-22）：这几条只写在两处，都不是插件管得到的：

- 人手写的 `~/home/AGENTS.md`「沟通风格」一节（`~/.claude/CLAUDE.md` 是指向它的软链接，每个会话都加载）：写了「结论在前」「陌生叫法说清」「后台的活不沉默」，没有「三句话开头」。换一台设备（公司虚拟机）跑 setup 建出的 home 里一条都没有：setup 只写 `## 设备地图`、`## 项目` 两节（`idea-loop/skills/engineering/setup/references/home.md` 第 1 步）。
- 插件 `decision-rules`「整体风格」里有「陌生叫法第一次出现就说清」，开场整份注入，仍反复出现。

人的方向（#164 retro）：「三句话说清楚问题是什么，解决方式是什么，需要什么资源、权限之类的……这个内容我觉的可以放到0.2.0 的home repo的claude.md」。

### 根因

`decision-rules` 把默认设在「问人」：依据只认三种（规则原文、人的决定、现存实例），人每次的「接受」「保持现状」只覆盖那一条，套到下一条要靠推断，于是每次落回「停下问人」（问题 1、2）。要停下问人，就得把每一类可以不问的穷举成例外（问题 3）。

人和 agent 怎么协作的规矩散在两处：插件里一份（开场注入，所有设备一样，但写的是插件的视角），人手写的 home 里一份（只在这台设备上，跟插件说法不一）。新设备上 setup 不写，这台设备上插件的那份又跟人的那份打架（问题 4）。

## 方案

改完人得到什么：每台跑过 setup 的设备，home 的 `AGENTS.md` 里都有同一份 idea-loop 管的固定文案，写思考原则、决策范围、沟通规矩、证据的通用描述；每个会话加载它。PR 流程、起草、实现里，固定文案没写成「只由我做」「停下问我」的事，模型照思考原则自己定、事后列进「已按规则处理」，人说推翻就改回（问题 1、2、3）。每条交给人的消息开头三句说清问题、解法、要人做什么，后台的活跑完说一句（问题 4）。插件里的 `decision-rules` 删掉，开场不再注入它；里面只对 idea-loop 流程有用的几条回到用它的 skill，证据三节原样搬进 `idea-loop:evidence`。

```
setup / dyna home config apply ──→ 把插件里的固定文案写进 ~/home/AGENTS.md 的 idea-loop 几节（新）
会话开场 ──→ 加载 ~/.claude/CLAUDE.md（= ~/home/AGENTS.md：固定文案 + 人自己写的 + 设备地图 + 项目）
        ──→ dyna home map --hook：固定文案落后于插件时提醒一行（新）
        ──→ 不再注入 decision-rules（删）
碰到一件要定的事
  ├─ 固定文案「只由我做」 ──→ 停下，交给人
  ├─ 固定文案「停下问我」 ──→ 摆成一道题（写法照固定文案「沟通」的「要我定的写成一道题」）
  └─ 其余 ──→ 照固定文案的四条原则定 → 列进「已按规则处理」（依据多一种「目标」）
Codex 审查者 ──→ 提示词里加传 ~/.claude/CLAUDE.md（新）
```

### 固定文案：放在哪、怎么写进 home

- **原文在插件里**：`setup` 的参考资料里一份（固定文案全文，见「实现决策」）。插件里只有这一份，别的 skill 不再转述它。
- **写进 home 的方式**：扩展已有的 `dyna home config`（setup 第 3 步用的那个），加第 4 项 `rules`：`plan` 列出 home 里 idea-loop 那几节的改前、改后，`apply` 照插件的版本写进去。跟 `## 设备地图`、`## 项目` 一样是 idea-loop 管的节（`dyna/internal/home/config.go` 的 `ownedSections`），人自己写的节原样保留。不新做命令。
- **插件升级后**：`dyna home map --hook`（开场已有的 hook）比对 home 里的几节和插件的版本，不一致时在开场留一行「home 的固定文案落后于插件，跑 `/idea-loop:setup`」，不拦会话。

### 插件里的 decision-rules 删掉，内容各回各处

人的决定（2026-11-22，本会话）：「思考模式这个点，其实是每一个会话、每一个子代理都需要加载的内容，我觉的思考甚至于决策本身就应该放在home/claude.md里面吧」；证据「#280 原样搬进 evidence」。这推翻了 2026-11-20 的「拆开放」「改名思考模式」（[[280]] 题 6、题 8）：当时删不掉，是因为 #340 把证据并进了 decision-rules；证据现在有了去处。

实测（2026-11-22，本会话）：起两个子代理只看开场上下文。通用子代理（general-purpose）看得到 home 的 `AGENTS.md`（有「设备地图」「以我的身份对别人说话」），看不到开场注入的 decision-rules 正文（没有「依据只认三种」）；只读搜索子代理（Explore）两样都没有。即现在的开场注入只到主会话，home 能到子代理。

| decision-rules 现在的节 | 去哪 |
|---|---|
| 核心（按 spec 的方案解决 spec 的问题） | 删：固定文案「先确认问题」「我已经定下的不自己改」覆盖；pr-review 的 Spec 轴本来就对着 spec 审 |
| 依据只认三种、依据明确：照标准做（「已按规则处理」的写法） | `pr-review` 的 review 标准：依据改成四种，加「目标」（spec 原文或用户真实路径里的一句目标，配一句达成、达成一部分、没达成）；`pr` 的汇报写法指过去。`dyna pr candidates` 按它核 |
| 依据冲突或没有：停下问人 | 删：停不停下看固定文案的「只由我做」「停下问我」 |
| 护栏 | 通用五条（合并改了代码的 PR、生产数据、真实支付、对外发布、术语）进固定文案「只由我做」；SEO 例外回 `pr-review` 的合并一步；「新词只在 `idea-loop:grill` 里加」回 `glossary` |
| 要人定的写成一道题 | 固定文案「沟通」已有；「范围题怎么推荐」一条进 `pr-review` 的 review 标准 |
| 证据是什么、整体风格、配什么图，加 `references/ui-flow.md`、`gif.md` | 原样搬进新的 `idea-loop:evidence`（`skills/productivity/evidence/`），一字不改，只改路径；description 照 `writing-for-agents`「调用方式」只写路由。#438 在它上面升级 |

## User Stories

只修问题，不加能力：

1. **期望行为**（对应问题 1）：PR 流程里碰到看得见、不丢东西的边缘情形（例：#68 题 3），出现在「已按规则处理」并补记成已知限制，不出现在「要你决定」；碰到时会悄悄出错的（例：#108 题 9），仍停下问人。
2. **期望行为**（对应问题 2）：执行方已做好一种、另一种也说得通、已做的那种不少满足 spec 任何一条的（例：#148 C1），出现在「已按规则处理」保持现状；已做的让 spec 某条只达成一部分的（例：#55 题 10），仍停下问人。
3. **期望行为**（对应问题 3）：会话停不停下问人，只看 home 固定文案的「只由我做」「停下问我」；改范围改的是插件里那一份固定文案，跑一次 setup 每台设备都生效。插件里不再有 `decision-rules` 这个名字，开场不再注入它；子代理也读得到这些范围。
4. **期望行为**（对应问题 4）：一台新设备跑完 setup，`~/home/AGENTS.md` 里有固定文案的几节；交给人的消息（给人自己，或以人的身份发给别人）开头三句依次是问题（落到具体对象）、解法（第一次出现的叫法带半句说明）、要对方做什么；后台起的活跑完，不等人问就说一句结果。

## 实现决策

- **实现从 #432 合入后的集成分支起**：#340 的 PR #432 已合进 `release/idea-loop-0.2.0`（`f12f7edc`），本 issue 改的是它重写后的 decision-rules、pr-review、pr。#438 排在本 issue 后面，从本 issue 搬好的 `idea-loop:evidence` 和固定文案「证据」一节往下升级。
- **删除不留旧名**：`decision-rules` 目录、引用、注入名、提示词键一次改完，不留重定向（同 #340「合并的 skill 删除」：0.2.0 一次发布、不留中间状态）。
- **不留旧节**：「依据冲突或没有」整节删。「已按规则处理」这个节名保留：pr-review、pr、implement、`dyna pr candidates` 都按它找（同 ADR-0035「不改名」的理由）。
- **固定文案不带任何项目的信息**：举例用通用例子，不写 #164、Toeflair 这些出处（AGENTS.md「插件里不出现任何项目的信息」；`no-project-leak.test.mjs` 守着，把固定文案那份文件加进它扫的范围）。出处留在本 spec 和人自己写的节里。
- **固定文案里的「我」是用这台设备的人**：home 是人的私有仓库，固定文案写成人对 agent 说话，跟人手写的节同一个口吻。
- **扩展 `dyna home config`，不新做命令**：home 的 AGENTS.md 已由它写（`claude-md` 项把旧文件搬进来，放在 idea-loop 的节之前），加一项最省（`~/.claude/CLAUDE.md`「做方案」：先扩展已在用的工具）。
- **通用护栏挪进固定文案、插件特有的回到用它的 skill**：固定文案每个会话、每个子代理都加载，护栏写两处会两处说法不一（问题 4 的根因）；SEO 例外只在 pr-review 合并时用，「新词只在 grill 里加」只在写术语表时用。
- **证据原样搬，不改字**：本 issue 只换位置，证据的写法、形态、视频、评测样本都归 #438，两个 issue 不改同一段文字。
- **只读搜索子代理（Explore）不加载 home**：实测如此，记成已知限制；它只搜、不做决定。

### 固定文案的原文（草稿，待人审，见「待定」）

节名是新叫法，按护栏由人定。「决策」一节沿用 2026-11-19 人定稿的原文（[[280]] 题 5），四条原则由 2026-11-20 人批的三步草稿（[[280]] 题 7）改来：2026-11-22 人参照一篇帖子里的 10 句 Prompt，加了「先确认问题」（问题重定义、找根因）和「往下多推一步」（二阶影响、自找漏洞），并定「这四句话其实并非是4个步骤，而是工作的四个原则」；又定固定文案是全局的工作原则，不提 spec：「考虑到这个是全局的工作原则，我建议将spec去掉」；「沟通」取 #427 的新文和人手写「沟通风格」「以我的身份对别人说话」里通用的几条；人定「无论是跟我沟通，还是以我的身份跟别人沟通，接收方都是人，我倾向于都是按照指定统一的原则来说」，三句话开头是人「自己在工作中总结出来的内容，并且参考了elon musk的工作风格」；「证据」是简要定义，各形态做法归 #438。

> ## 思考与决策
>
> 思考和决策都守这四条原则：
>
> - **先确认问题。** 不默认交代的问题定义就是对的：分清症状和原因、手段和目标，修问题先找到根因。有更值得解决的问题，直接指出来；我已经定下的不自己改，摆给我。
> - **目标说得出来。** 目标是我交代的事里的一句原话（写成了文档的，引文档里的原文），或用户的一条真实路径（哪个页面、哪类用户）。说不出，就停下问我。
> - **往下多推一步。** 每种做法沿这条路径走一遍，看它对目标是达成、达成一部分还是没达成；再看它对别的模块、用户行为、复杂度和长期维护的影响。选定前自己找一遍它的漏洞。
> - **目标先于省事。** 选达成目标、往下推的影响也能接受的那种；几种做法结果相同，才比改动大小和代价。
>
> - **只由我做**：合并改了代码的 PR；动生产数据；真实支付；对外发布；术语的起名、改名、定稿。
> - **停下问我**：
>   - 碰到时会悄悄出错的（没有提示、没人会发现）：写成一道题，推荐修。
>   - 说不出满足哪一条目标的做法。
>   - 方案的形状：做成什么样、解决到哪一步（我在场，当场定）。
> - **其余你自己定**：在交付里列进「已按规则处理」，一句话写做了什么、目标原文、为什么这个做法达成它；我说推翻就改回，之后同类不再自己定。
>
> ## 沟通
>
> 接收方都是人：我，或你以我的身份回复、评论、写文档时的对方。对谁都守同一套原则：
>
> - **三句话开头：问题、解法、要对方什么。** 每条交给人的消息（要人决定、要人看、汇报结果），开头三句依次说清：问题是什么（现象，落到具体对象：在哪、多少处、哪类用户）；解决方式是什么（里面第一次出现的字段、机制先用半句说它是什么）；要对方做什么（一个决定、一份资源或权限，或者「不用你做什么」）。三句之后只放对方做这件事用得上的过程、证据和细节：删掉一段对方照样能做，那一段就删。
> - **叫法落到具体对象。** 对方没见过的叫法、机制、文件，第一次出现时说清它是什么、在哪；指一样东西说到对方能找到它，不用「这个」「上面那个」和裸编号。
> - **要对方定的写成一道题。** 选项之间差在对方能感到的地方，每个选项配一个真实例子，给推荐和一句理由。
> - **后台的活不沉默。** 起了要过一会儿才有结果的事，说在等什么、大概多久、我怎么知道结果；结果回来时哪怕不用我做什么，也说一句做完了什么、现在到哪了。
> - **以我的身份说话时**：不署名，不加机器人标识；回复和评论发出后内容变了，不改原文，另发一条写清改了什么、谁定的（只改错字、格式的可以直接改）；文档和 PR 描述直接改成最新。
>
> ## 证据
>
> 我判断不了实现细节，只能看证据。
>
> - 关于现状的话带出处（在哪、什么时候、对着哪个版本查的）和数字；查不到就说查不到和原因，不估。
> - 摆给我的问题先证明它真的会发生：找到能走到它的真实路径；找不到、只是理论上可能的，记成已知限制，写一句让我知道。
> - 复现才是证据，比对在同样的条件下做。
> - 能用图、截图、改前改后、一个真实例子说清的就用它，放在它支撑的那句话旁边；各形态怎么做照 `idea-loop:evidence`。

### 待定：固定文案的节名和原文

依据为什么没有：节名是新叫法（护栏：术语的起名只由人定）；原文是人自己的规矩，每个会话都加载，「沟通」里「三句话开头」跟人现在手写的「结论在前，第一句就是结果或要我做的事」说法不同，要人定用哪种。

评判标准：好的固定文案，换一台没有任何项目的新设备读也成立（不提具体项目），每条是 agent 能照着做的动作；不好的，是只在这台设备上成立的偏好，或是一句原则、读完不知道该做什么。

- A 照上面的草稿定（推荐）：节名「思考与决策」「沟通」「证据」，「三句话开头」放在「沟通」第一条。例：#164 那道 `disallowedTools` 的题，开头第二句就得写「`disallowedTools` 是 agent 定义里禁用工具的名单」，人不用追问。理由：三句话开头是你 2026-11-22 定的方向，「结论在前」的意思被「问题」「要我什么」两句盖住了。
- B 改节名或改原文：直接在这份草稿上改。

### 你手写的「沟通风格」里跟固定文案重复的段落：你自己删

人的决定（2026-11-22，本会话）：「我自己删重复的」。跑 setup 时 `dyna home config plan` 把人手写的节里跟固定文案重复的段落列出来（这台设备上是「沟通风格」的「结论在前」「把实现翻译成我认识的东西」「证据贴着结论」「要我定的事写成一道题」「后台的活不沉默」五条，加上整节「以我的身份对别人说话」），删由人自己在 home 提交；setup 不改人写的字。「用我说的语言回复」「做方案」「可视化内容」是人个人的规矩，原样留着。
