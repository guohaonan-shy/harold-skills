# 02 — 端口验证技能吸收翻译机制，成为一个技能

**Blocked by**：01
**设计冻结**：不涉及 UI

## 要建什么

原来消费侧 plugin 里有两个分工的技能：一个只管把预览 HTML 的改动翻译成真实 React 组件（分类哪些 CSS 是原型专属、哪些是已经共享的品牌类，把属性映射到 Tailwind 工具类，把预览里的精确像素值对齐到 Tailwind 的离散刻度，识别一处改动是不是引入了新数据而不只是样式（这种情况需要真实的类型/后端契约改动，不能只改 JSX），按状态归属而不是预览扁平的 DOM 嵌套去找该改哪个组件，把命令式的 DOM 操作改写成 React 的声明式模型，在三档真实尺寸下复核有没有溢出）；另一个只管验证已经翻译完的端口是不是忠实还原预览（复用同一套人工复核-diff 循环机制，反方向跑：预览 HTML 是真值，线上路由是候选）。

这次要把翻译机制并入验证技能，让它变成一个技能，同时覆盖"把预览 HTML 的改动翻译进 React"和"验证端口是否忠实"两件事。不再保留一个独立的翻译技能——下游只需要认识、调用这一个技能。

合并进去之后，原来验证技能已有的触发场景（预览 HTML 已经落地、需要核对线上 React 路由是否一致）和原来翻译技能已有的触发场景（预览 HTML 有改动、要落进真实技术栈）都要能被这一个技能覆盖，调用方不需要先判断"这次是翻译还是验证"再去找两个不同的技能。

## 验收标准

- [ ] 端口验证技能的说明文本里能找到完整的翻译机制指导，不再只是一套验证协议
- [ ] 新 plugin 树里不存在独立的端口翻译技能
- [ ] 人工核对一次完整链路：给一段预览 HTML 的改动，按合并后这一个技能的说明，能一路走到"翻译进 React"再到"验证端口忠实"，中途不需要切到另一个技能

## 选中的存量回归

无 test-cases 库，本仓库也没有既有的自动化测试套件——本次验收全靠上面这几条人工核对。
