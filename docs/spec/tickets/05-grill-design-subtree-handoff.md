# 05 — grill 的设计子树：分叉转交 design，返回结果继续 frontier

**Blocked by**：01
**设计冻结**：不涉及 UI（这张 ticket 本身是在打通设计工作流的接入通道，不产出任何具体页面的设计）

## 要建什么

grill 的决策树不再假设设计是一条独立的、每次都要单独走一轮的轨道——设计形状的决策是挂在某个产品功能决策节点下面的子树，只有当确认某个产品决策需要设计层面的取证才能给出靠谱推荐答案时，这棵子树才长出来。

子树需要取证时，走的是 grill 自己"事实是模型的活、决策是人的活"这条既有原则的延伸：派一个纯粹做研究、不需要人介入的 subagent 去查设计参考研究（视觉方向、具体 UI 模式、多步骤流程这三层，取哪层取决于这条 frontier 问题实际需要哪层的事实），取证结果回到主会话，用来支撑这条 frontier 问题的推荐答案。设计相关的推荐必须有这类真实取证支撑，不能是模型凭印象编的。

frontier 完全清空之后（产品决策和设计的结构选择都已经拍板），才一次性 handoff 给设计总入口——用跨 plugin 的方式调用它，因为这时已经没有需要问的东西了，构建段本身不需要中途交互。设计总入口走完自己的候选生成/人工选择/下游路由/收尾把决策写回项目设计语言文档之后，把产出（预览 HTML 路径 + 冻结状态摘要）作为这条分叉的答案带回 grill 的决策树，grill 继续往下问其余的 frontier。

设计总入口被 grill 这样嵌套调用时，跳过它自己原生那轮"确认要设计什么"的澄清问答——这轮问答视为已经被 grill 的 frontier 覆盖了，避免访谈中途从连续编号问答切换成另一种问答格式。设计总入口被人直接单独调用（不经过 grill）时，仍然走它原生的完整流程，不受这条规则影响。

构建段跑完，人来判定这份设计产物满不满意——满意，才算这条 frontier 子树清空，可以往下走到落盘规格这一步；不满意，回到新一轮 grill 重新审视相关的产品决策，不是回到设计总入口内部原地调视觉细节。这个"不满意"信号被当成"可能是某个产品判断需要重新审"来处理，不是默认当成"视觉细节没调好"。

如果目标项目缺设计语言文档/产品说明文档，grill 的设计子树要把"建立这两份文档需要拍板的核心判断"当成新解锁的 frontier 节点问出来，不是悄悄推迟到后面另起一次交互。

顺带把设计总入口自己那条"结构已经谈拢就跳过候选生成"的分支重新措辞一遍：在 grill/规格/切票这条链路的语境下，结构通常已经在 grill 里谈定了，跳过候选生成是默认会走的路径；候选生成机制本体不变，保留给结构真正开放的场景（比如一个全新的、还没经过 grill 讨论的页面）。

## 验收标准

- [ ] grill 遇到设计形状的分叉时，能说清楚"什么时候该派 subagent 去取证、什么时候该整体 handoff"的判断依据，不是每次都强制单独拉一轮设计访谈
- [ ] 搭一个最小的目标项目骨架（含一份最小的设计语言文档），触发一次从 grill 到设计总入口的移交，能观察到产出的预览路径和冻结摘要
- [ ] 设计总入口被 grill 嵌套调用时，不会重复问 grill 在 frontier 里已经问过的问题
- [ ] 设计总入口被人直接单独调用时，原生的澄清问答流程不受影响

## 选中的存量回归

无 test-cases 库，本仓库也没有既有的自动化测试套件——本次验收全靠上面这几条人工核对（含一次真实的端到端干跑）。
