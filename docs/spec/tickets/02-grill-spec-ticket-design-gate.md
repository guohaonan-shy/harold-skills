# 02 — 访谈到切票这一段接上 prototype 与设计冻结闸门

**Blocked by**：01 — prototype
**设计冻结**：不涉及 UI

## 要建什么

让一次碰 UI 的需求能从访谈一路走到切票而不脱节：

- `grill` 的设计子树不再把整条高保真流水线甩出去。某条 frontier 问题文字定不了结构或行为时，把它压成一句话交给 prototype，人在原型里选，答案作为这条 frontier 的落定回到决策树继续问。
- `to-spec` 让"等设计冻结"成为一个真正会发生的状态：碰 UI 的 spec 就落这个状态，结构决策和原型指针记在实现决策那节，原型的 raw 在关联那节挂上。
- `to-ticket` 的设计冻结字段回到**只读 spec**：spec 已在飞且有冻结摘要就誊写，仍是等设计冻结就落 ⛔。切票不再依赖 cwd 里的临时文件，也不再依赖任何别的 plugin 的返回值。

做完这张，一个纯后端需求全程不会被拉去做设计，一个碰 UI 的需求会明确地停在"等设计冻结"，等后面的发散与收敛两段来解。

## 验收标准

- [x] `grill` 的设计子树**判据不变**：只有当某个产品决策需要设计层面的取证才能给出靠谱推荐答案时才长出来，不是每次涉及 UI 就强制拉一轮
- [x] `grill` 子树长出来后的动作改成：压成一句话 → 调 prototype → 人在原型里选 → 答案回决策树
- [x] `grill` 里「handoff 给设计总入口」「被嵌套调用时跳过 clarify」「不满意回 grill 而不是回设计」三条已删除，全文不再出现任何指向 `design` plugin 的调用
- [x] `grill` 缺 PRODUCT.md 时把核心判断当 frontier 问出来的规则**保持不变**；DESIGN.md 的建立不再由 grill 问，改由发散那一段负责，这一点在 grill 里写明
- [x] `to-spec`：碰 UI 的 spec 落 `等设计冻结`；实现决策那节记结构决策与原型指针；关联那节挂原型 raw；收工提示点名下一步是发散那个 skill
- [x] `to-ticket` 的设计冻结判定只有两条路：spec 状态在飞且实现决策里有冻结摘要小节 → 誊写（画布指针、matrix、mismatch 阈值、ledger 摘要一行）；spec 仍是等设计冻结 → `⛔ 未冻结 —— 不可开工`
- [x] `to-ticket` 里那段"产物从哪来、怎么誊写"的旧说明（依赖设计总入口带回路径）已删除
- [x] UI ticket 的验收标准里带 matrix 与阈值；非 UI ticket 不受设计冻结影响，可与设计并行
- [x] 黑盒可证伪：给一份仍是 `等设计冻结` 的 spec 切 UI ticket → 字段落 ⛔；给一个纯后端问题跑访谈 → 全程不触发 prototype
- [x] 三份 SKILL.md 各自主体仍 < 5000 字

## 选中的存量回归

本仓库**无 test-cases 库**，真实存在的套件只有 design 插件里 lint 规则的 node 单测，本张不碰。

需要人工回归的是**上一段的接缝**：`to-ticket` 之后 `implement` 会读设计冻结那一行并据此拦下开工，本张改了这行的产生方式，所以要确认 `implement` 的拦截判据仍能命中（它看的是 ⛔ 这个标记本身）。
