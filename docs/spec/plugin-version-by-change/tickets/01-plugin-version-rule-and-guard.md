# 01 — 改了插件就必须升版本：规则写进 REVIEW.md，漏升时测试红

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

这个仓库是一个 Claude Code marketplace，每个顶层目录是一个插件；带 `.claude-plugin/plugin.json` 的那些有一个 `version`，装了插件的项目按版本号取插件——版本号不变，改动就到不了人手上。现在改了插件的 PR 经常不升版本（2026-10-30 起合进 main 的 27 次插件改动里 20 次没升），升了也一律升 patch。

做完后：

1. 一个 PR 只要改了某个插件目录下的任何文件，而那个插件的 `version` 没有比主分支远端（`origin/main`）上的版本大，全量测试就红，报出是哪个插件、主分支上是哪一版、提示按三档规则升。没改插件的 PR 不受影响。主分支已经被别的 PR 升到同一个号（撞号），同样红，提示从主分支的新版本重新升。
2. 仓库根 `REVIEW.md` 的「额外要求」多一条三档规则（文字见下），审查者对着它核档位。
3. 根目录 `AGENTS.md` 里「说一个 plugin 的 PR 可以合并……一并说它合并后随哪个版本发」那句改写成跟新规则一致：说可以合并、或交审核报告时，一并说它升到哪一版、哪一档；没碰插件的，说「不碰插件，不升版本」。原句里「不升的，写明它会跟着哪个版本一起发」和那个 0.1.7 / 0.1.8 的例子去掉。

`REVIEW.md` 新增条目的文字（照抄）：

> 改了某个 plugin 目录下任何文件的 PR，交审核报告前按改动的性质升它 `.claude-plugin/plugin.json` 的 `version`，三档取最高的那一档：
> - **major**（1.0.0）：装了它的项目不改自己的配置或用法就会坏，比如删掉或改名一个 skill、改了一个 skill 的调用参数、产物换了位置。
> - **minor**（0.1.0）：新增能力，或改了流程的行为但老用法照样能用，比如加一个 skill，或者某个流程从停下等人改成自己执行。
> - **patch**（0.0.1）：不改行为的修正，比如修错字、修 bug、修说明里前后不一致的地方，以及只改 README 或测试。
>
> 定了哪一档、为什么，写进 PR 描述的「参考」。版本号从 main 上的当前版本往上升；合并前 main 已经升过（别的 PR 先合了），就从 main 的新版本重新按同一档升。`scripts/plugin-version.test.mjs` 守着「改了就必须升」。

检查的定法（spec「实现决策」定下的）：

- 测试放在仓库根下新建的 `scripts/` 目录，文件名 `plugin-version.test.mjs`，**不放进任何插件目录**（放进插件会随插件发给别的项目）。`REVIEW.md`「验证命令」表里的全量测试命令现在只匹配 `*/scripts/*.test.mjs`，改成同时带上根下 `scripts/*.test.mjs`。
- 插件 = 带 `.claude-plugin/plugin.json` 的顶层目录（`excalidrawer` 没有，自然跳过）。
- 改动 = 当前分支与基准 ref 的分叉点到**当前工作区**的差异（含未提交、未跟踪的文件）；版本对比用基准 ref 上的 `plugin.json`，当前版本读工作区。基准 ref 默认 `origin/main`，可用环境变量换成别的 ref（用于在历史状态上演示红）。基准 ref 不存在时跳过并说明原因。版本按 `x.y.z` 三段数字比大小；基准上还没有这个插件（新插件）就不要求。
- 判定逻辑写成纯函数（输入：改动文件列表、每个插件在基准上的版本、当前版本；输出：违规清单），单元测试喂构造的输入；另一条测试对真实仓库状态跑。
- 档位对不对不做机械判断。
- 这张工单本身不碰任何插件目录，不升任何版本。

## 验收标准
