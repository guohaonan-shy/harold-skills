# 01 — 回放用例多一种来源：从 spec 的期望写出的目标用例

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么
新加的能力没有出过错的历史、没有人当时的原话，现在写不出回放用例。做完后，写用例的人可以不填「人当时的原话」，改填「这道题出自哪份 spec 的哪条 User Story / 期望行为」，用例照样通过格式校验、照样用同一个 runner 改前改后各跑一遍、同一个评委判；评委看到的「这道题从哪来」那句话按来源换成对应说法。判法不变：改前「否」、改后「是」才过；改前就「是」仍判「用例没抓住问题」，对目标用例这条结论的说法是「不过：改前就做得到」，人判断换用例还是这段规则本来不用加（spec「实现决策」的「目标用例跑两边，判法同回放」一节）。

执行方读给 agent 的说明（改规则的工单怎么证明 skill 真的变了，implement 的参考文件）里，加上目标用例怎么写：来源字段指向哪、题怎么从那条 story 写出、提交号取基准分支上能让这个输入成立的提交、prompt 照旧不准出现会暴露在测的词。

## 验收标准
- [x] 用例格式校验：「原话」和「出自 spec 的哪条」二选一必填；两样都缺报缺，两样都填报冲突；只填「出自哪条」的用例通过。新测试先红后绿，照着现有必填字段的测试写。
- [x] 用例格式的文档注释写清新字段：它是什么、指向什么（spec 路径加 story 或期望行为的编号）、跟「原话」二选一。
- [x] 评委收到的提示里，「这道题从哪来」那一句：原话用例保持原样；目标用例写成「这道题是从 spec 里这条期望写出来的：<指向>」。有测试钉住两种说法。
- [x] 改前就「是」的目标用例，runner 给出的结论里能看出是「改前就做得到」，原话用例的结论说法不变。有测试钉住。
