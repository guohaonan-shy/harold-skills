# 09 — 规则回放的 runner 给老用例现搭临时 home，新用例记 home 的提交

**Blocked by**：01 — 认项目脚本会答「项目目录在哪」
**设计冻结**：不涉及 UI

## 要建什么

规则回放（`evals/retro/`）把一个历史决策点用改前、改后两版插件各跑一遍。现有的 13 个用例都钉在 home 出现之前的提交上，那时知识库在代码仓库里；改后的插件只认 home，在那些提交上会停下要求迁移。

- **老用例**：runner 在临时目录里现搭一份 home：把那个提交的 `docs/` 和引导文件复制进 `projects/<名字>/`，项目清单写上这个项目（远端取用例项目的远端、本地路径取 runner 检出的那份代码），`IDEA_LOOP_HOME` 指过去，传给改后那一侧的会话。改前的插件照旧读代码仓库里的同一份，两边输入相同。判定会话读产物时去这份临时 home 里找（产物路径要把临时 home 的位置告诉判定会话）。这个转换只活在 runner 里，skill 和脚本里没有。
- **新用例**：`case.json` 多一个可选字段 `home_commit`。有它时 runner 在临时目录里从 home 的这个提交切一份 home（home 仓库的位置从用例或 runner 的参数给），`IDEA_LOOP_HOME` 指过去，改前、改后两边都用它。
- runner 的纯函数部分（搭临时 home 要复制哪些文件、项目清单那一行怎么写、`IDEA_LOOP_HOME` 给谁）放在可单测的那一边，照现有回放决策函数的写法。

## 验收标准

- [x] 单测：给一个带 `docs/` 和若干引导文件的假代码仓库提交，搭出的临时 home 有 `projects/<名字>/docs/` 和那几份引导文件、项目清单有这一行，01 的 `where` 在它的 worktree 里认得出来
- [x] 单测：有 `home_commit` 的用例，两侧都拿到同一个 `IDEA_LOOP_HOME`；没有的，只有改后一侧拿到
- [ ] 用改后的插件跑一次现有用例 `draft-spec-orphan-capability`（size small）：临时 home 里有那个提交的 `docs/`，spec 草稿写进临时 home，判定会话的是/否题答「是」，与改前插件跑出的判定一致；跑不成的写明原因并 `⏭ 延后 → 10` ⏭ 延后 → 10：跑成了，临时 home 里有那个提交的 `docs/` 和引导文件，判定答「是」且与改前一致（都答是，runner 报「用例没抓住问题」：改前插件是 main，它已含这条 draft-spec 规则）；但 spec 草稿写在工作区的 `docs/`、没写进临时 home，因为 04–08 还没落地，改后插件的 skill 还不认 home。等 04–08 落地后由 10 重跑确认
- [x] 用例格式的说明（runner 的参考或 README）写了 `home_commit`
