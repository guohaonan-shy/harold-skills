# 06 — pr-review 的规则按 writing-for-agents 精简

**Blocked by**：03、04（都改过 pr-review 与 implement，已落地）
**设计冻结**：不涉及 UI

## 要建什么
pr-review 的规则正文约 1.6 万字符，远超仓库对 SKILL.md 主体 5000 字的要求，而且同一套动作写了好几遍，agent 读的时候注意力被摊薄。照 `idea-loop:writing-for-agents`（单一事实来源、就近归置、引导词、正向提示、分支放到指针后面）重写，**行为不变**：每个分支的做法和现在一样，只是写一次、放对层级。

要做的整理（人在会话里看过并同意放进这个 PR）：

1. **动作合成一张表**：「照规则的条目」的表和「人批示之后」的列表描述的是同一组动作（修 / 恢复、同步改、接受并补记、开 issue、不修），只是谁定的不同；「推翻」是同一组动作的撤回。合成一张表：每种动作一行，列出怎么做、链接记什么、被推翻时怎么撤；照规则 / 人批只是来源。
2. **「回工单」只写一次**：找归属工单 → 验收末尾追加一格 → 提交 → 派执行方，现在在人批了修、照规则修、推翻修、设计变更、交报告后 CI 红了五处出现。用一个引导词（如「回工单」）在一处定义，含按条目类型找归属工单的办法，其余处只引用它。
3. **一轮之后往哪走收成一节**：现在散在「人批示之后」末段、「没有要人定的：不等人，交审核报告」、「下一轮：什么时候自己起」三处。收成一节：前提是这一轮的条目都处理完（check 不列 + 逐题核过要你决定）；然后三选一——有修复且没跑满两轮 → 自动起下一轮；没有要人定的 → 交审核报告；其余 → 停下等人。
4. **「仍然停」改成指针**：和 `idea-loop:decision-rules`「不自动的」重复的几条只留指针，只保留 pr-review 特有的（跑满两轮、第 2 轮修复刚落地）。
5. **「改 spec / 工单就单独提交并推送」开头说一次**，各动作里不再重复。
6. **删空操作和否定句**：「只有这几种……不触发、不装 hook」「编排者不审代码、不改代码」这类，改成正向写法或删掉；pr-reviewer 内部等多久这类它自己定义里的细节不在这里写；回放排队的前提改成一句指向 implement 已核过的那一处。
7. **只有部分分支走的挪出正文**：UI 走查（有设计产物才起 ui-reviewer、给的指针、走查未完成的处理）挪进 pr-review 自己的参考文件；「设计变更：人接受了跟画布不同的设计」只留 `idea-loop:design-change-sync` 一个来源，pr-review 和 implement 各留一句指针（implement 里那一节同样收成指针，它与 pr-review 只差提交推送到集成分支还是 PR 分支，这个差别写进指针那一句）。
8. **「在会话里给人看」拆短**：补链接、同步文件、第 1 轮补 implement 期间开的 issue、推送通知、缺词，拆成几步或把偶发的放下去。

## 验收标准
- [x] pr-review 的 SKILL.md 主体不超过 5000 字符（按字符数，`wc -m` 去掉 frontmatter 计）；做不到的，把差多少和卡在哪写进交回
- [x] 上面 1–8 每条都做到；每个原有分支（照规则处理、人批示的每种、推翻、设计变更、UI 走查与未完成、交报告、自动下一轮、跑满两轮、合并）在新文本里都找得到去处，交回里给一张「原分支 → 新位置」对照
- [x] implement 的「设计变更」一节收成指向 design-change-sync 的一句，行为不变
- [x] 挪出去的参考文件只被 pr-review（和它起的 agent）读；正文里指向它的那句写明什么情况下去读
- [x] 全量套件全绿（仓库里有对 pr-review / implement 文字的文档测试，要随之更新而不是删掉断言的意思）
- [x] 在 retro 回放用例 `review-no-decision-report` 上跑一次改后（当场跑，`--base origin/release/idea-loop-0.1.8`），仍答「是」：精简没有把「无事不等、交审核报告」改丢
