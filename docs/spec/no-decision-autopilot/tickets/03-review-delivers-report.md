# 03 — review 没有要人定的就不等人，交一份审核报告

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么
idea-loop 的 pr-review 一轮跑完、没有修复时，现在停下「等人说合并或再跑一轮」；人说合并之后才推「spec 翻完成、删工单」那个只改 docs 的提交，这个提交又让整条 PR 的 CI 重跑一遍（#418 因此多了三轮「CI 绿了，合并」→「其实还在跑」的往返）。

改完后：
1. 一轮 review 里没有「要你决定」、也没有要修的（或要修的都已落地、下一轮也干净了），编排者不停下等人，直接往下：
2. 先做「spec 翻完成、删这个 PR 落地的工单」，作为一个只改 docs 的提交推到 PR 分支，等这次推送触发的 CI 全绿；
3. 再把**审核报告**写进 PR 描述，在会话里给人看并停下。审核报告的读者是没跟过这件事的人，一份讲完：问题是什么（复现现象 + 规模数字）→ 怎么修（照规则定的做法及依据，含切法：每张工单的标题、被谁挡着、端到端行为）→ 怎么验证（验成的、没验成的及原因）→ 顺带开的 issue → 要你做的事（推迁移、合并）。PR 描述和 review 结论都收进这一份，不再是「PR 描述不放 review」。
4. 人说合并：合并步骤里不再有「spec 翻完成、删工单」这一步（已经提前做了），只剩归档 review loop 和合并本身，不再等 CI。

仍然停的不变（决定规则「不自动的」）：有决定题、人验素材、生产写操作、合并改了代码的 PR、设计相关的停点（冻结、ui-measure、归档草稿过目）。有设计产物要归档的 PR，归档那一段仍在人说合并之后照旧走。

PR 描述的格式说明（PR 描述有哪几节、每节写什么）同步成审核报告的形状；描述由固定的几节组成、由脚本写入，新形状若需要新节（例如「问题」），脚本跟着认它，并补单元测试。

## 验收标准
- [ ] pr-review 写明：一轮没有「要你决定」、没有待落地的修复时不等人，进入交审核报告
- [ ] pr-review 写明交报告前的顺序：先推「spec 翻完成、删工单」的 docs 提交，等 CI 绿，再写报告、停下
- [ ] 合并步骤里删掉人说合并之后的「spec 翻完成、删工单」，合并时不再等 CI
- [ ] PR 描述的格式说明给出审核报告的五段（问题 → 怎么修 → 怎么验证 → 顺带开的 issue → 要你做的事），读者设定为没跟过这件事的人，删掉「PR 描述不放 review」的说法
- [ ] 若 PR 描述脚本加了节：单元测试覆盖新节能写入、顺序固定、正文里有代码指称时照旧拒写
- [ ] 仍然停的几种情况在 pr-review 里写明，有设计产物的归档仍在人说合并之后

## 选中的存量回归
- PR 描述脚本的现有单元测试：加节会动节的顺序与旧节兼容。
- review loop 脚本的现有单元测试：合并前检查依赖它的判法。
