# 07 — 根 issue 有一份薄的根 spec，集成审查拿它当参照

**Blocked by**：05（根 / 子会话分工与集成审查，已落地）
**设计冻结**：不涉及 UI

## 要建什么
现在根 issue 没有自己的 spec：版本根的会话在集成 PR 上跑审查时，审查者只拿到一串子 spec，不知道这几份之间约好了什么（共享文件里谁改哪一处、谁先合），查冲突没有参照。人定下（2026-10-30）：每个根都有一份薄的根 spec。

> 人的决定（2026-10-30）：「我其实觉得根issue也是需要一个spec的，不然pr-review没有参照。根spec里面要有对应issue spec的引用。」追问后选：薄的总纲；所有根（版本根和模块根）都写；放进这个 PR。

改完后：

1. **根 spec 写什么**：这一组要达成什么（版本根写版本号、模块根写哪个页面或模块）；子 spec 清单，每份一个链接加一句话；跨 spec 的约定（共享的文件或规则里每份 spec 各改哪一处、合并先后、谁依赖谁）。不写问题复现、user stories、测试决策（那些在子 spec 里），不切工单，自己不实现。格式写进起草 spec 的那份 skill 里，作为一种 spec 的写法；它要能被机械认出是根 spec（例如 frontmatter 标明它是根、列出子 spec），`issues:` 写根 issue 号。
2. **谁、什么时候写**：根的会话在审核阶段把子 spec 都 grill 完时写根 spec，跟子 spec 一起经 PR 合进主分支，然后才开子会话。issue 会话的规则写明这一步。
3. **状态**：根 spec 的状态只说文档成熟度。它不切工单，所以 spec 状态脚本对根 spec 放行「正式 → 实现中」（开子会话时翻），最后一个子 spec 完成、版本根的集成分支合回主分支时翻「完成」。根 issue 的 `status:*` 照旧跟着最慢的子 issue，issue 状态脚本不能因为根 spec 列了根 issue 就把根当成普通 issue 去推进或关掉（关根仍是最后一个子 issue 关闭时由根的会话做）。
4. **集成审查拿它当参照**：版本根在集成 PR 上跑审查时，给审查者的是根 spec 的路径，审查者从它的子 spec 清单找到各子 spec 与工单，按「跨 spec 的约定」逐条查守住了没有，再查几份合在一起的冲突。
5. **#165 的旧决定**：issue-consolidation 的 spec 里「根没有自己的 spec」已标为后来改了（本工单的 docs 提交里已做）；规则文字里所有「根没有 spec」的说法同步改掉。

## 验收标准
- [ ] 起草 spec 的 skill 写明根 spec 的写法（三块内容、frontmatter 怎么标根与子 spec、不切工单）
- [ ] issue 会话写明：子 spec 都 grill 完时写根 spec，跟子 spec 一起合进主分支，之后开子会话；版本根与模块根都写
- [ ] spec 状态脚本：根 spec 不切工单也能「正式 → 实现中」，普通 spec 照旧要工单；单元测试覆盖两边
- [ ] issue 状态脚本：根 spec 的 `issues:` 列着根 issue 时，根 issue 仍按「跟着最慢的子 issue、最后一个子 issue 关闭才关根」处理，不被提前推进或关闭；单元测试覆盖
- [ ] 集成审查：给审查者的是根 spec 路径，审查按跨 spec 约定逐条查；文档测试覆盖
- [ ] 规则与 README 里不再有「根没有自己的 spec」的说法；全量套件全绿
