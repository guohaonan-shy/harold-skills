# 05 — issue 会话：根与子会话分工，子会话收工停在审核报告

**Blocked by**：03（子会话收工停在审核报告，报告的形状由它定）；外部：#165（issue-consolidation）先把 issue 会话的「实现一律放在子会话里」结构合进集成分支 release/idea-loop-0.1.8，这一刀在它之上改
**设计冻结**：不涉及 UI

## 要建什么
#165 把实现一律放进子会话，但它写的是「issue 会话自己只管合并和收尾」。人在 grill 时定下了另一种分工（spec「审核报告写进 PR 描述，人在子会话里读、在子会话里说合并」一节）：

| | 根的会话 | 子会话（一份 spec 一个） |
|---|---|---|
| 做什么 | 前期 grill 全部 spec；根代表一个版本时，集成过程中的 pr-review 和合回主分支；最后一个子 issue 关闭后关根 | 切票、实现、它那个 PR 的 pr-review 和合并 |
| 人在哪说话 | grill、集成 PR 上的事 | 这份 spec 实现中的一切问题、它的审核报告、说合并 |

改完后 issue 会话照这张表写：
- 子会话的 PR：人在子会话里说「合并」，由子会话的 pr-review 合进集成分支（版本根）或主分支（模块根）。
- 根代表一个版本：第一个子 PR 合进集成分支后，根的会话开「集成分支 → 主分支」的 draft PR；之后每合进一个子 PR（子会话收工时通知根的会话），根的会话跑一轮 pr-review，查几份 spec 合在一起有没有冲突；全部合完、人说合并后，由根的会话合回主分支。
- 根代表一个模块（没有集成分支）：根的会话只管前期 grill 和最后关根，集成阶段不跑 review。
- 子会话实现不碰 UI 的 spec 时只在决定题、生产操作和合并前停；收工时交审核报告，停下等人在子会话里读、追问、说合并。碰 UI 的照旧每处停。
