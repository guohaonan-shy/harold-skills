# 实现阶段没有决定题就一路做到 PR，只在生产操作和合并前停

## 验证

| issue | 结论 | 证据 |
|---|---|---|
| #131 idea-loop：全程没有决定题的 issue 一路照规则做到 PR，只在生产操作和合并前停，交一份给不知情者的审核报告 | 存在 | issue 列的四处停点在 main 上都还在；详情在「问题」 |

## 问题

2026-10-30 对着 `origin/main`（da531af，idea-loop 0.1.7）读 skill 和脚本原文核过。

### 1. 切票后一定停下等人点头

`to-ticket` 的「把切法摆给人看」末尾是「迭代到人点头」，人点头后才落盘。#131 和它并进来的 #123 收集的记录里，人在这一步都原样放行：Tofelair#416、#527、#418 按推荐 3 次；本仓库的决定记录里切法按推荐 6 次（#51、#55、#108、#68、#115、#77），没有反例。

### 2. 停下汇报没有决定题也要等人批示

`implement` 的「没活了就停下」每次都写一条停下汇报，等人回复后处理。`review-loop.mjs` 判断条目处理完的规则里，review 轮和回放「没问人任何事、写了做了什么」就算处理完，停下条目则写死了「a stop report always does」：总要人批示。人在这一步的放行：#414、#418、#115、#77 各一次，都是「0 件要你决定、没有人验素材」的汇报，人回「可以」。

### 3. review 一轮没有要人定的也停

`pr-review` 一轮没有修复时「等人说合并或再跑一轮」。#418 全程审核、切票、实现、review 都没有决定题，人只做了推生产迁移和合并。

### 4. 合并前的 docs 提交在人说合并之后才推，触发一轮多余的 CI

`pr-review` 的 `references/merge.md` 第 4 步「spec 翻完成、删工单」在人说合并之后才推到 PR 分支。workflow 的 `paths` 对 pull_request 按整个 PR 的 diff 判，这个只改 docs 的提交会让整条 PR 的 CI 重跑。#418 里因此多了三轮「CI 绿了，合并」→「其实还在跑」的往返，还碰上一次卡住要重跑。

### 根因

不涉及（流程规则）：四处都是写死的「停下等人」，没有「这一步没有要人定的就继续」的分支。

## 方案

人最终得到：不碰 UI 的 spec，实现阶段只在三种情况下停：有要人定的决定题、要动生产（例：推迁移）、合并改了代码的 PR。其余步骤照规则往下走，最后交一份**写给没跟过这件事的人**的审核报告，人读完它就能决定合不合并。

审核报告一份讲完：问题是什么（复现现象 + 规模数字）→ 怎么修（照规则定的及依据）→ 怎么验证（验成的、没验成的及原因）→ 顺带开的 issue → 要你做的事（推迁移、合并）。PR 描述和 review 结论都收进这一份。交报告之前，「spec 翻完成、删工单」的 docs 提交先推上去，等它的 CI 绿了再交，人说合并就直接合。

同类入口（不再停的）：

- `to-ticket`「把切法摆给人看」：直接落盘，切法照写进报告（覆盖已关的 #123）。
- `implement`「没活了就停下」：没有决定题、没有未勾的人验项时，条目末尾记「做了什么」，直接 `gh pr ready` 进 pr-review。
- `review-loop.mjs` 的停下条目处理完判定：跟 review 轮一样，无「要你决定」且有「做了什么」即处理完。
- `pr-review` 一轮：没有「要你决定」、没有要修的，不等人，进审核报告。
- `pr-review/references/merge.md` 第 4 步：提前到交报告之前推。

仍然停的（`idea-loop:decision-rules`「不自动的」）：有决定题；人验素材；生产写操作；合并改了代码的 PR；设计相关的停点（冻结、`ui-measure`、归档草稿过目）。

## User Stories

只改流程、不加能力：每个问题一行期望行为。

1. 切票后不停：工单直接落盘，切法写进最后的审核报告。
2. 停下汇报没有决定题、没有未勾的人验项时，不等人，记下「做了什么」直接进 review；`review-loop.mjs check` 不再把它列成没处理完。
3. review 一轮没有要人定、没有要修的，不等人，直接交审核报告。
4. 「spec 翻完成、删工单」的 docs 提交在交报告之前推，CI 绿了再交；人说合并就直接合，不再等 CI。

## 实现决策

### 停与不停照 decision-rules 的「不自动的」

依据：`idea-loop:decision-rules`「不自动的」原文（人验素材、动生产业务数据、合并改了代码的 PR 只由人定），和 #131 原文「仍然停的：生产写操作（例：推迁移）；合并改了代码的 PR」。设计相关的停点不在 #131 的范围里，照旧。

### 停下条目的处理完判定跟 review 轮一致

`review-loop.mjs` 里停下条目改成：有批示的看批示后有没有「做了什么」；没批示的，无「要你决定」且有「做了什么」即处理完。依据：#131 原文「要改成和 review 轮一样：无『要你决定』且有『做了什么』即处理完」。带人验素材的停下照旧要人：素材本身是给人验的（「不自动的」）。

### docs 提交提前推

依据：#131 原文与 #418 的三轮往返。merge.md 第 4 步移到审核报告之前；人说合并后只剩归档 review loop 和合并。

### 这条路走所有不碰 UI 的 spec

人在本会话定下（2026-10-30）：「我觉的可以放宽到所有不碰UI的，grill我到时候看spec和pr，也可以问你问题」。

#165 定了审核在根的会话里 grill 完、实现一律放进子会话（[[issue-consolidation]]），所以进入实现时该定的已经定了：不碰 UI 的 spec，不管审核时 grill 过没有，实现阶段都只在新冒出的决定题、生产操作和合并前停。碰 UI 的照旧每处停，等这条路跑过几次再说。人要追问，看 spec 和 PR 时随时在会话里问。

### 审核报告写进 PR 描述，人在子会话里读、在子会话里说合并

人在本会话定下（2026-10-30）：「子会话的问题，我仍然是在子会话里面沟通吧，另外子会话实现的spec的pr-review是不是也放在子会话最好。根会话主要是前期的grill 以及 不断集成过程中的pr-review?」；三个细节「是，三个细节都按推荐」。

| | 根的会话 | 子会话（一份 spec 一个） |
|---|---|---|
| 做什么 | 前期 grill 全部 spec；根代表一个版本时，集成过程中的 pr-review 和合回主分支；最后一个子 issue 关闭后关根 | 切票、实现、它那个 PR 的 pr-review 和合并 |
| 人在哪说话 | grill、集成 PR 上的事 | 这份 spec 实现中的一切问题、它的审核报告、说合并 |

- 子会话的 PR：人在子会话里说「合并」，由子会话的 pr-review 合进集成分支（版本根）或主分支（模块根）。
- 根代表一个版本：第一个子 PR 合进集成分支后，根的会话开「集成分支 → 主分支」的 draft PR；之后每合进一个子 PR（子会话收工时会通知根的会话），根的会话跑一轮 pr-review，查几份 spec 合在一起有没有冲突；全部合完、人说合并后，由根的会话合回主分支。
- 根代表一个模块（没有集成分支）：根的会话只管前期 grill 和最后关根，集成阶段不跑 review。

审核报告写进子 PR 的描述，读者设定为没跟过这件事的人；子会话收工时停下等人，人在子会话里读、追问、说合并。

## Out of scope

- 设计阶段（imagine、refine、冻结）的停点不动：#131 只管实现阶段。
- 审核阶段的 grill 不动：有要人定的照旧在根的会话里问。
- 生产写操作、合并改了代码的 PR 照旧由人定。
