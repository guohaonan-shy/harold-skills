# 02 — 卡住的工单叫回原执行方

**Blocked by**：01 — implementer 按工单挑 skill、读写法规范、spec 全文可读（两张都改 implementer 定义的「输入」一节）
**设计冻结**：不涉及 UI

## 要建什么

现在一张工单卡住（执行方交回 `blocked` 或 `failed`）、人做完决定之后，编排者（`idea-loop:implement`）总是新起一个执行方，从上次的半成品分支接着做；上一个执行方为什么卡住、看过哪些代码，都要重新摸一遍。改成能复用就复用：

- **账本记 agent id。** 等决定的账本 `pending.md` 每条现在记工单号、问题、选项、推荐、半成品的 worktree 和分支，再多记一项：原执行方的 agent id（起它时 Agent 工具返回的那个）。会话被压缩或重启之后，靠这一项找回它。
- **人回复后先叫回原执行方。** 决定（含设计变更）、推翻写进工单并提交之后，工单要重新做时：pending 里有 agent id、它的 worktree 还在，就用 SendMessage 叫它回来，消息只给指针：「人的决定已写进工单 <路径>，提交 <SHA>」，加上要它先合进来的集成分支最新提交。它照常交回，编排者照常核对、落地、回收。SendMessage 报错（id 找不到、会话重启过）或没记 id，照现在的做法新起一个执行方，带上半成品分支。
- **已经落地的工单照旧新起。** 人验反馈、review 里的修、推翻已经落地的工单，这时执行方的 worktree 已经回收了，照现在的做法新起；「回收」的时机不改。
- **implement 开头「每张工单的执行方都是新上下文」** 改成跟上面一致的说法：每张工单第一次派出时是新上下文，卡住后可能被叫回。
- **implementer 定义的「输入」**：「这张工单不是第一次做」那条补一句：可能是同一个你被 SendMessage 叫回来，这时先把集成分支的最新提交合进来，再只做没勾的格。

人的决定（来自 spec）：「把能复用原来的ticket 的agent这条加上」；只复用卡住的，落地的照旧新起（人选了「只复用卡住的」）。已知代价是人知情后选的：隔得久时叫回来要重读整段旧上下文，所以新起这条路作为兜底保留。
