# 01 — issue 正文的「背景」改成必填

**Blocked by**：无——可立即开工
**设计冻结**：不涉及 UI

## 要建什么

idea-loop 插件里，开 issue 有一个统一的正文校验：`issues new`（开 issue）和 `issues body`（只校验，Linear 项目开 issue 前跑）都用它，现在只要求「问题」「证据」「影响范围」「从哪发现」四节在且不空，「背景」是可选节。做完之后：

- 正文缺「背景」节，或这一节只有空白，两个命令都拒绝，错误信息说出缺的是「背景」（跟现有四节的报错同一种说法）；`issues body` 退出 1，`issues new` 不调用创建。「背景」下写「无」算填了。
- `idea-loop:issues` 这个 skill 的「正文」一节：格式代码块里「背景」放第一行、标「必填：读懂问题要先知道的机制或现状」；代码块下面加一段完整说明，原文照抄：「读懂问题要先知道的机制或现状，写给隔了几周回来、已经忘了这一块的人：问题里第一次出现的叫法（规则名、字段、页面、命令）各用一句说清它是什么、管什么；规则或现状互相牵扯的，写出各自原文和出处。确实不需要的写『无』。」
- 同一 skill 的「开一个 issue」：开头说校验「四个必填节」的地方改成五个；第 1 步「写给一个没有上下文的人看」后补「，包括几周后的自己和人」。
- seo-scan 自动开 issue 的脚本（`seo-issues`）自己拼正文、过同一个校验。给它拼的正文加一节「背景」（放第一节），固定文字，说清三件事：这是 seo-scan 在哪天、哪个方向（用方向的中文名）提出的；「怎么复现」可以独立重跑；「建议的修法」是扫描时的判断，triage 时要核。做完后扫描照常能开出 issue。
- pr-review 合并后上线自查回滚时另开 issue 的那一步（pr-review 的合并参考里，列了正文各节写什么的那句），补上「背景：原 issue 改的是什么、上线自查查的是什么」。
- 插件 README 若描述了正文的必填节，同步；`plugin.json` 的 `version` 按 minor 升一档（从 main 当前版本往上）。

## 验收标准

- [ ] 一份四节齐、没有「背景」的正文跑 `issues body`：退出 1，输出含「背景」。先写这个测试，看它在改动前是红的。
- [ ] 「背景」节存在但只有空白：被拒，报「「背景」一节是空的」。
- [ ] 「背景」下写「无」：通过。
- [ ] `issues new` 遇到缺「背景」的正文：拒绝，不调用 gh 创建。
- [ ] seo-issues 拼出的正文过校验，且带「背景」一节，内容含扫描日期和方向中文名；seo-issues 现有测试全绿。
- [ ] skill 文档钉子测试钉住：「正文」一节含「## 背景」且标必填，「开一个 issue」写的是五个必填节。
- [ ] `idea-loop/scripts` 下全部测试绿（`node --test`）；`issues.mjs` 里描述必填节的注释同步成五节。
- [ ] `idea-loop:issues` 的 SKILL.md 主体 < 5000 字（量法见仓库 `AGENTS.md`）。
- [ ] `plugin.json` 版本按 minor 升了，`plugin-version` 测试绿。

## 选中的存量回归

- `issues.test.mjs` 的正文校验与 `new` 的几条：本次直接改它们依赖的必填节清单，现有的 GOOD_BODY 夹具会因清单变化而变红，要随之更新。
- `seo-issues.test.mjs` 里「正文过校验」的几条：seo 正文不补背景就会全部被拒。
- `issues-skill-doc.test.mjs`：钉着 skill「正文」一节的格式。
- `seo-live-record.test.mjs`：读回滚 issue 的正文，确认加节不影响它的识别。
