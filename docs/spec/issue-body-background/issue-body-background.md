# issue 正文必须写背景

> #297 存在：只写四个必填节、没有「背景」的正文，`issues body` 打印「正文齐了」、退出 0，照样放行；详情在「问题陈述」

## 问题陈述

### 正文只写现象，隔几周回来的人读不懂

开 issue 的会话照 `idea-loop:issues` 的「正文」写完「问题」「证据」「影响范围」「从哪发现」四节就算合规，「背景」是可选节。读正文的人（triage 会话、隔了几周回来的人）不知道问题里那些叫法是什么，只能靠回忆或重新查代码。

真实例子：harold-skills#69（设计档案：入口是加载中的长页面，加载完的状态不能分段）。正文直接引用「入口是加载中」「design-archive.md §3『分段』」，没说档案里「状态」「分段」是什么、两条规则各管什么。2026-11-12 triage 会话请人定「谁能声明分段」时，人回：「这个issue你能给我讲述下吗？时间有点久我有点遗忘了」，会话只好补讲一遍。2026-11-13 retro 里人说：「我反而觉得这个case的根本是在书写issue的时候要把这些上下文整理好，而不是重新描述问题靠我回忆。」

测了什么：2026-11-16 对着 `main`（5f26e2f）写一份四个必填节齐全、没有「背景」的正文（内容取 #69 的现象），跑 `issues body docs <文件>`。看到什么：打印「正文齐了」，退出 0。本该是：缺「背景」被拒，并说缺哪节。

复现材料：`.tmp/297/nobg.md`

### 根因

- `idea-loop:issues` 的「正文」一节把「背景」标成「可选：读懂问题要先知道的链路或现状」；「开一个 issue」第 1 步只说「写给一个没有上下文的人看」，太泛。
- `issues.mjs` 的必填节清单只有「问题」「证据」「影响范围」「从哪发现」四个，`issues new`、`issues body`（Linear 项目开 issue 前跑的）都只查这四个。

修正：issue 验证步骤写「先用 #69 的原正文跑一遍，看它被拒」。#69 现在的正文连「证据」等必填节都没有，会因缺那几节被拒，不是因为缺「背景」；红灯用例改用「四节齐、只缺背景」的正文（分拣评论已指出）。

## 方案

改完：任何经 `issues new` / `issues body` 的正文，缺「背景」节或这一节是空的，都被拒并说出缺的是「背景」；开 issue 的会话照新的格式说明写背景，写给隔了几周回来、已经忘了这一块的人。

两条开 issue 的路都过同一个正文校验（不画时序图：只有脚本内的一次校验，没有模块间的消息变化）：

- 开 issue 的会话写正文文件 → `issues new` / `issues body` 校验必填节 →【改】缺「背景」或为空就拒、说缺哪节；过了照旧开 issue / 打印「正文齐了」。
- seo-scan 的发现 → `seo-issues.mjs` 拼正文 →【改】多拼一节「背景」→ 同一个校验 → 开 issue。

这次改的四处（都是给 agent 读的文档或它们调的脚本；对的杠杆是「规则写在每次开 issue 都会读到的那一节，并由脚本机械地拦」）：

1. **`idea-loop:issues`「正文」一节**：「背景」从可选改必填，放在第一节，说明换成 issue 里人批过的新文：「必填：读懂问题要先知道的机制或现状，写给隔了几周回来、已经忘了这一块的人：问题里第一次出现的叫法（规则名、字段、页面、命令）各用一句说清它是什么、管什么；规则或现状互相牵扯的，写出各自原文和出处。确实不需要的写『无』。」代码块里每行一节的格式放不下这么长的话，代码块那一行只写「必填：读懂问题要先知道的机制或现状」，完整新文写在代码块下面一段。
2. **「开一个 issue」第 1 步**：「写给一个没有上下文的人看」后补「，包括几周后的自己和人」；同节开头「校验正文四个必填节」改成「五个」。
3. **`issues.mjs` 必填节清单**：加「背景」。`issues new` 和 `issues body` 共用这份清单，一起生效；Linear 项目开 issue 前跑的就是 `issues body`，也一起生效。
4. **`seo-issues.mjs`（seo-scan 开 issue 的脚本）**：它自己拼正文，也过同一个校验；不补「背景」，每次扫描的 issue 都会被拒。补一节固定的「背景」：这是 seo-scan 哪天哪个方向（方向的中文名）提出的、「怎么复现」可以独立重跑、「建议的修法」是扫描时的判断要在 triage 时核。

同一行为的其他入口：

- pr-review 合并后上线自查回滚时另开的 issue（`pr-review/references/merge.md` 第 5 步）：纳入，它列了正文各节写什么，补一句「背景：原 issue 改的是什么、上线自查查的是什么」。
- retro、dreaming 开 issue：纳入但不用改，它们都写「照『开一个 issue』开」，跟着「正文」一节走。
- 人在 GitHub 上手开的 issue：排除，不经过脚本，拦不住；由 issue-triager 分拣时读正文把关（不改它的规则）。
- 已经开着的 issue：排除，不回头补。

## User Stories

只修问题、不加能力：

1. 期望行为：正文缺「背景」节或这一节是空的，`issues new` 不开 issue、`issues body` 退出 1，都说出缺的是「背景」；写了「无」算填了。seo-scan 开的 issue 照常开得出来，正文带「背景」。

## 实现决策

- **「无」算填了**：issue 里人批的新文写明「确实不需要的写『无』」。已知限制：脚本只能拦住「没写」，拦不住「随手写个无」，由 review 和 triage 读正文把关。
- **「背景」排第一节**：读的人先知道机制再看现象；校验不看顺序，只看在不在、空不空，顺序只是格式说明里的建议。
- **seo-issues 的背景是固定文字，不让方向 agent 另写**：扫描无人值守，方向 agent 的发现格式不动；固定文字说清这个 issue 从哪来、各节怎么用，够读者接上。
- **版本档位：minor**。依据 `REVIEW.md`「额外要求」：改了流程的行为（多拒一类正文），装了它的项目不用改配置；照新格式写的会话照样能开。从 main 当前版本往上升。

| 纯逻辑、数据转换、状态机 | TDD 单元测试 | 必填节校验：缺「背景」、「背景」为空被拒，「无」放行；seo-issues 拼的正文过校验且带「背景」 |

## Out of scope

- 判断「背景」写得好不好（比如是不是真的解释了问题里的叫法）：机械检查做不到。
- 给已开着的 issue 补背景。
