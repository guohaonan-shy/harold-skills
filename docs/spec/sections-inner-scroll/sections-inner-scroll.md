# 设计档案：内层容器滚动的页面也能分段

## 验证

| issue | 结论 | 证据 |
|---|---|---|
| #68 idea-loop 设计档案：内层容器滚动的页面，分段脚本量不到首屏以下 | 存在 | 外壳整屏高、内容在 `<main>` 里滚的页面，分段脚本量出的页高等于视口（600），首屏以下两段一张图都没拍；详情在「问题」 |

## 问题

### 1 内层容器滚动的页面，首屏以下的段拍不到图

2026-10-26 对着 `main`（1444794）复现：照分段脚本自己的浏览器测试的做法，在真 Chromium 里打开一个最小的应用外壳页（800×600 视口；外壳 `height: 100vh`，顶栏 60 高，`<main>` 占满剩下的高度、`overflow-y: auto`，里面三段，各 700 / 900 / 500 高，加上顶栏一共 2160 高），用分段脚本的 `measure` → `attribute` → `shoot` 原样跑一遍：

| 量到 / 拍到的 | 实测 | 本该是 |
|---|---|---|
| 页高 | 600（等于视口） | 2160 |
| 四段的范围 | 顶栏 0–60、第一段 60–760、第二段 760–1660、第三段 1660–**600**（倒过来了） | 第三段 1660–2160 |
| 可点元素 | 第三段的「Save」按钮算成「落空」（不属于任何一段），归属结果 `ok: false` | 归进第三段，`ok: true` |
| 拍出的图 | 只有顶栏（800×60）和第一段（800×540，被视口截掉一截）；第二、三段被跳过，理由只印在 stderr：「范围没有高度，或在页面（高 600）之外」 | 四张，第二段 800×900、第三段 800×500 |

实际影响：Toeflair 2026-10-21 全站初扫，登录后的应用外壳（`AppShell`）是 `h-screen` + `overflow-hidden`，内容在页面自己的 `<main>` 里滚。练习列表四页、历史、设置、账单共 7 页都只拍了首屏，首屏以下改用文字写进状态文件。

复现材料：`.tmp/to-spec/sections-inner-scroll/repro/`（`repro.test.mjs` 与 `output.txt`，不提交）

### 根因

分段脚本的浏览器一侧从头到尾只认文档在滚：量页高读文档的滚动高度，「整页滚一遍」和拍图前的滚动都滚窗口，元素的位置是视口位置加窗口的滚动量，截图用整页截图加裁剪框。内容在内层容器里滚时，文档高度就是视口高度，窗口根本滚不动：页高量成 600；元素的位置因为容器还停在顶上，恰好算得对，于是首屏以下几段的范围超出了「页面」，最后一段的终点被截到 600 倒了过来；`shoot` 把超出页面的段当成「没有高度」跳过；整页截图也截不到容器裁掉的内容。

文档里「要不要分段」的判断同样只看文档：设计档案的分段参考写「页面的滚动高度大于主视口高度，入口状态就要声明分段」，全站初扫第 7 步写「页面比主视口高的」，UI 审查者定义里写「页面滚动高度大于主视口」。按这几句的字面量，这 7 页都「不超过一屏」。

修正：issue 原先说「脚本判断『不超过一屏、不用分段』」。实测脚本不做这个判断，要不要分段是写档案的 agent 照上面几句文档判的；声明了分段之后脚本照样跑，只是页高量错、首屏以下的段被静默跳过。两处都要改。

## 方案

**交付物**：内层容器滚动的页面，在档案里跟文档滚动的长页面一样，有分段、每段一张完整的图、每个可点元素归进某一段。写档案的 agent（全站初扫、UI 审查）不需要知道页面是哪种滚法，命令和步骤都不变。

- **认出真正在滚的元素**：文档自己能滚（文档的滚动高度大于视口高度），就是文档，跟现在一样；文档不滚时，找页面上内容比自己高（`scrollHeight > clientHeight`）、`overflow-y` 是 `auto` / `scroll` 的元素，取可见面积最大的那个。下文叫它「滚动容器」。
- **量**：页高取滚动容器的内容高度；「整页滚一遍」、回顶部、等高度不再变，都在滚动容器上做；元素的位置换算成「滚动容器滚到顶时的页面坐标」（容器里的元素：容器顶 + 在容器内容里的位置；容器外的顶栏一类：滚动 0 时的位置）。测量结果里写明认出的滚动容器（怎么找到它、内容高、可见高），没有内层容器时写文档。
- **算**：归属照旧，读的是上面换算过的坐标和页高，不改。
- **拍**：滚到一段时滚的是滚动容器；比容器可见区高的段在容器里逐屏截、拼成一张完整的图，宽度只取滚动容器（见「段比容器可见区高时」）。
- **判要不要分段**：「页面比主视口高」一律改成「滚动容器的内容比它的可见区高」，文档滚动的页面上两句话等价。

同一行为的其他入口：

| 入口 | 纳入 / 排除 |
|---|---|
| 分段脚本 `measure`（入口状态整页量，和 `--for` 段内状态量） | 纳入：两种都走同一套滚动容器 |
| 分段脚本 `shoot`（含 `--section`、`--include`） | 纳入 |
| 分段脚本 `attribute` | 纳入，但只是读到对的页高与坐标，逻辑不改 |
| 设计档案 skill 里分段的定义和 `sections` 字段的注释、分段参考里「写在哪、什么时候写」和「校验」两处的判断句 | 纳入：改成滚动容器的说法 |
| 全站初扫第 7 步「页面比主视口高的」 | 纳入 |
| UI 审查者定义里「长页面（比主视口高）」「页面滚动高度大于主视口」两处 | 纳入 |
| 单屏状态的主视口截图（不分段的状态） | 排除：只拍一屏，跟怎么滚无关 |
| `ui-measure` 的测量与比对 | 排除：它比对冻结画布的单屏，不量页高 |

## User Stories

只修问题，不加能力：

1. 问题 1 的期望行为：外壳整屏高、内容在内层容器里滚的页面，分段脚本量出的页高是容器的内容高度，每段的范围在页高之内，容器里的可点元素都归进某一段，`shoot` 给每段拍出一张跟它范围一样高的完整图，不跳过任何一段；写档案的 agent 照文档判断时，这类页面算作要分段。

## 实现决策

### 选哪个元素当滚动容器

文档能滚就用文档，不找内层容器；文档不滚才找内层容器，多个时取可见面积最大的。依据：默认改动最小（「自己定的四条」第 4 条）——文档滚动的页面行为一字不变，现有浏览器测试照旧成立；长页面里带一个可滚的小框（聊天框、代码块）时，文档在滚，不会被小框带偏。issue 原文给的判据（`scrollHeight > clientHeight`、`overflow-y` 为 auto / scroll、最大的那个）照用。

主从两栏、两个窗格各自滚动的页面，只认最大的一个，另一个的内容超出部分照旧拍不到：测量结果里把其余候选也列出来，写档案的 agent 看得到。Toeflair 这 7 页都只有一个滚动容器，这是罕见情形、不丢东西（「自己定的四条」第 3 条），写成已知限制。

### 坐标系

测量结果和归属结果里的位置一律是「滚动容器滚到顶时的页面坐标」。容器外不随容器滚的元素（应用外壳的顶栏）照它在滚动 0 时的位置算，跟现在文档滚动时顶栏落在顶上一样。依据：`attribute` 和单测读的是这些数，坐标系不变，`attribute` 一行不用改（「自己定的四条」第 4 条）。

「固定元素在哪出现」（目录一类滚到某处才淡入的固定元素）照旧记出现时的滚动量，滚动量取滚动容器的。容器外、不随容器滚的元素不算「固定元素」：它们在滚动 0 时就在原位，按位置归属。

### 测量结果多一项「滚动容器」

写明是文档还是内层容器、怎么定位到它（拍图时要再找到同一个）、内容高、可见高，加上没被选中的其余候选。`shoot` 照这一项滚，不再自己重新找；归属结果把它原样带给 `shoot`。依据：量和拍要对着同一个元素，拍时重新找可能找到另一个。

### 段比容器可见区高时：在容器里逐屏截、拼成一张

在滚动容器里每次滚一个可见区的高度，截容器的可见区，拼成一张；段图宽度只取滚动容器，侧栏、外壳顶栏不进段图（它们是共用组件，在自己的状态和组件文件里有图）。容器里吸顶的东西（列表的表头）每屏都会出现，照现有「顶上固定的栏不挡住段的头几行」那条做法让开。文档滚动的页面照旧用整页截图加裁剪框，不走拼接。例：Toeflair 历史页，假设列表段 2000 高、容器可见区 800 来高，截三屏拼成一张宽度等于内容区（1440 减去 288 宽的侧栏，1152）的图。

依据：人在审核会话里定的，原话「如果有交互可以外延到其他页面或者组件，我觉得往下滚动+截图是可以的。其实我觉得选择a 是一个方式。」（[[2026-10-26-inner-scroll-shot]]）。分段要拍到首屏以下，是因为那里有从这一页出发的交互（练习列表的翻页、页脚链接）和组件（页脚），档案里的边和组件要能指到它们所在的段；逐屏截拼出的图跟人往下翻看到的一致，拿去跟实现画面比对不会因为拍法改了页面的样子而出偏差。

没选的两种：拍之前临时解开外壳的高度锁、让文档变长（外壳里 `h-screen` 的侧栏只有首屏高，首屏以下一片空白）；把视口拉高到装得下全部内容（`min-h-screen` 一类的块被拉长到几千像素）。两种都要先改页面的样子，拍出的是页面平时不会出现的画面。浏览器自带的截图（整页截图、元素截图、Chrome 的「截到视口之外」）都截不到被容器裁掉的部分，复现时逐个试过（`.tmp/to-spec/sections-inner-scroll/repro/shots.txt`），没有不改页面又不拼接的第四条路。

| 变的是什么 | 仪器 | 本次 |

| API 契约（路由、schema、序列化） | TDD API 测试 | 碰到：测量结果和归属结果多一项「滚动容器」，CLI 帮助与文档里的参数表照旧对得上（现有的文档一致性测试） |
| DB schema、迁移、并发与事务语义 | 真 DB 测试 | 不涉及 |
| LLM 输出质量（prompt 改动） | eval（确定性断言） | 不涉及 |
| 视觉正确性 | UI 实现环 | 不涉及：不画界面 |
| 端到端用户流程 | 浏览器端到端测试 | 碰到：真 Chromium 里跑 `measure` → `attribute` → `shoot`（分段脚本现有的浏览器测试，没有 Chromium 时跳过不算失败） |

- **seam**：
  - 分段脚本的浏览器测试：在真 Chromium 里打开一个手写的小页面，跑脚本打印出来的量和拍的代码，读测量结果、归属结果和拍出的 PNG 尺寸与像素。抓得到：滚动容器认没认对、页高与范围、每段拍没拍到、图有多大、吸顶的东西挡没挡住；漏掉：真实框架页面上的懒加载与水合时序、机器上没有 Chromium 时整组跳过。
  - 分段脚本的纯逻辑单测：喂测量结果的 JSON，读归属结果和要拍的目标。抓得到：「滚动容器」这一项有没有被带下去、目标高度怎么裁；漏掉：浏览器里实际怎么滚。
- **增量功能测试**（都落在浏览器测试的小页面上）：
  - 前置：800×600 视口，外壳 `100vh`，顶栏 60 高，`<main>` `overflow-y: auto`，里面三段 700 / 900 / 500 高。步骤：量、算、拍。期望：测量结果的滚动容器是 `<main>`、内容高 2100、页高 2160；四段范围 0–60、60–760、760–1660、1660–2160，`ok: true`；拍出四张：顶栏 800×60，三段宽度都是滚动容器的宽 800、高 700 / 900 / 500；第二段图第 10 行、第 890 行像素都是这一段的颜色（逐屏拼接没有留白）。覆盖：问题 1。
  - 同上，`<main>` 里加一条吸顶的表头。期望：第二段的图顶上第 5 行像素是段本身的颜色，不是表头。覆盖：问题 1。
  - 现有的文档滚动小页面不改，全部现有断言照旧通过：文档在滚时行为不变。覆盖：问题 1。
- **prompt / eval 变动**：无 prompt/eval 变动。文档改动只是判断句换说法（设计档案 skill、分段参考、全站初扫、UI 审查者定义），不在 `evals/` 覆盖的范围里。
- **照着谁写**：分段脚本现有的浏览器测试（一个内联的小页面、`buildMeasureCode` / `buildShootCode` 交给真 page 跑、读 PNG 尺寸与像素），和它的纯逻辑单测。

## Out of scope

- 不分段的单屏状态的主视口截图：只拍一屏，跟怎么滚无关。
- `ui-measure` 的测量与比对：它比对冻结画布的单屏，不量页高。
- 两个窗格各自滚动的页面，第二个窗格超出可见区的内容：罕见、不丢东西，写成已知限制（见「选哪个元素当滚动容器」）。
- 一段从滚动容器外开始、延伸进容器里：不拼接，只截首屏看得见的部分并在拍图结果里加注记；分段参考要求在容器顶切成两段。依据：人在实现中的停下汇报里定的，原话「01 选 A：记成已知限制，分段参考里加一句在容器顶切成两段。」
- 横向滚动：Toeflair 这 7 页都只有纵向滚动，没见到需要。
