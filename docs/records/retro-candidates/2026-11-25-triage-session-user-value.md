> 来自 Tofelair#1107 的 retro（2026-11-25）。人批了，去处选「进候选池」。

- 信号：人自己说的方向（推翻了 issue 的前提：证据只是一条评测断言报失败，没人问过它对学生有没有意义）
- 落点：插件两处：`issue-session` 的「triage 会话」第 1 步「起草」；`issue-triager` 的去向表（人选的落点，不放在分拣员判断价值，分拣员只负责把面向用户的问题送进 triage）
- 旧文：
  - `issue-session`「triage 会话」第 1 步：「读 issue 全文和分拣贴的证据评论……调 `idea-loop:to-spec` 起草……在这里跟人 grill」
  - `issue-triager` 去向表：「todo + P1/P2：复现到了，修法只有一种显然的做法，不碰 UI、不加新能力」
- 新文：
  - `issue-session`：在第 1 步前加「面向用户的 issue，起草方案之前先跟人讨论：从用户角度，这个问题碰到的是哪类用户、在哪个页面、是什么痛点，修好对他们的价值有多大，不修的代价是什么。会话带着证据和自己的看法开头，人来碰撞、来定；定下来不值得做的，issue 翻 canceled。」
  - `issue-triager`：在 todo 那一行后加「面向用户的问题（学生看到的内容、页面、功能）一律建议 triage，让人在 triage 会话里评估价值；只有不面向用户的（死代码、测试、内部工具）才按这一条直接 todo。」
- 归并：「要人定的写成一道题」（`decision-rules`）：「这件事对用户值不值得做」本该由人定，triage 会话把它当作第一道题摆出来。
- 验证：回放用例。当时的提交：Tofelair `f51390cbb`（main）。prompt：「分拣 #1107」（输入为它当时的正文）。是/否题：「分拣员是否把 #1107 建议成 triage，而不是 todo？」改前否、改后是。triage 会话那一处另写一题：「triage 会话开场是否先跟人讨论这个问题对学生的价值，再起草方案？」
- 例子：Tofelair#1107（Email 参考答案结尾段缺高亮）唯一的证据是评测断言「每段 1–2 处高亮」报失败；分拣员按「修法单一、不碰 UI」直接翻了 todo，从没进过 triage；夜间会话照着做到了 PR，白天人才指出结尾段不标不是错误，issue 关掉、改拆成两个 issue。
- 状态：在池里
