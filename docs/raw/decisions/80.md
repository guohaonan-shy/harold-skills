## 题 1：讲话方式在插件里留不留、留哪

- 类别：方案形状-人提第三条路
- 摆给人的：只写全局 / 插件按场景各补一两句（推荐）/ 插件另起共享参考
- 人的原话：「第一题，按照交付物拆分成两个方向：1 spec（markdown file）和pr（github）作为交付物的其中之一 我觉得这些内容是需要放在 to-spec 以及 pr 这两个skills内。这两个需要定义清楚交付物的结构，每个章节主要内容是什么。借此机会，我在想这两个skills哪些内容是可以简化，哪些规则可以通用化的」
- 做法：to-spec、pr 按交付物重写，参照 Matt Pocock 的同名 skill
- 情形：一组写法规则要从一个 skill 搬走，几个 skill 都用
- 处置：按交付物归位，并借机重写那两个 skill
- 理由：交付物的结构要先定义清楚，每节给读者什么
- 不自动的：是（方案形状被人提出第三条路的）

## 题 2：「现状先查清」归哪

- 类别：方案形状-人提第三条路
- 摆给人的：按场景拆进 to-spec 与 pr（推荐）/ 进全局 / 留在 decision-rules
- 人的原话：「第二题，关于现状其实是一个共享的内容，无论是跟我沟通还是产出交付物，我觉得都需要，其实skills和全局沟通风格都是需要添加的。」
- 做法：插件里写进 evidence 的共用写法，全局沟通风格也写
- 情形：一条规则对人说话和写交付物都适用
- 处置：插件与全局各写一次
- 理由：两边都需要
- 不自动的：是（方案形状被人提出第三条路的）

## 题 3：to-spec 与 pr 的重写放不放进这份 spec

- 类别：范围-并进本 spec
- 摆给人的：放进本 spec、切三张工单（推荐）/ 另开 issue
- 人的原话：「首先，to-spec 和 pr 的重写放在这个spec内，关于共用的那几条，我觉得放进evidence没什么毛病」
- 做法：放进本 spec；共用写法进 evidence
- 情形：人借机提出的重写
- 处置：同一份 spec
- 理由：讲话方式要落进这两个 skill 的结构，拆开要改两遍
- 不自动的：否

## 题 4：全局 CLAUDE.md 的骨架与语言

- 类别：方案形状-按推荐
- 摆给人的：读者模型开头 + 四条做法 + 两条操作性的（推荐）；文件语言
- 人的原话：「其次，全局的claude.md用中文。」「没问题，我暂时没有其他问题了。」
- 做法：按骨架、用中文；人自己改了多处，适用范围那句加上，「插件画不了就直说」不加
- 情形：重写人的全局偏好文件
- 处置：按推荐骨架，中文
- 理由：人的偏好
- 不自动的：否

## 题 5：to-spec 新节表

- 类别：方案形状-人改节表
- 摆给人的：拆掉「技术方案总览」（推荐）/ 保留外壳；随后问「验证」节的结论放哪（推荐 issue 不存在不写 spec）、「方案」配什么图（推荐改前改后图、时序图留实现决策）
- 人的原话：「我觉得，to-spec 开头可以用quota一句话描述问题是否存在，为什么不存在即可。spec还是需要的，方便dreaming归档进入adr。」「方案这一节，我在想是不是把原来的前端、后端作为方案的子章节。但是方案章节的开头，我希望是可以有一个前后端或者模块之间的交互时序图。」
- 做法：标题下引用块写结论、不存在也写 spec；「问题陈述」；「方案」开头交互时序图，后端 / 前端内部 / 前端交互为其子小节
- 情形：spec 模板的节怎么取舍
- 处置：照人改的节表
- 理由：spec 要留给 dreaming 归档成 ADR；方案要让人一眼看懂交互
- 不自动的：是（方案形状被人提出第三条路的）

## 题 6：pr 的交付物与「合并风险」

- 类别：方案形状-人提第三条路
- 摆给人的：四份交付物的节表；加「合并风险」（推荐）/ 不加；停下汇报与 review 汇报合不合并（推荐合并）
- 人的原话：「PR 可以在汇报和pr描述内加上“能否回滚”的章节。我觉得停下来汇报有些多余，将两个汇报合并成一个Review汇报。review是每一个汇报项的汇报格式？」「我觉得pr的汇报合并成一个吧」
- 做法：只剩 PR 描述与 Review 汇报两份；「要你决定」统一格式、选项带能否回滚；两处各加「能否回滚」
- 情形：PR 上给人看的东西怎么分
- 处置：两份交付物，统一条目格式
- 理由：人只在 GitHub PR 和对话两处看东西
- 不自动的：是（方案形状被人提出第三条路的）

## 题 8：两轮自动 review 跑满后再跑还是合并

- 不自动的：是（合并改了代码的 PR）

## 题 9：旧写法 spec 关 issue 时关闭评论指错位置

- 类别：边缘情形-不丢数据
- 摆给人的：接受成已知限制（推荐）/ 修
- 人的原话：「接受」
- 做法：写成已知限制记进工单

- 理由：现在触发不了，issue 照样关对
- 不自动的：否
