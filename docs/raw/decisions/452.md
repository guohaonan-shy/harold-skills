## 题 1：以什么为底

- 摆给人的：折叠外一屏四块 / 七节照旧加限额 / 只调顺序，推荐一屏四块
- 人的原话：「这个是matt的pr 结构，我们根据他的结果进行讨论」（mattpocock/skills 的 skills/engineering/pr/SKILL.md）
- 做法：改以 Matt 的三节（Summary / Evidence / Merge Danger）为底

## 题 2：我们多出来的节怎么处理

- 摆给人的：三节 + 流程要用的节 / 再留折叠参考 / 只要 Matt 三节，推荐第一种
- 人的原话：「我倾向于先只要matt的三件，然后我们基于这3件，看哪些部分是要修改、拓展的，哪些部分是不需要的」
- 做法：先只要三节，逐节逐块过；其余节默认不要，过到非它不可时再拿出来问（已知受影响：SEO 自动合并读「上线自查的网址」、夜间模式写「夜里替你定的」）

## 题 3：概要节怎么过

- 人的原话：「我们来讨论下吧，按照matt在summary下面定义的内容一块一块的过」
- 做法：按 Matt Summary 的九块逐块定

## 题 4：概要 · 伪代码

- 摆给人的：留，用领域叫法 / 留，代码式 / 不要，推荐第一种
- 人的原话：「我允许保留，section 这个部分 可太重要了Skip all preambles and keep prose brief. Use the user's domain language from GLOSSARY.md.」
- 做法：伪代码保留；Matt「Sections」开头那句（不写开场白、文字短、叫法用 GLOSSARY.md）对三节都适用，图里也用领域叫法

## 题 5：概要 · 调用树起，改成整份照抄

- 摆给人的：调用树 留 / 只留 diff 版 / 不要，推荐留
- 人的原话：「我们先完全照抄matt的，将mermaid 那块换成我们的excalidrawer。」
- 做法：PR 描述先整份照抄 Matt 的 pr skill（三节、Summary 的九块、Evidence、Merge Danger），唯一的改动是 Summary 里 Mermaid 那块换成 excalidrawer；其余改动、扩展在照抄稿之上逐条再定
- 顺带问的：Matt 开头 metadata 里的 credits 是什么——答：只是署名。Summary 那一串视图写法几乎逐字取自 Dex Horthy（Humanlayer）的 show-me skill，Matt 的 CREDITS.md 说明是复制进来、不依赖它（硬依赖会让单独安装坏掉）；Claude Code 不读这个字段，不会加载或调用 show-me

## 题 6：概要里允许哪些代码叫法

- 摆给人的：只放开路径 / 概要里全放开 / 照旧全拦，推荐只放开路径（照旧全拦会让文件树、文件布局 diff 两块整块用不了）
- 人的原话：「只放开路径，你是担心runtime control flow 这种格式不允许，这个要不用我们的evidence（excalidrawer的时序图）描述？你觉得这个是否OK？」
- 做法：概要里允许目录、文件路径（每个后面 # 一句术语表叫法的说明），命令名、函数名、变量名照旧拦；证据、合并风险两节全拦

## 题 7：调用树和 excalidrawer 那块留哪个

- 摆给人的：只留调用树 / 只留时序图，推荐调用树（最近 80 个已合并 PR 画了时序图的是 0 个）
- 人先问清了两者的区别：调用树的节点是同一个程序里的函数，嵌套是调用者和被调用者；Mermaid 的角色是各自独立运行的组件和人，线是跨程序的消息
- 人的原话：「我倾向于两个都保留」
- 做法：照 Matt 原样，调用树（含调用树 diff）和 excalidrawer 那块都留
- 撞上的一处：调用树的节点是函数，题 6 定了函数名照旧拦

## 题 8：调用树的函数名

- 人的原话：「我觉的可以放开」
- 做法：概要节里代码叫法全部放开（路径、函数名、命令名；Matt 的组件树带 hook 和 props、整块代码那块本身就是代码，照抄就得全放开）。题 6 的「只放开路径」作废。dyna 的拦截只管证据、合并风险两节。节点名能用术语表叫法的照 Matt「叫法用 GLOSSARY.md」用术语表的

## 题 9：证据节

- 摆给人的：逐块（模板、证据只证明改动生效、截图 S 级、执行类 A 级）加「没验成的」一项，每块给建议
- 人的原话：「都按你的建议来」
- 做法：
  - 模板「之前 / 之后」照抄；在基准分支和本分支各走一遍
  - 证据只证明改动生效：review 轮次、每条检查逐列都不放（review 合并时整份进归档评论）
  - S 级保留排序，形态照 `idea-loop:evidence`「证据的几种形态」选（看得见的单个状态用截图，端到端一条流程用录屏，#438 定的）
  - A 级：代码叫法照旧拦；测试用伪代码、术语表叫法写，全量只写结果（如「插件测试 1127 条、dyna 全部包，都是绿的」）
  - 扩展：节末一行「没验成：<哪个行为>，<为什么>，<谁补>」，没有就不写（例：#432 桌面端真机交出、#482 录屏能否在 PR 里播放）

## 题 10：合并风险节

- 摆给人的：门、影响面两块照抄；「上线前要注意的」先放影响面的可选说明里；「顺带开的 issue」从描述删掉
- 人的原话：「都按照推荐来就好」
- 做法：**门**：双向 / 单向（我们的「部分能」= 单向 + 说明退不回的部分）；**影响面**：一个词 + 可选说明，代码叫法照旧拦；「上线前要注意的」暂放影响面说明里，过「要你做的事」时再定归属；「顺带开的 issue」不进描述，留在 review loop 文件、随合并归档评论贴出

## 题 11：夜间两节（夜里替你定的、等你定的）

- 摆给人的：并进「要你做的事」作两组子项（推荐）
- 人先问清了它们是什么：夜间模式的会话按推荐替人定的题、推荐替不了而停下的事；#403 定了 5 条、#411 定了 1 条，「等你定的」最近 200 个 PR 里 0 次
- 人的原话：「我倾向于不要带这一节」
- 做法：PR 描述不带夜间两节。夜里按推荐定的题本来就作为批示记进 review loop 文件（night-mode.md「要人定的，按推荐定」），合并时随归档评论贴出；「等你定的」改成跟 PR 没开时一样，在 issue 上留评论。night-mode.md 里写 PR 描述这两处要跟着改

## 题 12：概要之前加「问题」节

- 起因：人问清概要的总则（挑最小视图讲清改动要点）后，判断概要相当于解决方案的描述
- 人的原话：「如果是这样，summary其实相当于解决方案的描述；那我觉得summary 之前是需要有一个问题章节，用最小试图的证据 + 文字说清楚问题是什么。」
- 做法：概要之前加「问题」：短文字 + 一个最小视图的证据，证明问题真的会发生（真实路径、出处、数字，照 home「证据贴着结论」）。顺序：问题 → 概要 → 证据 → 合并风险（→ 要你做的事，待定）
- 跟「证据」节的「之前」怎么分：会话里提议，等人确认
- 人补充「必要的证据」是什么：「比如提示词修改时候，就可以用统计学来表示出现问题的频率；比如UI/ux问题，就可以用ui flow。我不是让你按照case决定，而是告诉你什么是必要的证据，同时也考虑pr 这个skill 如何和evidence 这个skill 结合」

## 题 13：pr / spec 跟 evidence 怎么分工

- 人的类比：「无论是pr 还是 spec ，我都倾向于他们和evidence的关系，类似于拆分工单和tdd的关系」（仓库里实际的分工：spec 测试决策定验证什么、用哪种仪器，tdd 只管怎么跑，to-ticket / implement 不复述 tdd）
- 摆给人的：A pr / spec 里写清用什么证据（对照表在 pr、to-spec 等处各一份）/ B 不写，调 evidence，evidence 写清每种证据常用来证明什么，推荐 B
- 人的原话：「我的思路就是B」
- 做法：
  - pr 只写每节要证明什么：问题节证明问题真的会发生、有多常见；证据节证明改后好了，之前 / 之后跟问题节用同一种证据、同一组输入（两边是同一份时，问题节放，证据节的「之前」写「同问题」）；用什么证据写「照 `idea-loop:evidence`」
  - evidence 的「证据的几种形态」表把「让人看到什么」一列扩成「常用来证明什么」（例：图表——概率性问题（提示词、skill 规则）出现多频繁、改前改后各几次；UI 流程图——用户路径上哪一步出了问题），不新加一节
  - 题 9 里 Matt 的「截图 S 级、执行类 A 级」排序不用了，形态交给 evidence；A 级里「测试用伪代码、术语表叫法写、全量只写结果」「没验成」一行保留
  - 问题节同证据、合并风险一样拦代码叫法
