#293 的 triage 会话。分拣评论问了两件事：要吸收 toeflair 的哪部分、形状怎么定。会话查到 toeflair 已有一个 `ai-eval` 插件，它自称项目无关，还写着「稳定了再迁到个人 marketplace」，于是形状变成迁它、再补规则。spec 是 [[ai-eval-plugin]]，提交在 `issue/293-eval-writing` 分支上，#293 翻成 todo。这场会话没有规则候选：人没纠正过，也没自己说出跨 issue 的原则；两道题都只对这个 issue 成立。

## 题 1：eval 写法放哪

- 类别：方案形状-按推荐
- 摆给人的（选择题）：
  - 迁 ai-eval + 补规则（推荐）
  - idea-loop 新开一个 skill，ai-eval 留在 toeflair
  - 先迁，规则另开 issue
- 人的原话：「迁 ai-eval + 补规则 (推荐)」（选择题的回答）
- 做法：spec 写成 toeflair 的 `ai-eval` 迁成 harold-skills 的 plugin，补报数口径，新开 eval-replay，to-spec 那一行指向它
- 情形：要做的能力在一个已在用的工具里有一半，那个工具在别的仓库
- 处置：扩展已在用的工具，把它迁过来，不另起一套
- 理由：`CLAUDE.md`「先扩展已在用的工具，不为一件事新增组件」
- 不自动的：否

## 题 2：toeflair 那边的切换谁来做

- 类别：方案形状-人改推荐
- 摆给人的：
  - A（推荐）：合并后在 toeflair 仓库开 issue，由那边自己的流程做
  - B：把 toeflair 加进本仓库的仓库表，两个仓库各开一个 PR
- 人的原话：「这个事儿在harold-skills 开issue，toeflair项目暂时用旧的，两个不相互冲突～」
- 做法：在 harold-skills 开 #361（被 #293 挡着）；迁移期间 toeflair 继续用旧副本；spec 的「待定」改成定下的决定
- 情形：迁移的另一半在别的仓库，要定在哪里跟踪
- 处置：在插件所在的仓库开 issue 跟踪，旧副本先留着
- 理由：两份副本互不冲突，不用同步切
- 不自动的：否
