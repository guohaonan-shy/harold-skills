## 题 1：执行方定义按 writing-for-agents / agent-builder 精简，放在哪做

- 类别：顺手发现-本 PR 做还是另开
- 摆给人的：人问「implementer的prompt是否可以参考writing-for-agent，agent-builder进行优化和精简…我们只需要告诉agent能用的工具是什么即可吧」。我答：可以精简到 5000 字内，但不精简到「只列工具」（交回格式被机械核对、命令不写死执行方就自己现想）；推荐开 issue、等 #371 合并后再做
- 人的原话：「放在这里做」
- 做法：同一个 PR 加工单 02，spec 补问题 2；「不只列工具」写进 spec「实现决策」
- 情形：人在 PR 已进 review 时提出的改动，跟 PR 改同一份文件
- 处置：在同一个 PR 里做
- 理由：人定；两件改同一份文件，分开会冲突
- 不自动的：否

- 理由：人定
- 不自动的：否

## 题 3：交回、CI 结果回来后会话没反应，要不要加兜底

- 类别：交回卡住-加不加机制
- 摆给人的：扫本机会话记录：11-16 以后子代理交回卡住 6/168（约 3.6%，以前 42/2579 约 1.6%），后台命令跑完卡住 4/90（以前 29/404）；11-16 以后平台合成的「No response requested.」23 次，11 次前面有 ECONNRESET（集中在 11-17 北京时间 14:40–15:43），12 次请求发出后无记录。选项：维持不加（推荐，样本小、根因在网络侧）/ 加开口提示（下次人发消息时钩子查漏处理的交回）
- 人的原话：「维持不加」
- 做法：不改；结论同 #292
- 情形：交回或后台命令结果到达那一轮的模型请求断了或挂住
- 处置：不加机制，人开口接上
- 理由：根因在网络、API 或桌面端，不在仓库；比例上升样本还小
- 不自动的：否
