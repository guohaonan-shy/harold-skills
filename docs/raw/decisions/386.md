## 题 1：spec 写的前提（#400 先同步进集成分支）没满足，现在开工还是等

- 类别：前提未满足-先做还是等
- 摆给人的：现在开工，#400 的口径被新算法包含、同步时取 #386 一侧（推荐）/ 等 #400 合进 main 并同步后再做
- 人的原话：「现在开工」
- 做法：在集成分支现有文字上实现；同步第二批进来后冲突照 #386 解
- 情形：上游 PR 的口径被本 spec 的方案完全包含，只是顺序没到
- 处置：先做，冲突时取本 spec 一侧
- 理由：等同步只换来再解一遍同样的冲突
- 不自动的：否

## 题 2：夜里每轮默认派几个 todo

- 类别：两次人的决定冲突-取最新
- 摆给人的：A 每轮 1 个（30 分钟一轮，一晚最多 20 个，推荐）/ B 保持 spec 的每轮 3 个（一晚最多 60 个）
- 人的原话：「1 A」
- 做法：默认调度表夜里 todo 每轮 1；spec、工单记下人的决定
- 情形：spec 定稿后，人在 main 上另定了更小的名额（11-20 22:52「夜里每小时派 1 个」）
- 处置：取最新决定的意图，换算到新的轮次间隔
- 理由：每晚 30 个已嫌多，60 个翻倍
- 不自动的：否

## 题 3：调度会话的模型怎么钉

- 类别：spec 缺口-平台不支持
- 摆给人的：A skill 开头钉 Sonnet、medium，再提醒人手动选（推荐）/ B skill 不钉，全靠人在桌面 app 里手动选
- 人的原话：「2 B」
- 做法：调度 skill 不写 model、effort；起调度时提醒人在桌面 app 里把 dispatch-home 的模型选成 Sonnet
- 情形：spec 要「钉在定时任务上」，建任务的工具没有模型参数
- 处置：不在 skill 里钉，交给人手动选
- 理由：无（人没给理由）
- 不自动的：否

## 题 4：命令行 0.0.7 什么时候发

- 类别：规则原文与现存做法冲突
- 摆给人的：A 照集成分支做法，下限先抬、0.2.0 收尾一起发（推荐）/ B 这个 PR 合并前单独发
- 人的原话：「3 A」
- 做法：下限抬到未发布的 0.0.7，发布留到 0.2.0 收尾
- 情形：REVIEW.md 写下限只在已发布时抬，0.2.0 集成分支上一直先抬后发
- 处置：照集成分支现存做法
- 理由：发布只做一次
- 不自动的：是（对外发布）

## 题 5：合并 #455 前要不要等 main 的 5 个 PR 先同步

- 类别：合并顺序-先合还是等同步
- 摆给人的：先合 #455，同步时调度文字取集成分支一侧（推荐）/ 等同步会话先合 main
- 人的原话：「合并」（人说合并后，父会话回：「#455 你先合，不用等同步。」）
- 做法：先合 #455（f7d78253），#400 在下一批同步里记「被 #386 取代，丢弃」
- 情形：待同步的 main PR 里只有一个跟本 PR 改同一处，且已被本 PR 取代
- 处置：本 PR 先合
- 理由：避免再解一遍同样的冲突
- 不自动的：是（合并改了代码的 PR）
