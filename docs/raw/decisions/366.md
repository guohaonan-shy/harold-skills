## 题 1：共用实现配的源码扫描检查由谁写

- 类别：结构-新增还是扩展已有
- 摆给人的：A 项目各自写测试（跟项目 CI 跑）；B 插件给通用扫描脚本。推荐 A：插件目录不在项目仓库里，项目 CI 跑不到；判断「像不像失败视图」是项目自己的写法（先例 Toeflair #764）。名单写正文、豁免清单放检查旁两件按规则已定。
- 人的原话：「这个issue想解决什么问题？」，之后让先调研：「首先，我比较好奇，失败页其实类似于营销页的404页面，这种整个站点可能共享的路径页面，是否要写入design.md，你先调研下github，x上的一些内容。然后我们再来讨论」；看完调研：「没问题，Voice & Content Strategy也在这个issue里面一起解决」
- 做法：A；条目用官方 `@` 外部引用指向共用实现，写进 spec design-shared-implementations
- 情形：一类界面要全站统一，需要一个会红的检查
- 处置：检查放项目测试里跟 CI 跑；插件只规定条目形状与对账
- 理由：只有项目 CI 拦得住人；识别写法是项目特有的
- 不自动的：否

## 题 2：失败页、404 这类整页共用视图进不进 DESIGN.md

- 类别：准入-设计规范收不收
- 摆给人的：调研结论（官方规范 Components 可用 `@` 指向实现、错误文案归 Voice 章；84 份样本 0 份写错误页；USWDS / GOV.UK 写成模板或模式；Atlassian 实测只给配方 agent 更会重画）。推荐进，写成 `@` 指针 + 可变 / 不许自画 + 项目测试，不重抄外观。
- 人的原话：「没问题，Voice & Content Strategy也在这个issue里面一起解决」
- 做法：按推荐写进 spec
- 情形：被一组页面共用的整页视图
- 处置：以共用实现条目进 Components
- 理由：跨页、只属于本产品、能被检查（准入分层表的页面家族复用机制）
- 不自动的：否
