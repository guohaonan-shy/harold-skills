## 题 1：要不要顺手加一条检查，防止插件里再出现术语表的避用词

- 类别：范围-并进还是另开
- 摆给人的：这次不加，只改两处措辞，要加另开 issue（推荐）/ 在这个 PR 里加一条扫描插件的测试
- 人的原话：无（夜间模式，人不在，按推荐定；人读到「夜里替你定的」后没有推翻，直接说「直接合并吧」）
- 做法：不加检查，记进 spec 的 Out of scope
- 情形：只修措辞的 issue，冒出一个能防回归的新检查
- 处置：不并进当前 PR，交回调用方自己的流程
- 理由：issue 只要求改两处；加检查是新能力，范围超出 issue
- 不自动的：否

## 题 2：改了插件文件但插件 README 没提到这两句话，要不要同步改 README

- 类别：规则歧义-README 同步
- 摆给人的：按「README 讲到的东西变了才同步」读，不改 README（推荐）/ 按字面，只要改了插件文件就动 README
- 人的原话：无（review 第 1 轮审查者判为规则有两种读法、不算违反，写进审核报告请人推翻；人没有推翻，直接说「直接合并吧」）
- 做法：不改 README
- 情形：改动只是 README 本来没提到的措辞
- 处置：不同步 README
- 理由：README 里没有可同步的内容；以前只改措辞的提交（747b775c、5eed4c0a、dc504fcd）也都没动 README
- 不自动的：否

## 题 3：合并 PR #443

- 类别：合并
- 摆给人的：审核报告交出，review 1 轮无条目，说「合并」即可
- 人的原话：「直接合并吧」
- 做法：归档 review loop，merge 合并，#389 翻 done
- 情形：review 无条目、全量测试全过
- 处置：人说合并后合并
- 理由：合并只由人定
- 不自动的：是（护栏：合并改了代码的 PR）
