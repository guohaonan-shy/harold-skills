## 题 1：review 第 1 轮 S2，提议表说明里只列三类的「大意」要不要一起改

- 类别：review-spec 偏差-接受
- 摆给人的：A 在本 PR 里改成指向 dreaming 开头并同步 spec；B 不改照原样合。推荐 A。
- 人的原话：无（夜间模式按推荐定，记进 PR 描述「夜里替你定的」，人合并前未推翻）
- 做法：改成指向 dreaming 开头，spec「同一说法的其他入口」表同步改
- 情形：review 发现 spec 盘点入口时漏判了一处同类说法
- 处置：并进当前 PR
- 理由：是这份 spec 要消掉的同一个问题，只差一句话
- 不自动的：否

## 题 2：review 第 2 轮 S1，测试里五个说法要不要只留一份

- 类别：review-spec 偏差-接受
- 摆给人的：A 并成一张表、对着脚本推出的类别查；B 接受现状记成已知限制。推荐 A。
- 人的原话：无（夜间模式按推荐定，人合并前未推翻）
- 做法：测试里五个说法只出现一次
- 情形：验收原文「不把五个词写死」字面上没做到
- 处置：并进当前 PR 修
- 理由：验收原文已批，改动只在一个测试文件
- 不自动的：否

## 题 3：PR #409 和 0.2.0 发版分支怎么配合

- 类别：范围-并进在途版本
- 摆给人的：A #409 照常合进 main，0.2.0 在 #331 下另开子 issue 基于 release 分支重做；B #409 不合，只在 release 上修。推荐 A。
- 人的原话：「选 A，开子 issue」
- 做法：开 #418 挂到 #331 下；#409 描述「能否回滚」加了合 main 进 release 时怎么解冲突
- 情形：同一问题在 main 和在途发版分支上都存在，但发版分支上的实现（判定位置、类别）已经不同，修法搬不过去
- 处置：两边各修，main 先合，发版分支另开子 issue
- 理由：main 还在发版；发版分支的修法本来就得重做
- 不自动的：否
- 跟 #376 题 2（同类别，处置「并进那个版本」）的差别：#376 是 issue 要改的文件正被发版分支上的 PR 改，现在做要返工；这次 main 上的修法本身成立、0.1.x 还在发，发版分支只是有同一问题的另一份

## 题 4：合并

- 类别：合并
- 摆给人的：审核报告，要你做的事里只有「看夜里替你定的两条」和「说合并」
- 人的原话：「合并吧」
- 做法：合入最新 main、版本升到 0.1.40（patch）、删工单、归档 review loop、merge 合并、#350 翻 done
- 情形：两轮 review 后无未处理条目
- 处置：人说合并就合
- 理由：无
- 不自动的：是（护栏：合并改了代码的 PR）
