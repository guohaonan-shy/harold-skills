## 题 1：没有真实路径的误判，关掉记成已知限制，还是加「不是滚动驱动」的声明

- 类别：边缘情形-不丢数据
- 摆给人的：关掉 #128、把已知限制那句改准（推荐，理由：真实项目里唯一带钉住目录的博客页不会被误判，找不到真实路径）/ 加「不是滚动驱动」的声明、起草 spec
- 人的原话：「我不能接受这个已知的限制，我在想对于滚动驱动这种内容，本质上是不是也可以是做正常滚动？滚动驱动本质上是通过滚动来更换元素的同时保证整段被钉在视口。」
- 做法：两个都没选。按人的定义收窄检出：只认整段钉住，删掉「不到半屏但文字随滚动变了也算」那条信号；窄钉子的段照普通长图拍；不加声明。
- 情形：一条没有真实实例的边缘情形，是我们自己按 spec 写法补的一条检出规则造成的
- 处置：删掉造成它的规则，不记已知限制，也不加新声明
- 理由：人对滚动驱动下了定义（整段钉住、滚动换内容），这条规则不在定义里；删掉后真实的两个滚动驱动段都还能检出
- 不自动的：否

## 题 2：整段钉住的段存成什么形状，另开 issue 还是并进 #128

- 类别：范围-并入还是另开
- 摆给人的：每一步一个段内状态、一张钉住视口图（现在的做法）/ 拼成一段一张图；推荐另开 issue 改成拼图
- 人的原话：「我其实觉得右边的符合我的预期，listen/hold/delivery可能都有一个图～」「按这两件起草」
- 做法：保持每一步一张钉住视口图，去掉「结构相同的步骤只记第一个」，并进 #128
- 情形：现有规则的拍法符合人的预期，只是少拍了步骤
- 处置：在本 issue 里改规则，不另开
- 理由：人看到档案里的真实图之后选了现在的拍法
- 不自动的：否
