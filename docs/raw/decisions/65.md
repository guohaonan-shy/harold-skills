人在审 spec 时一次授权到合并（题 1 的原话），之后各题都由 agent 引这句原话按推荐定，收尾时单列给人。

## 题 1：滚动驱动的段怎么存进档案（审 spec 的待定）

- 类别：grill-按推荐
- 摆给人的：A 每一步建成段内状态 / B 段上声明几个滚动位置、一段几张图，推荐 A
- 人的原话：「这块内容我对于前端不是很懂，全部交给你了，你直接开始按照推荐to-spec、拆分工单实现以及合并吧」
- 做法：选 A，写进 spec「实现决策」，依据引人的原话；对话落 [[2026-10-26-unstable-sections]]
- 情形：建模选择，两种建法差在档案结构上，人不熟这个领域
- 处置：按推荐
- 理由：跟「段内交互是另一个状态」同一种建法，营销站档案已有实例
- 不自动的：否

## 题 2：不分段的单屏状态要不要一起换拍法（审 spec 的待定）

- 类别：grill-按推荐
- 摆给人的：A 一起换 / B 这次只管分段、另开 issue，推荐 A
- 人的原话：同题 1
- 做法：选 A
- 情形：范围选择，误报原因和修法都相同
- 处置：按推荐
- 理由：分开做要把同一套改动走两遍
- 不自动的：否

## 题 3：批注演示段第一步的存档图比用户看到的多亮了几处（交付验收）

- 类别：人验-代验
- 摆给人的：执行方交回的人验素材（存档图与用户看到的两张），要人判断能不能接受
- 人的原话：同题 1
- 做法：编排者代验接受，依据 2026-10-21 定的「完全展示出来就截一张，不用考虑动效」；在 PR 描述「要你做的事」与会话里单列，可推翻
- 情形：人事先授权到合并，人验素材差别小、不丢东西
- 处置：代验接受并单列
- 理由：人原话授权；差别只是出现动画多走了一点
- 不自动的：是（人验素材）

## 题 4：窄的钉住栏检不出（review 第 1 轮 S2）

- 类别：spec 缺口-会悄悄出错
- 摆给人的：补上 spec 原定的第二条信号 / 接受收窄、记成已知限制，推荐补上
- 人的原话：同题 1
- 做法：补上，工单 02 追加一格派修
- 情形：实现比 spec 收窄，漏检时档案悄悄缺图
- 处置：修
- 理由：spec 定的是两条信号任一成立
- 不自动的：否

## 题 5：插件版本号要不要升（review 第 1 轮 S3）

- 类别：版本号-按推荐
- 摆给人的：这次升一个小版本 / 不升、攒几项再升，推荐升
- 人的原话：同题 1
- 做法：升到 0.1.6
- 情形：子命令和返回字段变了，仓库没写升版本的规则，上一个功能 PR 没升
- 处置：按推荐升
- 理由：旧文档配新脚本会拍错
- 不自动的：否

## 题 6：使用说明用虚构例子、没写工单点名的真实页面（review 第 1 轮 S4）

- 类别：形状上的小差别-接受并补记

- 人的原话：同题 1

- 情形：工单要求和插件「不出现来源项目」的检查冲突，两种驱动方式已写全
- 处置：接受并补记
- 理由：插件文档不带具体项目更好维护
- 不自动的：否

## 候选 1：开 issue 时「在哪」写到具体页面、组件或文件；验证 issue 时先回到出处复现，夹具只用来做最小化

- 信号：纠正与追问
- 原话：「这些case是针对当时在toeflair项目里的什么内容开设的？」；「我觉得其实这算是落issue的时候上下文不足的原因，核心还是问题的根源是什么决定我们的技术方案」
- 落点：插件 `idea-loop:spec-status` 的「开一个待验证的 issue」第 2 步；插件 `idea-loop:issue-verify` 的「先复现」
- 结果：不批（人的原话：「我倾向于暂时不批」）。起先提的是给候选池里「例子先从真实材料取」那条加一次出现，人改成落在开 issue 与验证 issue 的源头，再摆后不批

- 落点：插件 `idea-loop:decision-rules` 的 `references/handing-to-human.md`，「先写交付物，再列做法」
- 结果：改成（进候选池：`docs/records/retro-candidates/2026-10-26-goal-figures-for-human.md`；人的原话「进候选」）。起先提的是「人事先授权一路做完时 issue 会话怎么走」，人改成交付目标用图文讲清
