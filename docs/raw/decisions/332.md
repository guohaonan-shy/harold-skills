## 题 1：记忆整理由谁跑

- 类别：落地顺序
- 摆给人的：A 项目 dreaming 顺带跑，`~/home/memory/` 记上次整理日期、满 7 天的那次才跑 / B home 单独一个设备级定时任务、只管记忆；推荐 A（不加新的定时任务）
- 人的原话：「我倾向于设备纬度只有一个dreaming任务」；再问范围（只剩一个全包，还是只多一个管记忆的）时选「只剩一个，全包」
- 做法：设备上只剩一个 dreaming 定时任务 `dreaming-home`，开在 `~/home`：先整理记忆，再逐个跑项目对账；项目各自的任务取消
- 情形：记忆全设备一份，dreaming 却每个项目一个任务
- 处置：#332 定任务形状和记忆一段；逐个跑项目对账归 #333，取消本机旧任务归 #247；已写进共享笔记并告诉 #333 的会话
- 理由：人的选择，比推荐走得更远——不只记忆，整个 dreaming 按设备跑
- 不自动的：否

## 题 2：dreaming 改记忆时问不问人

- 类别：人机分工
- 摆给人的：A 全自动、只问互相矛盾的规矩 / B feedback 类的合并、改写、删除都问人；推荐 A
- 人的原话：选「全自动，只问矛盾 (推荐)」
- 做法：A；`记忆` 一节只有「问人」的行进问人的小表
- 情形：例子是 Toeflair 的「PR 开出≠授权合并」和「prod gate 不止 git merge」可以合成一条
- 处置：照 A 写进 spec
- 理由：跟 dreaming 现有的「只问会判错的两类」同一个口径；home 是 git，错了能 revert
- 不自动的：否

## 题 3：项目记忆挪走后，项目里的会话怎么看到

- 类别：范围-分刀
- 摆给人的：A 根索引每个项目一行指针、项目地图指到项目记忆索引，按需读 / B #252 的 hook 连项目记忆索引一起注入；推荐 A
- 人的原话：选「只留指针，按需读 (推荐)」
- 做法：A
- 情形：例子是在 Toeflair 会话里问「9 月新题批次到哪了」
- 处置：照 A 写进 spec；项目地图模板要有那一行（#252 的模板）
- 理由：每轮的负担只留跨项目的；够不够由 #252 的 token 测量看
- 不自动的：否
- 订正：摆题时说 Toeflair 的项目条目「约 7 KB」，实测 project 一节 10,562 字节、reference 一节 5,414 字节，spec 里用实测数

## 题 4：判一条记忆归不归某个项目时，能不能读它的正文（todo 会话，PR #363 review 第 1 轮 S2，2026-11-17）

- 类别：spec 缺口
- 摆给人的：A 只对有项目出处（项目前缀、`originSessionId` 对得上某个项目）的条目放开读正文 / B 判归属不读正文，只看前缀、会话出处和索引那一句；推荐 A
- 人的原话：「你让我决策这个问题，能让我看下嘛？」；补上两句打架的原文、Scriben 那条记忆的原文和 A、B 各自走一遍之后：「按照a」
- 做法：A；spec「一次记忆整理」第 2 步与「dreaming 自己做」一条、记忆整理参考文件同步改，文档测试钉住
- 情形：spec 一处说只在合并、订正时读正文，另一处说判归属看正文；Scriben 那条「不要自己开 PR」只在正文第一句写着「On Scriben」
- 处置：照 A
- 理由：spec 已定的判据本来就是看内容；只对有出处的条目放开，多读的量有边界
- 不自动的：否
