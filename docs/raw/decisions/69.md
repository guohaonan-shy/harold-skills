#69 原想让加载完的状态也能声明分段。triage 会话起草了这一版，进 retro 时人推翻了方向：分段留给营销页，真正要守的是会连出边的交互组件要进截图。spec `design-archive-loaded-sections` 在分支 `issue/69-design-archive-loaded-sections` 上重写成「按屏补拍 + 边写 `shot` + 校验规则 8」，#69 经 backlog → triage → todo 交给调度。

## 题 1：分段放开到哪些状态

- 类别：放开范围-最小够用
- 摆给人的：入口或加载完（从入口只经 system 边能到） / 任意一个状态，推荐前者
- 人的原话：「我觉的可以只给入口或者加载完的状态，我当时之所以有这样的想法是因为可能在入口没有截取到的信息这里会有可以交互的组件，那我觉得一个没有截取完整的内容延伸出来的边会有些不准确。」
- 做法：先按「入口或加载完」写了 spec、翻了 todo；后被题 2 推翻
- 情形：放开一条限制，真实页面只用得上较窄的一档
- 处置：选够用的那一档
- 理由：三个报告页都覆盖，改动最小（后来方向整体改了）
- 不自动的：否

## 题 2：#69 维持分段方案，还是改成组件进截图

- 类别：方向-按人说的本质重定
- 摆给人的：A 维持分段（加载完声明分段） / B 不分段，每条 user 边的组件都要进出发状态的截图，推荐 B
- 人的原话：「B 改成组件进截图」
- 做法：#69 todo → backlog → triage，spec 重写，再翻 todo
- 情形：人指出 issue 的核心不是它写的那个手段
- 处置：按人说的本质重写 spec，已提交的旧版不保留
- 理由：分段适合营销页的结构组织，报告页硬套段型不合适
- 不自动的：否

## 题 3：首屏以下的组件补拍，按屏合并还是一条边一张图

- 类别：产物粒度-少而全
- 摆给人的：按屏合并（边写 `shot`） / 一条边一张图，推荐按屏合并
- 人的原话：「按屏合并」
- 做法：spec 写成 `cover` 按屏合并，图叫 `<状态 id>@<这一屏第一条边的 id>.png`
- 情形：同一屏里多个组件各自要图
- 处置：合成一张，边上指明在哪张
- 理由：图少，成排的页脚链接不会拍成一堆重复图
- 不自动的：否

## 候选 1：issue 正文的「背景」改成必填，写给隔了几周回来的人

- 信号：纠正与追问
- 原话：「这个issue你能给我讲述下吗？时间有点久我有点遗忘了」；「我反而觉得这个case的根本是在书写issue的时候要把这些上下文整理好，而不是重新描述问题靠我回忆。」
- 落点：插件 `idea-loop:issues` 的「正文」一节，加 `issues new` 的正文校验
- 归并：「开一个 issue」第 1 步「写给一个没有上下文的人看」（加强它）
- 验证：检查：`issues new` 拒绝缺「背景」或为空的正文，先用 #69 的原正文看它被拒
- 结果：改成（原先落在「先讲 issue 再摆题」、并进 2026-10-31-problem-first-in-handoff；人改成写 issue 时就整理好上下文）；批·开 issue（https://github.com/guohaonan-shy/harold-skills/issues/297）

## 候选 2：会连出边的交互组件，要出现在出发状态的截图里

- 信号：人自己说的方向
- 原话：「我觉的不是分段，分段比较适合marketing部分的结构组织，而这个issue和候选2的核心是，如果有交互导致我们的设计内容需要出边，我觉的截图就是想要包含可交互组件的部分。」
- 落点：插件 `idea-loop:design-archive` 的拍图手册与校验规则 8，由 #69 的 spec 落地
- 归并：池里的 2026-10-26-sections-below-fold-interactions（修正了它的手段）
- 验证：检查：规则 8 与 `cover` 的浏览器测试，随 #69 的 PR 做
- 结果：改成（新文从「首屏以下要分段拍」改为「会连出边的组件要进截图，分段只用于营销页结构」）；批·进候选池（[[2026-10-26-sections-below-fold-interactions]]，第 2 次）
