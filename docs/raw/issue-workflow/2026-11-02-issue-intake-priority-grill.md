## U1

现在有个问题就是，toeflair每6个小时的根据github的issue进行合并，我看会话有时候还会提出新的问题，这个原因是扫代码发现的问题吗？

## A1

不是扫代码。cloud 整合任务只把已有的待验证 issue 挂到根下（新开的只有根）；新 issue 是 issue 会话路上顺手发现的：issue-session 的「边界」写着路上发现的别的问题照 spec-status 的「开一个待验证的 issue」开出去，implement 对跟这次无关的存量问题自动开 issue（decision-rules「自己定的四条」第 2 条）。

## U2

我现在的发现是issue越干越干不完，现在仓库里都累积了150个issue了，我合并这个方式本质上还是希望有限的精力可以放在少的会话上，从而快速迭代，方便我进行新feature的推广，现在整的我issue都修不完。我们现在的idea-loop的工作流有什么办法可以优化吗

## A2

Toeflair 的量（2026-11-02 取）：开着 151 个，其中待验证 122 个（107 个没打分类）。按周开 / 关：10-12 那周 78 / 15，10-19 那周 57 / 17，10-26 那周 95 / 47；关得越来越快，开得更快。待验证 122 个按来源：会话顺手发现 47、其他 39、人在 review 或验收时提的 15、整合开出的根 12、retro 5、想法 3、SEO 1。做完的从开到关中位数 4.5 天。

问题不在合并，在入口：调度按号取最早的（先进先出），没有任何「值不值得现在做」的判断，会话每做一个又顺手开出新的。提议：先定优先级、收紧入口，再清存量。

## U3

我倾向于先拍优先级并收紧入口，然后清理一手存量issue吧。关于合并这个是不是改成每次开issue都时候都要去考虑优先级以及合并？这样其实就不需要云端每次合并了？

## A3

对：开 issue 的那一刻就挂到模块的根下、判是不是 P0；人直接在 GitHub 上开的，由调度每轮对账时补挂、补判。这样 cloud 整合任务就多余了，6 小时的等待（只为等整合）也可以删。

## U4

## A4

## U6

## A6

是：人自己开一个新会话（要有 worktree），说「新想法，开聊」加一句想法；会话先开一个带想法 label 的 issue（不进调度队列），再在同一个会话里照 issue-session 走：验证一步对想法不复现，直接 grill，有了 spec 就照常进「设计中」或「实现中」。

## U8

按照我们现在的标准之前实现的那些issue（会话）那些属于P2，这个标准我觉得需要明确下，我倾向于P2属于那种只需要不超过3个ticket就可以解决的事儿，另外还有个问题我想一起解决，就是to-ticket其实我一般都是不看的，我在想能不能类似https://github.com/mattpocock/skills/blob/main/skills/engineering/implement-spec/SKILL.md 直接开始实现spec（里面将ticket拆分已经包括在其中了）。

## A8

按工单数：Toeflair 已实现的 44 份 spec 里，1 张工单 29 份、2–3 张 8 份、6 张以上 7 份。「≤3 张 = P2」会让 37/44 成 P2，包括 `student-table-rls`（1 张，学生数据不登录可读写）和 `stripe-billing-correctness`（3 张，付款）；而且工单数要到切票后才知道，调度出卡片时还不知道。建议优先级按价值（P0 线上坏了或安全 / P1 本期焦点 / P2 其余），大小另作一条轴。

Pocock 的 implement-spec 不拆工单，它消费 `/to-tickets` 的产物。我们的 to-ticket 本来就「切法直接落盘，不停下」；人觉得多一步，是手动敲 `/idea-loop:implement` 时它发现没工单就停下让人先跑 to-ticket。改成 implement 没工单就自己调 to-ticket 再接着做。

## 本轮决议

| 议题 | 决议 |
|---|---|
| 优先级标准 | 按价值：P0 = 线上坏了或安全问题；P1 = 本期焦点里的模块；P2 = 其余。不按工单数 |
| 大小 | 不进优先级，也不加新机制：实现阶段本来就不停 |
| 合并 / 整合 | 开 issue 时就挂模块的根、判 P0；人直接在 GitHub 开的由调度对账补；停掉 cloud 整合任务，删 6 小时等待 |
| 调度出卡片 | 只给 P0 和本期焦点模块的；P2 不出卡片、不关 |
| 焦点 | 目标仓库 ISSUE_TRACKER.md 里写一行模块名，调度判每个 issue 属于哪个模块 |
| 想法入口 | 人自己开新会话说「新想法，开聊」：开一个想法 issue（不进队列），同一个会话照 issue-session 走，验证不复现直接 grill |
| 顺手发现 | P0 照开；非 P0 写进汇报，人批了才开 |
| P2 与想法 | Dreaming 提议表每周列出来；人可以在 Dreaming 会话里聊几句、定优先级或模块，可选 |
| to-ticket | implement 没工单就自己切票再接着做 |
