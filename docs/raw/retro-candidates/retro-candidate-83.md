# idea-loop grill：推荐的做法靠的可行性也是推断，摆出推荐前先验

## 是什么

`grill` 的「推断要验证，留下证据」只点名了根因、接口返回、耗时这类说法；agent 自己**推荐的做法**靠着的可行性没被当成推断，于是推荐了一个没验过能不能跑通的方案。

例子：#51 的 grill 里，agent 推荐「回放命令交给你晚上跑」，没想谁来触发、无人值守时能不能跑通。人追问之后才去验，一验冒出四个前提：计划任务里的命令要匹配允许规则，不然被 auto 分类器拦；Bash 前台命令最长 10 分钟；无人值守的会话发不了 SendMessage（要用 send_message）；无人值守的会话改不了自己的排程。另外，验之前 agent 先问了「回『是』我就建」，而 grill 原文写的是「直接去验证，不用先问要不要验证」。

## 落点（人在 #51 的 retro 里批的）

插件的 `grill`，「推断要验证，留下证据」一节。

- 旧文：「你的推理靠着的每一条说法，人描述的问题、你读代码推出来的根因、『这个接口会返回 X』『这一步要 3 秒』，在真的走一遍之前都只是推断。」
- 新文：在这句后面加：「你**推荐的做法**靠着的可行性也算：『这条命令能在夜里无人值守地跑』『这个工具能把结果发回去』。摆出推荐之前先走一遍；走不了的（要动人的环境、要花钱），在题里写明卡在哪，不把没验过的做法当成推荐。」

## 会话里的原话（#51 issue 会话，2026-10-22）

「Q5 claude -p 起的是什么样的会话，我觉得夜里跑没有问题，但是我们不能只嘴上说说，我觉得更核心的是怎么跑？比如创建一个一次性的routine，在本机时间的00:00-07:00跑？」

## 怎么证明生效

按 retro 的回放：取 #51 grill 那一轮的上下文作输入，让 grill 出到推荐那一题停下；是/否题「推荐的做法里，靠着的可行性是否已经走过一遍，或写明了卡在哪」。改前应「否」、改后应「是」。
