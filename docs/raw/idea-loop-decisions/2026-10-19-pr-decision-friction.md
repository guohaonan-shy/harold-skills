## A0

开场概括 spec：#34 提的五处 pr-review / to-spec 改动在 main（0.0.24）上都已落地，没有要解决的问题，建议把 #34 关成已解决；没有标「需要 grill」。

## U1

我觉得没问题，不如我们这个会话专门处理这个问题：基于已经归档的“审核：”会话，我们看看PR过程中每一轮我都是怎么处理都哪些内容可以抽象成规则让你自动判断（即我将决策逻辑和规则给你，你来决策）

## A1

数据源：10 个已合并的 Toeflair「审核：」PR（391 392 393 394 395 399 474 477 478 482）合并时归档的 review loop 评论——每次停下、每轮 review 的汇报、人的原话批示、做了什么。抽出约 80 个人的决定。

发现：
- 约 85% 是「按推荐」；跟推荐相反或另起一条路的 12 次。
- 历史上从没被推翻的几类：有明文规则可依的 Standards 违规一律修（10/10）；说明文字跟已定做法对不上一律本 PR 补改（4/4）；跟这次无关的存量问题一律开 issue、本 PR 不动（7/7）；评测固定输入定点上传到评测存储桶一律同意（5/5）。
- 唯一的存量例外：存量 bug 让这次改动拿到的输入全是错的，人选了本 PR 一起修，跟推荐相反。
- agent 两次推荐「为边缘情形加机制」被推翻，理由都是用户不会失去东西（「毕竟只是一个 fallback」「没有用户的录音，就没必要弹窗」）。
- 起名人每次都改；人验素材、分类体系怎么切、方案形状由人提出第三条路的，都不能自动。
- 人追问约 20 次，多数是汇报没讲清：前提没对着最新 main 核（放量 infra 已经合进 main，选项全过时）、比对不同条件（英文画布对中文实现）、机制没说清（哪个请求、哪条测试）、给人判断文案却没给判断标准。

## U2

我们整理下，这些内容对于我们的spec-drafter，to-spec以及pr-review这些skill/agent有没有哪些内容和和现有的内容合并成通用的规则（尽可能通用，而不是case by case的罗列）

## A2

idea-loop 里没有叫 spec-drafter 的，按现在的起草方（issue-explorer + to-spec backlog 模式）处理。

现在「谁来定」散在四处，而且都交给人：implementer「停，还是延后」（行为没定就停，存量不修）、backlog 模式（修法有分歧给选项留给人）、review-standards / pr-description（每条 Spec 都写「要你决定」）、pr-review（人批示之前不修任何东西）。另发现 pr-review 的「进 backlog」仍写追加到 `docs/quality-backlog.md`，实际做法已经是开 issue。

提出六条原则草案：判得出来的不是决定题 / 归不归这次看依赖 / 加机制跟用户损失相称 / 个案沉淀成规则、能机械检查别只写文档 / 读数要真 / 出题先核前提讲清楚。问：判得出来的条目什么时候执行。

## U3

规则判得出的条目不等我，编排者直接派人修，汇报里单列「已按规则处理」并写依据，我一句话就能推翻。

## U4

为什么你考虑要将这个规则写到一个共享文档，而非to-spec或者pr-review内？

## A4

共享是因为同一个判断要在四处做（起草方、执行方、审查者、编排者），各写一份会漂（「进 backlog」那处就是例子）。但六条里真正四处共用的只有两条半，其余各有归属，全塞一个新文件反而多一层跳转。

## U5

我觉得这个跟我想的不太一样，比如个案沉淀成规则、能机械检查就别只写进文档，其实这个有点像dreaming要做的事儿，它评估这些会话中有哪些决策能沉淀（就像我们现在做的，我觉得这个以单独的issue做）

我目前的最大目标是减少我们在to-spec 到to-ticket之间的阐明摩擦，以及在pr review里面的决策次数。

## A5

「从会话里沉淀规则」开成 issue #51（dreaming）。

补看 spec 审核阶段：导出 6 个审核会话（对应 PR 391 394 399 477 478 482 的 spec），从起草完到切工单之间人的发言里约 30 次摩擦：

| 来源 | 次数 |
|---|---|
| 现状事实起草时没查，人问了才去查（代码现状、生产数据规模、相邻在飞的 spec、被写成缺陷的现有做法） | 约 12 |
| 问题和选项没给具体例子，陌生记号没解释 | 约 8 |
| 选项没对准人要的东西，先列做法没先写要交付什么，方案形状被人重定 | 约 7 |
| 范围没扫同类入口 | 约 4 |
| 决定牵出的后续没写，或改了 spec 没同步图和测试表 | 约 4 |

implement 停下问的决定里，有几件是 spec 该定没定、而产品已有统一做法的（文案写法、分数颜色规则）。

两个阶段是同一组原则，收成七条：
- 自己定：一、有依据就照办（写下的规则、已做的决定、产品已有的统一做法）；二、归不归这次看依赖；三、代价跟用户会失去的相称；四、默认改动最小。
- 交给人时：五、现状先查清（出处、规模、同类入口、相邻工作、最新基准）；六、先写交付物再列做法；七、每个问题和选项配具体例子。

一到四条四类读者共用，五到七条是「写给人的题」的写法，起草与汇报共用，所以放一份共享文件、分两半。

## U6

把本分支的 pr-review-report-followups spec 改写成这 7 条原则的 spec（#34 照旧写进建议关闭），我来审。

## A6

按七条原则改写 spec，#34 照旧写进「建议关闭」，推送到集成分支。留一个分歧给人：「代价相称」在 PR 流程里只决定推荐，还是也自动处置。

## U7

下一轮review我觉得也可以决定，比如pr- review在整个loop最多跑2次，如果还能跑且本轮有修复我觉得就可以跑。

## A7

写进 spec：这一轮有修复、条目都处理完且修复已落地、还没跑满两轮时，编排者自己起下一轮；上限只约束自动触发，人说「再跑一轮」照旧可以跑。依据：10 个 PR 里有 5 个跑了第二轮，其中 4 个第二轮仍有新发现、多是上一轮的修复或决定带出来的；没有一个跑到第三轮。

## 本轮决议

| 议题 | 决议 |

| #34 | 五处都已落地，照旧写进「建议关闭」 |
