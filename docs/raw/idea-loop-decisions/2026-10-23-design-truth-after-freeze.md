#55 审核会话里对 spec 初稿的 grill。初稿照 #55 正文写成「ui-reviewer 每轮照实现改写 `delta/`」，Harold 在这里推翻了它。U 是人的原话，逐字保留；A 是 AI 的结论与发现。

## U1

我其实这么想的，UI reviewer其实就是真实设计师来进行走查，看看当前的产品的实现跟UI设计稿的实现是否一致，不一致需要将问题反馈出来，让工程师进行解决。所以我理解是针对功能feature走查一遍看看哪些问题，这个问题跟随pr反馈出来，然后调度者会根据问题交给实现者实现的。所以，我觉得仍然只负责review是没有问题的。

我们进一步讨论下，我们现在要解决的问题是开发在实现过程中基于tmp/本期的设计改动是否符合预期，还是以代码为准的内容diff。我理解如果开发期间有设计点的改变是需要让designer知道更新在tmp画布的。我们先明确问题。

## A1

现状（idea-loop 0.1.3 原文）：冻结后 designer 再不被起；review 里人对 UI 偏差选「改档案，接受实现」时，是编排者手改 `delta/`，画布不动（原文还写着「本地、不进 git」，与冻结时已提交 `delta/` 矛盾）；合并前归档拿代码对被手改过的 `delta/`，画布早已落后。

提问：问题表述；「设计点变了」包括哪几种来源（人接受实现、实现者做不下去、人改主意）；ui-reviewer 只走查；开发期间以 `tmp/` 冻结设计为唯一真相。

## A3

解释 `canvas/`（设计本身，HTML，按 `?state=` 打开，实现者与 ui-reviewer 按像素对的基准）与 `delta/`（冻结时从画布抄写出来的档案差异，归档进 `prod/` 的来源）。只改 `delta/` 会让按像素对的基准停在旧画布，与 U2「更新到设计画布」方向相反。提问：两处一起改，还是冻结后只认 `delta/`；改完人要不要看。

## U4

Q1 这块我们得想清楚，我觉得无论是canvas/imagine/delta，本质都是设计画稿的不同状态，imagine好比我们在画稿上随便乱化，canvas 则是我们给予某个版本进行打磨，delta是最终的定稿。我觉得不需要分的这么细，里面上就应该是在delta 或者 canvas上维护feature阶段的设计改动。而不是维护多个真相源

## A4

冻结后谁读什么：实现者的比对脚本按格对画布；ui-reviewer 每轮按像素对画布、拿 `delta/` 当清单和进入方式；合并前归档写 `delta/` 并进 `prod/`。`delta/` 的截图与边的定位都抄自画布，画布是原件。

提问：A 画布是唯一真相，冻结时不写 `delta/`，合并前由 ui-reviewer 从最终画布加实现整份写出；B `delta/` 是唯一真相，画布作废（丢多视口矩阵、比对脚本要改）。designer 改完要不要请 ui-master 只评改动的几格。

## 本轮决议

| 议题 | 决议 |
|---|---|
| ui-reviewer 的职责 | 只走查、只报问题；不改设计、不判改哪边。收回 #55 原定的「照实现改写 `delta/`」 |
| 冻结后的真相源 | 画布 `canvas/` 唯一；代码去对它 |
| 冻结时写不写 `delta/` | 不写；合并前由 ui-reviewer 归档模式从最终画布加实现整份写出 |
| 设计变更的来源 | 人接受实现、实现者做不下去、人改主意，人接受后都算 |
| 谁改设计 | 当前阶段编排者起 `idea-loop:designer` 只改受影响的格子 |
| 改完谁把关 | `idea-loop:ui-master` 只评改动的格子；下一轮 review 的 ui-reviewer 对实现走查 |
| 设计变更提交到哪 | 当前 PR 分支；代码不一致的照「修」派实现者 |
| 合并前归档 | 保留（核不过退回），草稿给人批后进 `prod/` |
| 合并前钩子 | 删掉；网页上点合并由 dreaming 兜底 |
| 过期检查归谁 | 并进 spec → ADR agent |
| 设计规范维护 agent 模型 | opus · high |
