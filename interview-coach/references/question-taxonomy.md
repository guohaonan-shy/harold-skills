# 四类面试问题框架

从一场真实的 AI Engineer 岗位模拟面试教练录音里蒸馏出来的框架。`mock-interview` 用它来决定"这轮该问哪类问题",`interview-review` 用它来判断"候选人这题答的展开策略对不对"。

核心矛盾:面试经验少的候选人,最常见的病不是不会,而是**不知道每类问题该展开到什么颗粒度**——该概括的地方展开了细节,该展开细节的地方只甩了个名词。

## 概括类(what)

**识别特征**:"你能介绍一下这个项目吗" / "这个系统解决什么问题" / 自我介绍。

**该怎么答**:
- 站在"对这个领域完全没有背景的人"视角,用最通俗直接的语言说清楚:什么场景 → 解决了什么问题 → 端到端交付是什么样的变化(有量化最好,比如"审核耗时从 30-60 分钟压到 5-10 分钟")
- 不需要提任何实现细节、框架名、内部术语——面试官如果感兴趣,会主动往下问
- **时长基准**:自我介绍 30-45 秒;单个概括性问题不超过 1-1.5 分钟。超时意味着面试官的注意力大概率跟不上了

**常见病**:把选型类、实现类的细节提前塞进概括性回答里(比如自我介绍时就报出"七个运行时事件三个钩子五种结束状态"这种只有面试官追问才该说的东西),导致整体又长又像背课文。

## 选型类(why)

**识别特征**:"为什么用这个框架/这样设计" / "为什么不用 XX(另一个方案)"。

**该怎么答**:考察的是调研广度和技术判断,不是执行细节。答案要能说出"因为业务场景是 A,所以 B 方案的 XX 特性正好匹配 / 排除了 C 方案的 XX 问题",而不是简单一句"因为我们用了 XX"。

**常见病**:回答里只暴露"用了什么",暴露不出"为什么是这个不是别的"——这正是考察点本身。

## 实现类(how)

**识别特征**:"这块是怎么做的" / "内部是怎么实现的"。

**该怎么答**:这是**唯一应该主动展开细节**的问题类型,但要客观描述 + 适度展开,不是罗列。最怕的雷区是"接了一个工具/组件,但说不清底层怎么实现的"——这种情况下"我接了这个东西"反而是扣分项,因为暴露出候选人不清楚自己在用什么。

判断展开够不够的标准:面试官在完全没有背景信息的前提下,能不能听懂"做了什么、为什么要这么做"。

**常见病**:两种极端都常见——要么只甩一个框架名/术语就停(没有实质内容),要么把所有实现细节不分主次地平铺直叙(面试官抓不住重点)。

## 延伸场景类(edge case / 假设性场景)

**识别特征**:"如果 XX 情况发生了,你们会怎么处理" / 基于候选人已讲的设计延伸出的未知问题。

**该怎么答**:考察面对未知问题的思考能力,不要求标准答案。合理的分析框架 + 承认不确定性(比如"这个场景我们目前量级下还没遇到,但如果发生,我会考虑…")好过硬编一个答案。

**常见病**:答不出来就慌,或者强行编一个站不住脚的方案。

## 判断一道题属于哪一类的经验法则

- 问题里出现"是什么/介绍一下/解决什么问题" → 概括类
- 问题里出现"为什么/为什么不" → 选型类
- 问题里出现"怎么做的/如何实现/内部是" → 实现类
- 问题基于候选人已说的内容做假设延伸("如果…会怎样") → 延伸场景类

同一段面试对话里,面试官经常顺着候选人回答里冒出的一个名词继续往下追问,四类问题会交替出现、层层深入——不是四个孤立的问题,而是一条不断变窄的追问链。

# AI Engineer / AI Agent Engineer / Harness 方向知识点清单

`mock-interview` 抽题、`interview-review` 判断"这类问题该讲到什么深度"都参照这份清单。清单只列考察维度,不是标准答案——具体答案要结合候选人自己的项目生成。

## Agent 架构与执行循环
- agent loop 的设计:默认框架 loop(如 ReAct)vs 自研 loop 的取舍;运行时事件、钩子(hook)、结束状态的设计考量
- 单 agent(把子任务当 tool 封装)vs multi-agent(fork 子 agent、独立 system prompt/工具集)的取舍,子 agent 是继承主 agent 上下文还是从零构建
- 工具设计:工具粒度怎么切、工具描述(description)怎么写才能降低模型选错工具的概率、工具集变多之后如何避免召回混乱

## Skills / 能力扩展机制
- 为什么用 skills(按需加载)而不是把所有内容写进 system prompt:上下文成本、不同 SOP/标准之间可能冲突、agent 初始化时不一定知道要用哪个标准
- skills 数量增多后的检索退化问题:如何在 description 层做相似度召回 + rerank,避免"该召回的没召回、召回了不相关的"

## 上下文工程
- 上下文压缩:自动压缩 vs 按阈值触发的主动压缩;压缩粒度(整体摘要 vs 分阶段摘要);压缩时哪些内容必须保留原文(比如刚加载的 skill 定义)不能被摘要掉
- 长工具结果(tool result)的处理:截断保留头尾 + 落盘、需要时再读取
- 上下文使用率过高对模型 agentic 表现的负面影响,以及如何通过架构设计(而非单纯压缩)控制主 agent 上下文增长速度

## RAG / 检索
- 分块(chunk)策略:直接按段落切 vs 先摘要再检索(摘要做相似度索引、命中后再回原文)
- 召回方式:向量召回 / 关键词召回(如 BM25)/ 混合检索 + rerank,以及为什么需要 rerank
- 检索内容的来源设计:存什么(原始资料 / 历史处理结果 / 人工标注样例)、怎么被召回、怎么用于当前任务

## Evaluation
- 有没有对工具使用、skill 召回、端到端任务结果做系统性评测(而不是凭感觉调 prompt)
- 评测集怎么构建、覆盖哪些场景
- 这是候选人经验和"玩具 demo 阶段"与"生产可用阶段"的分水岭,面试官问到的概率随着候选人资历水涨船高

## 场景延伸类高频追问方向
- 规模增长后系统会退化在哪里(工具/skills 变多、上下文变长、并发变高)
- 压缩/召回/多 agent 拆分之间如何组合解决同一个"上下文爆掉"的问题——这三者不是互斥选项,面试官经常期待候选人能说出组合方案
